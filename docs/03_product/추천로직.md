## DEC-LIVE-ACTION-HANDOFF-01 — 잠금화면 동작 확장 (2026-09-06)

상태: **사용자 확정·구현/검증 전**, COURSE-13·UX-19 보완. 이 절과 충돌하는 과거 출발 확인만 기록하는 흐름은 철회이며 나머지 로컬 우선 계약은 유지한다.

- 도착 확인은 잠금화면에서 한 번만 한다. native 저장과 Activity의 즉시 머무는 중 전환, 앱 복귀 시 다음 단계 복구를 연결한다. 예정 시각 전 확인도 허용한다.
- 이제 출발해요는 명시 출발과 다음 길찾기 요청을 함께 만든다. 필요한 잠금 해제 → TimeFit 활성화 → 기존 adapter로 다음 구간 카카오맵 자동 실행이며 앱에서 재탭을 요구하지 않는다. 확정 snapshot 순서의 다음 방문 장소 또는 최종 목적지를 사용한다.
- 이 명시 출발의 최초 확인 시각과 handoff 성공은 별개다. 외부 실행 실패/재시도는 departedAt을 바꾸지 않으며 성공 전 routeOpened로 표시하지 않는다. 앱의 일반 길찾기만 누른 경우는 기존대로 handoff 성공 때 출발로 기록한다.
- 잠금 해제 취소/활성화 실패/외부 전환 실패 때 성공을 합성하지 않는다. 요청 중복 소비·stale run/stop/revision·완료 코스 재실행을 차단한다. 외부 앱 실행과 로컬 저장은 원자적이지 않으므로 중단으로 성공 여부가 불명확하면 자동 반복 대신 앱에서 명시 재시도를 제공한다.
- 로컬 단계의 서버 표본/업로드 큐/개인화 적용0, GPS/원격 push 미사용, exact cleanup을 유지한다. 알림 발화 정책 변경은 이번 범위가 아니다.

이력: 출발 기록 후 앱 길찾기 재탭 → 사용자 중복 조작 및 잠금화면 도착 무반응 관찰 → 도착 동기화 복구와 명시 출발/단일 길찾기 요청 연결 → 잠금 해제 이후 추가 조작 감소. 테스트는 cold/warm start, 잠금 해제 취소, 중복 이벤트, 외부 실패/불명확 결과, 실제 1/2곳 순서와 cleanup을 포함한다. 상세 실행 기준: docs/work/uiux/live-activity-dwell-progress.md의 “잠금화면 도착 복구·출발 자동 길찾기” 명령.

### 1.0 실제 경로 기반 탐색 전환 결정 (2026-08-17, 일부 철회·구현 기록)

좌표 반경 후보 수집을 실제 경로 주변 단일 반경 `R`로 바꾸는 결정은 유지한다. 다만 당시의 `도보·차량·대중교통` 세 수단 기준 경로 합집합은 2026-08-21에 철회했다. 차량 경로가 먼 후보를 기본 결과에 섞어 단일 자투리 활동이라는 현재 목적과 충돌했기 때문이다. 전환 후에는 도보·대중교통 기준 경로만 사용하며, 실제 경로 기반 공간 탐색·캐시·선택 뒤 재계산이라는 구조만 계승한다. 상세 구현 기록은 [추천_실경로탐색전환계획](../archive/product-history/추천_실경로탐색전환계획.md)에 보관한다.

### 1.0.1 자투리 활동 장소·체류 범위 전환 (2026-08-22, 현행)

이전 방식은 원천 데이터의 일반 관광/업종 분류와 단일 `dwell` 값을 곧바로 추천 성격으로 사용했다. 관찰된 문제는 시장·관광지·카페가 모두 같은 체류 논리로 보이고, 짧게 들를 수 있는지 설명할 수 없다는 점이었다. 이를 `src/data/busan_poi_catalog.json`의 활동 카탈로그로 교체했다. 현재 후보는 짧은 시간에 경험이 완결되는지 검토한 활동 유형과 `최소·권장·최대` 체류 범위를 가지며, 일반 식당·장기 활동·내부 개별 시설은 제외 또는 보류 기록으로 남긴다. 구체적인 데이터 모델·하드 제외·생활권 심사는 [자투리 장소 선별 및 체류 범위 계획](자투리장소_선별및체류범위_계획.md)을 따른다.

### 1.0.3 근거 프로필 기반 장소 재분류 (2026-08-24, 현행 결정·데이터 전환 전)

기존의 `approved / conditional`만으로는 운영시간이 부족한 경우와 체류 근거가 활동 유형 수준인 경우, 권역과 내부 점포가 섞인 경우를 구분하지 못했다. 따라서 한 숫자 점수나 인기 지표로 합치지 않고, 각 장소에 아래 **근거 프로필**을 먼저 기록한 뒤 처리 결과를 판정한다.

| 항목 | 허용 값과 최소 근거 | 판정에 쓰는 방식 |
|---|---|---|
| 장소 동일성 `identity` | 공식 원천 ID 또는 정규화한 대표명·좌표가 일치한 `verified`; 권역은 대표 권역명과 범위 설명이 일치한 `area_verified`; 그 외 `unverified` | `unverified`는 자동 추천 불가다. 권역은 내부 상점·시설의 근거를 상속하지 않는다. |
| 장소 범위 `placeKind` | `point_facility`(독립 시설), `area`(시장·거리·골목 등 권역), `outdoor_route`(검토된 야외 접근형), `event`(기간 한정) | 같은 권역 내부 장소와 대표 권역을 함께 코스에 넣지 않으며, 종류별 운영 가능성 규칙을 적용한다. |
| 활동 적합성 `activityEvidence` | `place_specific`(장소별 근거), `area_specific`(권역 활동 근거), `activity_template`(검토된 활동 유형 템플릿), `unknown` | `unknown`은 자동 추천 불가다. `activity_template`은 장소별 관측 체류로 표시하지 않는다. |
| 체류 근거 `stayEvidence` | `place_observed`, `area_observed`, `activity_template`, `unknown`과 최소·권장·최대 범위 및 출처 | 장소별·권역별 근거를 우선하고, 부족할 때만 활동 유형 범위를 쓴다. `unknown`은 자동 추천 불가다. |
| 이용 가능성 `availability` | `fixed_hours`(공식 정기 시간), `area_hours`(공식 권역 가능 시간), `always_accessible_audited`(검토된 야외 상시 접근), `event_window`(공식 기간·시간), `unknown` | `unknown`은 조건부 더보기만 가능하다. 행사 종료·휴무·운영시간 밖은 제외한다. |
| 이용 부담 `accessFriction` | `open`, `known_ticket_or_fee`, `reservation_required`, `program_dependent`, `unknown` | 예약 필수·프로그램 의존은 해당 회차의 정원·시간 근거가 없으면 자동 추천에서 보류한다. 유료 자체는 제외 사유가 아니다. |
| 근거 이력 `evidence` | 원천명·원천 ID/URL·확인일·적용 범위를 각 필드와 연결 | 상업성·인기도·리뷰 수가 아니라 이 이력만 자동 추천 근거로 사용한다. 시설·상권은 90일, 야외 상시형은 365일, 행사는 시작 전 재확인 주기를 넘기면 재검토 큐로 보낸다. |

재분류 결과는 다음 네 가지다. 이는 사용자에게 별도 A/B 등급으로 표시하지 않는 내부 데이터 계약이다.

| 결과 | 필수 조건 | 추천 처리 |
|---|---|---|
| `representative_core` | `identity`가 `verified/area_verified`, 활동·체류가 장소 또는 권역 근거, 이용 가능성이 확인됨 | 대표 코스 우선 후보. 실제 경로·시간 게이트를 추가로 통과해야 한다. |
| `representative_standard` | 장소 동일성·운영 가능성은 확인됐고, 활동 또는 체류 중 하나가 검토된 `activity_template` 근거 | 대표 코스 가능 후보. 동일한 시간 적합성에서는 `core`보다 뒤에 둔다. 템플릿 체류임을 데이터 이력에 보존한다. |
| `conditional_more` | 장소 동일성과 활동 적합성은 있으나 운영 가능성이 `unknown` | 더보기에만 `운영시간 확인 필요`로 표시한다. 사용자의 확인 뒤에도 대표 후보로 승격하지 않는다. |
| `hold` | 장소 동일성·활동·체류 중 하나가 미확인, 중복/내부 장소, 예약 필수·프로그램 의존, 행사 기간 만료 | 자동 추천과 조건부 수동 포함에서 제외하고, 누락 근거를 재검토 큐에 기록한다. |

이 기준은 장소 수를 A등급만으로 제한하는 방식이 아니다. 운영시간과 장소 동일성이 확인된 권역·활동 템플릿 장소는 `representative_standard`로 자동 추천 풀을 넓히되, 운영시간이 불명확한 장소만 `conditional_more`로 분리한다.

### 1.1 결과와 우선순위 (공통 순위 + 과거 다장소 형태 이력)

이 절의 신뢰도·운영시간·발견성 우선순위는 유지한다. 다만 아래 `1~3개 장소 코스` 형태는 과거 자동 다장소 계약이며 현재 출시 기본이 아니다. 현행 기본은 [1.6](#16-출시-대표-코스-파이프라인-2026-09-02-현행)의 one-stop이고, 자동 게이트 뒤 추가될 2곳은 `DEC-TWO-STOP-SELECTION-01`의 사용자 명시 A 선택 branch만 따른다.

- **과거 자동 다장소 전환의 기본 단위**는 엔진이 조립한 **1~3개 장소 코스**였다. 이 형태는 배포 후 보류이며, 현재 one-stop 기본과 새 pair-only 2곳 제한 조립으로 부분 교체됐다. 사용자가 임의로 조립하는 장바구니가 아니라는 원칙은 유지한다.
- **1순위 하드 조건**: 도보·대중교통으로 `출발 → 후보 1~3곳 → 도착/복귀` 이동과 각 장소의 최소 체류를 마친 뒤, 사용자가 설정한 도착 여유를 남길 수 있어야 한다. 대표 코스의 모든 장소는 운영시간이 확인돼야 한다.
- **2순위**: 권장 체류 충족, 추가 이동 부담, 시간대·운영 상태, 체류 근거 신뢰도, 활동 유형 다양성을 반영한다. 후보 부족을 메우기 위해 차량 가능성이나 일반 음식점을 가점으로 쓰지 않는다.
- **근거 우선순위**: 대표 코스는 `representative_core`와 `representative_standard`만 사용한다. 둘의 시간 적합성이 같을 때 `core`를 먼저 쓰되, `standard`를 후보 부족의 예외나 숨은 폴백으로 취급하지 않는다. `conditional_more`와 `hold`는 이 순위 비교 전에 분리한다.
- **3순위 발견성**: 위 조건과 기본 적합성이 같은 후보 사이에서만, 앱 안에서 완료 기록이 없는 지역·활동을 보조 순위로 사용할 수 있다. 여기서 완료 기록은 후기 작성이 아니라 진행 화면의 명시 `코스 마치기`로 생성된 활동이다. 실제 체류가 미측정이어도 완료 장소/활동 발견성에는 반영할 수 있지만, 체류시간 개인화 표본에는 사용하지 않는다. 이는 계획 밖의 부산 장소를 만날 기회를 넓히기 위한 것이며, GPS 방문·소비 이력이나 근거 없는 `처음/숨은/인기` 주장을 만들지 않는다. 발견성은 시간·운영시간·실제 경로 하드 조건을 절대 대체하지 않는다.
- 일반 식당은 기본 후보에서 제외한다. 카페·베이커리 등 `quick_rest`는 자투리 활동 카탈로그와 운영 상태 정책을 충족한 경우에만 후보가 될 수 있다.
- 장소 매력은 사용 후 후기 만족도로 만들 계획이며, 현재는 **랭킹 점수에 반영하지 않는다.** 로컬 후기 수집만 구현돼 있다.

### 1.3 이동수단과 후보 범위 (2026-08-21 현행 결정, 구현 전)

- 추천 전에 이동수단을 고르게 하지 않는다. 후보 판정은 **도보와 대중교통의 현실적인 구간 조합**만 사용한다. 차량·택시는 카카오맵 길찾기에서 사용자가 선택할 수 있으나 후보 통과, 후보 반경, 순위에는 쓰지 않는다.
- 대표 코스는 `출발지 → 후보 1~3곳 → 도착지` 전체 일정에 삽입 가능한지로 판정한다. 도착지가 없으면 마지막 장소에서 출발지로 복귀한다.
- 출발지 근처·실제 경로 주변·도착지 근처는 서로 다른 추천 규칙이 아니라 후보의 **공간 성격 표시**다. 세 영역 모두 같은 **코스 시간식**을 통과해야 한다.
- 기본 탐색은 실제 기준 경로 주변의 좁은 생활권으로 제한한다. 사용자가 명시적으로 범위를 넓힐 때만 후보 표시 범위를 확장하며, 확장 후보도 같은 시간·체류·운영시간 판정을 통과해야 한다.
- 후보 화면은 시간 예산을 먼저 보여 주고, 지도는 장소 위치·세부 확인용으로 사용한다. 지도에 후보를 많이 나열하는 것을 기본 경험으로 삼지 않는다.
- 카카오 검증은 장소 본체와 일치한 `verified` 결과만 상세 링크로 제공한다. 주차장·물품보관함 등 보조시설 결과는 `weak` 위치 단서로만 남기고 해당 링크를 제공하지 않는다.

이전의 `도보·대중교통·차량 중 하나라도 가능`, 다중 장소 장바구니, 카드별 진입 수단 선택은 [1.0.2](#102-한-곳-추천과-사용자-도착-여유-전환-2026-08-21-구현-전)에서 철회한 방식이다. 런타임 코드와 UI 테스트는 전환 전까지 이를 구분해 유지한다.

### 1.4 시간 예산과 체류 상태 (2026-09-02 출시 현행)

```text
effectiveBudget = 종료시각 - 현재시각 - 사용자가 선택한 도착 여유
routeTotal = 출발 → 후보 1곳 → 도착/복귀의 도보·대중교통 이동시간 합
stayTotal = 후보 1곳에 엔진이 내부 배정한 체류시간
```

- `도착 여유`의 기본값은 **10분**이다. 사용자는 슬라이더로 조절할 수 있으나 0분은 허용하지 않는다.
- 장소는 단일 `dwell`이 아니라 `minStayMin / recommendedStayMin / maxStayMin`을 가진다.
- 현행 범위는 `20분 / 30분 / 60분`이며, 문화시설(`compact_culture`)만 `20분 / 30분 / 120분`이다. 30분은 활동 대응 AI-Hub 카테고리의 최빈 체류시간, 20분과 60·120분은 짧은 방문·긴 관람을 각각 허용하는 제품 정책이다.
- 출시 입력 종료 시각은 현재 시각부터 최대 **120분**이다. 이전 180분은 배포 후 다장소 복구 전까지 사용하지 않는다.
- 대표·대안의 하드 조건은 각 장소의 `minStayMin` 이상을 실제 경로·구조화 운영시간 안에 배정하고 `routeTotal + selectedStayTotal <= effectiveBudget`을 만족하는 것이다. 모든 활성 장소의 현행 최소값은 20분이다. 권장 30분을 확보한 코스는 같은 안전성의 짧은 방문 코스보다 우선하지만, 전자가 있다고 후자를 전역 폴백으로 숨기지 않는다.
- 엔진은 같은 장소를 20·30·…분의 여러 코스로 중복 반환하지 않는다. 내부 snapshot에는 하나의 선택 체류를 기록하되, 권장 30분을 확보하지 못하고 최소 20~29분만 가능한 경우 `stayState=short`로 남긴다. 사용자 화면은 이를 `가볍게 둘러보기`로 표현한다.
- `maxStayMin`은 내부 선택 체류의 상한이다. 일반 장소의 60분과 문화시설의 120분은 입력 시간이 길거나 남는다고 자동 배정하지 않으며, 남는 시간은 독립 구간으로 남긴다. 출시 결과 카드와 진행 화면에는 체류 분을 따로 표시하지 않는다. 코스 확인 상세에서만 선택 체류를 `둘러보기 약 N분`으로 설명하고, `최대 가능`·최소/최대 범위·체류시간 조절 UI는 표시하지 않는다.
- 대표 코스·검증 대안 목록·지도 상세의 시간 막대와 이동·체류·도착 여유는 **같은 실제 경로 결과**만 사용한다. 지도에 처음 보이기만 한 후보는 정밀 호출을 하지 않으며, 사용자가 상세를 열면 실제 경로 결과를 받은 뒤에만 시간을 표시한다. 근사값은 내부 후보 선별·순위용이며 사용자에게 대표 코스 시간으로 표시하지 않는다.

### 1.5 운영시간 확인과 카카오맵 상세 연결

- **현행 데이터**: TourAPI 원본 ID가 있는 장소는 `detailIntro2`에서 운영시간 문자열을 파싱해 게이트를 적용한다. 부산시 공식 데이터 단독 장소는 제공된 운영시간 문구를 안내하며 자동 영업 판정은 하지 않는다.
- **전환 후 운영시간 정책(현행 결정, 구현 전)**: 운영시간이 확인된 장소는 후보 근사 단계와 선택 뒤 실제 경로 단계에서 모두 `최소/권장 체류` 범위가 운영시간 안에 있는지 판정한다. 이 장소만 대표 코스와 자동 확정에 사용한다.
- **조건부 더보기 정책(2026-08-31 1.5.1로 구체화)**: 운영시간 미확인 후보는 대표 추천·검증 대안에서 제외한다. 시장·거리·골목 중 데이터가 `conditional_visit`으로 식별하고 제외 분류를 통과한 후보만 별도 `운영시간 확인 후 들러볼 곳`에 제품 탐색 창 10:00–18:00 동안 표시한다. 카카오맵 확인 뒤 사용자가 명시하면 경로·시간 재계산을 통과한 조건부 수동 포함 코스에만 넣을 수 있다. 이 행동은 공식 근거를 만들거나 후보를 `추천/검증됨`으로 승격하지 않으며, 코스·상세·저장 스냅샷에 `운영시간 확인 필요(사용자 확인)` 상태를 유지한다.

아래의 권역형 재검증 수치와 과거 게이트는 **전환 전 런타임 데이터 정제 기록**이다. 새 카탈로그에서는 위 전환 후 운영시간 정책을 우선한다.
- **권역형 장소 정책(정제 진행 중)**: 시장·거리·골목·문화마을은 모든 점포의 영업시간을 임의로 추정하지 않는다. 공식 관광·구청·상인회·대표 안내시설의 근거로 **추천 가능 시간대**를 별도 관리한다. 이는 전체 점포의 영업시간이 아니라, 사용자가 기대한 시장·쇼핑·관람 경험을 할 수 있는 보수적 시간대다.
- **TourAPI 재검증 현황(2026-08-13)**: 우선순위 권역형 후보 40건의 `detailIntro2` 원문을 재조회했다. `시간범위확인` 14건은 `src/data/area_availability_policy.json`에 공식 시간대 정책으로 등록해 통과 여부를 판단한다. `시간범위+조건부` 4건은 점포별 상이 문구를 함께 보여 별도 검토하고, `조건부안내` 또는 `시간범위미확인` 22건은 공식 시간대가 확정될 때까지 자동 추천에서 제외한다.
- **원본 ID 없는 권역형 장소(2026-08-13)**: 광안종합시장 등 16건은 TourAPI `searchKeyword2`로 재탐색했지만, 이름 완전 일치와 250m 이내 좌표를 동시에 만족한 후보가 없었다. 이 목록은 `data/processed/review/권역형장소_TourAPI키워드재탐색_검토.json`에서 유지하며, 유사명 결과를 체류시간·운영시간 근거로 상속하지 않는다.
- **전포공구길(2026-08-15)**: 실제 골목 전체를 대표하는 장소를 AIHub 개별 상점 `오브젝트 에디트`의 체류시간으로 매칭했던 사례다. `상업지구 / 거리·골목` 포괄 장소·카테고리 체류시간으로 재분류했으며, TourAPI의 `매장별 상이` 운영시간은 권역 추천 가능 시간대로 사용하지 않는다.
- **추천 가능 성격 프로필(2026-08-15)**: 오분류가 확인된 장소에는 `facility`(운영시간 필수), `area`(공식 권역 시간대 필수), `outdoor`(검토된 야외 접근형), `hold`(자동 추천 보류)를 명시한다. 카테고리만으로 운영시간을 우회하지 않도록 이 프로필을 우선 적용한다.
- **야외 상시형 정책(확정)**: 해변·공원·산책로 중 별도 검토로 상시 접근이 확인된 장소만 운영시간 없이 추천할 수 있다. 자연관광지라는 카테고리만으로 시설형 장소를 상시 허용하지 않는다. 사용자가 말한 자연관광지 운영시간 예외도 이 `outdoor` 성격 장소에만 적용한다. 아직 프로필이 없는 기존 자연관광지 전체는 후속 전수 정제 대상이다.
- **근거 미확인 처리(전환 후)**: 상권 의존형 권역과 시설형 장소는 삭제하지 않는다. 다만 `운영시간 확인 필요`로 명확히 구분하며, 카카오맵 링크는 메뉴·사진·후기와 함께 운영시간을 사용자가 최종 확인하는 보조 수단이다. 앱은 해당 후보를 열려 있거나 시간 안에 확실히 가능하다고 단정하지 않는다.
- **구현 작업**: 카카오 검색에서 확인된 장소에는 Kakao Place ID와 `place_url`을 저장한다. `not_found`는 보관만 하고 추천 엔진에서 제외한다.

### 1.5.1 검증 대안 이어보기와 조건부 시장/거리 (2026-09-02 출시 범위 갱신)

**이전 방식 → 문제 → 교체 방식.** 2026-08-31의 “대표 1개 + 무경로 고유 장소 탐색 목록”은 장소 발견성을 위해 검증 대안 목록을 대체했다. 그러나 미검증 장소를 시간 안에 가능한 코스처럼 해석하게 했고, 실제 통과한 2·3곳 대안을 비교할 수 없었다. 이 방식은 **철회**한다. 결과의 기본 영역은 다시 실제 경로·운영시간·체류·도착 여유를 통과한 코스만 쓴다. 시장·거리의 발견성은 검증 코스와 섞지 않는 별도 조건부 후보 영역으로 해결한다.

**DEC-CONTINUATION-01 — 다장소 범위는 배포 후 보류.** continuation의 안전한 재수화 원칙과 구현은 삭제하지 않는다. 아래 1~4의 **1~3곳·첫 8→16회·multi-stop entry** 규칙은 public store 원인을 배포 후 다시 다룰 때만 재활성화한다. 이번 출시의 one-stop은 이 entry를 호출하지 않고, [1.6 출시 대표 코스 파이프라인](#16-출시-대표-코스-파이프라인-2026-09-02-현행)과 `DEC-ONE-STOP-MORE-01`의 single 전용 continuation만 사용한다. 아래 5~6의 조건부 시장·거리 정보 확인 정책은 이번 출시에도 유지한다.

1. **첫 검증 결과.** 상단은 대표 1개, 아래 `이 시간에 가능한 다른 코스`는 대체 최대 3개를 목표로 한다. 모든 카드는 `출발 → 1~3개 장소 → 도착/복귀`의 동일 실제 시간 여정 스냅샷을 표시한다. 대표는 1~2곳을 우선하며 3곳은 유효한 1~2곳이 없을 때만 대표가 된다. 대안에는 유효한 1·2·3곳 코스를 모두 둘 수 있다.
2. **적응형 첫 검증 예산.** 사전 선별은 분류·운영시간·최소 체류·공간 범위·도착 여유와 동일/중첩 코스 제거를 route 호출 없이 먼저 수행한다. 첫 stage는 새 Kakao provider attempt 최대 8회다. 대표 포함 검증 코스가 4개 미만이고 아직 사전 선별한 미검증 코스가 남은 경우에만 두 번째 stage를 열어 **첫 결과 전체 최대 16회**까지 보충한다. 후보 큐가 소진됐거나 전역 provider/daily-limit 실패면 목표 수를 채우기 위해 추가 호출하지 않는다. 4개는 목표이지 보장이 아니다.
   - **코스 형태의 검증 기회.** 첫 결과 큐는 1곳만 연속 검증해 목표 수를 먼저 채우지 않는다. 사전 최소 체류·도착 여유를 통과한 독립 2곳 후보가 있으면 근접 1곳과 교차해 검증 기회를 준다. 3곳은 1·2곳을 밀어내지 않는 다음 기회에만 한 번 검증한다. 이는 2·3곳 결과를 보장하거나 장소 수를 채우는 규칙이 아니다. 실제 경로·운영시간·최소 체류에서 탈락하면 1곳만 반환하며, 8→16회·adapter 호출 상한은 그대로다.
3. **대체 코스 이어보기.** `다른 검증 코스 더 보기`는 기존 결과를 다시 계산하거나 새로고침하지 않는다. 공개 continuation은 독립 재실행 토큰이 아니라 클라이언트의 **안전한 큐 참조값**이다. 엔진 공개 entry는 `continueLimitedRepresentativeCourseV1({ ...originalInput, continuation })`으로 고정한다. 여기서 `originalInput`은 첫 계산과 같은 `now·origin·destination·remainingMin·arrivalBufferMin·provider·route ports`를 다시 전달한 `CourseV1LimitedInput`이며, UI는 같은 결과 화면의 메모리 세션에서만 이를 조립한다. continuation에는 `version`, `cursor`, 후보 place ID 집합과 그 opaque signature, attempted/rejected/verified course signature, opaque route receipt key, typed 종료 reason만 직렬화해 둔다. 좌표 정밀값·사용자 ID·입력 시각 원문·provider 객체·함수·API key·비직렬 runtime context는 넣지 않는다. 엔진은 현재 provider가 같은 후보 ID 집합을 재생성하는지 확인한 뒤에만 다음 미검증 코스를 로컬 재수화한다. 재수화가 불가능하거나 집합/signature가 달라지면 route 호출 없이 `continuation_unavailable`으로 종료하며, 새 후보 집합을 섞어 이어보지 않는다. API 서버는 continuation·추천 세션·후보 큐를 전달받거나 저장하지 않는다. 한 번의 사용자 행동은 새 provider attempt 최대 8회, 새 검증 코스 최대 3개를 추가한다. 총 표시 수에는 제품상 고정 상한을 두지 않으며, 후보 소진·시간/운영 종료·경로 미확인·일일 한도는 해당 근거와 함께 종료한다.
4. **중복·캐시·호출량.** 이미 보인 동일 stop 순서 코스, 같은 장소 집합의 순서만 바꾼 중복, 이미 탈락한 코스는 다시 검증하지 않는다. 그러나 `A`, `A→B`, `A→B→C`처럼 장소 수가 다른 부분집합 코스는 서로 다른 선택지이므로 시간 적합 시 함께 검증·표시할 수 있다. 실제 route adapter는 로컬 재수화된 현재 구간의 좌표만 일시 요청 값으로 받을 수 있지만, route cache/서버에는 현행 공개 구간 cache 경계 외 추천 세션·사용자 ID·정밀 위치를 보관하지 않는다. 동일 구간·수단의 세션/서버 cache hit와 in-flight 재사용은 새 provider attempt가 아니다. 도보·대중교통 Kakao 일일 한도와 typed 실패는 유지하며 ODsay·TMAP·근사시간 fallback을 만들지 않는다.
5. **운영시간 확인 후 들러볼 시장·거리.** 구조화 운영시간이 없는 `conditional_more` 중 데이터가 `market/street/alley` 권역으로 식별하고 시설·개별 점포·도매/새벽 전용·장기 이용 장소를 제외한 후보는, 제품 휴리스틱 `10:00–18:00` 안에서만 별도 영역 `운영시간 확인 후 들러볼 곳`에 표시할 수 있다. **노출 경계는 기기의 실제 현재 시각**으로 `10:00 ≤ t < 18:00`이다. 따라서 09:59는 숨김, 10:00·17:59는 노출, 18:00은 숨김이며, 18:00 경계를 넘거나 앱이 foreground로 돌아오면 이미 열린 결과에서도 조건부 카드·더 보기·수동 CTA를 숨긴다. 개발용 추천 시작 시각은 이 노출 창을 연장하지 않는다. 이 시간대는 **안전시간·영업 보장·자동 추천 근거가 아닌 탐색 노출 기준**이다. 142개 같은 부산 전역 후보를 한 화면에 모두 렌더하지 않는다. 출발지(도착지가 있으면 출발·도착 중 더 가까운 쪽)와의 직선거리로만 결정적으로 정렬해 가까운 8개를 먼저 보이고, `더 보기`는 다음 8개를 기존 카드 뒤에 추가한다. 이 탐색 페이지는 실제 경로·route/API 호출·운영시간 상태 변경을 만들지 않으며, 전체 조건부 후보에는 고정 총량 상한을 두지 않는다. 카드에는 `운영시간을 카카오맵에서 확인해 주세요`와 장소 정보 외부 전환을 표시한다. 사용자가 확인 뒤 명시적으로 계산을 요청할 때만 `출발 → 해당 권역 → 도착/복귀`를 실제 경로로 계산한 조건부 수동 코스를 만든다. **수동 계산은 버튼을 누른 실제 확인 시각도 `10:00 ≤ t < 18:00`일 때만** 허용한다. 그때 엔진은 최초 시작 시각을 재사용하지 않고 확인 시각과 그동안 차감한 남은 시간을 입력으로 쓴다. 18:00 이후에는 route 호출 없이 재추천 안내로 끝난다. 이 코스는 끝까지 `운영시간 확인 필요(사용자 확인)` 상태이며 대표·검증 대안·`추천/검증됨`으로 승격하지 않는다.
6. 카카오맵 링크는 장소 정보 확인 행동일 뿐 route 호출·추천 상태 변경을 만들지 않는다. 앱은 카카오 장소 검색 REST 응답에 없는 운영시간을 수집·추정·보관하여 자동 판정하지 않는다. 공식 운영시간 근거가 추가된 시장만 별도 데이터 감사 뒤 `representative_*`로 승격할 수 있다.

**DEC-CONDITIONAL-CLOCK-02 — 조건부 노출의 실제 시각 우선 (2026-08-31, 현행·구현 보완 필요).** 이전 방식은 추천 시작의 `session.nowIso`만으로 조건부 카드 노출을 고정해, 17:59에 연 결과가 실제 18:00 이후에도 시장을 계속 보여 주었다. 수동 계산만 실제 시각에서 막아 “추천처럼 보이지만 계산은 못 하는” 모순이 생겼다. 교체 방식은 **기기의 실제 현재 시각**을 조건부 영역의 독립 노출 기준으로 쓰는 것이다. 18:00 경계·foreground 복귀에서는 이미 열린 카드도 숨긴다. 추천의 고정 입력·대표/대안 시간표는 바꾸지 않으며, 개발용 추천 시각도 조건부 노출 창을 연장하지 않는다. 상태: **현행 정책, U-RESULTS-04 구현 대기**.

### 1.6 출시 대표 코스 파이프라인 (2026-09-02 현행)

```text
입력: 현재 위치 · 도착지/복귀 · 최대 120분 종료 시각 · 도착 여유(기본 10분)
  → provider가 자동 대표 후보 191개만 제공(조건부·hold 제외)
  → representative 분류·운영 가능성·공간 관련성을 통과한 1곳 후보 풀만 선별
  → origin → candidate → destination/return의 두 구간을 실제 receipt로 검증
  → 최소 20분·구조화 운영시간·도착 여유를 모두 통과한 1곳만 결과로 채택
  → 신규 provider attempt 최대 8회 안에서 대표 1개와 서로 다른 1곳 대안 최대 3개를 목표로 반환
  → 미검증 single 후보가 남으면 one-stop continuation과 `다른 장소 더 보기`를 제공
  → 사용자가 누를 때마다 다음 후보를 신규 provider attempt 최대 8회로 검증해 새 1곳 코스 최대 3개를 기존 목록 뒤에 추가
  → 첫 요청의 자동 16회 보충·2/3곳 조립·candidate-to-candidate receipt·조건부 자동 승격은 하지 않음
```

사용자 화면에는 실제 이동 구간·도착 여유·남는 시간을 표시한다. 결과 카드는 선택 체류를 분리하지 않고 이동+선택 체류 합계만 보여 주며, 코스 확인 상세에서만 `둘러보기 약 N분`으로 선택 체류의 근거를 설명한다. 20~29분만 가능한 경우 카드에는 `가볍게 둘러보기`, 상세에는 `가볍게 둘러보기 약 N분`을 표시한다. 첫 대표와 이미 보인 대안의 순서는 더보기 뒤에도 유지하며, 새로 검증된 서로 다른 single만 아래에 누적한다. 후보가 남는 동안 더보기를 반복할 수 있고 화면 총량에는 별도 고정 상한을 두지 않는다. 조건부 시장·거리는 자동 결과와 분리한다.

#### DEC-TWO-STOP-SELECTION-01 — 최대 2곳 제한 조립 구현 계약 (2026-09-04 UX 보완, 원격 활성화 전)

현재 one-stop 결과는 최대 2곳 조립의 시작점이다. 사용자가 추천 화면의 실제 표시 one-stop 카드 A를 누르면 같은 화면에서 A를 고정하고, 그때만 두 번째 장소 검증을 시작한다. A만 선택한 상태에서도 one-stop 코스 확인 CTA는 항상 유지한다. A를 제외한 representative 후보 B에 대해 `origin→A→B→target`과 `origin→B→A→target`의 세 leg, 두 장소 도착별 구조화 운영시간, 각 최소 20분, 최종 도착 여유를 모두 exact 검증한다. 둘 다 유효하면 세 leg 총 이동시간이 짧은 순서를 쓰고 동률이면 A를 앞에 둔다. 사용자는 순서를 편집하지 않으며 3곳을 추가할 수 없다.

두 번째 후보는 exact 성공 순서대로 점진 표시하고 이미 보인 카드 순서를 바꾸지 않는다. 기본 성공 목표는 3개이나 0~2개를 허용하고, 더보기까지 누적 최대 6개다. 실패하면 미검증·근사·조건부 후보로 채우지 않고 A one-stop과 확인 가능한 부족 이유를 유지한다. B 선택은 이미 검증된 snapshot을 같은 Results 화면에 보관하며 navigation·추천 route 0이다. 사용자가 fixed CTA를 눌렀을 때만 선택된 snapshot으로 코스 상세를 연다.

첫 B 지연 보완(2026-09-04): 같은 recommendation session에서 이미 표시까지 마친 exact one-stop course들을 runtime seed로 동결한다. A와 우선 검토할 B의 `origin→place`, `place→target` exact leg는 시간·수단·geometry를 보존해 receipt cache에 `reused=true`, 신규 provider attempt 0으로 넣고, pair에서 새로 생기는 `A→B`, `B→A`만 요청한다. 이는 pair를 미리 계산하거나 one-stop 결과만으로 2곳 가능을 추정하는 규칙이 아니다. 엔진은 두 새 교차 leg가 exact일 때만 두 순서의 도착 시각, 장소별 구조화 운영시간, 각 최소 체류, 최종 도착 여유를 다시 계산해 B를 확정한다. 무효·불일치 seed는 무시하고 기존 exact 검증으로 돌아가며 검증되지 않은 B를 표시하지 않는다.

신규 route provider attempt는 한 recommendation session에서 `최초 one-stop 8 + A 선택 자동 16 + 명시적 확장 공유 12 = 최대 36회`다. 공유 12회는 A 선택 전 one-stop `다른 장소 더 보기`와 A 선택 후 두 번째 후보 `더 보기`가 함께 소비한다. cache/session hit은 attempt가 아니다. 선택 단계의 live 장소 API는 0회이며 선택한 2곳 상세의 endpoint geometry connector는 별도 최대 6회를 예약한다. A 취소·재선택은 예산을 초기화하지 않는다.

A를 선택하기 직전 one-stop place ID·순서·이미 연 더보기·continuation·완료/부족 상태·스크롤 위치를 화면 메모리 snapshot으로 보존한다. A 취소는 새 provider attempt 0회로 이 상태를 그대로 복원한다. B 선택은 검증된 2곳 snapshot을 화면에 보관할 뿐 상세로 즉시 이동하거나 route를 다시 호출하지 않는다. 사용자가 고정 CTA를 눌렀을 때 A만 선택했으면 one-stop, B도 선택했으면 해당 exact pair snapshot으로 코스 확인을 연다. 모든 pair 진행 결과는 `selectedFirstPlaceId + requestId(epoch)`와 일치할 때만 반영해 취소·재선택 뒤의 늦은 응답이 목록에 섞이지 않게 한다. 공개 continuation에는 후보 ID·cursor·signature·attempt ledger·opaque receipt key·typed 이유만 두며 좌표·사용자 ID·함수/provider 객체를 넣지 않는다.

진입점 변경 이력(2026-09-04): 처음 구현한 `one-stop 상세의 한 곳 더 고르기`는 엔진·예산 안전성을 증명한 전환 단계였지만, 실제 선택은 추천 결과 화면에서 이루어지는 편이 비교와 취소에 유리하다. production UI 진입점만 결과 카드 직접 선택과 고정 tray/CTA로 교체한다. 첫 인라인 구현도 선택 전/후에 서로 다른 전체 화면 트리와 ScrollView를 반환해 페이지 전환처럼 보여 반환했다. 이를 **같은 Results tree·ScrollView를 유지하고, 기존 one-stop 카드 영역만 B loading/후보 영역으로 교체**하는 방식으로 교체했다. A 취소 시 같은 영역에 저장한 one-stop 목록과 scroll을 복원한다. pair-only exact 검증, 공유 12회·session 36회, snapshot identity 계약은 그대로다. 상태: **2-Z·U-TWO-STOP-03 자동 수락·실기기 체감 확인 전**.

역선택 재사용 보완(2026-09-04): 같은 recommendation session과 같은 입력에서 exact로 확정한 두 장소 집합 `{A,B}`는 A별 branch 이름과 무관한 **순서 없는 검증 pair**다. A 선택에서 B가 검증된 뒤 취소하고 B를 선택하면, A를 새로운 후보처럼 다시 호출하지 않고 동일 exact course snapshot을 현재 branch의 우선 후보로 재검증·재사용한다. 실제 방문 순서는 기존 snapshot의 `placeIds`와 legs를 유지하며 사용자가 먼저 누른 장소를 임의로 첫 방문으로 바꾸지 않는다. 이 재사용은 current session runtime에만 존재하고 신규 provider attempt·adapter call은 0이며 B 목표 3·누적 6에는 한 후보로 센다. 다른 시각·출발지·도착지·남은 시간·provider/catalog signature에는 재사용하지 않는다. 아직 어느 방향에서도 검증하지 않은 pair는 첫 페이지 노출을 보장하지 않고 기존 공간 순서·호출 예산·더보기를 따른다. provider/store/continuation terminal partial은 runtime pair로 승격하지 않고, attempt-limit 시점에 이미 exact인 partial은 유지한다. B 후보에는 pair 전체를 B 자체 시간처럼 표시하지 않고 A one-stop 대비 이동+체류 추가분을 표시한다. 상태: **정책 보완 확정·2-AA·U-TWO-STOP-04·QA-TWO-STOP-02 자동 수락, 작은 iPhone UI 체감만 출시 후보 smoke에 남음**.

이 결정은 기존 one-stop 더보기의 무제한 명시 페이지를 **2곳 기능이 활성화된 recommendation session에서만** 공유 12회로 제한한다. 자동 회귀와 public A↔B store 게이트가 실패하면 일반 사용자 활성화만 보류하고 현행 one-stop fallback을 유지한다. 상세 계약과 역할별 활성화 게이트는 `docs/work/integration-decision/two-stop-limited-assembly.md`를 따른다.

```text
  → 첫 stage에서 큐 앞부분을 실제 경로로 최대 8회 검증하고, 검증 코스가 4개 미만이면서 큐가 남을 때만 전체 최대 16회까지 보충한다
  → 각 코스의 출발 → 1~3곳 → 도착/복귀 모든 구간이 실제 도보·대중교통이고 최소 체류·운영시간·도착 여유를 통과할 때만 검증 완료
  → 상단 대표 1개와 첫 대안 최대 3개를 반환한다. 대표는 1~2곳을 우선하고, 짧게 가능·3곳 코스도 실제로 검증되면 대안에서 숨기지 않는다
  → 사용자가 `다른 검증 코스 더 보기`를 누르면 같은 큐의 다음 후보만 최대 8회 검증해 최대 3개를 기존 목록 뒤에 추가한다
  → 조건부 시장·거리 후보는 이 흐름 밖의 정보 확인·명시 확인 수동 계산으로만 처리
```

사용자 결과는 실제 경로 검증을 통과한 코스와 그 구간 시간만 표시한다. 상단 대표는 1곳 또는 2곳 코스를 우선하며, 유효한 1·2곳 코스가 없을 때만 3곳 코스를 대표로 쓴다. 3곳 코스는 대표 우선순위가 낮을 뿐, 시간 안에 가능하면 다른 코스 목록에서 숨기지 않는다. 내부 공간 점수·18개 장소 풀·5,220개 조합·8/16회 호출 예산은 사용자에게 표시하지 않는다. 대표 후보 자체가 없을 때와 검증 코스가 없을 때는 구분하되, 어느 경우에도 일반 카페를 억지로 추천하거나 조건부 장소를 대표로 승격하지 않는다. 날씨가 실제로 불리하다고 판정하는 데이터 연동 전에는 `날씨가 좋지 않으니`라는 문구를 쓰지 않는다.

**DATA-SUPPLY-01 반영 (2026-09-01, 현행).** 기존 대표 190개는 불변으로 유지하고, 중구 공식 접근 시간(매일 09:00–20:00)과 20분 가벼운 방문 근거를 각각 확인한 부평깡통시장(`poi_4`) 1개만 `representative_standard`로 승격했다. 따라서 자동 대표 provider 입력은 현재 191개다. 이 변경은 부산역·남포 생활권의 한 후보 보강일 뿐, 서면·전포·사상↔서면·센텀·해운대의 대안 부족을 해결했다는 판정은 아니다. 네 생활권의 실제 재확인은 `QA-SUPPLY-01`에서 분리해 판단한다.

### 1.7 결과 구성 전환 기록 (2026-08-25, 배포 후 보류 이력)

- **이전 방식:** 첫 결과에는 대표 코스 하나만 보이고, 사용자가 `새 추천`을 눌러 같은 세션의 대안을 한 개씩 교체했다. 사전선정은 권장 체류 합계가 입력 시간을 많이 채우는 코스를 우선했다.
- **문제/관찰:** 사용자는 하나의 대표만으로 선택하지 않으며, 시간이 길다는 이유만으로 2·3곳을 강제하거나 남는 시간을 채우기 위해 체류를 늘리는 것은 자투리 시간 활용 목적과 맞지 않는다. 서로 겹치는 대안을 순차로 보는 경험도 선택 폭을 전달하지 못했다.
- **교체 방식:** 분 단위 입력마다 1·2·3곳 코스를 모두 검토한다. 실제 경로 검증을 통과한 결과 중 상단에는 1~2곳을 우선한 `시간의 추천` 하나를, 아래에는 서로 실질적으로 다른 검증 코스 목록을 함께 보인다. 각 코스는 최소 체류 기준으로 시간 안에 끝나야 하며, 권장 체류를 확보한 코스가 우선한다. 최소만 가능한 코스도 별도 시간 변형으로 중복하지 않고 `짧게 가능` 상태로 함께 보인다. 남는 시간은 그대로 표시한다.
- **이동·체류 품질:** 도보·대중교통의 추가 이동이 지나치게 길고 선택 체류가 짧은 후보는 낮은 품질로 본다. 다만 고정된 시간 구간이나 경직된 이동/체류 비율로 후보를 일괄 제외하지 않는다. 60·120분 상한은 남은 시간을 채우는 목표가 아니며, 먼 한 곳의 활동 범위·권장 체류와 실제 경로의 균형은 고정 fixture 체감 검증으로 조정한다.
- **상태:** 배포 후 보류 이력. mixed 1~3곳 자동 결과에는 다시 쓰지 않으며, 현재 one-stop 기본과 `DEC-TWO-STOP-SELECTION-01` pair-only branch가 우선한다.

### 1.8 실경로 캐시·호출량 운영 결정 (2026-08-26, 구현 전)

- **결정:** 시간 안에 가능하다고 표시하는 대표·대안 코스는 클릭 뒤가 아니라 표시 전에 실제 도보·대중교통 경로를 검증한다. 검증 전 다수 코스 생성은 내부 선별용이며, 사용자에게 시간 보장 추천으로 노출하지 않는다.
- **캐시 단위:** 서버 공용 캐시는 코스 전체가 아니라 방향·수단·좌표/카탈로그 장소 ID가 일치하는 **이동 구간**으로 둔다. 여러 코스가 공유하는 장소↔장소 구간은 재사용하고, 현재 GPS 출발지처럼 개인 위치가 들어간 구간은 요청·짧은 세션 안에서만 쓰고 장기 저장하지 않는다.
- **호출량 전제 변경 (2026-08-26):** 이전 설계는 ODsay Basic을 `1,000/일`로 가정했으나, 현 공식 운영정책의 Basic 한도는 **30/일**이며 기본 대중교통 API는 출발–도착 단일 호출 용도에 한정된다. 1~3곳 코스는 2~4개 구간을 가질 수 있고, 대안까지 표시 전 검증하면 사용자 한 명의 첫 요청에도 여러 ODsay 호출이 생긴다. 따라서 30/일은 다중 사용자 자동 대중교통 검증의 운영 예산이 될 수 없다.
- **대체 수단 조사 (2026-08-26):** 카카오맵 REST API는 장소 검색뿐 아니라 좌표 기반 `대중교통 경로 조회`와 `도보 경로 조회`를 제공하며, 첫 무료 쿼터 적용 앱에 각각 일 1,000건을 명시한다. 현재 앱 키로 부산 고정 좌표 한 쌍을 각 1회 확인해 두 API 모두 HTTP 200·`OK`·총 소요시간·구간 정보를 반환했다. TMAP은 보행자 경로안내 Free 일 1,000건이 확인됐지만, TMAP 대중교통은 공개 무료 한도가 확인되지 않는 별도 상품이다. 부산 공공데이터의 무료 버스 도착정보는 찾았으나, 출발–도착 멀티모달 경로 생성의 대체재는 아니다.
- **결정 이력:** Kakao 대중교통 경로를 ODsay 대체 adapter로 채택할지는 대기 상태였다. 2026-08-26 사용자 결정으로 아래 1.9의 제공사 분담 정책으로 전환한다. 이 전환 전까지 ODsay 한도를 임의로 우회하거나 근사시간을 검증 결과로 승격하지 않는다.
- **개인정보 경계:** 장기 저장은 공개 장소 간 경로와 개인을 식별하지 않는 제공사별 집계뿐이다. 사용자 ID·정밀 GPS·IP와 결합한 경로 이력은 서버 분석·공용 캐시의 입력으로 저장하지 않는다.
- **상태:** 전환 구현 전. 외부 API 어댑터 `API-4-B → API-4-A`, 엔진 `2-J` 순으로 구현한다.

### 1.9 Kakao 단일 경로 제공사 전환 기록 (2026-08-28, 구현 전)

- **이전 방식:** 도보는 TMAP, 대중교통은 ODsay를 기본으로 실제 경로 검증했다. ODsay Basic 30건/일은 다중 사용자·대안 코스 검증에 맞지 않는다.
- **발생한 문제:** 카카오·TMAP 이중 도보는 별도 TMAP server key·quota·보관 조건·fallback 운영을 요구한다. TMAP은 대중교통 자동 추천의 제공사가 아니며, 공모전 배포 단계에서 두 제공사의 도보 분산은 활성화 조건과 장애 원인을 불필요하게 늘린다.
- **교체 방식(현행 결정):** 대중교통과 도보의 실제 경로는 모두 **Kakao REST 단일 제공사**를 사용한다. ODsay와 TMAP은 런타임 자동 추천에서 제외한다. 먼저 방향·수단·공개 장소 ID 단위의 유효 cache를 재사용하고, cache miss만 Kakao로 보낸다. provider fallback·동시 이중 호출은 하지 않는다.
- **운영 경계:** 대중교통과 도보는 각각의 Kakao API 예산·soft limit을 독립적으로 관리한다. 어느 한도 초과·timeout·실패도 근사시간·ODsay·TMAP으로 우회하지 않고 검증 불가 상태로 반환한다. route key, budget 계수, 공용 구간 cache는 server Route Proxy에만 두며, 앱의 `EXPO_PUBLIC_KAKAO_REST_API_KEY`는 장소 검색·역지오코딩 client key로만 남긴다.
- **교체 이유:** Kakao 대중교통 실호출 가능을 확인했고, 서버 전용 Kakao route key를 준비한 현재 조건에서 추천 경로를 하나의 호출·보안·quota 경계로 운영하는 편이 공모전 배포의 신뢰성과 관찰 가능성에 더 적합하기 때문이다. 이후 실사용 데이터에서 도보 장애·한도 문제가 확인될 때만 TMAP fallback을 별도 계약으로 재도입한다.
- **상태:** 구현 전환 진행 예정. API-4-A-ACT-02-K가 Kakao-only proxy fixture·runtime 전환을 완료한 뒤에만 2-J가 cache hit/miss·예산을 소비한다.

### 1.10 실제 경로 검증 보충·페이지 호출 예산 정책

- **2026-09-02 출시 one-stop 현행:** 첫 계산은 신규 attempt 최대 8회에서 자동 보충하지 않는다. 사용자가 `다른 장소 더 보기`를 누를 때만 single 전용 다음 후보를 신규 attempt 최대 8회로 검증해 최대 3개를 누적한다. 아래의 첫 8→조건부 16회와 1~3곳 queue 설명은 배포 후 보류한 multi-stop 기록이다.

- **이전 방식:** 대표 후보 18곳에서 만든 순서 코스 중 사전선정 상위 4개만 실제 경로로 검증했다. 그 네 코스가 실제 이동시간·운영시간에서 탈락해도, 뒤의 후보는 검증하지 않았다.
- **문제/관찰:** 실제로 갈 수 있는 뒤 후보가 있어도 첫 네 코스의 탈락만으로 추천이 비거나 대안 수가 적을 수 있다. 반대로 고정 코스 수를 무제한으로 늘리면 Kakao 호출량과 응답 시간이 통제되지 않는다.
- **교체 방식(2026-08-31 multi-stop 구현 기록):** 첫 결과는 새 Kakao provider attempt 최대 8회로 대표 포함 검증 코스 4개(대표 1 + 대안 최대 3)를 목표로 한다. 그 뒤에도 4개 미만이고 사전 선별한 미검증 큐가 남은 경우에만 전체 최대 16회까지 보충한다. 각 `다른 검증 코스 더 보기` 행동은 같은 세션의 다음 큐를 새 attempt 최대 8회로 검증해 새 코스 최대 3개를 추가한다. Route Proxy의 서버 cache hit와 앱 세션 안의 같은 구간 재사용은 새 attempt로 세지 않는다. 도보 확인 뒤 대중교통 확인이 추가로 발생하면 각각 1회씩 센다. 후보 큐 소진·Kakao 한도·timeout·검증 실패는 ODsay·TMAP·근사시간으로 우회하지 않는다.
- **결과 구성 경계:** 대표 1개와 실제 검증된 대안을 가능한 만큼 보존한다. 장소 중복을 전면 금지하거나, 사용자가 장소를 고정·삭제·순서 편집하는 재조립은 이 단계에서 구현하지 않는다. 그 기능은 이후 `장소 중심 재추천` 작업에서 별도 결정한다. 코스는 ordered `stopIds`·실제 legs·공통 출발/도착 정보를 보존해 후속 재추천이 가능해야 한다.
- **설명 가능성:** 코스 0개·대안 부족은 단순 빈 문장이 아니라 후보 부족, 운영 종료, 실제 이동/시간 초과, 경로 검증 불가/한도 중 어느 단계에서 생겼는지 비밀 없는 reason과 개수로 반환한다. UI 문구 매핑은 UIUX 후속 작업의 책임이다.
- **상태:** 2026-08-29의 고정 8회와 2026-08-31의 multi-stop `2-Q / API-PAGE-01` 구현은 회귀 기준으로 보존하되 출시 entry에서는 사용하지 않는다. one-stop 요청형 이어보기는 `2-V / U-ONE-MORE-01 / QA-ONE-MORE-01`에서 구현·고정 fixture 검증까지 수락했다. 실제 Kakao 응답 품질·cache/budget과 네이티브 화면은 출시 후보의 제한 실기기 smoke로 분리한다.

### 1.11 사용자 확인 체류 개인화 (2026-09-04, 구현 전)

- 체류 개인화의 근거는 Live Activity 또는 앱 안에서 사용자가 명시한 `도착했어요`와, 이후 실제 길찾기 handoff 성공 또는 명시 완료로 확인한 출발 사이의 완료 표본뿐이다. 도착 또는 출발이 없으면 표본을 합성하지 않는다.
- Route Proxy용 Supabase anonymous Auth, 비로그인, 미동의 사용자의 기록은 서버 개인화 데이터가 아니다. 일반 로그인과 별도 체류 기록 동의가 모두 있어야 한다.
- 개인화 키는 정제 카탈로그의 `(category, subCategory)` 복합 키다. 같은 subCategory 문자열이 다른 category에 반복되므로 문자열 하나만 전역 키로 쓰지 않는다. `subCategory`가 없는 장소는 완료 표본을 보존할 수 있어도 개인화 계산에는 사용하지 않으며, UI·엔진이 category/subCategory를 임의 분류하지 않는다.
- 유효 표본 1~2개는 수집만 한다. 3개부터 새 표본마다 최신 최대 5개의 중앙값을 계산하고 5분 단위로 반올림한다. 평균·최빈값·3개 단위 배치는 이번 버전에서 사용하지 않는다.
- 적용값은 카탈로그 기본 권장값 대비 최대 `±10분`이고 장소 `minStayMin...maxStayMin`을 벗어나지 않는다.
- 개인화는 후보가 기존 하드 조건을 통과한 뒤 기존 체류 배정기의 soft recommended override와 동률 보조 순위에만 적용한다. 개인화 목표가 1곳/2곳의 운영시간·총예산 안에 맞지 않으면 목표를 줄이거나 기존 비개인화 선택 체류로 되돌린다. 개인화값 때문에 원래 가능한 장소를 제거하거나 route를 추가 호출하거나 실제 경로·운영시간·최소 체류·도착 여유를 완화해서는 안 된다.
- 카탈로그 기본값과 개인화 프로필은 별개다. 사용자별 결과를 `src/data` 원본이나 공용 route cache에 기록하지 않는다.

상세 시각·동의·저장·실패 계약은 [DEC-LIVE-DWELL-01](../work/integration-decision/live-activity-dwell-personalization.md)을 따른다.

### 1.12 명시 선택과 최적 방문 순서 (2026-09-05, 현행 결정·UI 구현 전)

- **이전 방식:** Results의 검증 one-stop 카드를 누르는 즉시 첫 장소 A를 선택하고 pair 후보 계산을 시작했다. 사용자가 장소 위치·성격·운영시간을 확인하기 전부터 선택 상태와 호출이 바뀌었다.
- **교체 방식:** 카드 tap은 장소 상세 미리보기일 뿐이다. 전체 지도형 상세에서 사용자가 `선택하기`를 명시한 경우에만 A/B 선택 상태를 갱신하고 A 확정 뒤에만 pair 후보 계산을 시작한다. 상세 열기·닫기는 추천·route attempt 0회다.
- **최적화 기준:** 두 장소가 선택되면 선택 순서를 방문 순서로 쓰지 않는다. 기존 exact pair 계약의 `O→A→B→D`와 `O→B→A→D`를 모두 비교하고, 실제 경로·두 운영시간·각 최소 체류·도착 여유를 통과한 순서 중 총 검증 이동시간이 짧은 것을 사용한다. 동률은 기존대로 첫 선택 A 우선이다.
- **단일 snapshot:** 최종 지도 번호, 세로 장소 카드, 구간 수단·시간, 카카오 길찾기의 출발·도착은 모두 같은 최적화 snapshot 순서를 사용한다. UI가 직선거리나 사용자의 담은 순서로 다시 정렬하지 않는다.
- **복원:** 첫 장소 취소는 선택 전 one-stop 목록·순서·더보기·continuation·스크롤을 신규 route 0회로 복원한다. 장소 상세를 닫는 것은 선택 취소가 아니며 진입 전 A0/A1 상태를 그대로 유지한다.
- **상태:** exact 양방향 비교와 예산 계약은 `REC-32/33` 구현을 재사용한다. 카드 tap 즉시 선택 UI는 철회하고 `DEC-PLACE-COURSE-FLOW-01`의 상세 후 명시 선택으로 교체한다. 최대 2곳·B 3 목표/누적 6·session 36 attempt·3곳 금지 경계는 바꾸지 않는다.

상세 화면·진행 상태 계약은 [DEC-PLACE-COURSE-FLOW-01](../work/integration-decision/place-detail-and-optimized-course-flow.md)을 따른다.

## 2-1. 시간 안전·체류 정책 (전환 전 구현 기록)

아래 고정 수단별 버퍼, 단일 `dwell`, 다중 장소 조립 규칙은 전환 전 런타임 기록이다. 현재 동작 설명이 아니며 [1.4](#14-시간-예산과-체류-상태-2026-08-21-현행-결정-구현-전)의 사용자 도착 여유와 체류 범위 규칙으로 교체됐다.

### 안전 여유시간

약속 지연 위험이 수단마다 다르므로, 입력한 남은 시간에서 아래 시간을 먼저 확보한다. 이전의 `남은 시간 12%` 계산은 사용하지 않는다.

| 이동수단 | 안전 여유시간 | 이유 |
|---|---:|---|
| 도보 | 8분 | TMAP 실제 경로 재검증을 전제로 신호·보행 속도 차이만 흡수 |
| 대중교통 | 20분 | TAGO 실시간 버스 도착 연동 전의 접근 도보·환승·배차 변동 대응 |
| 차량 | 10분 | 교통 상황은 있으나 경로 재탐색이 쉬움 |

### 최소 체류시간

- 기본값은 장소당 `30분`이다.
- 자연관광지와 거리·골목·광장·시장 성격의 상업지구만 접근 이동시간에 따라 예외를 둔다.
  - 접근 `10분 이하`: `15분`
  - 접근 `11~15분`: `20분`
  - 접근 `16분 이상`: `30분`
- 카페·식당·문화시설·레저/스포츠와 개별상점·아울렛·쇼핑복합공간은 시설형·유료 성격으로 본다.

### 이동 대비 체류

약속지까지 원래 가야 하는 시간 자체는 불이익으로 계산하지 않는다. 대신 `경유 장소를 넣어 추가된 이동시간`과 체류시간을 비교한다.

- 시설형·유료 성격: 배정 체류시간이 추가 이동시간보다 짧으면 추천 및 장바구니 추가에서 제외한다.
- 자연·거리·광장 등 가볍게 구경 가능한 장소: 시간 예산과 최소 체류시간을 충족하면 표시한다. 추가 이동시간이 체류시간보다 길면 **제외하지 않고 낮은 순위**로 둔다.
- 장바구니에서 장소를 추가할 때도 같은 정책을 즉시 재계산한다.

운영시간 또는 권역 추천 가능 시간대가 확인되지 않은 시설형·상권 의존형 장소는 자동 추천에서 보류한다. 카카오맵 상세 링크는 사용자가 메뉴·사진·후기를 추가 탐색하는 보조 기능이다.

### 사용자에게 보이는 시간 상태

`가능 여부`와 `빠듯함`은 분리한다. 수단별 안전 여유시간(도보 8분, 대중교통 20분, 차량 10분)은 약속 지연을 막기 위한 **하드 조건**이며, 이를 충족하지 못하면 항상 불가능이다. 별도의 10분은 사용자가 판단할 수 있도록 보여 주는 **추가 여유 기준**이다.

대중교통의 20분은 임시 고정값이다. TAGO 버스 실시간 도착과 부산도시철도 시간표를 연결한 뒤에는 노선 구성에 따라 `실시간 대기시간 + 환승·지연 안전 여유`로 교체한다. 실시간 정보가 없거나 조회에 실패한 경우에는 20분을 폴백으로 유지한다.

| 상태 | 조건 | 사용자 의미 |
|---|---|---|
| 여유 | 권장 체류시간을 모두 확보하고, 안전 여유를 제외한 추가 시간이 10분 이상 | 계획대로 둘러볼 수 있음 |
| 짧게 가능 | 최소 체류시간은 확보했지만 권장 체류시간보다 짧고, 추가 시간은 10분 이상 | 짧게 들를 수 있음 |
| 빠듯 | 최소 체류시간은 확보했지만 안전 여유 외 추가 시간이 10분 미만 | 가능하지만 일정 변경 위험이 있음 |
| 불가능 | 최소 체류시간 또는 수단별 안전 여유시간을 충족하지 못함 | 장바구니에 담을 수 없음 |

10분을 모든 장소의 체류시간 단위로 쓰지는 않는다. 카페·식당·시설처럼 목적 활동이 있는 장소의 최소 체류는 30분을 유지하고, 거리·골목·광장 같은 가벼운 구경 장소만 접근 시간에 따라 15~20분을 허용한다.

## 2-2. 시행착오 기록: 지도 후보와 장바구니의 시간 판정 불일치 (2026-08-16)

이 기록은 단순 변경 이력이 아니다. 추천 규칙을 바꿀 때 **사용자에게 보이는 후보, 장소 상세, 장바구니**가 같은 판단을 하는지 확인하기 위한 사고 순서다.

### 1. 사용자에게 보인 증상

- 지도에는 음식점·카페 마커가 보였지만, 마커를 눌러 도보·대중교통·차량을 모두 확인하면 어느 수단으로도 장바구니에 담을 수 없는 경우가 있었다.
- 사용자는 "담을 수 없다면 왜 처음부터 추천했는가"라고 받아들인다. 이는 단순히 시간이 빠듯한 문제가 아니라 추천 결과의 신뢰를 훼손하는 오류다.

### 2. 처음의 잘못된 가정

사전 이동수단 선택을 없애고 "세 수단 중 하나라도 시간 안에 가능하면 지도에 보인다"는 방향 자체는 맞았다. 다만 후보를 거르는 계산과 상세 화면의 계산이 서로 달랐다.

| 단계 | 당시 계산 | 문제 |
|---|---|---|
| 지도 후보 | `출발 → 장소 → 약속` 전 구간을 같은 수단 하나로 계산 | 차량으로 전 구간이 가능하면 후보가 통과할 수 있었다. |
| 장소 상세·장바구니 | `출발 → 장소`는 사용자가 고른 수단, `장소 → 약속`은 구간 거리 기반 자동 수단으로 계산 | 차량으로 장소까지 간 뒤 약속지까지는 자동으로 도보·대중교통이 선택될 수 있어, 후보 단계의 차량 전 구간 계산과 결과가 달라졌다. |

즉, 지도에서는 `차량 → 차량`으로 통과했지만 실제 선택 화면에서는 `차량 → 자동 수단`으로 다시 계산되어 전부 불가능해지는 모순이 생겼다. 안전 여유시간도 구간 수단별로 달라 이 차이를 더 키웠다.

### 3. 확인한 방법

서면 출발, 약속 장소 없음(왕복), 일요일 14시, 60분 조건으로 후보와 상세 계산을 비교했다.

- 수정 전에는 지도 후보의 통과 여부와 상세의 세 수단 상태가 일치하지 않는 경우가 있었다.
- 수정 후 시간 조건을 통과한 24곳 중 운영시간 게이트를 통과해 표시된 17곳은 모두 상세와 같은 계산 기준에서 최소 한 수단이 가능했다.
- 이 검증은 직선거리 근사와 운영시간 데이터 기준이다. 장바구니 확정 시에는 실제 경로 API로 다시 계산하므로, 실제 길찾기 시간을 완전히 보장한다는 뜻은 아니다.

### 4. 채택한 단일 규칙

지도 후보, 마커 선택 상태, 장바구니 추가는 아래 규칙을 공유한다.

1. 각 후보에 대해 도보·대중교통·차량을 하나씩 `출발 → 장소`의 **진입 수단**으로 시험한다.
2. `장소 → 약속`은 사용자가 아직 고정하지 않은 구간이므로 자동 수단으로 계산한다. 도보 약 14분 이하는 도보, 초과하면 대중교통을 기본값으로 하며 차량은 자동 선택하지 않는다.
3. 이 조합 중 하나라도 최소 체류시간과 안전 여유시간을 만족할 때만 초기 지도 후보로 표시한다.
4. 사용자가 장소를 담은 뒤에는 선택한 진입 수단과 이미 담긴 순서를 기준으로 전체 코스를 다시 계산한다.
5. 코스를 확정할 때만 실제 경로 API로 구간별 소요시간과 운영시간을 재검증한다.

초기 후보에서 수단 순서는 도보, 대중교통, 차량이다. 이는 차량 보유를 기본값으로 가정하지 않기 위한 정렬 기준일 뿐, 차량만 가능한 장소도 시간 조건을 만족하면 표시한다.

실제 코스를 만든 뒤 길찾기 화면은 각 구간의 이동수단을 명확히 표시해야 한다. 예를 들어 `도보 이동 → 대중교통 이동 → 도보 이동`처럼 구간별 수단·예상 소요시간·다음 목적지를 보여 주며, 자동 선택된 마지막 구간도 숨기지 않는다.

### 5. 제외한 해결 방식

- "차량 후보만 예외 처리" 또는 "약속 장소가 없을 때만 별도 계산"처럼 조건을 덧붙이는 방식은 채택하지 않았다.
- 이런 방식은 후보 화면과 장바구니 화면에 서로 다른 분기 규칙을 늘리고, 다음 UI 변경에서 같은 문제가 다시 발생한다.
- 이동수단 선택 방식은 화면별 예외가 아니라 추천 도메인의 공통 규칙이므로, 공용 계산 함수로 유지한다.

### 6. 이후 변경 시 확인할 질문

1. 이 변경이 후보 표시, 장소 상세, 장바구니, 코스 확정 중 어느 단계의 시간 계산을 바꾸는가?
2. 바뀌는 단계가 있다면 나머지 단계도 같은 공용 규칙을 호출하는가?
3. 지도에 보이는 장소가 현재 선택 가능한 수단 중 하나로 실제 담기는가?
4. 근사 계산에서 통과한 뒤 실제 경로 재검증에서 탈락했을 때, 사용자에게 사유를 보여주는가?

## 6. 원칙 (불변)

- **ML 없음** — 가중치는 손으로 정하고, 근거를 문서에 남긴다 (데이터 해상도·설명가능성, [AI-Hub 카테고리별 체류시간 분포](../02_data/AI허브_카테고리별_체류시간분포.md) 참조)
- **모든 코스는 why를 가진다** — 점수 내역으로 설명 못 하는 랭킹 변경 금지
- **TMAP 호출 상한 의식** — 지도 전체 후보에는 정밀 경로를 호출하지 않는다. 대표 추천·새 추천·사용자가 연 상세 장소만 도보·대중교통 두 구간을 정밀 계산하고, 좌표쌍·수단 TTL 캐시와 최대 3개 후보 재검사 상한을 적용한다.
- **이 문서와 코드는 항상 일치** — 추천 후보·필터·조합·랭킹·시간 게이트를 수정하는 모든 작업은 같은 변경 단위에서 본 문서와 자동검증 수치를 함께 갱신한다.
- **지도 후보와 자동 추천을 구분** — 지도에 표시하는 시간 적합 후보를 모두 강한 추천으로 표현하지 않는다
- **정책은 단일 기준으로 단순화** — 기존 규칙을 보존하기 위한 예외·누적 분기를 추가하지 않는다. 추천 가능 여부는 시간·최소 체류·운영시간의 하드 조건으로, 이동 효율은 전체 시간 대비 비중의 랭킹 조건으로 분리한다.
