> 목적: "어떻게 추천되는가"를 단계별 수치까지 정확히 기록하고, **불완전한 지점**을 진단해 개선 방향을 정한다.

## 1. 전체 파이프라인 (7단계)

```
입력: 현재위치 · 약속(장소·시각)|없음 · 남은시간 · 이동수단 · 요일/시간대
  │
  ▼
[0] 예산 계산      buffer = max(10분, 남은시간×12%) → budget = 남은시간 − buffer
                   target = 약속장소 (없으면 현재위치=왕복)
  │
  ▼
[1] 후보 수집      TourAPI locationBasedList2 — 반경 1,500m 고정 · 최대 60건
                   → 카테고리 매핑(관광지/문화/식당/카페/쇼핑/레포츠/축제)
                   → 체류시간 부여: POI실측(표본≥5) → 카테고리 중앙값 폴백
                                    × 혼잡배수(요일×시간대, 0.8~1.8)
  │
  ▼
[2] 1차 컷        haversine 왕복추정 + 체류 ≤ budget 인 것만 · 가까운 순 정렬
  │
  ▼
[3] 운영시간 게이트  ⚠️ 가까운 순 상위 16개만 detailIntro2 조회
                   도착예정~체류종료가 영업시간 내? (축제=행사기간도 검사)
  │
  ▼
[4] 코스 조립      (haversine 추정만, TMAP 0건)
                   · 단일: 게이트 통과 전부, total ≤ budget
                   · 미니코스 2곳: 남은시간 ≥ 60분일 때, 상위 8개 풀의 순서쌍
                     — 두 곳 카테고리 달라야 함 · budget×0.6 ≤ total ≤ budget
  │
  ▼
[5] 랭킹 ⭐        정렬 기준 단 2개:
                   ① 스팟 수 많은 코스 우선 (미니 > 단일)
                   ② 총소요(totalMin) 큰 순 = "시간을 알차게"
                   → 같은 조합 중복 제거 → 상위 6개 후보
  │
  ▼
[6] 지연 정밀화    후보 6개 순서대로 구간만 TMAP(시간+실경로) 호출
                   → 예산 재검증 통과분 3개 확정 (탈락 시 다음 후보)
  │
  ▼
출력: 코스 3개 (spots · legs(시간분해+실경로) · 총소요 · 여유)
```

## 2. 핵심 진실 — 지금 랭킹의 정체

**현재 "추천 점수"는 사실상 `총소요시간이 큰 것` 하나다.**

시간-적합(들어가느냐/마느냐)은 정교하게 계산하지만, 통과한 후보들 **사이의 순위**는 "누가 시간을 더 꽉 채우나"로만 정한다. 장소가 *좋은지*는 전혀 안 본다.

> "해신킹크랩이 1위인 이유" = 맛집이라서가 아니라, 체류 60분 + 적당한 거리로 **총합이 제일 커서**다.

## 3. 약점 진단 (구체적)

### A. 랭킹 자체의 결함

| # | 약점 | 증상 | 심각도 |
|---|---|---|---|
| A1 | **장소의 질 무시** — 인기·만족도·평점 0% 반영 | 유명 관광지와 무명 뷔페가 동급. 총합만 크면 뷔페가 이김 | 🔴 |
| A2 | **이동 낭비를 오히려 보상** — totalMin(이동+체류) 큰 순이라, 같은 체류라면 *이동이 긴* 코스가 상위 | "멀리 걷게 하는 코스"가 1위 가능 — 알차게가 아니라 고생하게 | 🔴 |
| A3 | **단일 코스 다양성 없음** — 카테고리 규칙이 미니코스에만 있음 | 상위 3개 전부 식당 (실측 발생) | 🟠 |
| A4 | **시간대 맥락 없음** — 점심에 식당 가점, 저녁에 야경 가점 같은 개념 부재 | 오후 3시에 뷔페 3개 추천 | 🟠 |
| A5 | 취향/필터가 랭킹 미반영 — 분위기·활동 칩은 **사후 필터링**(UI)일 뿐 | 필터 켜면 후보가 사라질 뿐, 취향 맞는 게 위로 오진 않음 | 🟡 |

### B. 후보 수집의 결함

| # | 약점 | 증상 | 심각도 |
|---|---|---|---|
| B1 | **반경 1,500m 고정** — 이동수단 무시 | 자차인데 걸어갈 거리만 탐색. 자차 120분이면 10km도 가능한데 | 🔴 |
| B2 | 게이트 상한 16개가 **"가까운 순"** 컷 | 좋은 곳이 1.2km에 있어도 가까운 식당 16개에 밀려 게이트조차 못 감 → A3의 근원 | 🟠 |
| B3 | 후보 60건 상한 (1페이지) | 밀집 지역(서면)에선 일부만 봄 | 🟡 |
| B4 | 경유 모드에서 "약속장소 방향" 무시 — 수집은 현재위치 반경뿐 | 서면→부산역인데 반대방향(북쪽) 후보도 동급 취급 | 🟠 |

### C. 명세 대비 미구현

| # | 항목 | 상태 |
|---|---|---|
| C1 | **>150분 = 2~3곳+식사** (MVP시나리오 §2) | 미구현 — 지금은 최대 2곳 |
| C2 | 예산 필터 (무료/저렴) | 미구현 — 데이터 소스도 미정 |
| C3 | 시간 적응형 포맷 中 "≤60분=단일만" | 부분 — 60분 미만이면 미니 안 만들지만, 명시적 규칙은 아님 |

### D. 데이터 한계 (이미 알고 있는 것)
- 체류 폴백 뭉툭(관광지=60분 일괄) → cat3 세분화 백로그
- 혼잡배수 저신뢰(자기보고 30분 버킷 파생)

## 4. 개선 방향 — 결정적 점수 함수 도입 (제안)

원칙 유지: **ML 아님, 설명 가능한 가중합.** "왜 1위인지" 한 줄로 말할 수 있어야 한다.

```
score(코스) =
    w1 · 체류비율      (Σ체류 / totalMin)          ← A2 해결: 이동 낭비 벌점
  + w2 · 시간활용      (totalMin / budget)          ← 기존 "알차게" 유지하되 위와 균형
  + w3 · 장소 질       (AI-Hub 만족도 DGSTFN·재방문의향, 매칭 시)   ← A1: 이미 가진 데이터!
  + w4 · 시간대 적합    (점심/저녁=식당·카페 가점, 오후=관광 가점)     ← A4
  + w5 · 경유 방향성    (약속 방향 진행 시 가점, 역주행 벌점)          ← B4
  − w6 · 다양성 벌점    (이미 뽑힌 코스와 같은 카테고리면 감점)        ← A3: 선택 시 순차 적용
```

- **w3의 재료가 이미 있다**: AI-Hub `DGSTFN(만족도)·REVISIT_INTENTION`(채움률 81%)을 POI 매칭분에 붙일 수 있음(부산 58.6%). build_dwell 파이프라인 확장으로 해결.
- 후보 수집도 같이 손봄: **반경 = f(이동수단, 남은시간)** (도보 1.5km / 자차 5~10km), 경유 모드는 **중간점 중심 탐색** 추가.

### 적용 순서 제안 (효과 큰 순)
1. **A2+A3 즉효약**: 정렬을 `체류비율 우선 + 단일 상위 3개 카테고리 중복 ≤ 1` 로 교체 — 코드 몇 줄, 즉시 체감
2. **B1**: 반경을 이동수단·시간 함수로
3. **점수 함수 v1** (w1·w2·w4·w6) — 데이터 추가 없이 가능
4. **w3 장소 질**: build_dwell에 만족도 집계 추가 → poi_dwell.json 확장
5. B4 경유 방향성 · C1 3곳 코스

## 5. 랭킹 설명가능성 규칙 (지키기)

개선 후에도 각 코스 카드의 "왜"는 점수 내역으로 말한다:
> "▶ 체류 85% · 점심시간 식당 적합 · 방문자 만족 4.2 — 총 100분 ≤ 120분"

이게 되면 심사에서 "AI 추천의 근거가 뭐냐"에 완벽히 답할 수 있다.
