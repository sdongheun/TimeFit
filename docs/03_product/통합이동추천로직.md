# TimeFit 통합 이동 추천 로직 v1

> 작성: 2026-07-23 · 목적: 장소를 먼저 추천하고, 코스별로 이동수단별 소요시간을 함께 보여주는 추천 기준을 확정한다.

## 1. 방향 전환

초기에는 보행자, 대중교통, 자동차를 각각 따로 구현하려고 했다. 하지만 실제 사용자는 장소를 보고 이동수단을 결정한다.

따라서 v1의 추천 흐름은 다음처럼 바꾼다.

```text
이동수단 선택 -> 해당 수단에 맞는 장소 추천
```

이 아니라

```text
장소/코스 추천 -> 코스를 눌렀을 때 도보·자동차 소요시간 비교
```

로 간다.

추천 단계에서는 "사용자에게 최소 30분 정도 머물 시간이 남는가"를 핵심 기준으로 둔다. 이후 상세 화면에서 사용자는 도보/자동차 이동시간을 보고 직접 선택한다. 대중교통은 API 비용과 호출 한도 문제로 v1에서는 구조만 열어두고 후순위로 둔다.

## 2. 입력과 출력

사용자는 다음 값을 입력한다.

| 입력 | 의미 | 필수 |
|---|---|---|
| 현재 위치 | 직접 입력 또는 내 위치 찾기 | 필수 |
| 약속 장소 | 마지막에 도착해야 하는 장소 | 필수 |
| 남은 시간 | 지금부터 약속 장소에 도착해야 하는 시간까지의 총 분 | 필수 |

추천 결과는 장소/코스 단위로 보여준다.

```text
현재 위치 -> 추천 장소 1 -> (추천 장소 2) -> 약속 장소
```

코스를 누르면 다음 정보를 함께 보여준다.

| 항목 | 의미 |
|---|---|
| 도보 이동시간 | 전 구간을 걸었을 때의 총 이동시간 |
| 자동차 이동시간 | 택시/자차 기준 총 이동시간 |
| 예상 체류시간 | AI-Hub 또는 카테고리 기반 체류시간 |
| 실제로 머물 수 있는 시간 | `남은 시간 - 선택한 이동수단의 총 이동시간 - 안전버퍼` |

## 3. 핵심 판단식

사용자가 입력한 남은 시간은 전체 시간이다. 체류시간만의 상한이 아니다.

```text
bufferMin = max(10, round(remainingMin * 0.12))
usableMin = remainingMin - bufferMin
```

추천 후보가 되려면 적어도 다음 조건을 만족해야 한다.

```text
remainingDwellMin = usableMin - 이동시간
remainingDwellMin >= 30
```

즉, 특정 장소를 추천하려면 이동하고 나서 최소 30분 정도는 머물 수 있어야 한다.

예시:

| 남은 시간 | 안전버퍼 | 계산 가능 시간 | 이동시간 합계 | 추천 가능 여부 |
|---:|---:|---:|---:|---|
| 60분 | 10분 | 50분 | 25분 | 가능, 약 25분 체류라 부족하므로 낮은 우선순위 또는 제외 |
| 90분 | 11분 | 79분 | 35분 | 가능, 약 44분 체류 |
| 120분 | 14분 | 106분 | 60분 | 가능, 약 46분 체류 |

MVP에서는 추천 가능 기준을 `remainingDwellMin >= 30`으로 둔다.

## 4. 이동수단별 계산 방식

### 4.1 추천 후보 필터용 이동시간

추천 후보를 처음 거를 때는 모든 수단의 정밀 API를 전부 호출하지 않는다. 먼저 빠른 추정값으로 "가능성이 있는 장소"를 만든다.

```text
origin -> spot1 -> optional spot2 -> appointment
```

이 경로에 대해 도보/자동차 예상 이동시간을 각각 계산한다.

초기 구현에서는 다음 순서로 간다.

| 수단 | v1 계산 | 이후 개선 |
|---|---|---|
| 도보 | TMAP 보행자 경로 API | 유지 |
| 자동차 | TMAP 자동차 경로 API | 택시/자차 표시만 분리 |
| 대중교통 | v1 제외 | TMAP 대중교통 또는 별도 API 검토 |

추천 후보가 되려면 두 수단 중 하나 이상에서 `remainingDwellMin >= 30`이어야 한다.

```text
maxRemainingDwellMin = max(
  usableMin - walkMoveMin,
  usableMin - carMoveMin
)

maxRemainingDwellMin >= 30
```

이 방식이면 걸어서 힘든 장소라도 자동차로 충분히 다녀올 수 있으면 추천될 수 있다.

### 4.2 상세 화면용 이동시간

상세 화면에서는 수단별 시간을 나란히 보여준다.

```text
도보: 이동 42분 -> 약 50분 머물 수 있음
자동차: 이동 16분 -> 약 76분 머물 수 있음
```

사용자는 이 정보를 보고 이동수단을 결정한다.

## 5. 체류시간 데이터

### 5.1 직접 매칭 장소

`src/data/busan_poi_catalog.json`의 `matched`에 있는 장소는 AI-Hub 부산 방문 데이터와 직접 매칭된 장소다.

```text
dwell = AI-Hub 매칭 장소의 median 체류시간
confidence = direct_match
```

### 5.2 카테고리 폴백 장소

장소 수가 부족하므로, `src/data/busan_poi_catalog.json`의 `unmatched` 장소도 처음부터 섞는다.

직접 체류시간이 없는 장소는 AI-Hub 카테고리 체류시간을 사용한다.

```text
dwell = 같은 카테고리의 AI-Hub median 체류시간
confidence = category_fallback
```

단, 아래 조건을 만족하는 장소만 포함한다.

| 조건 | 이유 |
|---|---|
| 부산 TourAPI 장소 | 서비스 범위 유지 |
| 숙박/축제/여행코스 제외 | MVP 목적과 맞지 않음 |
| 쇼핑/자연/문화/레포츠/식당/카페 계열 | 자투리 시간에 활용 가능 |
| 좌표 존재 | 이동시간 계산 필수 |
| 카테고리 체류시간 존재 | 시간 판단 근거 필요 |

결과에서는 직접 매칭과 카테고리 폴백을 구분한다.

```text
AI-Hub 방문 데이터 기준 예상 체류
```

또는

```text
같은 카테고리의 부산 방문 패턴 기준 예상 체류
```

음식점/카페는 웨이팅 변수가 있으므로, 결과 문구는 "권장 체류"보다 "현재 시간으로 머물 수 있는 시간"을 우선한다.

## 6. 1개 장소와 2개 장소 코스

2개 장소 코스는 "남은 시간이 몇 분 이상이면 허용"처럼 단순 시간 기준으로만 결정하지 않는다. 두 장소가 가까이 붙어 있으면 짧은 시간에도 자연스러운 코스가 될 수 있다.

따라서 2개 장소 코스는 다음 조건을 사용한다.

```text
spot1 -> spot2 이동시간이 짧고
두 장소를 합친 뒤에도 최소 30분 이상 머물 시간이 남으면
2개 장소 코스로 추천 가능
```

초기 기준:

| 조건 | 값 |
|---|---:|
| 두 장소 사이 도보 이동시간 | 12분 이하 |
| 두 장소 카테고리 | 같아도 가능, 단 완전 중복 장소는 제외 |
| 코스 전체 체류 가능 시간 | 30분 이상 |
| 추천 장소 수 | 최대 2개 |

2개 장소의 실제 체류시간은 AI-Hub 중앙값 합산을 그대로 강제하지 않는다. 사용자가 가진 시간이 더 짧을 수 있기 때문이다.

대신 상세 화면에서 다음처럼 보여준다.

```text
AI-Hub 기준으로는 두 장소를 합쳐 약 70분 체류가 일반적입니다.
현재 시간으로는 이동 후 약 45분 정도 나눠서 머물 수 있어요.
```

즉, 추천 가능 여부는 "사용자가 실제로 머물 수 있는 시간"을 기준으로 판단하고, AI-Hub 체류시간은 권장 체류 길이와 랭킹 근거로 사용한다.

## 7. 추천 생성 순서

```text
[1] 입력 검증
    현재 위치, 약속 장소, 남은 시간 확인
    남은 시간 240분 초과면 MVP 범위 밖으로 처리

[2] 시간 예산 계산
    bufferMin, usableMin 계산

[3] 후보 수집
    TourAPI 부산 후보 수집
    AI-Hub 직접 매칭 후보 + 카테고리 폴백 후보를 처음부터 함께 사용

[4] 단일 장소 후보 생성
    origin -> spot -> appointment 이동시간 추정
    도보/자동차 중 하나에서 이동 후 30분 이상 남으면 유지

[5] 2개 장소 후보 생성
    가까운 장소 쌍을 먼저 만든다
    origin -> spot1 -> spot2 -> appointment 이동시간 추정
    도보/자동차 중 하나에서 이동 후 30분 이상 남으면 유지

[6] 운영 가능성 확인
    TourAPI 운영시간이 있으면 도착 예상 시각 기준으로 검사
    운영시간이 없으면 제외하지 않고 신뢰도 감점

[7] 수단별 정밀 이동시간 계산
    상위 후보에 대해서만 도보·자동차 경로를 정밀 계산

[8] 랭킹
    머물 수 있는 시간, 이동 효율, 시간대 적합도, 데이터 신뢰도, 2개 장소 근접성을 반영

[9] 결과 설명
    코스 카드에는 대표 추천 이유를 표시
    상세 화면에는 도보/자동차 이동시간과 머물 수 있는 시간을 표시
```

## 8. 랭킹 기준

```text
score =
  0.30 * stayOpportunityScore
+ 0.20 * routeEfficiencyScore
+ 0.20 * timeOfDayFitScore
+ 0.15 * dataConfidenceScore
+ 0.15 * courseCompactnessScore
```

| 점수 | 의미 |
|---|---|
| stayOpportunityScore | 이동 후 실제로 머물 수 있는 시간이 충분한지 |
| routeEfficiencyScore | 약속 장소까지 가는 길에서 크게 벗어나지 않는지 |
| timeOfDayFitScore | 현재 시간대와 장소 카테고리가 맞는지 |
| dataConfidenceScore | AI-Hub 직접 매칭인지, 카테고리 폴백인지 |
| courseCompactnessScore | 2개 장소가 가까워서 한 코스로 자연스러운지 |

데이터 신뢰도:

| 데이터 유형 | confidence |
|---|---:|
| AI-Hub 장소 직접 매칭 | 1.0 |
| AI-Hub 카테고리 폴백 | 0.7 |
| 운영시간 없음 | -0.1 감점 |
| 정밀 경로 실패 후 추정 이동시간 사용 | -0.1 감점 |

## 9. 사용자에게 보여줄 문장

코스 카드:

```text
약속 전 2시간 기준, 이동 후 최소 45분 정도 머물 수 있어요.
```

상세 화면:

```text
도보로는 이동 52분, 약 40분 체류 가능
자동차로는 이동 18분, 약 74분 체류 가능
```

카테고리 폴백:

```text
이 장소는 직접 체류 데이터가 부족해 같은 카테고리의 부산 방문 패턴으로 체류시간을 추정했어요.
```

2개 장소 코스:

```text
두 장소가 걸어서 약 8분 거리라 한 번에 둘러보기 좋아요.
이동수단에 따라 40~70분 정도 나눠서 머물 수 있습니다.
```

## 10. 먼저 구현할 범위

1. 추천 입력을 현재 위치, 약속 장소, 남은 시간으로 고정
2. AI-Hub 직접 매칭 후보와 카테고리 폴백 후보를 함께 로드
3. 단일 장소 후보에서 도보/자동차 이동시간 필드 구조 만들기
4. 도보/자동차 중 하나에서 이동 후 30분 이상 남는 장소만 추천
5. 결과 카드와 상세 화면에 이동시간/체류가능시간을 분리 표시
6. 가까운 장소 쌍 기준으로 2개 장소 코스 추가
7. 대중교통 API는 추후 확정하고, 별도 필드로 확장

## 11. 확정된 정책

| 항목 | 결정 |
|---|---|
| 이동수단 선택 방식 | 추천 전 선택이 아니라 코스 상세에서 도보·자동차 비교 |
| 추천 가능 기준 | 이동 후 최소 30분 정도 머물 시간이 남아야 함 |
| 2개 장소 코스 | 남은 시간 기준보다 장소 간 근접성을 우선 |
| 카테고리 폴백 | 처음부터 섞어서 장소 수 부족 문제 완화 |
| 장소 수 | 한 코스 최대 2개 |

## 12. 구현 시 주의점

- 추천 가능 여부는 AI-Hub 체류시간을 전부 만족하는지가 아니라, 사용자가 이동 후 실제로 머물 시간이 최소 30분 이상 남는지로 판단한다.
- AI-Hub 체류시간은 "권장 체류 길이"와 "랭킹 근거"로 사용한다.
- 직접 매칭 장소와 카테고리 폴백 장소는 결과 설명에서 반드시 구분한다.
- 대중교통은 v1에서 제외하되, 나중에 자동차와 같은 값으로 뭉개지 않도록 별도 필드로 확장한다.
- 수단별 정밀 API 호출은 상위 후보에만 적용해 호출량을 관리한다.
