# 자투리 장소 선별 및 체류 범위 전환 계획

> 상태: **병렬 초안 생성 완료 - 생활권별 수동 검토 및 런타임 전환 전**
> 상위 결정: `REC-01` 추천 신뢰도, `TIME-01` 현재 자투리 시간 모델
> 관련 기준: `추천로직.md`, `docs/테스트.md`의 `DATA-09`~`DATA-11`. 과거 실제 경로 전환 기록은 `docs/archive/product-history/추천_실경로탐색전환계획.md`에 보관한다.

> 2026-08-21 보완: 이 카탈로그는 다중 장소 조립이 아니라 `출발 → 장소 1곳 → 도착/복귀`에 삽입하는 추천 엔진의 입력으로 전환한다. 사용자가 설정한 도착 여유(기본 10분)를 제외한 예산 안에서 `권장 체류` 또는 `최소 체류`를 충족하는지를 판단한다.

## 1. 전환 배경

### 이전 방식

TourAPI, 부산시 공식 명소·쇼핑·맛집 데이터의 유효 장소를 넓게 카탈로그에 넣고, AIHub 직접 매칭 체류시간 또는 카테고리 중앙값으로 추천했다. 음식점·카페·관광 활동 장소를 같은 후보 풀에서 다뤘다.

### 관찰된 문제

- 원천 데이터의 관광·업종 카테고리는 `짧은 시간에 들러도 경험이 성립하는가`를 뜻하지 않는다.
- AIHub 체류 중앙값 하나는 최소 방문 가능 시간, 권장 시간, 사용자가 더 머물 수 있는 상한을 구분하지 못한다.
- 식당은 대기·주문·식사 변동이 커서 현재 데이터만으로 시간 신뢰도를 만들기 어렵다.
- 상권 데이터의 상호·업종·좌표만으로 빵집, 카페, 소품샵을 자동 추천하면 대기·예약·테이크아웃·운영시간을 알 수 없다.

### 교체 방향

원천 데이터는 **장소 후보와 근거**로만 사용한다. 자동 추천은 별도 `자투리 활동 적합성(short-stay suitability)` 검토를 통과한 장소만 대상으로 하고, 각 장소는 단일 체류시간 대신 `최소 / 권장 / 최대` 체류 범위를 가진다.

### 교체 이유

TimeFit의 가치는 관광지 수를 많이 보여주는 것이 아니라, 약속 전 짧은 시간에 실패 없이 선택할 수 있는 활동을 좁혀 주는 데 있다.

## 3. 자투리 활동 유형

관광 분류가 아니라, 짧은 방문이 완결되는 활동 단위로 태그한다. 한 장소는 주 활동 유형 하나와 보조 유형만 가질 수 있다. 태그가 애매하면 `REVIEW`로 보류한다.

| `shortStayType` | 정의 | 초기 체류 템플릿(분) | 주요 제외 사유 |
|---|---|---:|---|
| `scenic_pause` | 전망·해안·조망 공간에서 짧게 보고 나올 수 있음 | 최소 10 / 권장 15 / 최대 25 | 출입 제한, 주차장·단순 통행 공간, 야간 위험 |
| `walk_break` | 공원·산책로·공공 쉼터를 짧게 걸을 수 있음 | 최소 15 / 권장 25 / 최대 45 | 단순 벤치 좌표, 공사·출입 제한, 장거리 등산 코스 |
| `quick_browse` | 시장·거리·독립서점·선물·소품처럼 중간 퇴장이 자연스러움 | 최소 15 / 권장 25 / 최대 40 | 내부 개별 점포, 점포별 상이만 있는 권역, 대기 위험 |
| `compact_culture` | 예약 없이 짧게 관람 가능한 전시·문화·공공 공간 | 최소 20 / 권장 35 / 최대 60 | 회차제·예약제·프로그램 의존, 휴관 정보 불명 |
| `quick_rest` | 짧은 휴식이 가능한 카페·베이커리·테이크아웃 중심 공간 | 최소 15 / 권장 25 / 최대 45 | 운영시간 불명, 일반 식당 |

이 표의 숫자는 **초기 템플릿**일 뿐 최종 장소 값이 아니다. 개별 장소의 근거가 있으면 그 값이 우선하고, 근거가 없으면 자동 추천으로 승격하지 않는다.

## 4. 장소별 필수 데이터 모델

```ts
type ShortStayProfile = {
  shortStayType: "scenic_pause" | "walk_break" | "quick_browse" | "compact_culture" | "quick_rest";
  minStayMin: number;
  recommendedStayMin: number;
  maxStayMin: number;
  entryExitFriction: "low" | "medium" | "high";
  queueRisk: "low" | "unknown" | "high";
  reservationRequired: boolean | "unknown";
  weatherDependency: "none" | "moderate" | "high";
  selectionStatus: "approved" | "review" | "hold" | "excluded";
  selectionEvidence: Array<{
    source: "tourapi" | "busan_official" | "aihub" | "sbiz" | "manual_review";
    fieldOrUrl: string;
    checkedAt: string;
  }>;
};
```

불변 조건:

```text
0 < minStayMin <= recommendedStayMin <= maxStayMin
approved 이면 정확한 좌표·장소명·원천 출처·운영 가능 정책이 모두 있어야 함
facility / quick_rest / compact_culture 이면 운영시간 근거가 필수
outdoor 이면 별도 야외 접근 정책 또는 날씨 의존성 근거가 필수
quick_rest 는 대기시간을 추정하지 않으며, 파싱 가능한 공식 운영시간이 없으면 approved 로 올리지 않음
일반 식당은 queueRisk 값과 무관하게 기본 추천 approved 로 올리지 않음
```

### 체류 범위 산출 우선순위

1. **직접 AIHub 매칭 + 표본 충분**: 실제 방문 분포를 사용한다. 최소는 활동 완결 하한, 권장은 중앙값, 최대는 상위 분위값을 활용하되 운영시간과 활동 유형 상한으로 자른다.
2. **포괄 AIHub 매칭**: 개별 상점에 상속하지 않는다. 공원·시장·거리처럼 포괄 장소에만 사용한다.
3. **AIHub 표본 부족 또는 미매칭**: 활동 유형 템플릿을 임시로 쓰되 `review` 상태로 남긴다. 수동 근거나 초기 사용자 기록 없이 `approved`로 올리지 않는다.
4. **사용자 행동 데이터 축적 후**: 충분한 표본과 편향 보정 규칙이 정해진 뒤에만 개인별 권장 체류시간을 덮어쓴다.

`최대`는 사용자가 반드시 머물러야 하는 시간이 아니라, 앱이 자동 배정해도 과도하지 않은 권장 상한이다. 남는 시간 전체를 한 장소 체류로 강제하지 않는다.

### 4-1. 시간 판정과 운영시간 미확인 후보

```text
effectiveBudget = 종료시각 - 현재시각 - 사용자가 설정한 도착 여유(기본 10분)
recommended: 이동 + recommendedStayMin <= effectiveBudget
brief:       이동 + minStayMin <= effectiveBudget
unavailable: 이동 + minStayMin > effectiveBudget
```

- 운영시간이 확인된 후보는 위 판정과 별개로 도착부터 해당 체류가 끝날 때까지 운영시간 안인지 확인한다.
- 운영시간이 미확인인 시설·카페·권역 후보는 삭제하지 않는다. 다만 `conditional` 상태로 두며 `운영시간 확인 필요`와 카카오맵 확인 링크를 제공한다.
- `conditional`은 시간 내 이용 가능을 보증하거나 자동 확정 추천으로 표시하지 않는다. 사용자가 카카오맵에서 최종 확인하는 탐색 후보이다.
- 날씨 정보 API가 아직 연결되지 않았으므로, 후보 부족 안내에 날씨를 원인으로 단정하지 않는다. 날씨 기반 안내는 실제 날씨 상태를 입력으로 받는 후속 기능에서만 허용한다.

## 5. 원천 데이터 역할과 금지 사항

| 원천 | 허용 역할 | 자동 추천 근거로 단독 사용 금지 |
|---|---|---|
| TourAPI | 관광 장소명·좌표·사진·상세·일부 운영시간·콘텐츠 유형 | 관광지라는 이유만으로 `approved` 부여 |
| 부산시 공식 데이터 | 공공 공간·공식 시설·지역 장소의 존재와 공식 안내 근거 | 개별 장소의 대기·짧은 체류 가능성 추정 |
| AIHub `TN_VISIT_AREA_INFO` | 체류시간 분포, 포괄/독립 장소 매칭 검토 | 현재 인기·운영 가능·대기 없음 판단 |
| 소상공인시장진흥공단 상가정보 | 카페·베이커리·서점·소품점의 검토 후보 발굴 | 상호·업종·좌표만으로 자동 추천 승격 |
| 수동 검토 | 활동 완결성, 입·퇴장 부담, 예약·대기 위험, 대표 장소 여부 판정 | 출처 없이 주관적 “인기” 라벨 부여 |

### 5-1. 원천별 사용 결정

| 원천 | 결정 | 이유 | 상태 |
|---|---|---|---|
| 전국도시공원정보표준데이터 | 추천 원천으로 미사용 | TourAPI·부산 공식 데이터에 큰 공원이 이미 있고, 표준데이터의 723개를 추가하면 작은 어린이공원·단순 녹지가 대량 유입되며 운영시간·사진도 없다 | 현행 |
| 전국전통시장표준데이터 | 대표 시장 `review` 후보와 권역 판정 보조에 사용 | 기존 장소와 정확한 이름·300m 이내 좌표로 중복 제거한 대표 시장만 병렬 초안에 추가한다. 운영시간·사진이 없어 자동 추천 근거는 아니다 | 현행 |
| 전국공공시설개방정보표준데이터 | 추천 원천으로 미사용 | 부산 79개 그룹 중 운동장·회의실·예약 시설 비중이 높고, 전시·휴식 후보가 적어 자투리 추천 품질을 높이지 못한다 | 현행 |
| TourAPI 문화시설 상세 | 운영시간 재확인에 사용 | `detailIntro2`의 시간 범위·휴관일을 별도 감사 파일로 저장한다. 행사/프로그램별 상이는 시간 근거로 쓰지 않는다 | 현행 |

장소가 많이 방문된다는 주장을 하려면 별도의 최신 개별 POI 방문 근거가 필요하다. 현 단계에서는 `인기`라는 라벨을 쓰지 않고 `자투리 활동 검토 완료`만 사용한다.

## 6. 단계별 실행 계획

### 0단계: 기준 카탈로그 동결과 작업 단위 분리

- 현재 `busan_poi_catalog.json`과 원천별 정제 파일을 읽기 전용 기준본으로 기록한다.
- 새 산출물은 `data/processed/review/`에서 시작한다. 런타임 카탈로그를 직접 수정하지 않는다.
- 산출물에 기존 `contentId`, TourAPI/부산시/AIHub 출처, 병합·포괄 관계를 보존한다.

### 1단계: 하드 제외와 검토 후보 생성

다음은 우선 제외 또는 보류한다.

- 숙박·교통시설·병원·주차장·종교시설·사무실·단순 상업시설
- 일반 식당, 주점, 배달/포장 전문점
- 시장·거리 내부의 개별 상점
- 예약/회차제/입장 대기 가능성이 높은 문화·체험 시설
- 정확한 장소 좌표 또는 장소 본체 검증이 없는 후보

남은 후보를 다섯 `shortStayType`에 자동 초안 태그하되, 초안은 모두 `review`다.

#### 2026-08-21 1차 병렬 초안 결과

- 산출물: `data/processed/review/부산_자투리장소_카탈로그_초안.json`, `data/processed/review/부산_자투리장소_보류및제외.json`
- 입력: 기존 최종 매칭·미매칭 911개. 기존 `src/data/busan_poi_catalog.json`은 수정하지 않았다.
- 적용: `식당`과 이름상 음식·카페·베이커리 후보는 자동 승인에서 제외했다. 긴 체험·예약 성격 장소도 제외했다.
- AIHub 개인 체류 근거: `name+coord`이면서 AIHub 이름이 제목 또는 별칭과 정규화 후 정확히 일치하고, 좌표 거리가 100m 이하인 경우만 인정한다. 좌표 단독·유사명 100m 근접은 승인 근거가 아니다.
- 한계: 이 결과는 자동 분류 초안이다. 카페·베이커리·서점·소품샵은 의도적으로 `review`에 남으며, 승인 수를 늘리기 위해 임의로 승격하지 않는다.

### 2단계: 포괄 장소와 독립 장소 판정

- 시장·거리·골목·공원·해변·문화마을은 포괄 장소를 우선한다.
- 포괄 장소 안의 카페·분식점·기념품점은 독립적으로 검토된 경우 외에는 후보에서 제외한다.
- 포괄/내부 관계는 현재 `siteGroupId`를 재사용하되, 최종 후보에는 대표 장소가 무엇인지 명시한다.

#### 2026-08-21 보완: 권역 우선 추천 단위

| 이전 방식 | 관찰된 문제 | 교체 방식 | 상태 |
|---|---|---|---|
| 포괄 장소와 내부 장소를 함께 후보로 유지 | 시장·거리·마을·길 내부의 한 점포/시설이 권역 자체보다 먼저 보이면, 사용자가 무엇을 할 수 있는지 파악하기 어렵고 운영시간·체류시간도 개별 점포에 잘못 귀속될 수 있음 | 기존 정제 데이터에서 `scope.type = 내부장소`이며 `siteGroupId`의 부모가 확인되는 후보는 자동 추천에서 제외하고 `representedBy`에 포괄 대표 장소를 기록 | 현행 병렬 초안 |

이 규칙은 좌표가 가깝다는 이유만으로 새 부모-자식 관계를 만드는 규칙이 아니다. 명시된 `siteGroupId` 또는 수동 검토로 확인된 권역 관계에만 적용한다. 독립 방문 목적이 분명한 박물관·미술관·도서관은 거리·마을 안에 있더라도 내부 장소로 자동 처리하지 않는다.

### 3단계: 체류 범위 산출

- AIHub 직접 매칭은 방문 체류 분포와 활동 유형 템플릿을 비교한다.
- 분포가 활동 유형의 최소/최대와 크게 충돌하면 자동 채택하지 않고 수동 검토한다.
- 미매칭 장소는 템플릿만으로 `approved`가 될 수 없다. 운영·활동 근거가 추가돼야 한다.
- 장소별 `min / recommended / max`와 산출 방식(`aihub_distribution`, `area_distribution`, `manual_template`)을 저장한다.

### 4단계: 운영·입장 위험 검증

- 시설형·카페·베이커리·서점·문화공간은 공식 운영시간, 휴관·예약·회차 여부를 확인한다. `행사별 상이`, `프로그램별 상이`, `매장별 상이`는 운영시간 근거로 인정하지 않는다.
- 카페·베이커리·서점·소품샵은 대기 위험을 현재 점수에 넣지 않는다. 공식 출처와 파싱 가능한 운영시간이 있으면 초기 체류 템플릿으로 승인할 수 있으며, 대기 데이터가 확보되기 전에는 `대기 없음`이라고 표현하지 않는다.
- 야외형은 상시 접근 여부, 야간 안전/출입 제한, 날씨 의존성을 기록한다.
- 시장·거리·골목은 현재 `area_availability_policy`와 같은 공식 권역 시간대가 있을 때만 `approved`로 한다.

### 5단계: 생활권별 수동 심사

첫 대상은 서면·전포, 광안리·남천, 해운대·센텀이다.

- 각 생활권에서 `scenic_pause`, `walk_break`, `quick_browse`, `compact_culture`, `quick_rest`가 한 유형에 과도하게 치우치지 않는지 점검한다.
- 장소 하나하나를 `approved / review / hold / excluded`로 결정한다.
- 목표는 장소 수가 아니라, 각 `approved` 장소가 필수 근거를 빠짐없이 가지는 것이다.

### 6단계: 병렬 카탈로그·엔진 어댑터 구현

- `busan_short_stay_poi_catalog.json`을 새로 만들고 기존 카탈로그와 병렬 비교한다.
- 플래너에는 feature flag 또는 주입 가능한 카탈로그 어댑터를 둔다. 기존 추천을 조용히 대체하지 않는다.
- 추천 시 `recommendedStayMin`을 기본 체류 배정에 사용하고, 남는 시간 표현에는 `min~max` 범위를 함께 계산한다.
- 엔진은 다중 장소 조립 대신 후보 하나를 `출발 → 후보 → 도착/복귀`에 삽입한다. 차량은 추천 판정에서 제외하고 도보·대중교통 조합만 사용한다.

#### 2026-08-21 보완: 장소 부족을 위한 조건부 후보 활용

| 이전 방식 | 관찰된 문제 | 교체 방식 | 상태 |
|---|---|---|---|
| `approved`만 지도 후보로 사용 | 검증 장소 수가 49개에 머물러 생활권별 후보 부족이 심함 | 활동 유형·좌표가 있는 `review` 후보는 `conditional`로 승격해 지도 탐색 후보에 포함한다. 활동 유형이 없는 후보는 계속 `review`, 하드 제외는 그대로 유지한다 | 현행 병렬 초안 |

`conditional` 후보의 불변 조건:

- `shortStayType`, 좌표, 원천 출처가 있어야 한다.
- 운영시간이 없으면 `운영시간을 카카오맵에서 확인한 뒤 선택하세요` 상태와 검색 링크를 제공한다.
- 앱은 조건부 후보를 `운영 중` 또는 `시간 안에 확실히 가능`하다고 표현하지 않는다.
- 코스 확정 단계에서 운영시간을 확인할 수 없으면 자동 확정 추천으로 승격하지 않는다. 사용자가 외부 지도에서 확인한 뒤 선택하는 탐색 후보로만 쓴다.
- 음식점·긴 체험·잘못된 엔터티·내부 장소 하드 제외는 조건부로도 되살리지 않는다.

#### 2026-08-21 전통시장 원천 병합

- 기존 911개와 정확히 같은 시장명·300m 이내 좌표인 경우에만 중복으로 본다. 유사명·근접 좌표만으로는 병합하지 않는다.
- 추가 시장은 `상업지구 / 포괄장소 / 시장`으로 기록하고 운영시간이 없으므로 전부 `review`다.
- 수산물·농산물·건어물·먹자골목 등 음식 목적이 명확한 권역은 `excluded`다.
- 도시공원·공공개방시설은 이 초안에 추가하지 않는다. 독립서점·상가업소·전시 API 응답 데이터는 로컬 원천을 확보한 뒤 동일한 방식으로 추가한다.

### 7단계: 검증과 교체 결정

다음 조건을 모두 충족해야 런타임 기본 카탈로그로 교체한다.

1. `approved` 장소 100%가 필수 필드와 출처를 갖는다.
2. 시설형/상권형 후보 100%가 운영 가능 정책을 갖는다.
3. `min <= recommended <= max` 데이터 계약과 체류 배정 경계 테스트가 통과한다.
4. 고정 시각·출발/도착 fixture에서 기존 카탈로그보다 불가능 후보가 늘지 않고, 추천 사유가 활동 유형과 일치한다.
5. 생활권별 실제 기기 확인에서 각 기본 탐색 시나리오가 최소 3개 이상의 유효 후보 또는 명확한 부족 사유를 반환한다.

## 8. 비범위와 후속 과제

- 현재 단계에서 `인기`, 실시간 대기시간, 현재 혼잡도는 점수에 넣지 않는다.
- 사용자 후기 기반 개인화는 장소 후보의 자투리 적합성을 대체하지 않는다. 승인 카탈로그가 먼저다.
- 음식점 재도입은 대기 위험과 짧은 이용 근거를 별도로 확보했을 때만 결정한다.
- 관광공사 관광빅데이터의 관심 POI·관광 소요시간 API는 최신성·부산 커버리지·이용 조건을 확인한 후 보조 근거로 별도 평가한다.
