# 부산 매칭 데이터 정리 목표

> 작성: 2026-07-23 · 목적: AI-Hub 원본 데이터를 다시 정리해 TimeFit MVP 추천 후보를 부산 매칭 장소로 제한한다.

## 1. 타깃

- **지역:** 부산 전용
- **사용자:** 부산에 출장·여행을 와서 약속 전 시간이 비는 사람, 특히 직장인
- **상황:** 다음 약속 전 자투리 시간에 가볍게 둘러볼 곳을 찾는 상황

## 2. 추천 범위

- 자투리 시간은 **최대 4시간(240분)** 까지만 다룬다.
- 한 코스는 **1~2개 장소**까지만 추천한다.
- 계산 기준은 항상 다음 식이다.

```text
현재 위치 -> 장소 1 -> (장소 2) -> 출발지/약속장소
이동시간 + 체류시간 <= 입력 시간 - 안전버퍼
```

## 3. 장소 원칙

추천 후보에는 음식점/카페도 포함한다. 다만 앱의 목적은 맛집 추천이 아니라 남는 시간 활용이므로, 음식점/카페는 "꼭 이 시간만큼 먹어야 한다"가 아니라 **이동 후 실제로 머물 수 있는 시간**을 보여주는 방식으로 다룬다.

우선 포함하는 TourAPI 타입:

| contentTypeId | 의미 | 포함 이유 |
|---|---|---|
| `12` | 관광지 | 자연관광·명소·가볍게 둘러볼 장소 |
| `14` | 문화시설 | 박물관·전시·실내 대안 |
| `28` | 레포츠 | 짧은 체험 가능 후보만 향후 선별 |
| `38` | 쇼핑 | 시장·거리·쇼핑 장소 |
| `39` | 음식점 | 식사/카페도 약속 전 자투리 시간 활용 후보로 포함 |

우선 제외하는 TourAPI 타입:

| contentTypeId | 의미 | 제외 이유 |
|---|---|---|
| `32` | 숙박 | 자투리 시간 코스와 무관 |
| `15` | 축제공연행사 | 날짜·운영·혼잡 변수가 커서 후순위 |
| `25` | 여행코스 | 단일 장소가 아니라 코스 콘텐츠라 엔진 후보로 부적합 |

음식점/카페 주의점:

- 웨이팅이 있을 수 있으므로 추천 결과에서는 체류시간을 강제하지 않는다.
- `남은시간 - 이동시간 - 안전버퍼`로 계산한 실제 체류 가능 시간을 함께 표시한다.
- AI-Hub 체류시간은 권장/평균적 체류 경향과 랭킹 근거로만 사용한다.

## 4. 데이터 원칙

추천 후보는 TourAPI 부산 장소와 부산광역시 공식 명소·쇼핑·맛집 OpenAPI를 합친 뒤, AI-Hub 체류 데이터와 다시 대조해 정제한다. 보류·제외 후보는 앱 번들에 넣지 않는다.

매칭 기준:

1. 이름 정규화와 좌표 거리 150m 이내를 함께 만족하면 독립 장소의 직접 체류시간으로 사용한다.
2. 시장·거리·골목·문화마을·공원·해변·쇼핑복합공간은 포괄 장소로 분류한다. 이 경우에는 해당 지역 맥락의 AI-Hub 체류시간만 사용한다.
3. 포괄 장소 내부의 상점·식당은 포괄 장소 체류시간을 상속하지 않고 보류한다.
4. 좌표 단독 매칭, AI-Hub 미매칭 장소는 카테고리 체류시간으로 폴백한다.

앱에서 최종적으로 필요한 데이터는 다음 형태다.

```text
src/data/busan_poi_catalog.json
```

이 파일은 로컬 `contentId`를 기준으로 직접 매칭 장소, 미매칭 폴백 장소, 카테고리 체류시간을 합친 앱 런타임용 부산 추천 후보 카탈로그다. 후보 수집도 더 이상 TourAPI 실시간 목록에 의존하지 않고, 이 카탈로그를 좌표 반경으로 탐색한다. TourAPI 원본 ID가 있는 장소에만 `detailIntro2` 운영시간 확인을 추가로 수행한다.

## 5. 산출 JSON

`scripts/build_runtime_poi_catalog.mjs`가 최종 정제 파일을 앱 카탈로그로 변환한다.

| 파일 | 역할 |
|---|---|
| `data/processed/부산_최종매칭장소.json` | AI-Hub 직접/포괄 맥락 체류시간 사용 가능 장소 123개 |
| `data/processed/부산_최종미매칭장소.json` | 카테고리 체류시간 폴백 장소 788개 |
| `data/processed/review/부산_최종장소_보류.json` | 포괄 장소 내부·동명 지점·미분류·복수 장소 표기 등 검토 대상 231개 |
| `data/processed/review/부산_최종장소_제외.json` | 숙박·교통·의료·주차·상품성 레코드 등 제외 대상 6개 |
| `data/processed/review/부산_중복제외장소.json` | 일반명·동일 장소 중복으로 제거한 후보 1개 |
| `data/processed/review/부산_오분류제외장소.json` | 자연관광지로 오분류된 교통성 후보 1개 |
| `src/data/busan_poi_catalog.json` | 앱 번들용 최종 카탈로그 911개 |
| `src/data/busan_poi_catalog.legacy.json` | 교체 전 TourAPI 중심 카탈로그 보관본 |

### 지도 식별 검증 현황 (2026-08-10)

- 카카오 로컬 키워드 검색으로 장소명·좌표를 대조했다.
- 카탈로그 924개 중 `verified` 771개, `weak` 39개, `not_found` 114개다.
- `not_found` 114개는 기록으로 보관하지만 추천 엔진에서 제외한다. 따라서 현재 실제 추천 후보 풀은 810개다.
- 부산시 공식 데이터 단독 장소의 검증 결과는 `data/processed/review/부산시_공식장소_카카오검증.json`에 보관한다.

필드 예시:

```json
{
  "contentId": "poi_1",
  "title": "광안리해수욕장",
  "contentTypeId": "12",
  "category": "자연관광지",
  "lat": 35.153,
  "lon": 129.118,
  "aihubName": "광안리해수욕장",
  "matchType": "name+coord",
  "matchDistanceM": 12,
  "dwell": {
    "count": 182,
    "median": 30,
    "p25": 30,
    "p75": 60,
    "mean": 42
  }
}
```

## 6. 다음 구현 순서

1. 5개 원천 데이터에서 최종 매칭·미매칭·보류·제외 후보를 정제한다.
2. 앱 번들용 `busan_poi_catalog.json`을 생성하고 기존 카탈로그를 보관한다.
3. 엔진에서 로컬 카탈로그를 출발·약속·경유 중심의 좌표 반경으로 탐색한다.
4. TourAPI 원본 ID가 있는 장소에만 상세 운영시간을 확인하고, 공식 데이터 단독 장소는 제공된 운영시간 또는 카카오맵 링크로 확인한다.
5. 단일 장소 및 장바구니 기반 다중 장소 추천을 시간 예산 안에서 조립한다.
