# 부산 매칭 데이터 정리 목표

> 작성: 2026-07-23 · 목적: AI-Hub 원본 데이터를 다시 정리해 TimeFit MVP 추천 후보를 부산 매칭 장소로 제한한다.

## 1. 타깃

- **지역:** 부산 전용
- **사용자:** 부산에 출장·여행을 와서 약속 전 시간이 비는 사람, 특히 직장인
- **상황:** 다음 약속 전 자투리 시간에 가볍게 둘러볼 곳을 찾는 상황

## 2. 추천 범위

- 자투리 시간은 **최대 4시간(240분)** 까지만 다룬다.
- 한 코스는 **1~2개 장소**까지만 추천한다.
- 계산 기준은 항상 다음 식이다.

```text
현재 위치 -> 장소 1 -> (장소 2) -> 출발지/약속장소
이동시간 + 체류시간 <= 입력 시간 - 안전버퍼
```

## 3. 장소 원칙

추천 후보에는 음식점/카페도 포함한다. 다만 앱의 목적은 맛집 추천이 아니라 남는 시간 활용이므로, 음식점/카페는 "꼭 이 시간만큼 먹어야 한다"가 아니라 **이동 후 실제로 머물 수 있는 시간**을 보여주는 방식으로 다룬다.

우선 포함하는 TourAPI 타입:

| contentTypeId | 의미 | 포함 이유 |
|---|---|---|
| `12` | 관광지 | 자연관광·명소·가볍게 둘러볼 장소 |
| `14` | 문화시설 | 박물관·전시·실내 대안 |
| `28` | 레포츠 | 짧은 체험 가능 후보만 향후 선별 |
| `38` | 쇼핑 | 시장·거리·쇼핑 장소 |
| `39` | 음식점 | 식사/카페도 약속 전 자투리 시간 활용 후보로 포함 |

우선 제외하는 TourAPI 타입:

| contentTypeId | 의미 | 제외 이유 |
|---|---|---|
| `32` | 숙박 | 자투리 시간 코스와 무관 |
| `15` | 축제공연행사 | 날짜·운영·혼잡 변수가 커서 후순위 |
| `25` | 여행코스 | 단일 장소가 아니라 코스 콘텐츠라 엔진 후보로 부적합 |

음식점/카페 주의점:

- 웨이팅이 있을 수 있으므로 추천 결과에서는 체류시간을 강제하지 않는다.
- `남은시간 - 이동시간 - 안전버퍼`로 계산한 실제 체류 가능 시간을 함께 표시한다.
- AI-Hub 체류시간은 권장/평균적 체류 경향과 랭킹 근거로만 사용한다.

## 4. 데이터 원칙

추천 후보는 **TourAPI 부산 장소이면서 AI-Hub 부산 방문 데이터와 매칭된 장소**를 우선 사용하고, 매칭되지 않은 장소도 카테고리 체류시간으로 폴백해 함께 사용한다.

매칭 기준:

1. 이름 정규화 일치
2. 좌표 거리 150m 이내
3. 둘 다 있으면 `name+coord`, 좌표만 있으면 `coord`, 이름만 있으면 `name`

앱에서 최종적으로 필요한 데이터는 다음 형태다.

```text
src/data/busan_poi_catalog.json
```

이 파일은 TourAPI `contentId`를 기준으로 직접 매칭 장소, 미매칭 폴백 장소, 카테고리 체류시간을 합친 앱 런타임용 부산 추천 후보 카탈로그다.

## 5. 산출 JSON

`scripts/build_busan_matched_poi.mjs`가 생성한다.

| 파일 | 역할 |
|---|---|
| `data/processed/busan_matched_poi.json` | 작업용 직접 매칭 산출물 |
| `data/processed/busan_unmatched_tourapi.json` | 작업용 미매칭 TourAPI 후보 |
| `data/processed/category_dwell.json` | 미매칭 후보 체류시간 폴백용 카테고리 집계 |
| `src/data/busan_poi_catalog.json` | 앱 번들용 단일 카탈로그 |

필드 예시:

```json
{
  "contentId": "126081",
  "title": "광안리해수욕장",
  "contentTypeId": "12",
  "category": "자연관광지",
  "lat": 35.153,
  "lon": 129.118,
  "aihubName": "광안리해수욕장",
  "matchType": "name+coord",
  "matchDistanceM": 12,
  "dwell": {
    "count": 182,
    "median": 30,
    "p25": 30,
    "p75": 60,
    "mean": 42
  }
}
```

## 6. 다음 구현 순서

1. 부산 매칭/미매칭 후보 JSON 생성
2. 앱 번들용 `busan_poi_catalog.json` 생성
3. 엔진에서 TourAPI 후보를 catalog의 `matched + unmatched` 기준으로 통과시키기
4. 단일 장소 추천을 안정화
5. 가까운 장소 쌍 기준 2개 장소 미니코스로 확장
6. 도보/자동차 이동시간을 각각 정확히 분리
