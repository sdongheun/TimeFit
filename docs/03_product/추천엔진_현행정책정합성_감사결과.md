# 추천 엔진 현행 정책 정합성 감사 결과

> 감사일: 2026-08-24  
> 작성 역할: 추천 엔진  
> 범위: 코드·고정 fixture 읽기 및 재현만 수행. 정책, UI, 데이터, 엔진 코드는 수정하지 않았다.

## 1. 결론

최신 장소 카탈로그와 근거 프로필은 준비됐지만, 런타임 추천 엔진은 이전 단일 장소·다수 후보 배치 정책을 아직 사용한다. 현행 정책인 `180분 · 대표 코스 정확히 1개 · 1~3곳 · 도보/대중교통 자동 조합 · 실제 경로·구조화 운영시간 · 조건부 더보기`를 구현 완료로 볼 수 없다.

| 판정 | 수 | 항목 |
| --- | ---: | --- |
| 구현됨 | 0 | - |
| 부분 구현 | 2 | 왕복/별도 도착지, 관계 중복 일부 |
| 미구현 | 2 | 1~180분 엔진 입력 검증, 완료 기록 기반 발견성 |
| 정책과 충돌 | 7 | 대표 결과, 1~3곳 조립, 차량 제외, 실제 경로, 운영시간, 조건부 후보, 대안 |

이 문서는 코드 동작을 정책으로 승격하지 않는다. 기준은 `추천로직.md`와 `테스트.md`의 현행 요구사항이다.

## 2. 카탈로그 적용 상태

`src/data/busan_poi_catalog.json`은 기대값과 일치한다.

| 구분 | 수 |
| --- | ---: |
| 전체 런타임 장소 | 368 |
| `representative_core` | 28 |
| `representative_standard` | 162 |
| `conditional_more` | 178 |
| 런타임 `hold` | 0 |
| 런타임 내부 장소 (`siteRole=child`) | 0 |

`src/engine/data.ts`는 위 카탈로그의 368개를 읽는다. 그러나 `BusanCatalogPlace`과 `ResolvedBusanDwell`은 `classification`을 계약 필드로 보존하지 않고, `listBusanPoiCandidates()`는 세 분류를 함께 반환한다. 플래너에는 과거 호환 필드인 `shortStay.selectionStatus`만 전달되며 이것도 후보 차단 규칙으로 사용되지 않는다.

따라서 현재 코드만으로는 `conditional_more` 178개가 대표 추천·자동 확정에 섞이지 않는다고 보장할 수 없다. 현재 런타임에 `hold`와 내부 장소가 없는 것은 데이터 정제 결과이며, 엔진의 분류 방어 규칙이 있다는 뜻은 아니다.

## 3. 현행 정책별 감사 결과

| 현행 기대 결과 | 판정 | 코드 증거와 영향 |
| --- | --- | --- |
| 현재 시각부터 1~180분 | 미구현 | `PlanInput.remainingMin`에 범위 검증이 없다. 엔진 직접 호출이 0·181분을 거부하지 않는다. |
| 대표 결과는 1개 코스 | 정책과 충돌 | `planTimeFit()`은 최대 10개 `courses`와 `pending`을 반환한다. |
| 1·2·3곳을 비교하되 3곳 강제 없음 | 정책과 충돌 | `planner.ts`는 단일과 2곳 조합만 생성하며 3곳 순열·관계 필터가 없다. |
| 왕복과 별도 도착지 반영 | 부분 구현 | `target = input.destination ?? input.origin`으로 마지막 구간을 처리한다. 다만 구간별 자동 조합·정밀 코스 계약에는 아직 연결되지 않았다. |
| 차량 미사용, 도보·대중교통 자동 조합 | 정책과 충돌 | `Mode`, `normalizedCandidateModes`, `ROAD_MODES`, `routeBaselineService`가 `car`를 포함한다. 기존 플래너는 차량 후보를 통과·랭킹·조립에 쓸 수 있다. |
| 대표·새 추천·상세·확인의 동일 실제 구간 시간 | 정책과 충돌 | `INITIAL_TMAP_REFINE_COUNT = 0`이며 대표 목록은 근사값으로 반환된다. 단일 장소 `oneStopRouteService`만 두 구간 정밀화·TTL 캐시를 제공한다. |
| 구조화 운영시간으로 도착~체류 종료 판정 | 정책과 충돌 | 플래너는 TourAPI/운영시간 문자열 게이트를 사용한다. `부산_장소_구조화_운영시간.json`은 감사 fixture에만 연결돼 있다. |
| 조건부 후보는 더보기 전용, 확인 뒤에도 조건부 유지 | 정책과 충돌 | `classification` 기반 대표/더보기 분리, 사용자 명시 확인, 저장 상태 보존이 엔진 출력 계약에 없다. |
| 검증된 서로 다른 코스만 새 추천 | 정책과 충돌 | 기존 `courses/pending` 배치와 `Math.random()` 기반 유사 후보 순환을 쓴다. `no_alternative_verified_course` 상태를 반환하지 않는다. |
| 완료 기록 기반 발견성은 동률 보조 순위만 사용 | 미구현 | 완료 기록 입력·동률 처리·순위 근거가 없다. GPS·소비·외부 인기도를 사용하는 엔진 코드는 발견하지 못했다. |
| 관계 중복 제외 | 부분 구현 | `isAllowedPair()`가 같은 `siteGroupId`의 2곳 조합을 차단한다. 3곳 조합, 동일성 중복 전반, 조건부 수동 포함 재조립에는 적용 범위가 없다. |

## 4. 기존 구현·검증에서 재사용 가능한 부분

- `oneStopRouteService.ts`: 도보·대중교통 두 구간의 정밀 경로, 성공 수단 제한, 실패 시 비추천, 24시간 TTL·동시 요청 공유.
- `validateCourseOpening()`: 순서가 있는 장소별 도착·체류 종료를 다시 검사하는 기본 골격. 현행 구조화 운영시간 어댑터와 코스 구간 모델로 교체가 필요하다.
- `mixedTravel.ts`: 자동 도보/대중교통 선택의 출발점. 현재 `arrivalModes` 사용자 선택 호환 계약은 현행 정책에서 제거 대상이다.
- 데이터 감사 fixture: 1·2·3곳, 왕복·별도 도착지, 실제 도보 경로, 구조화 운영시간, 관계 중복의 고정 근거를 이미 보유한다. 다만 이 fixture는 런타임 `planner.ts`를 실행하지 않는다.

## 5. 통합·결정 세션에 인계할 정책 충돌

다음은 엔진 코드만의 내부 선택으로 해결하면 안 되는 공개 계약 변경이다.

1. 기존 `PlanInput`/`PlanResult`와 화면·저장 모델을 대표 코스 1개 및 조건부 수동 포함 상태로 교체할 계약 경계
2. 실제 경로 호출의 상한: 1~3곳 코스 후보를 몇 개까지 정밀 검증하고, 실패 시 어떤 결과 상태를 반환할지
3. 조건부 사용자의 명시 확인을 저장 payload에 어떤 상태·근거로 남기고, 이후 변경·재계산에서 어떻게 유지할지
4. 완료 기록 기반 발견성의 입력 소유자·익명성·동률 정의와, 기록이 없는 사용자의 결정적 폴백
5. 기존 장바구니·진행 중 코스 변경 기능을 대표 코스 재조립과 어떻게 호환 또는 대체할지

## 6. 추천 엔진 다음 구현 순서

정책 확정 뒤 다음 단위를 순서대로 구현한다. 각 단계는 외부 API가 아닌 고정 adapter fixture로 먼저 실패시킨다.

1. `classification`과 조건부 상태를 엔진 입력·출력 타입에 보존하고, 대표 후보를 `representative_core/representative_standard`로 한정한다.
2. `1~180분`, 왕복/도착지, 차량 불가, 1·2·3곳 조립, 관계 중복을 검증하는 순수 코스 엔진을 만든다.
3. 코스 모든 구간에 실제 경로 adapter·캐시를 적용하고, 근사·실패 경로는 대표 결과에서 제외한다.
4. 구조화 운영시간 adapter로 장소별 도착~체류 종료를 게이트한다.
5. 대표 1개·검증 대안 상태·조건부 수동 포함 상태·발견성 보조 순위를 결정적 결과 모델로 추가한다.

외부 API 호출 없이 아래를 실행했다.
