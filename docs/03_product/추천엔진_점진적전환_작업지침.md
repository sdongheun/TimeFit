# 추천 엔진 점진적 전환 작업 지침

> 대상 역할: **추천 엔진 세션**
>
> 상태: **현행 작업 방향**
>
> 목적: 처음부터 완벽한 개인화·공급량 최적화 엔진을 만들지 않는다. 안전한 최소 추천 경험을 먼저 앱에서 체감하고, 관찰된 빈 결과·단조로움·이해 어려움만 다음 단계에서 고도화한다.

## 0. 제품 판단 원칙

TimeFit의 첫 목표는 사용자가 남은 시간에 실제로 이해하고 선택할 수 있는 부산 코스 하나를 받는 것이다. 점수식의 정교함, 부산 전역 전수 경로 측정, 모든 예외의 사전 제거가 첫 출시 조건은 아니다.

그러나 아래 안전 조건은 “나중에”로 미루지 않는다.

- 현재 시각부터 최대 180분의 시간 예산
- 대표 후보(`representative_core`, `representative_standard`)만 자동 추천
- 운영시간·이동·체류·도착 여유가 코스 전체에서 성립
- 차량을 추천 판정에 사용하지 않음
- 조건부 후보를 대표 추천·자동 확정으로 표시하지 않음

**대표 결과 1개**는 첫 화면의 집중도를 위한 규칙이다. 엔진은 새 추천을 위해 여러 유효 대안을 내부적으로 보존해야 한다. 단, 처음부터 대안 수를 극대화하거나 모든 부산 장소쌍을 정밀 조회하지 않는다.

## 1. 이번 전환의 최소 목표 (v1: 체감 검증용)

v1은 아래만 구현해 실제 사용자가 “남는 시간에 갈 만한 코스를 이해하고 선택하는가”를 확인한다.

```text
입력: 출발지, 도착지 또는 복귀, 도착 시각(최대 180분), 도착 여유
후보: 최신 런타임 368개 중 representative_core / representative_standard 190개
출력: 실제 경로·운영시간을 통과한 대표 코스 1개(1~3곳), 검증 대안 목록 또는 대안 없음 상태
```

### v1에 반드시 포함

1. 엔진이 1·2·3곳을 비교하고, 시간 조건에 맞는 가장 단순한 규모를 포함해 대표 코스 1개를 반환한다. 3곳은 강제하지 않는다.
2. 도보·대중교통만 사용한다. 사용자 수단 선택과 차량은 입력·후보·순위에서 제거한다.
3. 후보는 근사값으로 좁힐 수 있지만, **대표로 표시하거나 새 추천으로 전환하는 코스는** 모든 구간의 실제 경로 adapter 결과와 구조화 운영시간을 통과해야 한다.
4. 1개 코스만 남으면 `no_alternative_verified_course`를 반환한다. 없는 대안을 반복 추천하지 않는다.
5. 조건부 178개는 대표 계산에서 제외한다. 더보기의 조건부 수동 포함은 v1에서 UI가 준비되지 않았으면 노출하지 않아도 되지만, 대표 후보로 섞어서는 안 된다.
6. 고정 fixture로 45/90/180분, 왕복/별도 도착지, 1/2/3곳, 후보 없음, 대안 없음, 차량 전용 제외를 단위 테스트한다.

### v1에서 의도적으로 하지 않는 것

- 완료 기록 기반 발견성 개인화
- 조건부 후보의 사용자 확인·저장·재조립 흐름
- 진행 중 코스 변경의 재조립
- 부산 전역 실경로 공급량 측정과 장소 추가 수집
- 복잡한 다목적 점수식·취향 학습·활동 다양성의 강한 강제
- 모든 후보의 실제 경로 전수 호출

이 항목은 “제외”가 아니라 **실사용 관찰 뒤에 우선순위를 정할 고도화 백로그**다.

## 2. v1 구현 순서

### 단계 1 — 순수 코스 조립 계약

- 새 타입은 기존 다중 `courses/pending` 또는 장바구니 계약을 그대로 확장하지 않는다.
- 입력에는 현재 시각, 출발·도착, 도착 여유, 고정 후보, 구조화 운영시간, 실제 경로 adapter 결과를 주입할 수 있어야 한다.
- 출력에는 `representativeCourse | null`, `alternativeCourseIds`, `alternativeState`, 장소별·구간별 시간 상태를 둔다.
- 우선 작은 고정 후보 집합에서 1~3곳 순열·관계 중복·시간 예산을 결정적으로 검사한다.

### 단계 2 — 실제 경로·운영시간 경계

- 기존 `oneStopRouteService`와 캐시를 다구간 adapter로 재사용하거나 그 계약을 일반화한다.
- 실제 경로 실패·근사 폴백은 대표·새 추천 결과가 아니라 재시도/후보 없음 상태로 돌린다.
- 운영시간은 원문 문자열 파서가 아닌 `부산_장소_구조화_운영시간.json`에 연결된 구조화 adapter를 쓴다.

### 단계 3 — 앱 연결 전 검증

- 대표 1개, 1/2/3곳, 대안 없음, 후보 없음의 결과 모델을 UI가 소비할 수 있게 문서화한다.
- UI·저장 코드를 이 단계에서 직접 수정하지 않는다. 필요한 입출력 변경은 UIUX·DB 세션에 인계한다.
- 엔진은 실제 사용 체감 테스트를 위한 진단값만 반환한다: 후보 수, 대표/대안 수, 탈락 사유(운영시간/경로/예산/관계). 사용자에게 내부 점수·등급을 노출하지 않는다.

## 3. 체감 테스트 뒤 고도화 판단

v1을 고정된 시간·위치 시나리오와 소수의 실제 사용 테스트에 연결한 뒤, 아래 관찰 중 반복되는 것만 다음 작업으로 승격한다.

| 관찰 | 다음 고도화 후보 |
| --- | --- |
| 같은 장소·비슷한 조합만 반복 | 대안 중복 제거·활동/지역 다양성 순위 강화 |
| 특정 시간대·생활권에서 빈 결과가 반복 | 해당 조건의 후보 범위·운영시간·장소 데이터 조사 |
| 2~3곳 코스가 이동만 많고 매력 없음 | 체류/이동 균형과 활동 조합 점수 보정 |
| 사용자가 조건부 장소를 계속 원함 | 명시 확인·조건부 수동 포함·저장 상태 구현 |
| 완료 기록이 쌓여도 새로움 체감이 없음 | 동률 보조 순위로 발견성 개인화 추가 |
| 실제 경로 호출이 느리거나 실패가 많음 | adapter 캐시·호출 상한·재시도 UX 개선 |

관찰 없이 “완벽도를 높이기 위한” 새 점수식이나 대량 데이터 수집을 시작하지 않는다.

## 4. 역할 경계와 완료 인수인계

- 추천 엔진 세션은 `src/engine/`과 순수 엔진 테스트만 수정한다.
- 데이터·UI·DB 정책 문서를 직접 바꾸지 않는다. 새 데이터 필드, 화면 상태, 저장 payload가 필요하면 계약을 인계한다.
- 외부 API는 고정 adapter fixture로 먼저 테스트한다. 실제 호출은 소수 수동 검증으로 분리한다.

v1 완료 인수인계에는 다음을 남긴다.

1. 변경한 엔진 파일과 새 입출력 계약
2. 45/90/180분·왕복/도착지·1/2/3곳·후보/대안 없음 테스트 결과
3. 아직 제외한 고도화 항목과 그 이유
4. UIUX·DB·API 어댑터 세션이 연결할 정확한 상태와 fixture
5. 실제 체감 테스트에서 관찰해야 할 지표와 재현 조건

## 5. 금지 사항

- 기존 장바구니형 플래너에 예외를 누적해 v1을 만들지 않는다.
- 조건부 후보·차량·근사 경로를 대표 추천에 섞지 않는다.
- 3곳 결과를 만들기 위해 장소를 강제 추가하지 않는다.
- 장소가 충분한지 확인하려고 부산 전체 실제 경로를 수집하지 않는다.
- 실사용 관찰 없이 개인화·인기도·소비 추정 점수식을 추가하지 않는다.

## 6. 작업 기록 사용 방식

시간순 작업 명령, 완료 결과, 통합·결정 피드백은 [추천엔진 작업기록](추천엔진_작업기록.md)에만 누적한다. 이 문서는 v1의 제품 방향·범위·역할 경계 참고용으로 유지하며, 다음 작업을 추가하지 않는다.
