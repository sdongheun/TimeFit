# TimeFit 추천 로직 현재 흐름과 부족한 점

> 작성일: 2026-07-26  
> 목적: 현재 TimeFit이 어떤 순서로 추천을 만들고, 어떤 기준으로 점수를 매기며, 무엇이 아직 부족한지 한눈에 이해하기 위한 정리 문서  
> 기준 코드: `src/engine/planner.ts`, `src/engine/travel.ts`

## 1. 한 줄 요약

TimeFit은 사용자의 현재 위치, 약속 장소, 남은 시간, 이동수단을 받아서 **이동시간을 뺀 뒤 자투리 시간에 의미 있게 머물 수 있는 부산 장소 코스**를 추천한다.

현재 추천은 다음 세 가지를 합친 규칙 기반 추천이다.

```text
장소 후보 = TourAPI + 부산 POI catalog
체류시간 = AI-Hub 직접 매칭 또는 카테고리 중앙값
이동시간 = 도보/차량 TMAP 또는 haversine, 대중교통 ODsay
```

즉 지금 앱은 "좋아 보이는 관광지"를 고르는 앱이라기보다, **남은 시간 안에 실제로 들렀다가 다음 일정으로 갈 수 있는 장소를 계산하는 앱**에 가깝다.

## 2. 사용자가 입력하는 값

현재 추천은 아래 입력을 기준으로 시작한다.

| 입력 | 의미 |
|---|---|
| 현재 위치 | 직접 입력 또는 GPS |
| 약속 장소 | 선택 사항. 있으면 코스 마지막 도착지로 사용 |
| 남은 시간 | 최대 240분 |
| 이동수단 | 도보, 차량, 대중교통 |
| 현재 시각/테스트 시각 | 시간대 적합도와 운영시간 검사에 사용 |

약속 장소가 없으면 현재 위치로 다시 돌아오는 왕복 코스로 계산한다.

```text
약속 장소 있음:
현재 위치 -> 추천 장소 1 -> 추천 장소 2 -> 약속 장소

약속 장소 없음:
현재 위치 -> 추천 장소 1 -> 추천 장소 2 -> 현재 위치
```

## 3. 전체 추천 흐름

현재 추천은 아래 순서로 만들어진다.

```text
[1] 입력 받기
    현재 위치, 약속 장소, 남은 시간, 이동수단

[2] 실제 사용 가능 시간 계산
    buffer = max(10분, 남은 시간의 12%)
    budget = 남은 시간 - buffer

[3] 후보 장소 수집
    출발지 근처, 약속지 근처, 중간 지점 주변의 TourAPI 장소 검색

[4] TimeFit 데이터에 있는 장소만 통과
    src/data/busan_poi_catalog.json에 있는 contentId만 추천 후보로 사용

[5] 체류시간 붙이기
    AI-Hub 직접 매칭 장소: 해당 장소 체류시간
    미매칭 장소: 카테고리 중앙값

[5-1] 저신뢰 직접 매칭 제외
    좌표 매칭인데 TourAPI 장소명과 AI-Hub 장소명이 다르고,
    매칭 거리/표본 수/카테고리가 불안정한 장소는 추천 후보에서 제외

[6] 1차 시간 필터
    선택한 이동수단 기준으로 이동 후 카테고리별 최소 체류시간 이상 머물 수 있어야 통과

[7] 운영시간 게이트
    TourAPI detailIntro로 영업/행사기간 검사

[8] 코스 조립
    단일 장소 코스
    2곳 미니코스

[9] 점수 계산과 랭킹
    체류가능시간, 시간활용도, 시간대 적합도, 데이터 신뢰도, 장소 조합 등을 점수화

[10] 이동수단별 정밀화
    도보/차량: 추천 목록에서는 TMAP 호출 0건 유지
    대중교통: 상위 후보군을 ODsay로 정밀 계산 후 재랭킹

[11] 최종 10개 추천
    사용자에게 최대 10개 코스 노출
```

## 4. 시간 계산 방식

사용자가 입력한 시간을 전부 추천에 쓰지 않고, 약간의 여유 시간을 먼저 뺀다.

```text
buffer = max(10분, 남은 시간 * 12%)
budget = 남은 시간 - buffer
```

예를 들어 사용자가 120분을 입력하면:

```text
buffer = max(10, 120 * 0.12) = 14분
budget = 106분
```

이 106분 안에:

```text
출발지 -> 장소 이동시간
+ 장소 체류시간
+ 장소 -> 약속장소 이동시간
```

이 들어와야 한다.

그리고 추천 가능 조건은 최소한 아래를 만족해야 한다.

```text
선택 이동수단 기준 체류 가능 시간 >= 30분
```

## 4.1 숫자로 보는 추천 예시

예를 들어 사용자가 아래처럼 입력했다고 가정한다.

```text
현재 위치: 서면역
약속 장소: 사상역
남은 시간: 120분
이동수단: 대중교통
```

앱은 먼저 안전 여유시간을 뺀다.

```text
buffer = max(10분, 120분 * 12%) = 14분
budget = 120분 - 14분 = 106분
```

그 다음 추천 장소를 하나 가정한다.

```text
추천 장소: 놀이마루
현재 위치 -> 놀이마루: 6분
놀이마루 -> 사상역: 22분
총 이동시간: 28분
```

그러면 실제로 장소에 머물 수 있는 시간은 다음과 같다.

```text
체류 가능 시간 = budget - 총 이동시간
체류 가능 시간 = 106분 - 28분 = 78분
```

이제 AI-Hub 체류시간과 비교한다.

```text
놀이마루 AI-Hub 기준 체류시간: 예를 들어 40분
사용자가 실제로 머물 수 있는 시간: 78분
```

이 경우 앱은 이렇게 판단한다.

```text
최소 30분 이상 머물 수 있음
AI-Hub 기준 체류시간도 충분히 소화 가능
따라서 추천 가능
```

중요한 점은 AI-Hub 체류시간을 반드시 정확히 채워야만 추천하는 것은 아니라는 점이다.

```text
AI-Hub 체류시간 = 이 장소를 보통 어느 정도 머무는지에 대한 기준값
체류 가능 시간 = 사용자가 이번 상황에서 실제로 머물 수 있는 시간
```

따라서 현재 추천은 아래 구조에 가깝다.

```text
사용자 입력 시간
- 안전 여유시간
- 이동시간
= 실제 머물 수 있는 시간

그리고 이 시간이 카테고리별 최소 체류시간 이상이면 추천 후보가 된다.
AI-Hub 체류시간은 이 장소가 그 시간에 적절한지 판단하는 기준으로 사용한다.
```

현재 최소 체류시간은 다음처럼 적용한다.

| 상황 | 카테고리 | 최소 체류시간 |
|---|---|---:|
| 남은 시간 60분 이하 | 카페, 상업지구 | 20분 |
| 남은 시간 60분 이하 | 문화시설, 자연관광지 | 25분 |
| 남은 시간 90분 이하 | 카페, 상업지구 | 25분 |
| 그 외 단일 장소 | 모든 카테고리 | 30분 |
| 2곳 미니코스 | 모든 조합 | 30분 |

이 규칙은 1시간 같은 짧은 자투리 시간에 카페, 시장, 거리 구경처럼 짧게 이용 가능한 장소가 과하게 탈락하는 문제를 줄이기 위한 것이다.

## 5. 후보 장소를 어디서 가져오는가

장소는 TourAPI에서 검색하지만, TourAPI 결과를 전부 쓰지는 않는다.

현재는 부산 대상으로 정리한 `src/data/busan_poi_catalog.json`에 들어 있는 장소만 사용한다.

이 catalog 안에는 두 종류가 섞여 있다.

| 유형 | 의미 | 체류시간 근거 |
|---|---|---|
| matched | TourAPI 장소와 AI-Hub 장소가 매칭됨 | 해당 장소의 AI-Hub 체류시간 |
| unmatched | TourAPI에는 있지만 AI-Hub 장소와 직접 매칭 안 됨 | 카테고리 중앙값 |

matched는 신뢰도가 상대적으로 높고, unmatched는 추천 후보 수를 늘리기 위한 보완 데이터다.

단, matched라고 해서 모두 그대로 믿지는 않는다.

```text
저신뢰 제외 예시:
TourAPI title = 그런고로
AI-Hub name = 포셋 전포점
matchType = coord
matchDistanceM = 97m
dwell count = 3
TourAPI category = 자연관광지
AI-Hub category = 상업지구
```

이처럼 좌표만으로 붙었고 이름/카테고리/거리/표본 수가 모두 불안정하면 추천 후보에서 제외한다.

## 6. 현재 사용하는 카테고리

현재 추천에는 다음 성격의 장소가 들어올 수 있다.

```text
문화시설
자연관광지
상업지구
레저/스포츠
식당
카페
지역축제/행사
```

숙박, 주차장, 병원, 주유소 같은 자투리 시간 앱과 맞지 않는 시설은 자동진단에서 강하게 걸러야 하는 대상으로 본다.

레저/스포츠는 예약, 장비, 장시간 체험이 필요한 장소가 많이 섞여 있어 2026-07-27 기준으로 10개만 유지한다.

```text
matched:
- 광안리 해양레포츠센터
- 미포정거장
- 송도 구름산책로

unmatched:
- 구포무장애숲길
- 문탠로드
- 부산광역시 부산실내빙상장
- 삼락강변체육공원인라인스케이트장
- 송도해안볼레길
- 해안누리길 몰운대길
- 회동수원지 둘레길
```

제외한 레저/스포츠 29개는 `data/processed/부산_제외_레저스포츠.json`에 보관한다.

## 7. 세 가지 위치 전략

약속 장소가 있을 때는 후보를 한 곳에서만 찾지 않는다.

```text
1. 출발지 근처
2. 약속지 근처
3. 출발지와 약속지 중간 지점
```

이 세 전략은 실제 사용자 행동을 반영하려는 것이다.

예를 들어 서면에 있고 사상역에서 약속이 있다면:

```text
전략 A: 서면 근처에서 시간을 보내고 사상역으로 이동
전략 B: 먼저 사상역 근처로 가서 시간을 보냄
전략 C: 가는 길 중간에서 내려 시간을 보냄
```

현재는 이 세 전략을 모두 후보로 만들고, 점수에서 약속지 근처와 중간 지점에 약간의 가점을 준다.

## 8. 이동수단별 계산 방식

### 도보

추천 목록 단계에서는 TMAP을 호출하지 않는다.

초기 추천은 haversine 기반 도보 추정으로 만든다.

상세 화면에 들어갔을 때 선택한 코스만 TMAP 보행자 경로 API로 정밀화할 수 있다.

남은 시간이 60분 이하인 도보 추천은 후보 검색 반경을 1km까지 넓힌다. 단, 추천 여부는 이동시간을 뺀 체류 가능 시간으로 다시 판단하므로 반경이 넓어졌다고 무조건 먼 장소가 추천되는 것은 아니다.

### 차량

도보와 비슷하게 추천 목록에서는 TMAP 호출을 하지 않는다.

초기 추천은 차량 속도 기반 추정으로 만들고, 상세 화면에서 선택 코스만 TMAP 차량 경로 API로 정밀화한다.

현재 차량은 주차 여부를 고려하지 않는다.

### 대중교통

대중교통은 ODsay를 사용한다.

현재 방식:

```text
1. 먼저 근사값으로 후보 코스를 만든다.
2. 상위 후보군 18개를 ODsay로 정밀 계산한다.
3. ODsay 결과를 반영해 다시 랭킹한다.
4. 최종 10개를 보여준다.
```

짧은 구간은 ODsay를 호출하지 않는다.

```text
750m 이하 또는 도보 10분 이하 -> walk_short
```

ODsay가 실패한 구간은 `transit_fallback`으로 남고, 점수에서 약하게 감점한다.

## 9. 경로 표시 방식

현재 지도 경로는 이동수단에 따라 정확도가 다르다.

| 구간 | 지도 표시 방식 | 완성도 |
|---|---|---|
| TMAP 도보 | TMAP geometry | 높음 |
| TMAP 차량 | TMAP geometry | 높음 |
| ODsay 대중교통 | 역/정류장 좌표를 연결한 간이 polyline | 중간 |
| walk_short | 출발/도착 좌표 직선 | 낮음~중간 |
| transit_fallback | 출발/도착 좌표 직선 | 낮음 |

대중교통은 실제 선로나 도로 모양을 따라가는 완전한 polyline이 아니다.

현재는 ODsay 응답의 `subPath`, `passStopList`에서 역/정류장 좌표를 뽑아서 연결한다.

```text
서면역 -> 전포역 -> 국제금융센터·부산은행역 -> 문현역 -> ... -> 사상역
```

처럼 역과 역을 잇는 간이 경로다.

## 10. 코스는 어떻게 만들어지는가

코스는 두 종류다.

| 코스 | 의미 |
|---|---|
| 단일 코스 | 장소 1개만 추천 |
| 미니코스 | 장소 2개를 묶어서 추천 |

2곳 미니코스는 다음 조건을 만족해야 한다.

```text
첫 번째 장소만 갔을 때 남는 체류 가능 시간이 35분 이상
두 장소 사이 이동 부담이 너무 크지 않음
식당+식당 제외
카페+카페 제외
전체 코스가 budget 안에 들어옴
```

사용자가 2시간을 입력했다고 해서 무조건 2곳을 추천하는 것은 아니다.

첫 장소의 체류시간이 길면 1곳만 추천될 수 있고, 첫 장소의 체류시간이 짧고 이동 부담이 작으면 2곳 코스가 만들어진다.

## 11. 현재 점수 계산 방식

현재 랭킹 점수는 대략 아래 요소로 구성된다.

| 요소 | 의미 |
|---|---|
| 체류 가능 시간 | 이동 후 얼마나 머물 수 있는가 |
| 체류 비율 | 이동시간 대비 체류시간이 충분한가 |
| 시간대 적합도 | 아침/점심/오후/저녁/야간에 어울리는 카테고리인가 |
| 데이터 신뢰도 | AI-Hub 직접 매칭인지, 카테고리 폴백인지 |
| 장소 간 밀집도 | 2곳 코스일 때 서로 가까운가 |
| 전략 가점 | 약속지 근처, 가는 길 중간 여부 |
| 짧은 시간 가점 | 60분 이하에서 카페/상업지구/가벼운 구경 장소 우선 |
| 지하철 가점 | 대중교통에서 지하철 경로가 확인됐는가 |
| fallback 감점 | 대중교통 근사값이 남았는가 |
| 카테고리 다양성 | 같은 카테고리만 반복되지 않는가 |

코드 기준 핵심 점수는 다음 형태다.

```text
score =
  체류가능시간 점수
+ 체류비율 점수
+ 시간대 적합도
+ 데이터 신뢰도
+ 장소 밀집도
+ 전략 가점
+ 짧은 시간 카테고리 가점
+ 지하철 가점
- fallback 감점
- 중복 카테고리 감점
```

현재는 ML 모델이 아니라 설명 가능한 규칙 기반 점수다.

남은 시간이 60분 이하이면 짧게 이용하기 쉬운 카테고리에 추가 가점을 준다.

| 카테고리 | 짧은 시간 가중치 |
|---|---:|
| 카페 | 높음 |
| 상업지구 | 높음 |
| 문화시설 | 중간 |
| 자연관광지 | 중간 |
| 식당 | 낮음 |

즉 1시간처럼 짧은 시간에는 멀리 있는 유명 관광지보다 가까운 카페, 시장, 거리 구경, 짧은 문화시설이 더 위로 오도록 조정한다.

## 12. 왜 같은 입력에서도 추천 순서가 조금 달라지는가

같은 위치와 같은 시간으로 추천을 다시 눌렀을 때 완전히 같은 결과만 나오면 사용자는 추천 풀이 적다고 느낄 수 있다.

그래서 현재는 점수 차이가 작은 후보끼리만 약한 랜덤성을 적용한다.

```text
점수 차이가 큰 후보 -> 기존 우선순위 유지
점수 차이가 작은 후보 -> 순서가 조금 바뀔 수 있음
```

이 방식은 정확도가 높은 후보를 망가뜨리지 않으면서 추천 반복감을 줄이기 위한 절충안이다.

## 13. 현재 추천 로직의 강점

### 13.1 시간 안에 가능한지 계산한다

단순히 가까운 장소를 보여주는 것이 아니라:

```text
남은 시간 - 이동시간 = 체류 가능 시간
```

을 계산한다.

이 앱의 핵심 차별점이다.

### 13.2 다음 일정 장소를 고려한다

약속 장소가 있으면 최종 도착지를 약속 장소로 잡는다.

따라서 그냥 "근처 추천"이 아니라:

```text
현재 위치 -> 들를 장소 -> 약속 장소
```

흐름으로 판단한다.

### 13.3 이동수단을 분리했다

도보 사용자가 차량으로만 가능한 장소를 추천받는 문제를 줄였다.

현재는 도보, 차량, 대중교통을 각각 선택해서 계산한다.

### 13.4 대중교통은 실제 API로 검증한다

대중교통은 단순 직선거리만 보지 않고, 상위 후보군을 ODsay로 정밀 계산한다.

지하철 경로가 있으면 가점을 준다.

### 13.5 추천을 자동진단할 수 있다

`scripts/audit_recommendations.ts`, `scripts/audit_transit_recommendations.ts`로 추천 결과를 자동 점검할 수 있다.

이건 혼자 개발할 때 매우 중요하다.

## 14. 현재 부족한 점

## 14.1 장소의 질 점수가 약하다

현재 추천은 "시간 안에 갈 수 있는가"에 강하고, "그 장소가 정말 좋은가"에는 약하다.

예를 들어 시간상 가능하면 평범한 식당이나 애매한 장소도 추천될 수 있다.

필요한 개선:

```text
AI-Hub 만족도
재방문 의향
장소별 체류시간 분포 안정성
TourAPI 이미지/소개 유무
직접 매칭 신뢰도
```

를 점수에 반영해야 한다.

우선순위가 가장 높다.

## 14.2 사용자 취향이 아직 없다

현재는 사용자마다 거의 같은 추천이 나온다.

예를 들어 아래 차이가 반영되지 않는다.

```text
조용한 곳 선호
카페 선호
쇼핑 싫어함
전시/문화 선호
야외 산책 선호
혼자 가기 좋은 곳 선호
```

처음부터 복잡한 개인화는 필요 없고, 칩 선택 정도면 충분하다.

```text
카페
산책
쇼핑
전시/문화
로컬 맛집
조용한 곳
```

## 14.3 음식점/카페 규칙이 더 필요하다

음식점과 카페는 추천 후보 수를 늘려주지만 리스크가 크다.

부족한 점:

```text
웨이팅 가능성
식사 시간대 여부
약속 전에 식당을 추천하는 것이 자연스러운지
남은 시간이 짧을 때 음식점이 적절한지
카페가 너무 많이 반복되는지
```

개선 방향:

```text
점심/저녁 시간대에는 식당 가점
약속까지 60분 이하이면 식당 감점
카페는 짧은 체류 보완용으로 사용
식당+식당, 카페+카페는 계속 제외
```

현재 반영된 개선:

```text
60분 이하 자투리 시간에서는 카페/상업지구 최소 체류 기준을 20분으로 완화
문화시설/자연관광지는 25분 이상 체류 가능하면 후보 유지
카페/상업지구/문화시설/자연관광지에 짧은 시간 가점 부여
식당은 짧은 시간에서 약하게 감점
```

## 14.4 운영시간 데이터 신뢰도가 낮다

TourAPI 운영시간은 비어 있거나 부정확할 수 있다.

현재는 운영시간이 명확하면 검사하지만, 데이터가 없을 때 판단이 약하다.

개선 방향:

```text
운영시간 정보 없음 -> 통과시키되 신뢰도 낮춤
아침/야간 추천에서는 운영시간 정보 없는 장소 감점
음식점/카페는 시간대 기준 더 엄격하게 판단
```

## 14.5 경로 전략 점수가 단순하다

현재는 출발지 근처, 약속지 근처, 중간 지점이라는 세 전략만 있다.

하지만 실제 추천은 더 정교해야 한다.

예:

```text
남은 시간이 짧다 -> 약속지 근처 우선
남은 시간이 길다 -> 출발지 근처 또는 중간 지점도 허용
대중교통 -> 환승역/주요역 주변 가점
차량 -> 우회율 낮은 장소 가점
도보 -> 반경이 좁고 안전한 동선 우선
```

## 14.6 대중교통 경로 완성도가 아직 중간 수준이다

대중교통 시간은 ODsay 기준으로 확인하지만, 지도 경로는 실제 선로/도로 geometry가 아니다.

현재는 역/정류장 좌표를 연결한 간이 polyline이다.

개선 후보:

```text
OSM/Overpass 지하철 노선 geometry
부산교통공사 역/노선 데이터
카카오맵 길찾기 위임
```

현재 방향은 일단 간이 polyline을 유지하고, 실제 길찾기는 카카오맵으로 위임하는 것이다.

## 14.7 추천 검증 기준이 아직 부족하다

자동진단은 있지만, 아직 "좋은 추천"의 정답 데이터가 없다.

필요한 것:

```text
대표 시나리오 5~10개
각 시나리오에서 사람이 보기 좋은 코스/나쁜 코스 표시
자동진단 결과와 비교
점수식 조정
```

## 14.8 지도 검색 존재 검증이 아직 없다

현재 후보는 TourAPI와 내부 catalog 기준으로 검증한다. 하지만 사용자가 카카오맵이나 네이버지도에 검색했을 때 장소가 안 뜨면 신뢰가 떨어진다.

필요한 개선:

```text
Kakao Local API 키 추가
TourAPI title + 좌표 기준으로 카카오 키워드 검색
일정 반경 안에 유사 이름 결과가 있으면 mapVerified=true
검색 결과가 없거나 이름이 크게 다르면 추천 제외 또는 강한 감점
```

현재 코드에는 Kakao API 키가 없으므로, 이번 단계에서는 명백한 저신뢰 매칭을 제외하는 내부 필터까지만 반영했다.

## 15. 추천 정교화를 위한 우선순위

현재 상태에서 가장 효과가 큰 순서는 다음과 같다.

| 우선순위 | 작업 | 기대 효과 |
|---:|---|---|
| 1 | 장소 품질 점수 추가 | 애매한 장소 추천 감소 |
| 2 | 경로 전략 점수 고도화 | 동선이 어색한 추천 감소 |
| 3 | 사용자 취향 칩 반영 | 사용자마다 다른 추천 가능 |
| 4 | 음식점/카페 시간대 규칙 | 부자연스러운 음식점 추천 감소 |
| 5 | 운영시간 신뢰도 반영 | 실제 사용 안정성 증가 |
| 6 | 대중교통 geometry 보강 | 지도 신뢰도 증가 |
| 7 | 날씨/실내외 가중치 | 공모전 차별화 강화 |

## 16. 추천 정확도 현재 평가

정확도를 하나의 숫자로 말하기는 어렵다. 영역별로 나눠야 한다.

| 영역 | 현재 수준 | 이유 |
|---|---|---|
| 시간 안에 가능한지 계산 | 중상 | 이동시간과 체류가능시간을 budget 안에서 계산함 |
| 도보/차량 이동시간 | 중 | 추천 목록은 추정, 상세는 TMAP 정밀화 가능 |
| 대중교통 이동시간 | 중상 | ODsay 성공 구간은 신뢰 가능, fallback은 낮음 |
| 대중교통 지도 경로 | 중 | 역/정류장 간이 polyline, 실제 노선 geometry는 아님 |
| 체류시간 | 중 | AI-Hub 직접 매칭은 쓸 만하지만 개인별/상황별 차이는 큼 |
| 장소 품질 | 낮음~중 | 만족도/재방문 의향/인기도가 아직 약함 |
| 사용자 개인화 | 낮음 | 취향 입력이 아직 없음 |
| 운영시간 안정성 | 낮음~중 | TourAPI 운영시간 누락/부정확 가능성 |

## 17. 지금 가장 먼저 하면 좋은 작업

추천을 더 정교하게 만들고 싶다면 다음 작업이 가장 좋다.

```text
장소 품질 점수 추가
```

이유:

```text
현재는 시간상 가능하면 장소 품질이 낮아도 추천될 수 있음
장소 품질 점수를 넣으면 추천 결과가 바로 좋아질 가능성이 큼
AI-Hub 데이터 활용성이 더 강해져 공모전 설명도 좋아짐
```

그 다음은:

```text
경로 전략 점수 고도화
사용자 취향 칩 반영
```

순서로 가는 것이 좋다.

## 18. 한눈에 보는 현재 상태

```text
가능한 것:
- 남은 시간 기반 추천
- 약속 장소 도착 고려
- 도보/차량/대중교통 분리
- AI-Hub 체류시간 활용
- 대중교통 ODsay 정밀화
- 자동진단과 호출량 측정

부족한 것:
- 장소 품질 점수
- 사용자 취향
- 음식점/카페 세부 규칙
- 운영시간 신뢰도
- 카카오맵 등 지도 검색 존재 검증
- 실제 대중교통 노선 geometry
- 대표 시나리오 기반 수동 검증
```
