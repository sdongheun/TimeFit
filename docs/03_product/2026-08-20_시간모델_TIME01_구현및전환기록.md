## 1. 개요 및 목적

본 문서는 2026-08-17에 확정된 **`TIME-01` 시간 모델(출시 UI 시작 시각 현재 시각 고정)**을 프론트엔드 코드에 반영하고, 실제 경로 기반 탐색 전환 계획의 **6단계 대표 시나리오 E2E 테스트**를 추가하여 검증한 상세 내역을 기록한다.

기존 기준 문서(`추천로직.md`, `추천_실경로탐색전환계획.md` 등)는 임의로 덮어쓰지 않고 보존하며, 본 문서를 통해 다음 작업자가 변경된 코드의 맥락과 테스트 결과를 즉시 파악하고 후속 작업을 이어갈 수 있도록 한다.

## 2. 정책 및 코드 변경 내역

### 2.1 TIME-01 시간 모델 반영 (`TimeSetupScreen.tsx`)

| 항목 | 상세 내용 |
|---|---|
| **이전 방식** | 시작 시각 휠(`startHour`, `startMinute`)과 종료 시각 휠(`endHour`, `endMinute`)을 모두 화면에 노출하여 사용자가 시작 시각을 미래/과거로 임의 조작함 |
| **발생한 문제/관찰** | TimeFit은 "미래 여행 계획 앱"이 아니라 **"지금 비는 짬 시간을 활용하는 서비스"**이다. 시작 시각을 계속 돌리게 하면 첫 입력 단계의 피로도가 증가하고 앱의 단일 정체성이 흐려진다. |
| **교체한 방식** | 1. **시작 시각 현재 시각 고정**: 출시 화면 상단에 `지금 출발 · HH:MM`으로 고정 표시.<br>2. **빠른 자투리 시간 프리셋 추가**: `30분`, `60분`, `90분`, `120분`, `180분` 칩을 상단에 배치하여 탭 한 번으로 남은 시간 설정.<br>3. **종료 시각 휠 단일화**: `종료 시각 (약속 도착 / 복귀)` 휠만 조작하여 목표 시각에 맞춤.<br>4. **개발/테스트 모드 격리 (`TIME-01.1`)**: 새벽 시간, 운영시간 경계, 자동 하네스 테스트를 위해 하단에 `[테스트] 시작 시각 직접 변경하기` 접이식 토글을 제공하여 테스트 가능성을 유지. |
| **교체 이유** | 사용자 인터랙션 최소화 (3초 안에 코스 탐색 진입 가능), 서비스 정체성(지금 짬 해결) 강화. |
| **상태** | **현행 (구현 완료)** |

### 2.2 실제 경로 기반 탐색 6단계 대표 시나리오 E2E 검증 (`actual-route-scenarios.test.ts`)

`docs/03_product/추천_실경로탐색전환계획.md`의 미착수였던 6단계를 고정 좌표 및 실제 기준 경로(Polyline) fixture를 사용해 자동 테스트로 구현했다.

| 시나리오 ID | 검증 내용 | 기대 결과 및 검증 상태 |
|---|---|---|
| **시나리오 1** | **서면 → 사상 이동 축 검증**<br>(가야대로 실제 기준 경로 geometry) | • 서면 생활권(전포), 가야(중간 경로), 사상 생활권(감전)은 포함<br>• 이동 축 밖의 남쪽 부산역, 동쪽 광안리는 1km 반경에서 **완벽 배제** 확인 (`통과`) |
| **시나리오 2** | **서면 왕복 120분 반경 확장 검증** | • 기본 1km: 서면 인근 생활권(전포)만 노출, 광안리/사상 배제<br>• 슬라이더 8km 확장: 광안리, 사상 등 원거리 후보 포함 확인 (`통과`) |
| **시나리오 3** | **3개 수단 기준 경로 전체 실패 안전성** | • 도보/차량/대중교통 기준 경로 조회가 모두 실패했을 때, 넓은 원(8km)으로 폴백하지 않고 **출발지/도착지 양 끝 1km 생활권으로만 안전하게 축소** 확인 (`통과`) |
| **시나리오 4** | **TIME-01 시간 예산 일치성** | • 현재 시각(`nowMin`)과 남은 시간(`remainingMin`)이 플래너에 전달될 때, 대중교통 안전 여유(20분)가 정확히 차감된 예산(`budgetMin`)이 계산되고 로컬 운영시간 게이트를 통과한 후보만 반환 확인 (`통과`) |

### 2.3 장소 상세 체류시간 표시 분리 (`CandidateDetail.tsx`)

| 항목 | 상세 내용 |
|---|---|
| **이전 방식** | 후보 상세 화면(`CandidateDetail`)의 가운데 메트릭에 다중 장소 코스의 합산 체류시간(`chosen.totalStayMin`, 예: 84분)을 `코스 체류`라는 단일 라벨로 표시함 |
| **발생한 문제/관찰** | 사용자가 첫 번째 장소(상상마당)를 담을 때 86분이 나온 뒤, 두 번째 장소(롯데백화점)를 눌렀을 때도 84분이라고 나오자, "두 곳 다 80분씩 머물면 160분인데 2시간 안에 어떻게 가능한가? 앱 오류인가?"라고 심각한 혼란을 느낌. 실제로는 롯데백화점에 약 35분이 배정되고 합산이 84분인데, 개별 체류시간이 보이지 않아 발생한 UX 문제임. |
| **교체한 방식** | 1. **메인 지표를 `이 장소 체류`(`chosen.stayPossibleMin`, 예: 35분)로 변경**하여 지금 선택한 장소에서 머무는 실제 시간을 가장 크게 표시.<br>2. **다중 장소일 때 보조 라벨 `(코스 총 84분)` 병기**: 단일 장소가 아닌 경우 코스 전체 체류시간을 하단에 작게 병기하여 혼란을 해소.<br>3. 체류시간 배분 기준을 AI-Hub 권장 체류시간 비례 배분 공식으로 유지하면서 사용자 전달력을 극대화. |
| **교체 이유** | 사용자가 개별 장소의 실제 체류 가능 시간을 직관적으로 확인하고, 다중 장소 코스의 시간 배분을 명확히 납득할 수 있도록 개선. |
| **상태** | **현행 (구현 완료)** |

### 2.4 이동수단별 안전 여유시간 안내 및 모드 힌트 제공 (`CandidateDetail.tsx`)

| 항목 | 상세 내용 |
|---|---|
| **이전 방식** | 도보(8분), 차량(10분), 대중교통(20분)의 이동수단별 안전 버퍼가 달라 버튼의 이동시간이 같아도 남는 시간과 체류시간이 다르게 변하는데, 화면에 아무런 설명이 없어 "왜 숫자가 제멋대로 바뀌지?" 하는 버그 의심 유발 |
| **발생한 문제/관찰** | 가까운 거리(도보 4분)에서 도보/대중교통/차량 버튼의 이동시간은 4분으로 동일한데, 버튼을 누를 때마다 남는 시간이 8분, 20분으로 바뀌고 체류시간도 달라져 사용자가 혼란을 겪음. 지연 방지 버퍼라는 훌륭한 핵심 기능이 설명 부족으로 역효과를 냄. |
| **교체한 방식** | 1. **남는 시간 메트릭 하단에 안전 여유 서브라벨 추가**: `(대기·환승 20분 포함)`, `(보행 여유 8분 포함)`, `(주차·정체 10분 포함)`을 병기하여 여유 시간이 왜 발생하는지 명확히 전달.<br>2. **수단 선택기 하단에 모드별 한 줄 힌트 추가**: *"대중교통 지연에 대비해 안전 여유 20분을 미리 확보해요"*, *"도보는 이동이 확실해 장소에 더 오래 머물 수 있어요"* 등의 친절한 가이드 표시. |
| **교체 이유** | 사용자의 혼란을 1초 만에 해소하고, "약속 시간에 늦지 않게 지연 위험을 대비해주는 똑똑한 AI 플래너"라는 신뢰감과 서비스 전문성 형성. |
| **상태** | **현행 (구현 완료)** |

### 2.5 출발지 초기 위치 자동 감지 및 수동 변경 보존 (`TimeSetupScreen.tsx`)

| 항목 | 상세 내용 |
|---|---|
| **이전 방식** | 화면 진입 시 기본 출발지가 '부산 서면'으로 고정되어 있어, 현장에서 매번 [GPS] 버튼을 수동으로 눌러야 현재 위치를 잡음 |
| **발생한 문제/관찰** | 현장 필드 테스트 시 매번 위치 갱신 버튼을 누르는 피로도가 발생하고, 앱을 켰을 때 즉시 내 주변 장소를 추천받기 어려움 |
| **교체한 방식** | 1. **화면 마운트 시 위치 권한 확인 후 자동 GPS 감지**: 권한이 허용되어 있다면 백그라운드에서 즉시 현재 좌표 및 한글 주소를 조회하여 출발지로 자동 세팅.<br>2. **수동 검색 및 장소 선택기 완벽 보존**: 사용자가 임의의 출발지를 검색(`PlacePicker`)하거나 개발용 시나리오를 테스트할 수 있도록 수동 변경 흐름을 그대로 유지. |
| **교체 이유** | 현장 테스트 및 실제 사용자 진입 단계에서의 인터랙션 최소화 (앱 켜자마자 바로 내 주변 장소 추천 가능). |
| **상태** | **현행 (구현 완료)** |
