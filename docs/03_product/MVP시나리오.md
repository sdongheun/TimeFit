> 작성: 2026-06-15 · 사용자 인터뷰 2라운드 반영. 이 문서 = "무엇을 만드나"의 제품 시나리오.

## 0. 한 줄 정의

> **다음 스케줄 전까지 비는 시간에, `(가는 시간 + 체류 시간 + 복귀/경유 이동) ≤ 비는 시간` 을 만족하는 *진짜 가능한* 미니코스 여러 개를 시간 적응형으로 추천.**

단순 근처 추천이 아니라 **두 지점(현재 ↔ 다음 스케줄) 사이 빈 시간에 끼울 수 있는가**의 계산.

---

## 1. 확정된 MVP 결정 (인터뷰)

| 항목 | 결정 |
|---|---|
| 다음 스케줄 장소 | **선택 입력** — 입력 시 *경유 최적화*(현재→코스→스케줄장소), 미입력 시 *현재위치 왕복* |
| 시간/일정 파악 | **수동 입력**(남은 시간 또는 다음 일정 시각). 캘린더 연동은 post-MVP |
| 추천 출력 | **여러 코스 후보**(2~3개) — 사용자가 선택 |
| 코스 구성 | **시간 적응형**: ≤60분 1곳 / 60~150분 미니코스 2곳 / >150분 2~3곳+식사 |
| 필터 흐름 | **핵심만 먼저 + 결과에서 점진 추가**(즉시성 보존) |
| 필터 종류 | 예산 · 활동유형 · 분위기 · 이동수단 (풍부하게, 단 단계적으로) |
| 시연 지역 | **부산·김해 우선**(동부권 데이터 확보), 전국은 확장 |

## 2. 핵심 사용자 플로우 (3화면)

```
[화면1 입력]  남은시간(30분/1h/2h/직접) + 현재위치(GPS) + 다음장소(선택)
              + 핵심필터 1~2개(이동수단 / 예산)            → [추천받기]
       ↓ 시간-적합 계산 엔진 (TourAPI 후보 → 체류(JSON)+이동(TMAP)+운영시간 게이트)
[화면2 결과]  여러 코스 후보 카드 (시간 적응형)
              각 카드: 코스명 · 총소요 분해[이동 X + 체류 Y + (복귀 Z)] · "왜 가능한지" 한 줄 · 지도썸네일
              상단 점진 필터칩: [예산] [활동] [분위기]                → 칩 누르면 즉시 재필터
       ↓ 카드 선택
[화면3 상세]  동선 지도 + 각 장소(체류시간·운영시간·이유) + 다음 스케줄까지 여유 표시
```

**즉시성 원칙:** 화면1은 최소 입력(시간+위치 필수, 나머지 선택). 풍부한 필터는 화면2에서 칩으로 점진 적용.

## 3. 구체 시나리오 예시

### 예시 A — 단시간·왕복 (부산 서면, 90분)
- **입력:** 현재 서면 / 남은 시간 90분 / 다음 장소 미입력(왕복) / 도보
- **계산:** (도보 이동 + 체류 + 도보 복귀) ≤ 90분 − 버퍼(~12분)
- **후보 출력(시간 적응형 → 미니코스 2곳):**
  - **후보1**: 전포 카페거리 산책(체류 40분) + 인근 전망카페(체류 30분), 이동 합 15분 = **85분** ✅ "도보 15분 내, 2시간 전 닫는 곳 없음"
  - **후보2**: 단일 — 국제시장 구경(체류 60분), 왕복 25분 = 85분 ✅
  - **후보3**(필터 '예산=무료' 적용 시): 부산시민공원 산책 70분

### 예시 B — 장시간·경유 (김해 → 부산 서면 스케줄, 3시간, 자차)
- **입력:** 현재 김해 / 남은 시간 3시간 / 다음 장소 **부산 서면(스케줄)** / 자차
- **계산:** (김해→코스 + 체류 + 코스→서면) ≤ 3시간. *가는 길에 들를 곳* 최적화
- **후보 출력(>150분 → 코스+식사):**
  - **후보1**: 김해 가는길 ○○ 명소(체류 60분) + 점심 맛집(체류 60분), 이동 합 70분 = **190분** ✅ "서면 도착 시각 여유 ○분"
  - **후보2**: 광안리 해변 산책(60분) + 카페(40분), 경유 이동 80분

> POI·체류시간은 `data/processed/poi_dwell.json`(부산 매칭 58.6%) + `category_dwell.json`(폴백)에서, 이동은 TMAP, 운영시간은 TourAPI 라이브.

## 4. 시간-적합 계산 (엔진 요약)

```
후보 가능? = Σ(이동시간[TMAP] + 유효체류[category/poi_dwell × 혼잡배수]) + 운영시간게이트[TourAPI]
            + (목적지 입력 시) 코스→목적지 복귀이동
          ≤ 남은시간 − 안전버퍼(10~15%)
```
- 운영시간 게이트: "남은 시간 동안 계속 열려 있나" (TourAPI usetime, 90~100% 실측)
- 폐업 검증: 휘발형 POI(음식점/카페)는 TourAPI/LOCALDATA 생존 확인 후 노출
- 코스 구성·"왜 가능한지" 설명: LLM(Claude, 서버 프록시)

## 5. 필터 정의 (핵심 먼저 → 점진)

| 필터 | 값(예) | 단계 |
|---|---|---|
| **이동수단** | 도보 / 대중교통 / 자차 | 핵심(화면1) — 계산에 직결 |
| **예산** | 무료 / 저렴 / 상관없음 | 핵심 or 결과칩 |
| 활동유형 | 먹기 / 보기 / 걷기 / 체험 / 쉬기 | 결과칩(점진) |
| 분위기 | 자연 / 도심 / 문화 | 결과칩(점진) |

---

## 6. MVP 범위

**포함:** 수동 시간입력 · GPS 현재위치 · 선택 목적지(경유/왕복) · TourAPI 후보 · 시간-적합 계산(체류JSON+TMAP+운영시간) · 여러 코스 후보(시간적응형) · 핵심+점진 필터 · LLM 코스설명 · 부산·김해

**제외(post-MVP):** 캘린더 연동 · 실시간 혼잡 override · 실시간 대기시간 · 전국 확장 · 개인화 학습 · 예약/네비
