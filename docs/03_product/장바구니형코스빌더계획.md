# 장바구니형 코스 빌더 계획

> 작성: 2026-08-02  
> 목적: 자동으로 여러 코스를 완성해 보여주는 방식의 반복/후보 부족 문제를 줄이고, 사용자가 장소를 하나씩 담으며 TimeFit이 시간 가능성을 계산하는 구조로 전환한다.

## 1. 배경

현재 추천은 `현재 위치 -> 장소 1~2개 -> 약속 장소/복귀` 형태의 완성 코스를 여러 개 생성한다. 서면처럼 TourAPI 후보가 적은 지역에서는 실제 후보 장소가 적기 때문에, 같은 장소가 여러 코스 조합으로 반복되는 문제가 생긴다.

사용자는 "여러 가지 추천"을 기대하지만 실제로는 같은 장소의 조합만 바뀌어 보일 수 있다. 이 문제는 코스 조합 로직만 바꿔서는 해결하기 어렵고, 후보 풀을 넓히거나 추천 방식을 바꿔야 한다.

따라서 MVP 방향을 다음처럼 전환한다.

```text
완성 코스 여러 개 추천
-> 장소 후보를 보여주고, 사용자가 담으면 TimeFit이 남은 시간/체류 가능성을 계속 계산
```

이 방식에서 TimeFit의 역할은 "장소를 강제로 골라주는 앱"이 아니라 "사용자가 고른 장소가 남은 시간 안에 가능한지 판단하고 다음 선택을 돕는 앱"이다.

## 2. 핵심 개념

### 기존 방식

```text
입력
-> 후보 장소 수집
-> 앱이 1~2개 장소를 조합해 코스 생성
-> 완성 코스 10개 표시
-> 사용자가 코스 선택
```

### 변경 방식

```text
입력
-> 현재 위치 기준 장소 후보 표시
-> 사용자가 장소를 담음
-> 앱이 이동시간 + 체류 가능 시간 + 약속 도착 가능 여부 계산
-> 같은 후보 목록을 다시 보여주되, 각 장소의 추가 가능 시간을 갱신
-> 사용자가 원하는 만큼 담음
-> 시간 초과 또는 과도하게 빠듯한 경우 경고/차단
-> 코스 확정
```

## 3. 사용자 흐름

### 3.0 재검색 제거 원칙

장바구니형 코스 빌더로 전환하면 기존 실행 화면의 `다른 장소 찾아보기`는 제거한다.

이유:

```text
장바구니 자체가 장소를 담고 빼며 계속 시간 가능성을 다시 계산하는 구조다.
별도 재검색 버튼을 남기면 "새 추천을 받아야 하는가"와 "현재 바구니를 조정해야 하는가"가 혼동된다.
```

대신 다음 기능만 남긴다.

```text
장소 담기
장소 빼기
현재 시간으로 코스 조정
장소 건너뛰기
이 코스로 갈래요
```

실행 중에는 새 장소 후보를 만들지 않는다. 실행 중에는 현재 선택한 코스를 기준으로 체류 가능 시간과 다음 이동만 조정한다. 새 장소 선택은 장바구니 화면에서 처리한다.

### 3.1 초기 입력

사용자는 기존처럼 입력한다.

```text
현재 위치
약속 장소 또는 복귀 여부
남은 시간
이동수단
현재/테스트 시간
```

### 3.2 장소 후보 보기

앱은 완성 코스가 아니라 장소 단위 후보를 보여준다.

카드에 보여줄 정보:

```text
장소명
카테고리
데이터 근거
현재 위치에서 이동시간
이 장소를 담으면 확보 가능한 체류시간
약속 장소까지 도착 여유
상태 라벨
담기 버튼
```

상태 라벨:

| 라벨 | 의미 |
|---|---|
| 여유 있음 | 이동 후 권장 체류시간 이상 확보 가능 |
| 짧게 가능 | 권장 체류보다 짧지만 p25 또는 최소 체류 기준 이상 가능 |
| 빠듯함 | 체류 가능 시간이 매우 짧음. 선택은 가능하되 경고 표시 |
| 시간 초과 | 선택하면 약속/복귀 시간이 초과됨. 담기 차단 |

### 3.3 장소 담기

사용자가 장소를 담으면 코스 바구니에 들어간다.

```text
현재 위치 -> 담은 장소들 -> 약속 장소/복귀
```

앱은 즉시 다음 값을 다시 계산한다.

```text
총 이동시간
장소별 체류 가능 시간
전체 남은 여유시간
약속/복귀 도착 가능 여부
다음 후보를 담았을 때의 예상 체류 가능 시간
```

### 3.4 다음 장소 후보

하나를 담았다고 해서 후보를 숨기지 않는다. 전체 후보는 계속 보여주되, 각 후보 카드의 계산값만 바꾼다.

예:

```text
후보 A: 추가하면 42분 머물 수 있음
후보 B: 추가하면 18분만 가능, 빠듯함
후보 C: 추가하면 약속 7분 초과, 담기 불가
```

이 구조에서는 앱이 사용자의 선택권을 뺏지 않는다. 대신 선택했을 때의 시간 결과를 명확하게 보여준다.

### 3.5 코스 확정

사용자는 원하는 만큼 장소를 담을 수 있다. 단, 시간 초과 장소는 담기 차단한다.

확정 조건:

```text
담은 장소가 1개 이상
약속/복귀 시각 초과 없음
각 장소의 체류 가능 시간이 최소 기준 이상이거나, 사용자가 빠듯함을 인지하고 선택
```

MVP에서는 시간 초과만 강하게 차단하고, 빠듯함은 경고로 둔다.

## 4. 계산 방식

### 4.1 기본 시간 예산

```text
endMin = startMin + remainingMin
buffer = max(10분, remainingMin * 0.12)
usableBudget = remainingMin - buffer
```

장바구니 진행 중에는 다음처럼 계산한다.

```text
currentRoute = origin -> selectedSpots -> target
routeMoveMin = 각 구간 이동시간 합
availableStayMin = usableBudget - routeMoveMin
```

담은 장소가 여러 개인 경우, 체류시간은 장소별 권장 체류시간을 기준으로 배분한다.

초기 배분:

```text
각 장소 권장 체류시간 합 = recommendedStayTotal
장소별 체류 가능 시간 = availableStayMin * (장소 권장 체류시간 / recommendedStayTotal)
```

이후 사용자 경험에 따라 단순화할 수 있다.

```text
선택 순서대로 권장 체류시간을 먼저 배정
마지막 장소에 남은 체류시간 배정
```

MVP에서는 기존 `buildCourseLegs`의 `allocatedStay` 분배 방식을 재사용한다.

### 4.2 후보별 추가 가능 시간

후보 X를 추가한다고 가정한다.

```text
trialRoute = origin -> selectedSpots -> candidateX -> target
trialMoveMin = trialRoute 이동시간 합
trialStayPool = usableBudget - trialMoveMin
candidateStayMin = trialStayPool에서 candidateX에 배정 가능한 시간
```

결과 카드에는 candidateX의 단독 체류 시간이 아니라, "현재 장바구니에 이 후보를 추가했을 때 확보 가능한 체류시간"을 보여준다.

### 4.3 가능성 등급

장소별 체류시간은 AIHub 기반 권장 체류시간을 사용한다. 가능하면 단일 중앙값이 아니라 p25/median/p75를 사용한다.

| 등급 | 기준 |
|---|---|
| 여유 있음 | 체류 가능 시간 >= median |
| 짧게 가능 | p25 <= 체류 가능 시간 < median |
| 빠듯함 | 최소 체류 기준 <= 체류 가능 시간 < p25 |
| 시간 초과 | 체류 가능 시간 < 최소 체류 기준 또는 전체 시간이 음수 |

현재 데이터에서 p25를 바로 쓰기 어려운 경우, MVP는 다음 기준으로 시작한다.

```text
카페/상업지구: 최소 15분
자연관광지: 최소 18분
문화시설: 최소 20분
식당: 최소 25분
기타: 최소 20분
```

추후 `busan_poi_catalog`의 p25를 엔진에 연결한다.

## 5. 후보 노출 정책

중요 원칙:

```text
하나를 선택했다고 해서 후보를 숨기지 않는다.
전체 후보를 보여주되, 각 후보의 체류 가능 시간과 상태를 갱신한다.
```

단, 다음은 후보 데이터 단계에서 제외한다.

```text
숙박/병원/학원/부동산 등 추천 제외 장소
카카오 검증 not_found
현재 앱 데이터에서 명백한 bad_match
```

이미 담은 장소는 목록에서 숨기지 않고 `담김` 상태로 보여준다. 사용자가 어떤 장소를 선택했는지 확인하고 바로 제거할 수 있어야 하기 때문이다.

시간 초과 후보는 숨기지 않는 것을 기본으로 한다. 다만 `담기` 버튼을 비활성화하고 이유를 보여준다.

예:

```text
담기 불가 · 약속까지 12분 초과
```

## 6. 후보 소스

### 6.1 1차 후보

현재와 동일하게 TourAPI + AIHub/TourAPI 매칭 카탈로그를 사용한다.

```text
source = tourapi_aihub
체류시간 = AIHub 직접 매칭 또는 카테고리 fallback
신뢰도 = 높음
```

### 6.2 2차 후보

후보 수가 너무 적은 지역에서는 보강이 필요하다. 단, 이 문서의 1차 구현에서는 카카오 확장 후보를 바로 넣지 않는다.

추후 후보 확장 방향:

```text
source = kakao_category 또는 kakao_keyword
체류시간 = AIHub 유사 장소군 분포
카드 표시 = 확장 후보
```

확장 후보는 단순 근처 추천이 되지 않도록 반드시 TimeFit 시간 계산을 통과해야 한다.

## 7. UI 구조

### 7.1 후보 리스트 화면

기존 `ResultsScreen`을 코스 카드가 아니라 장소 카드 중심으로 변경한다.

상단:

```text
남은 시간
약속/복귀 목표
선택 이동수단
현재 장바구니 요약
```

장바구니 요약:

```text
담은 장소 N개
예상 이동 M분
체류 가능 S분
여유 B분
```

장소 카드:

```text
장소명
카테고리 / 출처
이 장소 추가 시:
  이동 +N분
  체류 가능 N분
  약속까지 여유 N분
상태 라벨
담기 / 제거
```

### 7.2 바구니 영역

화면 상단 또는 하단 고정 영역으로 제공한다.

```text
현재 위치 -> 장소 A -> 장소 B -> 약속 장소
```

기능:

```text
장소 제거
순서 변경(후속)
코스 확정
```

MVP에서는 순서 변경은 제외하고 담은 순서를 유지한다.

### 7.3 상세/실행 화면

코스를 확정하면 기존 `DetailScreen -> ExecutionScreen` 흐름을 재사용한다.

필요한 작업:

```text
장바구니 selectedSpots를 Course 형태로 변환
legs 생성
상세 지도/시간표 표시
이 코스로 갈래요
실행 화면
```

## 8. 구현 단계

### 1단계: 화면 단위 장바구니 평가

현재 구현은 엔진 타입을 크게 늘리지 않고 `ResultsScreen` 안에서 기존 추천 결과의 장소 후보를 재평가한다.

```text
기존 planner: 후보 수집, 운영시간 게이트, 이동수단별 이동시간 근사, 코스 후보 생성
ResultsScreen: 코스 후보에서 중복 장소를 뽑아 장소 후보 목록으로 변환
ResultsScreen: 사용자가 담은 장소 + 후보 1개를 가정해 이동/체류/여유를 재계산
ResultsScreen: 확정 시 selectedSpots를 Course 형태로 변환
```

### 2단계: UI 전환

기존 `ResultsScreen`을 장소 카드 중심의 장바구니 화면으로 대체한다.

```text
Home -> Results(코스 만들기)
Results -> Detail
Detail -> Execution
```

기존 자동 코스 결과 화면은 별도 fallback 화면으로 남기지 않는다. 같은 장소가 여러 조합으로 반복되어 보이는 문제가 컸기 때문에, 사용자가 직접 장소를 담는 흐름을 기본 UX로 둔다.

### 3단계: 엔진 분리

현재는 장바구니 계산이 화면에 들어가 있다. 장바구니형이 안정화되면 테스트 가능한 순수 함수로 분리한다.

가능한 방향:

```text
evaluateBasketCandidate(input, selectedSpots, candidate)
buildCourseFromBasket(input, selectedSpots)
allocateStayMinutes(selectedSpots, availableStayMin)
```

### 4단계: 후보 확장

서면/부산역/해운대/사상 등 후보 부족 지역에서 카카오 후보 확장을 추가한다.

조건:

```text
1차 후보가 5개 미만
또는 good/short 후보가 3개 미만
```

확장 키워드:

```text
카페
베이커리
서점
소품샵
쇼핑몰
지하상가
전시
갤러리
산책
```

## 9. 공모전 관점 장점

이 방식은 단순 추천앱과 차별화된다.

일반 추천앱:

```text
근처 인기 장소를 보여준다.
```

TimeFit:

```text
사용자가 고른 장소 조합이 남은 시간 안에 가능한지 계속 계산한다.
AIHub 체류시간과 이동시간 API를 이용해 장소별 체류 가능성을 판단한다.
약속/복귀 시각을 초과하지 않도록 코스 구성을 돕는다.
```

즉, 핵심 가치는 "추천"보다 "자투리 시간 안에서 선택 가능한 코스 구성 보조"다.

## 10. 미해결 질문

1. 시간 초과 후보를 리스트 하단에 계속 보여줄지, 접힌 영역으로 보낼지 결정 필요
2. 빠듯함 후보를 사용자가 담을 때 확인 모달을 띄울지 결정 필요
3. 담은 장소 순서 변경을 MVP에 넣을지 후속으로 미룰지 결정 필요
4. 기존 자동 코스 10개 추천을 완전히 대체할지, 보조 기능으로 남길지 결정 필요
5. 카카오 확장 후보를 언제 도입할지 결정 필요
