# TimeFit 추천 엔진 현행 정책 정합성 감사 프롬프트

> 대상 역할: **추천 엔진 세션**
>
> 목적: 최신 장소 카탈로그(368개)가 현행 1~3곳 대표 코스 정책에 실제로 적용되는지 확인하고, 구현 완료·부분 구현·미구현을 증거 기반으로 판정한다.
>
> 이번 턴의 범위: **감사와 재현만 수행한다.** 정책·UI·데이터를 바꾸지 않으며, 발견한 구현 결함을 즉시 고치지 않는다.

## 1. 먼저 읽을 파일

1. 루트 `AGENTS.md`, `docs/README.md`
2. `docs/03_product/추천로직.md`의 1.0.2~1.6
3. `docs/테스트.md`의 `REC-01`, `REC-17~24`, `COURSE-01~03`, `COURSE-08~10`
4. `src/data/busan_poi_catalog.json`
5. `src/engine/data.ts`, `src/engine/types.ts`, `src/engine/planner.ts`, `src/engine/mixedTravel.ts`, `src/engine/oneStopRouteService.ts`, `src/engine/routeBaselineService.ts`
6. 관련 순수 엔진 테스트와 `test/evidence-profile-classification.test.mjs`

## 2. 최신 장소 카탈로그 확인

현재 런타임 카탈로그의 기대값은 아래다.

```text
총 368개
representative_core 28개
representative_standard 162개
conditional_more 178개
hold 0개(런타임 미포함)
```

아래를 코드 경로와 고정 fixture로 확인한다.

1. `src/engine/data.ts`가 실제로 위 최신 카탈로그를 읽는지
2. 대표 코스 기본 후보가 `representative_core / representative_standard`만 사용하는지
3. `conditional_more`가 대표·자동 확정에 섞이지 않고 더보기/사용자 명시 확인 뒤 조건부 수동 포함 경로로만 가는지
4. 과거 호환 필드 `shortStay.selectionStatus = approved/conditional`가 현행 `classification` 규칙을 우회시키지 않는지
5. `hold`·중복·권역 내부 장소가 런타임 추천 입력으로 다시 들어오지 않는지

## 3. 현행 추천 정책 감사 항목

각 항목을 `구현됨 / 부분 구현 / 미구현 / 정책과 충돌` 중 하나로 판정한다. 파일·함수·테스트명·고정 입력·관찰 결과를 반드시 붙인다.

| 항목 | 현행 기대 결과 |
| --- | --- |
| 시간 입력 | 현재 시각부터 1~180분, 자정 경계 포함 |
| 대표 결과 | 첫 결과는 대표 코스 정확히 1개이며 1~3곳을 엔진이 순서까지 조립 |
| 코스 크기 | 1·2·3곳을 모두 비교하되 3곳 강제 없음 |
| 도착 형태 | 출발지 복귀와 별도 도착지를 전체 일정에 반영 |
| 이동수단 | 차량은 후보·공간 탐색·순위·대표 결과에 사용하지 않음. 도보·대중교통을 자동 조합 |
| 실제 경로 | 대표·새 추천·상세·코스 확인은 동일한 실제 구간시간만 표시. 실패/근사 폴백은 추천으로 표시하지 않음 |
| 운영시간 | 구조화 운영시간으로 각 장소의 도착~체류 종료 전체를 판정 |
| 조건부 후보 | 대표 제외, 더보기 `운영시간 확인 필요`, 사용자 확인 뒤에도 조건부 상태 유지·재계산 |
| 대안 | 서로 다른 유효 코스만 새 추천으로 사용. 1개면 새 추천 없음 상태 반환 |
| 발견성 | 완료 기록 없는 지역·활동은 하드 조건 동률에서만 보조 순위. GPS 방문·소비·인기도 추정 금지 |
| 관계 중복 | 같은 `siteGroupId`, 권역/내부 장소, 동일 장소 반복은 코스에서 제외 |

## 4. 최소 재현 시나리오

외부 API를 새로 반복 호출하지 않는다. 기존 실제 경로 fixture와 mock/고정 adapter를 사용한다.

1. 45분 왕복: 1곳만 가능한 정상 결과
2. 90분 별도 도착지: 1~2곳과 도착 여유 검증
3. 180분: 1·2·3곳 전체 비교, 대표 1개·대안 존재 검증
4. 조건부 후보만 존재: 대표 0개, 더보기 상태 검증
5. 대표 코스 1개뿐: `no_alternative_verified_course` 반환 검증
6. 차량만 빠른 후보·실경로 실패·운영시간 종료 직전: 대표 제외 검증
7. 완료 기록 유무만 다른 동점 후보: 발견성만 바뀌고 하드 조건은 유지되는지 검증

## 5. 최종 보고 형식

최종 응답에 아래 네 항목을 포함한다.

1. **완성도 결론:** 정책 기준으로 구현됨/부분 구현/미구현 수와 출시 테스트 전 필요한 구현 범위
2. **카탈로그 적용 결론:** 368개가 어느 후보 경로까지 실제 쓰이는지, 조건부·hold 누출 여부
3. **정책 충돌 목록:** 차량, 최대 코스 수, 자유 장바구니, 근사 시간 표시 등 발견한 이전 정책 흔적과 영향
4. **다음 구현 순서:** 가장 작은 안전한 변경 단위와 먼저 실패시킬 순수 테스트. 이 감사 턴에서는 코드를 수정하지 않는다.

정책 문서와 코드가 다르면 코드 동작을 현행 정책으로 승격하지 않는다. 정책 문서가 단일 기준이며, 충돌은 통합·결정 세션에 인계한다.
