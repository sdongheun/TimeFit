# TimeFit 데이터베이스 설계와 마이그레이션 정책

> 상태: 핵심 스키마·RLS 마이그레이션 작성 완료. 이 문서는 로그인·저장·후기·개인화 기능을 위한 DB 계약의 단일 기준이다.
>
> 기준일: 2026-08-11. 실제 SQL은 `supabase/migrations/`에 추가했으며, 원격 적용 전에는 빈 DB와 기존 DB 모두에서 검증한다.

## 1. 목적과 범위

TimeFit은 로그인 사용자의 코스·후기·행동 데이터를 저장해 개인화 추천을 개선한다. 비로그인 사용자는 실제 현재 시각부터 약속 시각까지의 일회성 추천만 체험할 수 있으며, 이때 개인 행동 데이터는 서버에 저장하지 않는다. 추천 장소 카탈로그는 정제 완료 전까지 앱 JSON을 유지하고, 이번 DB 범위에는 포함하지 않는다.

- 인증: Supabase Auth 이메일·비밀번호 로그인
- 저장: 사용자가 삭제할 때까지 코스, 방문 순서, 구간별 이동·체류 추정값 보관
- 개인화: 연령대, 카테고리·장소 선택, 이동수단, 시간대, 후기 만족도를 추천 순위 보정에 사용
- 분석: 사용자와 연결된 원본 행동 로그는 계정 삭제 시 함께 삭제
- 확장: 동일 구조로 부산 외 지역의 장소 카탈로그와 추천 데이터를 추가할 수 있게 설계

게시물·공개 프로필·닉네임·사진 업로드는 현재 범위에서 제외한다.

| 계정 삭제 | 계정과 연결된 모든 원본 데이터 삭제. 개인 식별 불가능한 집계 통계만 별도 유지 가능 |

## 3. 개인정보와 위치정보 원칙

### 3.1 수집 최소화

- 출발 위치·다음 일정 장소 좌표는 사용자가 코스를 저장할 때만 코스에 저장한다.
- 비로그인 체험에서 사용한 현재 위치·약속 장소·추천 결과·행동은 앱 세션을 벗어나 저장하지 않는다.
- GPS 이동 이력, 실제 이동 경로, 기기 광고 ID는 저장하지 않는다.
- 추천 후보 조회에 쓴 현재 위치는 서버 행동 로그에 원본 좌표로 저장하지 않는다.
- 연령 분석에는 정확한 생년월일이나 출생연도 대신 계산된 `age_band`만 사용한다.
- 자유 의견은 개인화 점수의 보조 근거일 뿐, 외부에 공개하거나 익명 통계에 포함하지 않는다.

### 3.2 계정 삭제

계정 삭제는 클라이언트가 직접 Auth를 삭제하지 않는다. 인증된 사용자의 요청을 받은 서버 측 Edge Function이 다음을 하나의 처리 단위로 수행한다.

1. 사용자의 코스·장소·구간·후기·원본 행동 로그를 삭제한다.
2. 프로필을 삭제한다.
3. Supabase Auth 사용자를 삭제한다.
4. 예약된 로컬·서버 알림을 취소한다.

외래키의 `ON DELETE CASCADE`는 데이터베이스 삭제 전파를 보조한다. 서비스 역할 키는 Edge Function 환경 변수에만 두고 앱에는 절대 넣지 않는다.

### 3.3 익명 집계

계정 삭제 후에도 추천 품질을 위해 통계를 유지하려면, 사용자별 행을 남기지 않고 아래와 같이 집계된 값만 유지한다.

```text
age_band=30s / place_content_id=12345 / time_bucket=afternoon / saved_count=47
```

- `user_id`, 원본 생년월일·출생연도, 정확 좌표, 자유 의견, 분 단위 시각은 집계 테이블에 넣지 않는다.
- 소수 표본 조합은 상위 지역·카테고리로 합치거나 표시·활용하지 않는다.
- 익명화 요건을 충족하는지와 보유 기간은 배포 전 개인정보 처리방침 및 법률 검토로 확정한다.

## 4. 논리 데이터 모델

### 4.1 계정과 프로필

#### `profiles`

| 컬럼 | 설명 |
| --- | --- |
| `id` | `auth.users.id`와 같은 UUID, 기본키 |
| `birth_year` | 가입 시 생년월일 입력에서 파생한 연도 |
| `age_band` | `under_20`, `20s`, `30s`, `40s`, `50_plus` 등 추천용 구간 |
| `email_verified_at` | 인증 완료 시각 |
| `terms_agreed_at` | 이용약관 동의 시각 |
| `privacy_agreed_at` | 개인정보·개인화 데이터 이용 동의 시각 |
| `created_at`, `updated_at` | 생성·수정 시각 |

이메일과 비밀번호는 Supabase Auth가 관리한다. `profiles`에 비밀번호·이메일 원문을 중복 저장하지 않는다.

### 4.2 저장 코스

#### `courses`

코스 전체의 스냅샷과 상태를 보관한다.

| 컬럼 | 설명 |
| --- | --- |
| `id`, `user_id` | 코스 ID와 소유자 |
| `status` | `saved`, `in_progress`, `completed`, `cancelled`, `replanned` |
| `derived_from_course_id` | 진행 중 남은 코스를 다시 짤 때 원본 코스를 가리키는 선택 참조 |
| `origin_label`, `origin_lat`, `origin_lon` | 저장 당시 출발지 |
| `destination_label`, `destination_lat`, `destination_lon` | 다음 일정 장소. 왕복 코스면 `NULL` |
| `starts_at`, `ends_at` | 사용자 입력 기준 시작·종료 시각 |
| `mode` | `walk`, `transit`, `car` |
| `total_move_min`, `total_dwell_min`, `buffer_min` | 확정 당시 시간 요약 |
| `recommendation_snapshot` | 추천 근거·점수·전략 등 재현용 JSON 스냅샷 |
| `current_stop_order` | 진행 중 다음으로 이동할 장소 순서. 시작 전·완료 후에는 `NULL` |
| `last_recalculated_at` | 앱 복귀·다음 구간 이동 시 남은 코스를 마지막으로 재계산한 시각 |
| `created_at`, `updated_at`, `completed_at` | 생명주기 시각 |

#### `course_stops`

한 코스에 담긴 장소와 방문 순서를 저장한다.

| 컬럼 | 설명 |
| --- | --- |
| `id`, `course_id`, `stop_order` | 장소 ID, 코스 참조, 방문 순서 |
| `place_content_id` | TourAPI contentId. 외부 데이터가 아닌 장소는 출처와 ID를 함께 저장할 수 있도록 확장 |
| `place_source` | `timefit_catalog`, `tourapi` 등 장소 ID의 출처 |
| `title`, `category`, `sub_category` | 생성 당시 장소 표시 정보 스냅샷 |
| `lat`, `lon` | 해당 장소 좌표 |
| `planned_dwell_min`, `dwell_source` | 체류시간과 AIHub 개별/카테고리 폴백 근거 |
| `kakao_place_url` | 사용자가 확인할 카카오맵 상세 링크 |
| `visit_status` | `pending`, `visited`, `skipped`. 진행 중 남은 코스 재계산에 사용 |

#### `course_legs`

출발지·장소·다음 일정 사이의 구간 계산 결과를 저장한다.

| 컬럼 | 설명 |
| --- | --- |
| `id`, `course_id`, `leg_order` | 구간 ID와 순서 |
| `from_kind`, `to_kind` | `origin`, `stop`, `destination` 구분 |
| `mode`, `move_min`, `distance_m` | 이동수단과 계산값 |
| `source` | `TMAP`, `ODsay`, `haversine`, `walk_short` 등 시간 근거 |
| `route_summary` | 환승 요약 등 표시가 필요한 최소 경로 정보 |

지도 폴리라인·사용자의 실제 GPS 이동 이력은 저장하지 않는다.

### 4.3 진행 중 코스와 재계획

코스 시작 전의 장소 삭제·교체·순서 변경은 같은 저장 코스를 수정하고, 이동·체류·약속 도착 가능성을 즉시 다시 계산한다.

코스가 `in_progress` 상태가 된 뒤에는 아래 규칙을 따른다.

1. `다음 장소로 이동`을 누르거나 외부 카카오맵에서 앱으로 복귀하면 현재 시각과 권한이 허용된 현재 위치를 다시 읽는다.
2. 방문한 장소는 `visited`, 건너뛴 장소는 `skipped`, 아직 갈 장소는 `pending`으로 기록한다.
3. `현재 위치 -> pending 장소들 -> 약속 장소`를 다시 계산해 충분·빠듯·불가능 상태를 판단한다.
4. 충분하면 다음 구간을 계속 안내한다. 빠듯하면 체류시간 축소 예상값과 `계속 이동`, `장소 건너뛰기`, `남은 코스 다시 짜기`를 제시한다.
5. 약속 지연 가능성이 있으면 약속 장소 직행을 최우선으로 제시하고 남은 장소를 건너뛴다.
6. 사용자가 남은 장소를 교체하면 원본 진행 코스는 `replanned` 또는 `cancelled`로 끝내고, 현재 위치·남은 시간·약속 시각을 기준으로 새 코스를 만든다. 새 코스의 `derived_from_course_id`로 관계를 남긴다.

완료된 코스의 `다시 사용`은 과거 코스를 수정하지 않고 새 초안을 복제한 뒤, 새 시각·위치 기준으로 재계산한다. 앱이 종료되거나 외부 지도에서 돌아와도 `current_stop_order`, 장소 상태, 마지막 재계산 시각으로 진행 상태를 복원한다.

### 4.4 후기와 행동 로그

#### `course_feedback`

| 컬럼 | 설명 |
| --- | --- |
| `id`, `course_id`, `user_id` | 후기 ID와 소유 관계 |
| `rating` | 코스 전체 별점 1~5, 필수 |
| `comment` | 자유 의견, 선택 |
| `created_at` | 작성 시각 |

코스 하나에는 후기 하나만 허용한다. 장소별 별점·재방문 의향은 데이터 수집 필요성이 확정되기 전까지 추가하지 않는다.

#### `recommendation_events`

개인화 모델과 품질 분석에 쓰는 원본 이벤트다. 모든 행은 `user_id`와 연결되며 계정 삭제 시 제거한다.

| 컬럼 | 설명 |
| --- | --- |
| `id`, `user_id`, `created_at` | 이벤트 식별자·사용자·시각 |
| `event_type` | `recommendation_viewed`, `place_opened`, `basket_added`, `basket_removed`, `course_saved`, `course_edited`, `navigation_started`, `course_completed`, `feedback_submitted` |
| `course_id`, `place_content_id` | 관련 코스·장소. 해당하지 않으면 `NULL` |
| `mode`, `time_bucket`, `category` | 개인화·집계용 최소 맥락 |
| `metadata` | 버전·추천 근거 등 비식별 디버그 정보. 좌표·자유 의견·원본 생년월일 금지 |

## 5. 권한과 RLS

기본 원칙은 "사용자는 자신의 행만 읽고 쓴다"이다.

| 테이블 | 읽기 | 쓰기 | 삭제 |
| --- | --- | --- |
| `profiles` | 본인 | 본인(허용 컬럼만) | 계정 삭제 Edge Function |
| `courses` | 본인 | 본인 | 본인 또는 계정 삭제 |
| `course_stops`, `course_legs` | 코스 소유자 | 코스 소유자 | 코스 소유자 또는 cascade |
| `course_feedback` | 본인 | 본인 | 본인 또는 cascade |
| `recommendation_events` | 클라이언트 직접 조회 금지 | 본인 이벤트만 삽입 | 계정 삭제 또는 서버 |
| `analytics_aggregates` | 클라이언트 접근 금지 | 서버 집계 작업만 | 보존 정책에 따름 |

RLS는 모든 공개 스키마 테이블에서 활성화한다. 추천 통계 집계·계정 삭제·외부 API 프록시는 Edge Function만 수행한다.

## 6. 마이그레이션 방식

### 결론

**SQL 마이그레이션 방식으로 관리한다.** Supabase Dashboard에서 운영 DB를 수동 수정하는 방식은 사용하지 않는다.

이유는 다음과 같다.

- 스키마·RLS·함수·인덱스 변경 이력이 Git에 남아 심사·협업·복구가 가능하다.
- 개발·테스트·운영 환경에 같은 변경을 재현할 수 있다.
- 앱 코드 변경과 DB 계약 변경을 같은 커밋에서 검토할 수 있다.
- 계정 삭제, RLS처럼 실수 위험이 큰 보안 정책을 코드 리뷰와 테스트 대상으로 만들 수 있다.

### 디렉터리와 규칙

```text
supabase/
  migrations/
    202608090001_init_extensions_and_types.sql
    202608090002_create_profiles.sql
    202608090003_create_courses.sql
    202608090004_create_feedback_and_events.sql
    202608090005_enable_rls_and_policies.sql
    202608090006_account_deletion_function.sql
  seed.sql                 # 개발·E2E 전용 샘플 데이터
  functions/
    delete-account/        # service_role 사용 Edge Function
```

- 적용된 마이그레이션 파일은 수정하지 않는다. 변경이 필요하면 새 파일을 추가한다.
- 하나의 마이그레이션은 하나의 의도를 가진다. 테이블 생성, RLS 추가, 데이터 이관을 무분별하게 섞지 않는다.
- 파괴적 변경은 `추가 → 앱 이관 → 기존 컬럼 제거` 순서로 최소 두 단계에 나눈다.
- `seed.sql`에는 실제 사용자·API 키·실제 위치를 넣지 않는다.
- 배포 전에는 빈 DB에서 전체 마이그레이션을 적용하고, 업그레이드 DB에서도 적용해 둘 다 검증한다.

### 환경 변수

- 앱: `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_KEY`만 사용한다. publishable/anon 키는 RLS가 전제다.
- 서버: `SUPABASE_SERVICE_ROLE_KEY`는 Edge Function 배포 환경에만 둔다.
- TourAPI·TMAP·ODsay 등 호출량·비밀 보호가 필요한 키는 이후 Edge Function 프록시로 옮긴다.

## 7. 구현 순서

1. Supabase CLI 초기화와 프로젝트 연결, 로컬·원격 마이그레이션 운영 방식 확정
2. 비로그인 일회성 체험과 로그인 후 미래 시간 계획의 입력 제약을 분리하고, `profiles`와 이메일 인증, 만 14세 이상 가입 검증 구현
3. `courses`, `course_stops`, `course_legs`와 RLS 구현
4. 앱의 메모리 저장소를 `CourseRepository`로 분리하고 Supabase 저장·복원, 진행 장소 상태·재계획 연결
5. `course_feedback`, `recommendation_events` 추가
6. 계정 삭제 Edge Function, cascade·RLS·삭제 E2E 검증
7. 충분한 표본이 쌓인 뒤 익명 집계와 연령대·상황별 추천 보정 추가

## 8. 아직 결정할 사항

- 연령대 구간과 생년월일 입력 검증을 어느 컴포넌트에서 수행할지
- 이메일 인증 전 사용 범위와 인증 메일 딥링크 처리
- 개인화 동의를 서비스 필수 약관으로 둘지, 추천 품질 저하를 감수하고 선택 동의로 둘지
- 익명 집계의 최소 표본 수, 보유 기간, 재식별 방지 기준
- 코스 수정 시 기존 코스 버전을 남길지, 현재 값으로 덮어쓸지
- Supabase Edge Function으로 외부 경로 API 프록시를 옮기는 시점
