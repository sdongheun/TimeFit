## 1. 목적과 범위

TimeFit은 로그인 사용자의 명시적 계정 기록과 별도 동의한 사용자 확인 체류 표본만 저장해 개인화 추천을 개선한다. 비로그인 사용자는 실제 현재 시각부터 약속 시각까지의 일회성 추천만 체험할 수 있으며, 개인 행동 데이터는 서버에 저장하지 않는다. 단, Route Proxy 접근 제어를 위해서만 Supabase Auth의 익명 계정과 세션을 자동 생성·유지할 수 있다. 익명 계정에는 profile·코스·후기·이벤트·추천 이력·위치·검색어를 연결하거나 저장하지 않는다. 추천 장소 카탈로그는 앱 JSON을 유지하고 이번 DB 범위에는 포함하지 않는다.

- 인증: Supabase Auth 이메일·비밀번호 로그인
- 저장: 사용자가 삭제할 때까지 코스, 방문 순서, 구간별 이동·체류 추정값 보관
- 개인화: 사용자가 별도 동의하고 명시적으로 완료한 신규 account 체류 표본만 선택적으로 사용
- 분석: 사용자와 연결된 원본 행동 로그는 계정 삭제 시 함께 삭제
- 확장: 동일 구조로 부산 외 지역의 장소 카탈로그와 추천 데이터를 추가할 수 있게 설계

게시물·공개 프로필·사진 업로드는 현재 범위에서 제외한다. 닉네임은 비공개 계정 profile의 선택 필드다.

## 3. 개인정보와 위치정보 원칙

### 3.1 수집 최소화

- 출발 위치·다음 일정 장소 좌표는 사용자가 코스를 저장할 때만 코스에 저장한다.
- 비로그인 체험에서 사용한 현재 위치·약속 장소·추천 결과·행동은 앱 세션을 벗어나 저장하지 않는다.
- GPS 이동 이력, 실제 이동 경로, 기기 광고 ID는 저장하지 않는다.
- 추천 후보 조회에 쓴 현재 위치는 서버 행동 로그에 원본 좌표로 저장하지 않는다.
- 비로그인 Route Proxy 접근의 익명 Auth 계정은 authorization 전용이다. Auth의 `last_sign_in_at`(없으면 생성 시각)만 30일 미사용 정리 후보 판단에 쓰며, 추천 요청·GPS·검색어로 별도 활동 로그를 만들거나 갱신하지 않는다.
- 나이·생년월일·`birth_year`·`age_band`는 신규 가입에서 수집하지 않는다. 후속 migration은 기존 profile 값과 Auth metadata 값을 `NULL`/제거 대상으로 삼되 원격 적용 전 대상 건수·백업·복구 절차를 별도 승인받는다.
- 자유 의견은 개인화 점수의 보조 근거일 뿐, 외부에 공개하거나 익명 통계에 포함하지 않는다.

### 3.3 익명 Auth 접근 세션의 최소 보관과 자동 정리

**현행 정책 (SEC-RP-01-R / DB-PRIV-01):** 로그인 없는 Route Proxy 호출은 익명 Supabase Auth JWT로만 보호할 수 있다. 익명 계정은 개인정보로 취급하며, 마지막 Auth 인증·세션 갱신 시각부터 30일이 지난 뒤에도 anonymous이고 사용자 소유 public 행이 전혀 없을 때만 서버 정리 작업이 삭제 후보로 삼는다. 이메일·소셜 등 영구 identity를 연결한 계정, 일반 로그인 계정, 최근 세션, profile·코스·후기·이벤트 연결 계정은 자동 삭제하지 않는다.

- 삭제 후보 조회·재검증·집계 감사는 service role 전용 DB RPC를 거친다. 실제 `auth.users` Admin 삭제는 일 1회 이하의 Edge Function scheduler가 후보별 재검증 뒤 한 번만 수행한다. 클라이언트와 일반 Route Proxy 요청은 삭제를 시작할 수 없다.
- 감사는 날짜별 후보·삭제·건너뜀·실패 **개수**와 코드화한 사유만 보관한다. 대상 ID, 개별 시각, IP, 좌표, 검색어, 코스·추천 원문은 감사·진단에 넣지 않는다.
- 배포 전 개인정보 처리방침에는 익명 접근 세션의 목적, 30일 보유 기간, 자동 파기, 로그인 전환 계정 제외를 반영한다.

**변경 이력:** 이전에는 “비로그인 체험의 개인 행동 데이터는 서버에 저장하지 않는다”만으로 충분하다고 보았다. Route Proxy 무인증 endpoint를 피하기 위한 자동 익명 Auth가 추가되면서, 익명 계정 자체의 보관·삭제 기준이 빠지는 문제가 확인됐다. 개인화·위치 데이터를 추가 저장하는 대신 Auth authorization만 최소 예외로 허용하고, 30일·현재 anonymous·연결 데이터 부재의 세 조건과 service-role scheduler를 적용했다. 상태는 **현행**이며, 실제 scheduler 배포는 API-4-A-R2 소유다.

### 3.4 Route Proxy 공개 구간 예산

**현행 정책 (DB-RP-3):** Route Proxy의 공개 POI 구간 cache/lease와 분리해, provider·수단·일자 및 provider·수단·일자·초 단위 버킷으로 호출량을 저장한다. 현재 Kakao `walk`와 `transit`은 같은 provider여도 독립적인 daily soft/hard 및 per-second 한도를 쓴다. service role만 `route_proxy_read_budget(provider, mode, date_bucket)`과 `route_proxy_reserve_budget(provider, mode, date_bucket, second_bucket, soft_limit, hard_limit, per_second_limit)`을 호출할 수 있다.

- reserve는 provider/mode/day advisory lock 안에서 실행한다. hard 도달은 `daily_limit`, soft 도달은 `soft_limit`, 초당 도달은 `rate_limit`으로 거절하며 cache hit는 예산을 증가시키지 않는다.
- 기존 provider-only 사용량은 수단을 복원할 수 없으므로 삭제·0 초기화·임의 귀속하지 않는다. migration에서 같은 used 값을 `walk`와 `transit` 양쪽에 보수적으로 복제해 어느 수단도 과거 사용량보다 더 많이 허용되지 않게 한다.
- cache/lease/budget에는 user ID, anonymous JWT, IP, GPS 좌표, 검색어, provider 원문, API key를 저장하거나 RPC 인자로 받지 않는다.

**변경 이력:** 이전 provider-only budget은 Kakao 도보와 대중교통을 하나의 사용량으로 합쳐 각 API의 수단별 quota/soft limit을 표현하지 못했다. mode를 논리 키에 추가하고 과거 사용량을 양 수단에 보수 이관했다. 상태는 **현행**이며 handler의 mode별 환경 설정·RPC 소비는 API-4-A-ACT-02-K-R 소유다.

### 3.2 계정 삭제

계정 삭제는 클라이언트가 직접 Auth를 삭제하지 않는다. Edge Function은 Auth 서버가 검증한 user와 서명 검증된 JWT `amr`의 최신 `method=password` 시각이 서버 현재 시각 기준 600초 이내인지 확인한다. JWT `iat`, token refresh, client boolean, body의 user ID는 재인증·삭제 대상 근거로 쓰지 않는다. 이후 다음 단계를 순차 수행한다.

1. 사용자의 코스·장소·구간·후기·원본 행동 로그를 삭제한다.
2. 프로필을 삭제한다.
3. Supabase Auth 사용자를 삭제한다.
4. 삭제 뒤 user-linked DB 행이 0인지 확인하고 `localCleanupRequired`를 반환한다.

외래키의 `ON DELETE CASCADE`는 데이터베이스 삭제 전파를 보조한다. 서버 삭제 성공과 기기 로컬 정리는 하나의 transaction이 아니므로 guest/legacy 원본은 자동 삭제하지 않고, 삭제한 account namespace·pending·progress만 UI consumer가 재시도 가능하게 정리한다. Auth 삭제 성공 뒤 응답 유실은 같은 access token으로 최종 성공을 다시 증명할 수 없으므로 출시 전 UI는 이를 `local_cleanup_pending`과 구분한 복구 상태로 처리해야 한다. 서비스 역할 키는 Edge Function 환경 변수에만 둔다.

### 3.3 익명 집계

계정 삭제 후에도 추천 품질을 위해 통계를 유지하려면, 사용자별 행을 남기지 않고 아래와 같이 집계된 값만 유지한다.

```text
age_band=30s / place_content_id=12345 / time_bucket=afternoon / saved_count=47
```

- `user_id`, 원본 생년월일·출생연도, 정확 좌표, 자유 의견, 분 단위 시각은 집계 테이블에 넣지 않는다.
- 소수 표본 조합은 상위 지역·카테고리로 합치거나 표시·활용하지 않는다.
- 익명화 요건을 충족하는지와 보유 기간은 배포 전 개인정보 처리방침 및 법률 검토로 확정한다.

### 4.1 계정과 프로필

| `nickname`, `nickname_updated_at` | 선택 닉네임과 서버 갱신 시각 |
| `created_at`, `updated_at` | 생성·수정 시각 |

이메일과 비밀번호는 Supabase Auth가 관리한다. `profiles`에 비밀번호·이메일 원문을 중복 저장하지 않는다.

필수 가입 동의는 service-role 관리 `signup_consent_documents`의 활성 exact 문서와 `account_consent_records`의 서버 `accepted_at`으로 분리한다. 승인된 실제 공개 URL/version이 registry에 없으면 production 가입은 닫힌다. 선택 체류 동의는 이 가입 동의와 결합하지 않는다.

### 4.2 저장 코스

#### `courses`

| 컬럼 | 설명 |
| --- | --- |

| `origin_label`, `origin_lat`, `origin_lon` | 현재 유효 계획의 출발지. 진행 중 변경 때 현재 위치로 갱신된다 |

### 4.3 진행 중 코스와 재계획

코스 시작 전의 장소 삭제·교체·순서 변경은 같은 저장 코스를 수정하고, 이동·체류·약속 도착 가능성을 즉시 다시 계산한다.

코스가 `in_progress` 상태가 된 뒤에는 아래 규칙을 따른다.

1. 사용자가 진행 화면의 `코스 변경`을 누르면 권한이 허용된 현재 위치와 실제 현재 시각을 읽는다.
2. 약속 장소와 `ends_at`은 고정한 채 `현재 위치 -> 새 장소들 -> 약속 장소`를 다시 계산한다.
3. 사용자는 후보를 새로 담아 변경을 확정하거나, 시간 부족 시 약속 장소로 바로 이동한다.
4. 변경 확정 시 같은 `courses.id`를 `in_progress` 상태로 유지하며 현재 출발지·시간 요약·스냅샷을 갱신한다. `starts_at`, `ends_at`은 변경하지 않고 `last_recalculated_at`만 현재 시각으로 갱신한다.
5. 현재 단계에서는 최초 계획·교체 전 장소의 이력을 별도 저장하지 않는다. `course_stops`, `course_legs`는 새 현재 계획으로 원자적으로 교체한다. 실제 방문·체류 기록 수집은 Live Activity·위치 보조 기능을 도입할 때 추가한다.

완료된 코스의 `다시 사용`은 과거 코스를 수정하지 않고 새 초안을 복제한 뒤, 새 시각·위치 기준으로 재계산한다. 앱이 종료되거나 외부 지도에서 돌아와도 `current_stop_order`, 장소 상태, 마지막 재계산 시각으로 진행 상태를 복원한다.

## 5. 권한과 RLS

기본 원칙은 "사용자는 자신의 행만 읽고 쓴다"이다.

| 테이블 | 읽기 | 쓰기 | 삭제 |
| --- | --- | --- |
| `profiles` | 본인 | 본인(허용 컬럼만) | 계정 삭제 Edge Function |
| `courses` | 본인 | 본인 | 본인 또는 계정 삭제 |
| `course_stops`, `course_legs` | 코스 소유자 | 코스 소유자 | 코스 소유자 또는 cascade |
| `course_feedback` | 본인 | 본인 | 본인 또는 cascade |
| `recommendation_events` | 클라이언트 직접 조회 금지 | 본인 이벤트만 삽입 | 계정 삭제 또는 서버 |
| `analytics_aggregates` | 클라이언트 접근 금지 | 서버 집계 작업만 | 보존 정책에 따름 |

RLS는 모든 공개 스키마 테이블에서 활성화한다. 추천 통계 집계·계정 삭제·외부 API 프록시는 Edge Function만 수행한다.

RLS 정책만으로는 앱 접근이 가능하지 않다. `authenticated` 역할에는 `profiles`, `courses`, `course_stops`, `course_legs`, `course_feedback`의 필요한 PostgreSQL 테이블 권한을 부여하고, 그 위에서 RLS가 본인 행만 허용한다. `recommendation_events`는 앱에서 삽입만 허용한다.

## 6. 마이그레이션 방식

### 결론

**SQL 마이그레이션 방식으로 관리한다.** Supabase Dashboard에서 운영 DB를 수동 수정하는 방식은 사용하지 않는다.

이유는 다음과 같다.

- 스키마·RLS·함수·인덱스 변경 이력이 Git에 남아 심사·협업·복구가 가능하다.
- 개발·테스트·운영 환경에 같은 변경을 재현할 수 있다.
- 앱 코드 변경과 DB 계약 변경을 같은 커밋에서 검토할 수 있다.
- 계정 삭제, RLS처럼 실수 위험이 큰 보안 정책을 코드 리뷰와 테스트 대상으로 만들 수 있다.

### 디렉터리와 규칙

```text
supabase/
  migrations/
    202608110001_init_extensions_and_types.sql
    202608110002_create_profiles.sql
    202608110003_create_courses.sql
    202608110004_create_feedback_and_events.sql
    202608110005_enable_rls_and_policies.sql
    202608110006_account_deletion_function.sql
    202608110007_course_repository_grants.sql
    202608130008_course_graph_write_policies.sql
    202608150009_replace_course_plan.sql
  seed.sql                 # 개발·E2E 전용 샘플 데이터
  functions/
    delete-account/        # service_role 사용 Edge Function
```

- 적용된 마이그레이션 파일은 수정하지 않는다. 변경이 필요하면 새 파일을 추가한다.
- 하나의 마이그레이션은 하나의 의도를 가진다. 테이블 생성, RLS 추가, 데이터 이관을 무분별하게 섞지 않는다.
- 파괴적 변경은 `추가 → 앱 이관 → 기존 컬럼 제거` 순서로 최소 두 단계에 나눈다.
- `seed.sql`에는 실제 사용자·API 키·실제 위치를 넣지 않는다.
- 배포 전에는 빈 DB에서 전체 마이그레이션을 적용하고, 업그레이드 DB에서도 적용해 둘 다 검증한다.

### 환경 변수

- 앱: `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_KEY`만 사용한다. publishable/anon 키는 RLS가 전제다.
- 서버: `SUPABASE_SERVICE_ROLE_KEY`는 Edge Function 배포 환경에만 둔다.
- TourAPI·TMAP·ODsay 등 호출량·비밀 보호가 필요한 키는 이후 Edge Function 프록시로 옮긴다.

## 9. Live Activity 체류 기록 전환 (2026-09-07, 로컬 DB 계약 구현·원격 미적용)

유료 Apple Developer Program 가입은 완료됐다. 이전의 `유료 전환 뒤 결정` 상태는 종료됐으며, [DEC-LIVE-DWELL-01](../work/integration-decision/live-activity-dwell-personalization.md)이 새 기준이다.

### 9.1 저장 경계

- 일반 로그인과 `맞춤 추천을 위한 체류 기록` 동의가 모두 있고, 사용자 확인 `arrived`와 실제 다음/목적지/복귀 handoff 성공 또는 명시 완료 `departed`가 모두 있을 때만 완료 표본을 저장한다.
- Route Proxy용 Supabase anonymous Auth, 비로그인, 미동의, 도착 미확인, 출발 미확인, incomplete/cancelled/expired 상태는 표본을 저장하지 않는다.
- account 완료 이력은 nullable subCategory를 보존한다. 체류 표본은 사용자, 안전한 완료 identity, idempotency key, 정제된 non-null `category/sub_category`, `actual_dwell_min`, `arrival_source=user_confirmed`, 완료·schema version 등 목적에 필요한 최소 정보만 가진다. subCategory가 없는 완료는 체류 표본을 만들지 않는다. 좌표·GPS 이력·polyline·Kakao URL·알림 토큰을 포함하지 않는다.
- exact `arrived_at/departed_at`은 활성 코스 복구 동안 App Group 로컬 상태에서만 유지하는 것을 우선한다. 서버에 꼭 필요하다는 근거가 없으면 `actual_dwell_min`만 영속한다.
- 파생 프로필은 사용자+`category`+`subCategory` 복합 키로 격리한다. 같은 subCategory 문자열이 다른 category에 존재해도 합치지 않는다. 표본 3개부터 최근 최대 5개 중앙값을 저장하며 missing subCategory 표본은 프로필을 만들지 않는다.
- 동의 철회는 새 수집과 프로필 적용을 즉시 멈춘다. 사용자가 `개인화 데이터 초기화` 또는 계정 삭제를 실행하면 원시 표본과 파생 프로필을 모두 삭제한다.
- 정확 보유 기간과 자동 정리는 DB-DWELL-01에서 최소안을 제안하고 통합·결정 승인을 받은 뒤 활성화한다. 승인 전 영구 보관이나 production cleanup job을 임의로 선택하지 않는다.

### 9.2 네이티브·DB 역할 분리

- App Group, Live Activities capability, Widget Extension, App Intent와 로컬 알림은 UIUX/네이티브 작업의 책임이며 DB migration에 섞지 않는다.
- DB 작업은 migration, repository, RLS, 삭제와 idempotency 계약만 구현한다. UI나 추천 엔진의 상태 전이·시각 계산을 다시 정의하지 않는다.
- 개인정보 처리방침과 App Store Connect App Privacy에는 실제 구현 뒤 체류 기록 목적, 선택 동의, 보유·철회·삭제를 반영한다. GPS/background location을 수집한다고 잘못 표기하지 않는다.

### 9.3 DB-DWELL-01 현행 저장 계약과 이력

| 이전 방식 | 문제/관찰 | 교체 방식 | 교체 이유 | 상태 |
| --- | --- | --- | --- | --- |
| `course_stops`에 GPS 후보·raw 도착/출발 시각을 추가하는 초안 | 사용자 확인과 위치 추정이 섞이고 좌표·연속 위치·정확 시각 보유 범위가 목적보다 커짐 | `dwell_completion_samples`에 account owner, stable completion event/run/stop ID, 정제 category/subCategory, 양의 정수 체류 분, minute 정밀도 완료 시각, 고정 `arrival_source=user_confirmed`, schema version, consent epoch/revision만 저장 | 순서·180일 만료에 필요한 최소 완료 근거와 서버 수신 시각을 분리하면서 raw 시각·좌표·경로를 배제 | **현행 migration 작성·원격 미적용** |
| 체류 동의를 가입 동의 또는 단순 boolean으로 취급 | 철회·재동의 사이의 offline 표본이 소급 업로드될 수 있음 | `dwell_personalization_consents`의 revision+매 enable 새 epoch를 run/stop snapshot 및 현재 서버 상태와 모두 비교 | account 전환, off/reset race, 이전 outbox 재생을 fail closed 처리 | **현행 migration 작성·원격 미적용** |
| 보유 기간·queue 상한 미확정 | 무기한 local/server 민감 기록과 추천 순서 왜곡 위험 | outbox 최대 32건/7일 물리 정리, 서버 raw 표본 완료 시각 기준 180일 rolling, 파생 profile은 표본 3개부터 만들고 최신 최대 5개 중앙값으로 재계산 | 승인된 최소 보유·품질 경계를 코드와 재현 하네스에 동일 적용 | **현행. production cleanup job은 미활성** |

- `completed_at`은 사용자가 확인 완료한 기존 local completion 시각을 분 단위로 내림한 값이며 `received_at`은 서버 수신 시각이다. 미래 5분 초과와 180일 초과 표본을 거절하고, read는 `completed_at ASC, completion_event_id ASC`다.
- 서버는 같은 account의 `provenance=account_completed` 완료 기록과 run/stop/content/category/subCategory/completed minute가 일치할 때만 체류 표본을 받는다. `guest_import`, legacy 후기, missing subCategory는 학습 표본으로 승격하지 않는다.
- off는 신규 수집과 새 추천 적용만 멈추고 유효 raw 표본을 180일까지 유지한다. reset은 raw/profile을 삭제하고 disabled+새 revision으로 바꾸며, 계정 삭제는 Auth FK cascade로 consent/sample/profile을 모두 삭제한다.
- 원격 적용 전 `signup_consent_documents`의 실제 공개 URL/version 승인, migration 대상 기존 age metadata 건수/백업, production 180일 cleanup scheduler가 별도 출시 게이트다.

## 10. 후기와 분리한 로컬 코스 완료 기록 (2026-09-04, 현행 repository 구현)

| 이전 방식 | 문제/관찰 | 교체 방식 | 이유 | 상태 |
| --- | --- | --- | --- | --- |
| `@timefit/place-feedback-v1`의 선택 후기 데이터를 기록 탭의 완료 근거로 사용 | 후기를 남기지 않은 정상 완료가 누락되고, 계획 체류×사용자 응답으로 합성한 legacy `actualDwellMin`이 실제 측정 체류처럼 해석될 수 있음 | 명시 `코스 마치기`만 새 `@timefit/course-completions-v1` repository에 `courseRunId` 기준 한 번 저장하고, 후기는 복제·변형 없이 호환 read model에서 별도 source로 투영 | 완료 사실·만족도·사용자 확인 체류를 독립된 사실로 유지하기 위함 | **현행·DB-COMPLETION-RECORD-01 repository 구현 완료, UI 연결 전** |

### 10.1 로컬 완료 저장 경계

- 완료 기록은 비로그인도 사용할 수 있는 로컬 전용 데이터다. Supabase session, anonymous Auth, 네트워크나 서버 코스 저장 성공 여부에 의존하지 않으며 자동 업로드하지 않는다.
- record는 schema version, 최초 한 번 만든 completion ID, 코스 시작부터 재시도까지 유지되는 opaque `courseRunId`, 완료 시각, `explicit_course_finish`, 순서 있는 1~2개 장소의 ID·표시명·category·nullable subCategory·계획 체류·nullable 실제 체류만 보존한다.
- 같은 `courseRunId`의 연타·재시도는 최초 record를 반환하고 새 완료를 만들지 않는다. 저장 read-modify-write는 프로세스 내 직렬화하며 최대 1,000건을 최신순으로 보유한다.
- 출발지·도착지 좌표/주소, geometry·route/provider receipt·외부 URL, user ID·token·API key, GPS 추정 시각은 저장하지 않는다. 활성 진행 App Group, 로그인 코스 저장, 서버 체류 표본과 key·payload를 공유하지 않는다.
- 손상 JSON/schema는 `storage_corrupt`, storage read/write 실패는 `storage_unavailable`로 구분한다. 손상 데이터를 빈 배열이나 새 완료로 덮어쓰거나 저장 실패를 완료 성공으로 위장하지 않는다. 개인정보 초기화 후속을 위해 이 완료 key만 지우는 typed clear entry를 둔다.

### 10.2 완료·후기 호환 집계

- 새 완료 장소와 legacy 후기는 `source=completion|legacy_feedback`으로 구분해 순수 projection에서만 합친다. legacy 원본을 새 key로 복사하거나 rating 기본값을 만들지 않는다.
- legacy 후기의 기존 `actualDwellMin`은 실제 timestamp 차이가 아니라 계획 체류 기반 합성값이므로 새 `actualDwellMin`에는 항상 `null`로 투영한다. 호환 표시에 필요하면 `legacyEstimatedDwellMin`으로만 남기며 완료 활동 시간이나 개인화 표본에 사용하지 않는다.
- 장소 수와 category 분포에는 측정 여부와 무관하게 완료 장소를 포함한다. 활동 시간 합계는 유효한 새 실제 체류만 포함하고 `measuredCount`와 `unmeasuredCount`를 함께 제공해 0분과 미측정을 구분한다.
- UI의 `courseRunId` 생성·App Group 복구·`코스 마치기` 호출 및 저장 실패 표시는 후속 UIUX 작업이며, 로그인+별도 동의가 있는 실제 체류의 서버 저장은 별도 `DB-DWELL-01` 계약이다.
