# TimeFit 테스트 현황

> 기준일: 2026-08-15 16:50 KST  
> 목적: 사용자가 확정한 동작 요구사항을 단일 목록으로 관리하고, 구현 여부가 아니라 **검증 근거** 기준으로 테스트 충족률을 갱신한다.

## 1. 갱신 규칙

- 사용자가 새 요구사항이나 이상 사례를 말하면 먼저 이 문서에 ID와 기대 결과를 추가한다.
- 새 요구사항을 등록하기 전, 기존 ID와 비교해 관계를 `동일`, `보완`, `충돌`로 판정한다.
  - `동일`: 새 항목을 만들지 않고 기존 ID의 근거·테스트 시나리오만 갱신한다.
  - `보완`: 기존 ID를 유지하고 세부 조건을 추가한다. 기존 결과에 영향을 주면 변경 내용을 함께 기록한다.
  - `충돌`: 기존 규칙을 임의로 덮어쓰지 않는다. 사용자에게 기존 유지·새 규칙으로 대체·두 규칙 병행 중 선택을 물은 뒤, 확정된 방향만 반영한다.
- 대체된 요구사항은 삭제하지 않고 `대체됨` 상태와 대체한 ID·결정일을 남긴다. 현재 적용되는 요구사항만 충족률에 포함한다.
- 구현 전에는 `미검증`, 테스트 코드가 실패를 재현하면 `부분`, 자동 테스트 또는 재현 가능한 수동 시나리오가 통과하면 상태를 갱신한다.
- 추천·데이터·DB 정책을 변경한 커밋에는 관련 ID, 실행 명령, 결과를 함께 기록한다.
- 퍼센트는 코드 라인 수가 아니라 **요구사항 수** 기준이다. 수동 확인은 기능 확인이지 자동 회귀 방지는 아니므로 자동화율과 분리한다.

| 상태 | 의미 |
|---|---|
| `자동` | CI/로컬 명령으로 반복 검증 가능 |
| `수동확인` | 시뮬레이터 또는 실기기에서 사용자가 확인 |
| `부분` | 구현은 있으나 핵심 분기·실기기·회귀 검증이 부족 |
| `미검증` | 요구사항은 확정됐지만 검증 근거가 없음 |
| `대체됨` | 이후 확정된 요구사항으로 더 이상 적용하지 않음. 충족률 계산에서 제외 |

### 요구사항 등록 형식

```text
ID: REC-XX
관계: 신규 | 동일(REC-XX) | 보완(REC-XX) | 충돌(REC-XX)
기대 결과: 사용자가 확인 가능한 한 문장
검증 방식: 단위 | 통합 | E2E | 수동
결정: 유지 | 대체 | 병행 (충돌일 때 사용자 확정 후 기록)
```

## 2. 현재 요약

| 지표 | 요구사항 수 | 비율 |
|---|---:|---:|
| 자동 검증 완료 | 15 / 71 | **21%** |
| 수동 확인 완료 | 16 / 71 | **23%** |
| 확인 완료 합계 | 31 / 71 | **44%** |
| 부분 검증 | 24 / 71 | 34% |
| 미검증 | 16 / 71 | 23% |

**현재 검증 충족률은 44%**다. 2026-08-21 단일 장소·도착 여유·비차량 정책으로 차량 포함/다중 장소 요구사항 5개를 `대체됨` 처리하고, 새 요구사항 7개를 추가해 재계산했다. 기능 구현률이 아니라 자동 또는 수동으로 기대 결과를 확인한 비율이다. 공모전 제출 전 목표는 `확인 완료 90% 이상`, 그중 핵심 흐름 자동화 `50% 이상`이다. 후보 지도와 상세 시트의 세부 UIUX 요구사항은 [UIUX 테스트 명세](03_product/UIUX_테스트명세.md)에서 별도로 관리한다.
