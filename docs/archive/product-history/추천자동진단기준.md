# TimeFit 추천 자동진단 기준

> 작성: 2026-07-24 · 대상: `scripts/audit_recommendations.ts` · 목적: 추천 코스가 수학적으로 가능해도 사람 눈에 어색한 경우를 자동으로 걸러낸다.

## 1. 진단 목적

자동진단은 추천 결과의 정답 판정이 아니다. 앱을 하나하나 눌러보지 않고, 이상할 가능성이 높은 코스를 먼저 찾기 위한 품질 필터다.

앱은 비슷한 점수 후보를 약하게 순환시킬 수 있지만, 자동진단 스크립트는 고정 시드를 사용한다. 같은 데이터·API 응답 조건에서는 변경 전후 결과를 비교할 수 있어야 한다.

진단 대상:

```text
현재 위치 -> 추천 장소 1 -> (추천 장소 2) -> 약속 장소
```

각 코스에 대해 이동시간, 체류 가능 시간, 카테고리 조합, 우회율, 데이터 신뢰도, 부적합 키워드를 검사한다.

추가로 사용자가 실제 목록에서 탐색할 **장소 후보 풀**을 별도 진단한다. 이는 코스 PASS/WARN/FAIL과 다르며, 후보 데이터와 다양성의 충분성을 보는 지표다.

## 2. 판정 방식

각 코스는 100점에서 시작한다.

```text
score = 100 - Σ(penalty)
```

최종 판정:

| 판정 | 기준 | 의미 |
|---|---|---|
| `PASS` | 이슈 없음 | 자동 기준상 문제 없음 |
| `WARN` | fail 이슈는 없고 warn 이슈가 1개 이상 | 이상할 가능성이 있어 확인 필요 |
| `FAIL` | fail 이슈가 1개 이상 또는 score < 60 | 추천 로직에서 제거/강한 감점 후보 |

## 3. FAIL 규칙

| 코드 | 조건 | penalty | 이유 |
|---|---|---:|---|
| `lodging_keyword` | 호텔, 모텔, 리조트, 숙박, 숙소, 게스트하우스, 펜션, 여관, 여인숙, 호스텔, 콘도 포함 | 100 | 숙박성 장소는 자투리 시간 앱 목적과 맞지 않음 |
| `utility_keyword` | 주차장, 병원, 의원, 진료소, 약국, 주유소, 충전소, 정비소 포함 | 90 | 추천 장소라기보다 생활/편의 시설일 가능성이 큼 |
| `same_food_pair` | 식당 + 식당 2곳 코스 | 45 | 한 코스에서 식당 두 곳은 사용자 의도와 어긋날 가능성이 큼 |
| `far_pair` | 2개 장소 사이 도보 추정 12분 초과 | 60 | 2곳 코스라고 보기에는 장소 간 연결성이 약함 |
| `detour_high` | 약속 장소 직행 대비 코스 이동 우회율 1.8배 이상 | 45 | 약속 전 자투리 시간 활용이라기보다 돌아가는 코스가 됨 |

## 4. WARN 규칙

| 코드 | 조건 | penalty | 이유 |
|---|---|---:|---|
| `same_cafe_pair` | 카페 + 카페 2곳 코스 | 25 | 목적이 중복되어 코스 의미가 약할 수 있음 |
| `duplicate_category_pair` | 같은 카테고리 2곳 코스 | 15 | 다양성이 부족할 수 있음 |
| `detour_medium` | 약속 장소 직행 대비 코스 이동 우회율 1.45배 이상 1.8배 미만 | 20 | 약간 돌아가는 코스라 확인 필요 |
| `walk_too_long` | 도보 총 이동시간 60분 초과 | 15 | 도보 사용자가 선택하기 부담스러움 |
| `car_only` | 자동차로는 최소 체류 기준을 충족하지만 도보로는 충족하지 못함 | 20 | 자동차 전용에 가까운 코스이므로 표시/랭킹 주의 필요 |
| `low_stay_margin` | 최선 이동수단 기준 체류 가능 시간이 40분 미만 | 20 | 자투리 시간 활용 체감이 약할 수 있음 |
| `move_over_stay` | 이동시간이 체류 가능 시간보다 김 | 15 | 무료 구경 장소는 표시 가능하되 이동 효율이 낮아 순위를 낮춤 |
| `fallback_only_course` | 모든 장소가 카테고리 폴백 데이터 | 10 | 장소별 직접 체류 근거가 없어 신뢰도가 낮음 |

## 5. 현재 대표 시나리오

`scripts/audit_recommendations.ts`는 부산 주요 출발/약속 조합 20개를 실행한다.

예시:

```text
서면 -> 부산역 / 60분
서면 -> 부산역 / 120분
서면 왕복 / 90분
해운대 -> 벡스코 / 90분
광안리 -> 센텀 / 120분
부산역 -> 남포 / 90분
사상 -> 김해공항 / 120분
기장 -> 오시리아 / 120분
광안리 -> 부산역 / 180분
```

## 6. 리포트 읽는 법

HTML 리포트:

```text
docs/reports/recommendation_audit.html
```

리포트 상단에는 전체 요약이 표시된다.

```text
시나리오 수
추천 코스 수
PASS / WARN / FAIL 개수
이슈 코드별 발생 횟수
```

각 코스 카드에는 다음 정보가 표시된다.

```text
코스 장소
PASS/WARN/FAIL
품질 점수
도보 이동시간 / 체류 가능 시간
자동차 이동시간 / 체류 가능 시간
우회율
장소 간 도보 시간
이슈 코드와 설명
```

각 시나리오의 코스 카드 위에는 `후보 풀 진단`이 표시된다.

| 판정 | 기준 | 해석 |
|---|---|---|
| `후보 충분` | 상단 후보 5곳 이상, 카테고리 3개 이상, 특정 카테고리 비중 70% 미만 | 기본 지도 탐색과 장바구니 선택에 필요한 다양성이 확보됨 |
| `후보 제한` | 상단 후보 3~4곳, 카테고리 1~2개이거나 특정 카테고리 비중 70% 이상 | 점수 조정보다 후보 데이터 범위·운영시간 게이트·지역 특성을 검토할 대상 |
| `후보 부족` | 상단 후보 3곳 미만 | 해당 입력에서 장소 선택지가 실질적으로 부족함. 추천 실패로 단정하지 않고 후보 풀 보강 여부를 판단 |

후보 풀 진단에는 상단 10개 기준 카테고리·전략 분포, AIHub 직접 매칭/카테고리 폴백 비중, 운영시간 직접 근거 수, 지도 검증이 약한 후보 수를 함께 표시한다. 후보 부족·제한은 자동으로 장소를 제외하거나 점수를 조정하는 규칙이 아니다.

리포트는 `로컬 카탈로그 반경 후보 → 시간·방향 통과 → 운영시간 확인 → 최종 표시 후보`를 구분해 보여준다. `TourAPI 운영확인 가능` 수는 후보 중 TourAPI 원본 ID가 있어 상세 운영시간을 확인할 수 있는 장소 수이며, 전체 후보 수가 아니다.

표시 후보가 0곳이면 진단은 병목 단계를 함께 표시한다.

| 병목 | 의미 | 우선 확인할 것 |
|---|---|---|
| `시간·방향` | 카탈로그 후보는 있었지만 시간 예산 또는 약속 반대 방향 때문에 1차 컷에서 제외됨 | 입력 시간, 이동수단, 우회율·최소 체류 규칙. 데이터 부족으로 오해하지 않음 |
| `운영시간` | 1차 컷 통과 후보가 운영시간·행사기간 게이트에서 모두 제외됨 | TourAPI 운영시간 문자열·행사기간 파싱 |
| `코스 조립` | 운영시간 통과 후보는 있었지만 최소 체류시간을 배분한 코스가 없음 | 체류시간 폴백과 코스 조립 규칙 |

## 7. 개선 루프

추천 품질 개선은 아래 순서로 진행한다.

1. `recommendation_audit.html`에서 `FAIL` 코스를 먼저 본다.
2. 가장 많이 나온 이슈 코드를 확인한다.
3. 이슈가 타당하면 추천 로직에 제외/감점 규칙으로 반영한다.
4. 이슈가 과도하면 자동진단 기준을 완화한다.
5. 다시 감사 스크립트를 실행해 PASS/WARN/FAIL 변화량을 비교한다.

실행:

```bash
set -a && source .env && set +a && npx tsx scripts/audit_recommendations.ts
```

빠른 확인:

```bash
set -a && source .env && set +a && AUDIT_LIMIT=3 npx tsx scripts/audit_recommendations.ts
```

특정 지역/시나리오만 확인:

```bash
set -a && source .env && set +a && AUDIT_IDS=S12,S14,S15 npx tsx scripts/audit_recommendations.ts
```

이동수단별 후보 풀 비교:

```bash
set -a && source .env && set +a && AUDIT_MODE=walk AUDIT_OUT=docs/reports/recommendation_audit_walk.html npx tsx scripts/audit_recommendations.ts
set -a && source .env && set +a && AUDIT_MODE=car AUDIT_OUT=docs/reports/recommendation_audit_car.html npx tsx scripts/audit_recommendations.ts
set -a && source .env && set +a && AUDIT_MODE=transit AUDIT_OUT=docs/reports/recommendation_audit_transit_coverage.html npx tsx scripts/audit_recommendations.ts
```

대중교통 후보 풀 비교는 API 호출량을 보호하기 위해 ODsay 정밀 경로를 생략한 근사 이동시간 기준이다. 실제 대중교통 소요시간·환승 품질은 별도의 `audit_transit_recommendations.ts`로 검사한다.

세 수단의 A/B 장소 데이터 범위만 빠르게 비교할 때는 운영시간 상세 게이트도 생략한다. 이 모드는 실제 추천 품질 판정이 아니라 후보 데이터 부족 여부를 비교하기 위한 것이다.

```bash
AUDIT_COVERAGE_ONLY=1 AUDIT_MODE=walk npx tsx scripts/audit_recommendations.ts
```

## 8. 대중교통 자동진단

대중교통은 ODsay 호출량이 발생하므로 일반 추천 진단과 분리한다.

대상 스크립트:

```text
scripts/audit_transit_recommendations.ts
```

HTML 리포트:

```text
docs/reports/transit_recommendation_audit.html
```

대중교통 전용 진단은 다음 값을 함께 본다.

| 항목 | 의미 |
|---|---|
| `ODsay 호출` | 해당 시나리오에서 새로 발생한 ODsay API 호출 수 |
| `ODsay 성공/실패` | 실제 경로 계산 성공/실패 수 |
| `ODsay 구간` | 최종 추천 코스 안에서 ODsay로 확인된 이동 구간 수 |
| `walk_short` | 750m 이하 또는 도보 10분 이하라 대중교통 호출 없이 도보 처리한 구간 |
| `transit_fallback` | ODsay 실패 후 대중교통 근사값으로 남은 구간 |
| `지하철 구간` | ODsay 구간 중 지하철/호선 정보가 확인된 구간 |

대중교통 FAIL/WARN 기준:

| 코드 | 판정 | 의미 |
|---|---|---|
| `no_odsay_verified_leg` | FAIL | 약속장소가 있는 대중교통 코스인데 ODsay 확인 구간이 없음 |
| `below_min_stay` | FAIL | 대중교통 기준 체류 가능 시간이 30분 미만 |
| `far_two_spot_pair` | FAIL | 2곳 코스인데 두 장소 사이가 도보권이 아님 |
| `transit_fallback_leg` | WARN | ODsay 실패 후 근사값으로 남은 이동 구간이 있음 |
| `low_stay_margin` | WARN | 대중교통 기준 체류 가능 시간이 40분 미만 |
| `move_over_stay` | WARN | 이동시간이 체류 가능 시간보다 김 |
| `high_move_ratio` | WARN | 입력 시간 대비 이동시간 비율이 높음 |

빠른 확인:

```bash
set -a && source .env && set +a && AUDIT_LIMIT=1 npx tsx scripts/audit_transit_recommendations.ts
```

전체 확인:

```bash
set -a && source .env && set +a && npx tsx scripts/audit_transit_recommendations.ts
```
