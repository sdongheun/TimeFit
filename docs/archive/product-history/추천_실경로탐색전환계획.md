> 상위 결정: `REC-01` 추천 품질 기준 / `TIME-01` 현재 자투리 시간 모델

> **후속 결정:** 당시의 `도보·차량·대중교통` 3수단 경로 합집합과 다중 장소 장바구니는 차량 전용 먼 후보가 기본 결과에 섞이는 문제를 만들었다. 현재 실행 기준은 [추천로직.md](추천로직.md)의 `1.0.2`, `1.3~1.6`이다. 이 문서의 실제 경로 polyline, 캐시, 실패 시 좁은 생활권 폴백, 후보 선택 뒤 정밀 재계산은 유지하되 차량 기준 경로·차량 가능 후보·다중 장소 조립은 재구현하지 않는다.

## 1. 전환 목적

현재 후보 수집은 출발지·도착지·직선 중간 지점을 좌표 반경으로 탐색한다. 이 방식은 후보 수가 적을 때 넓은 반경을 사용하면 실제 이동 축 밖 장소까지 포함하는 문제가 있다. 예를 들어 서면→사상에서 부산역 식당이 후보가 되거나, 왕복 서면 2시간에 차량으로만 가능한 광안리가 기본 후보에 섞일 수 있다.

새 정책의 목적은 장소 수를 늘리기 위해 공간 관련성을 포기하지 않고, 사용자가 명시적으로 범위를 넓힐 때만 더 먼 장소를 탐색하게 하는 것이다.

## 3. 확정 정책

### 3.1 종료 조건과 시간

- 시작 시각은 출시 UI에서 현재 시각으로 고정한다.
- 도착지 미입력은 `출발지 복귀`로 계산하고, 화면에는 `현재 위치로 돌아오기`로 표시한다.
- 도착지는 약속·집·역 등 장소 검색으로 선택할 수 있다.
- 종료 조건은 항상 `도착지 + 종료 시각`이다. 도착지가 약속이면 약속 시각, 복귀 흐름이면 사용 가능한 시간 또는 종료 시각을 입력한다.
- 개발 빌드·자동화 하네스만 고정 현재 시각, 출발지, 도착지, 종료 시각을 주입한다. 출시 UI에는 테스트 시간 입력을 노출하지 않는다.

### 3.2 공간 탐색

`R`은 **지름이 아니라 반경**이다.

```text
도착지 없음:
  distance(현재 위치, 장소) <= R

도착지 있음:
  성공한 각 기준 경로 polyline에서 장소까지의 최단거리 <= R
```

- 기본값은 `R=1km`이다.
- 추천 실행 시 최대 `R=8km` 안의 공간 후보를 한 번 준비한다. 지도는 기본 `R=1km`만 표시한다.
- 사용자가 지도 슬라이더를 직접 조작한 경우에만 표시 반경을 최대 `R=8km`까지 확장한다. 슬라이더 조작은 기준 경로·장소 경로 API를 호출하지 않는다.
- 자동 확장은 하지 않는다. 기본 후보가 적은 문제는 데이터·장소 공급 문제로 별도 해결한다.
- 기준 경로가 모두 실패한 경우에는 슬라이더 값과 관계없이 양 끝의 기본 `1km` 생활권만 사용한다. 실제 이동 축을 알 수 없는 상태에서 8km 원을 쓰면 철회한 넓은 반경 정책으로 되돌아가기 때문이다.
- 도보·대중교통·차량 중 하나라도 시간 조건을 충족해야 지도 후보로 표시한다.
- 반경 확장은 공간 후보 풀만 넓힌다. 세 수단 모두 시간상 불가능한 장소는 확장 결과에도 표시하지 않는다.

### 3.3 기준 경로와 호출량

도착지가 있을 때 추천 실행 한 번에서 다음 기준 경로를 병렬 조회한다.

| 수단 | API | 경로 형상 | 용도 |
| --- | --- | --- | --- |
| 도보 | TMAP | 실제 보행 polyline | 도보 이동 축 탐색 |
| 차량 | TMAP | 실제 차량 polyline | 차량 이동 축 탐색 |
| 대중교통 | ODsay | 승하차·경유 정류장/역 좌표 연결선 | 대중교통 이동 축 탐색. 실제 도로 polyline으로 표시하지 않는다. |

- 초기 호출은 캐시 미스일 때 최대 3건이다.
- 슬라이더 변경, 지도 이동, 카드 펼침은 기준 경로 API를 호출하지 않는다.
- 요청 키는 정규화한 출발 좌표, 도착 좌표, 수단, 경로 옵션으로 구성한다.
- 동일 키의 동시 요청은 하나의 Promise를 공유한다.
- 캐시 TTL은 24시간이며 만료 즉시 삭제한다. API 약관·실제 한도가 바뀌면 TTL과 일일 소프트 예산을 재검토한다.
- 소프트 예산은 API 대시보드의 실제 무료 한도 확인 뒤 설정한다. 현재는 임의 한도로 기능을 막지 않는다.

### 3.4 정확도 단계

1. 기준 경로: 실제 API 응답으로 공간 탐색 범위를 만든다.
2. 후보 목록: 후보별 이동시간은 현재의 근사 계산과 수단별 안전 여유로 `예상` 상태를 만들고, 정제 카탈로그의 운영시간·권역 시간대 정책으로 현재 닫힌 후보를 제외한다.
3. 장소 선택: `현재 위치 → 선택 장소 → 최종 도착지`의 선택·자동 수단 구간을 실제 API로 재계산하고, TourAPI 상세 운영시간을 다시 확인한다.
4. 장바구니 확정: 실제 구간 이동시간, 최소 체류, 운영시간, 안전 여유를 모두 통과해야 저장·진행할 수 있다.

후보 목록의 근사값을 실제 경로 시간처럼 표현하지 않는다. UI 표현 방식은 별도 UIUX 결정에서 정한다.

### 5.1 직선 범위 교체 이력

| 상태 | 방식 | 관찰/문제 | 결정 |

### 5.2 기준 경로 캐시 변경 이력

| 상태 | 방식 | 관찰/문제 | 결정 |
| --- | --- | --- | --- |
| 철회 | 실패한 도보·차량·대중교통 결과도 24시간 캐시한다. | 일시적인 API 장애가 하루 동안 `추천 불가`로 고정되고, 사용자의 재시도에도 회복할 수 없다. | 실패 결과는 영속 저장하지 않는다. |
| 현행(플래너 연결 전) | 성공 geometry만 좌표·수단별 24시간 AsyncStorage 캐시에 저장한다. 동일 키 동시 요청은 Promise 하나를 공유한다. | 앱/Metro 재시작 뒤 반복 3회 호출을 줄이면서, 실패한 수단은 다음 요청에서 다시 조회할 수 있다. | 부분 성공은 성공한 수단만 사용하고, 전체 실패는 안전한 양 끝 1km 상태로 넘긴다. |

### 5.3 반경 UI 변경 이력

| 상태 | 방식 | 관찰/문제 | 결정 |
| --- | --- | --- | --- |
| 철회 | 시간 입력 화면에서 1~8km 슬라이더를 먼저 조작한다. | 사용자는 지도를 보기 전이라 반경이 장소 수와 위치에 어떤 영향을 주는지 판단하기 어렵다. | 슬라이더를 장소 마커가 보이는 지도 화면으로 이동했다. |
| 현행 | 추천 실행 시 최대 8km 후보를 한 번 준비하고, 지도에서 기본 1km만 표시한다. | 슬라이더 변경이 API 호출이나 추천 재계산을 일으키지 않는다. | 사용자가 지도 문맥에서 필요한 경우에만 표시 범위를 넓힌다. |

### 5.4 지도 운영시간 게이트 변경 이력

| 상태 | 방식 | 관찰/문제 | 결정 |
| --- | --- | --- | --- |
| 철회 | 지도 탐색은 공간·근사 시간만 확인하고, 운영시간은 장바구니 추가 때만 검사한다. | 기본 1km 서면 왕복 120분에서 36개가 표시됐지만, 일부는 운영시간 미확인 또는 마감 가능 후보였다. 지도 추천 수가 실제 이용 가능 수보다 부풀려진다. | 지도 표시 전에 로컬 운영시간·권역 시간대 정책을 적용한다. |

## 6. 완료 조건

- 기본 1km에서 생활권·실제 경로 축 밖 장소가 자동 후보로 표시되지 않는다.
- 8km 확장은 사용자가 직접 조작할 때만 적용되고, 슬라이더 조작은 API 요청을 늘리지 않는다.
- 세 기준 경로 호출은 캐시 미스에서만 발생하고, 앱 재시작 뒤에도 TTL 내 캐시가 재사용된다.
- 후보 목록의 근사 상태와 장소 선택 뒤 실제 판정이 서로 모순되지 않는다.
- 기준 경로가 모두 실패할 때 직선 경로를 사용하지 않고 안전한 생활권 상태와 재시도 UI를 보인다.
