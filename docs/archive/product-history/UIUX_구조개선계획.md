# UIUX 구조 개선 계획

> 기준일: 2026-08-16
>
> 목적: UI 변경이 추천 계산, 지도 제어, 저장 흐름을 함께 깨뜨리지 않도록 화면 표현·상태·외부 연동의 책임을 분리한다. 이 문서는 UIUX 개편의 코드 구조 기준이며, [UIUX 공통 규칙](UIUX_공통규칙.md)과 [UIUX 테스트 명세](UIUX_테스트명세.md)를 구현으로 연결한다.

## 1. 감사 결과

### 높은 우선순위

| 대상 | 확인된 문제 | 영향 | 개선 방향 |
| --- | --- | --- | --- |
| `src/ui/ResultsScreen.tsx` | 추천 후보 계산, 장바구니 계산, 시트 제스처, 지도 포커스, 후보 카드, 장소 상세, 저장·네비게이션을 한 컴포넌트가 처리한다. 분리 전 2,202줄이었다. | 카드·시트 UI 수정이 추천·저장 로직과 같은 파일에서 충돌하고, 화면 테스트가 구현 위치에 과도하게 의존한다. | Container-Presentational 패턴을 적용한다. 화면은 상태 연결만 맡기고 후보 목록·상세·시트·지도 컨트롤은 표현 컴포넌트, 시트 상태·지도 포커스는 훅으로 분리한다. |
| `ResultsScreen` 내부 스타일 | 카드·필터·상태 배지 스타일이 화면 로직과 함께 있었다. `42`, `52`, `12` 같은 제어 크기·반경 값도 여러 화면에 반복된다. | 수정 지점이 분산되고 화면 사이의 버튼 규격이 달라질 수 있다. | 색상 `C` 다음으로 spacing, radius, control size 토큰을 도입한다. 반복되는 버튼은 공통 컴포넌트로만 추출한다. |
| UI 계약 테스트 | 화면 요소가 `ResultsScreen` 문자열에 직접 묶여 있었다. | 컴포넌트를 분리하면 테스트가 실패하며, 파일 위치 변경이 동작 회귀처럼 보인다. | 테스트는 화면이 아니라 기능 모듈(`recommendation/*`)을 읽도록 바꾸고, 이후 `testID` 기반 E2E로 전환한다. |

### 테스트 우선 기준

- 화면을 옮기기 전에 화면 상태를 계산하는 순수 함수를 먼저 만들고, 입력과 출력의 단위 테스트를 추가한다.
- 첫 적용 대상은 추천 하단 시트다. `recommendation/sheetLayout.ts`는 확장·기본·접힘 높이, 지도 포커스 오프셋, 목록 끝 여백을 한 곳에서 계산한다.
- `npm run test:ui`는 TypeScript 기반 UI 상태 단위 테스트를 실행한다. 기존 `npm test`의 문자열 계약 검사는 당장 제거하지 않고, 대응되는 동작 테스트가 생길 때마다 단계적으로 축소한다.
- WebView 지도, 네이티브 제스처, 외부 앱 전환은 순수 단위 테스트만으로 검증할 수 없으므로, 추천 화면 분리 후 `testID`와 고정 API 응답을 추가해 iOS E2E 대상으로 전환한다.

## 2. 적용 원칙

1. **Container-Presentational**: 화면 컨테이너는 상태·엔진·네비게이션을 연결한다. 표시 전용 컴포넌트는 엔진이나 Supabase를 직접 호출하지 않고 props와 콜백만 받는다.
2. **Custom Hook**: 시트 위치, 드래그, 지도 중심 오프셋처럼 상태 전환이 있는 UI 동작은 `useRecommendationSheet`로 분리한다. 지도·시트 상태를 여러 `useState`와 이벤트에 흩어두지 않는다.
3. **Adapter 경계**: 카카오 지도·카카오 링크·TMAP·ODsay 호출은 UI 컴포넌트가 아닌 서비스 또는 어댑터에서만 다룬다.
4. **Design Token**: 색상은 `C`, 크기·간격·반경은 공통 토큰으로 관리한다. 화면별 임의 숫자는 지도 좌표·이미지 비율처럼 화면 고유 의미가 있을 때만 허용한다.
5. **Composition 우선**: 모든 버튼을 하나의 범용 컴포넌트로 만들지 않는다. 공통 구조가 안정된 뒤 재사용한다. 기능마다 조건문을 계속 추가하는 거대 컴포넌트를 피한다.
6. **행동 중심 테스트**: 파일명·내부 스타일보다 후보 선택, 시트 높이 유지, 장바구니 추가, 지도 포커스 같은 사용자 행동을 계약으로 검증한다.

## 3. 1차 적용 완료

`ResultsScreen`의 후보 평가와 목록 표현을 아래처럼 분리했다.

| 모듈 | 책임 |
| --- | --- |
| `ui/recommendation/types.ts` | 후보 상태, 이동수단 시나리오, 카테고리 필터, 표시 라벨 |
| `ui/recommendation/TransportGlyph.tsx` | 도보·대중교통·차량 아이콘 표시 |
| `ui/recommendation/CandidateList.tsx` | 가로 카테고리 필터, 후보 카드, 상태 배지, 카드 확장 표시 |
| `ui/recommendation/candidateEvaluation.ts` | 후보별 수단 시나리오, 체류 가능 시간, 장바구니 충돌, 필터·정렬 |
| `ResultsScreen.tsx` | API 정밀화, 선택 상태, 지도 포커스, 저장·네비게이션 이벤트 연결 |

이 분리 후 `ResultsScreen.tsx`는 806줄이다. 화면은 API 정밀 경로 검증·선택 상태·저장·네비게이션 연결만 맡는다. 후보 상태 판정과 정렬 규칙은 React 상태와 분리되어 단위 테스트할 수 있다.

## 4. 다음 분리 순서

1. 완료: `CandidateDetail`, `BasketPanel`, `useRecommendationSheet`, `MapControls`를 분리했다.
2. 완료: `ui/tokens.ts`에 아이콘 제어 크기, CTA 크기, 반경, 기본 화면 여백을 만들고 새 지도 제어부터 적용했다.
3. 완료: `ExecutionScreen`은 일정 계산과 외부 길찾기 URL을 `execution/schedule.ts`, 진행 상태 카드와 타임라인 표현을 `CourseProgress.tsx`로 분리했다. 현재 270줄이며 GPS, 알림, 저장·네비게이션 연결만 맡는다.
4. 진행 중: `KakaoRouteMap`은 지도 SDK 어댑터로 유지한다. 경로 세그먼트 정규화는 분리했다. WebView HTML은 카카오 SDK 전역 상태와 주입 순서가 하나의 실행 계약이므로, 현재는 한 템플릿으로 유지한다. 실제 기능 중복이 생길 때에만 HTML 템플릿·메시지 파서를 분리한다.
5. 공통 `PrimaryButton`, `MapIconButton`, `ScreenSurface`는 두 화면 이상에서 규격이 실제로 같을 때만 추가한다. 현재 `MapIconButton`만 추출했다.

### 분리하지 않은 화면의 기준

- `TimeSetupScreen`, `PlacePicker`처럼 단일 화면 흐름만 담당하고 300줄 미만인 파일은 억지로 쪼개지 않는다. 추상화가 실제 중복보다 커지는 것을 피하기 위함이다.
- `KakaoRouteMap.tsx`의 주입 HTML은 카카오 SDK 전역 객체, 로드 순서, WebView 메시지 처리의 하나의 실행 계약이다. 순수 경로 세그먼트만 분리했고, HTML을 문자열 조각으로 나누는 작업은 기능 중복이나 독립 테스트 경계가 생길 때까지 보류한다.

## 5. 완료 조건

- 화면 표현 변경이 추천 엔진·DB 저장 코드를 수정하지 않고 가능하다.
- 시트·지도·장바구니의 상태 전환은 각각 하나의 훅 또는 서비스에서 찾을 수 있다.
- 중복된 버튼·여백 규격은 디자인 토큰 또는 공통 컴포넌트로 관리한다.
- 새 UIUX 요구사항마다 [UIUX 테스트 명세](UIUX_테스트명세.md)의 시나리오와 자동화 대상이 함께 갱신된다.
- 타입 검사, 단위·계약 테스트를 통과한 뒤에만 화면 구조 리팩터링을 병합한다.

## 6. 정리한 구식 코드

- `ui/Chip.tsx`는 후기 화면의 체류시간·재방문 선택에 사용 중이므로 유지한다.
