## 운영 방식

| 상황 | 기록 위치 | 기록할 내용 |
| --- | --- | --- |
| 여러 역할이 순서·입출력 계약을 공유 | 이 보드 | 작업 ID, 담당, 상태, 선행 조건, 완료 산출물 링크, 결정 필요 사항 |
| 통합·결정과 하나의 역할만 소통 | 역할 고유 현재 작업 묶음 | 상세 명령, 구현·검증 결과, 다음 인계 |
| 정책 충돌·사용자 결정 | 제품 기준 문서와 통합·결정 기록 | 결정 ID, 이전 방식·문제·교체 방식·이유·상태 |

- 이 보드는 작업 지시 본문을 담지 않는다. 상세 내용은 역할 문서의 해당 작업 ID로 연결한다.
- 완료한 항목은 역할 archive와 [통합·결정 보드 archive](work/integration-decision/archive/2026-08-board-history.md)로 옮긴다. 이 보드에는 활성·대기·보류 상태와 다음 산출물만 남긴다.
- 새 역할 고유 현재 작업 묶음은 그 역할에 첫 직접 명령이 생길 때만 만든다. 빈 문서를 미리 늘리지 않는다.
- 한 작업은 한 역할만 수정한다. 다른 역할의 변경이 필요하면 이 보드에 `대기`와 필요한 공개 계약을 적는다.
- 통합·결정의 수락 검토는 `수락/보완 필요`만 말하고 끝내지 않는다. 수락이면 즉시 다음 작업의 ID·담당·선행 조건·사용자 결정 필요 여부를 함께 제시한다. 보완이 필요하면 새 suffix 작업을 만들지 않고 가능한 한 현재 활성 작업의 완료 기준에 흡수한다.

## 실행 우선순위와 게이트

- 추천 결과의 시간·운영시간·경로 정확성, 사용자 데이터·비용의 실제 손상, 보안 우회는 해당 기능의 **출시/활성화 차단**으로 다룬다.
- 활성화 전용 보완은 원칙적으로 추천 엔진의 순수 계산, 고정 fixture, UIUX의 화면·체감 개선을 멈추게 하지 않는다. 단, 보완 전제에 의존하는 런타임 전환만 보류한다.
- 각 세션은 먼저 고정 입력으로 동작하는 최소 구현과 회귀 테스트를 끝내고, 드문 장애·운영 자동화·관찰 보완은 별도 작업 ID와 활성화 조건으로 분리한다. 새 예외를 한 작업에 계속 누적하지 않는다.
- 통합·결정은 발견 위험의 영향 범위(추천 정확성 / 사용자 데이터·비용 / 외부 API 활성화 / 후속 개선)를 기록하고, 핵심 추천·UX 작업을 불필요하게 대기시키지 않는다.

## 작업 명령 완결성 원칙

- 통합·결정은 작업을 지시할 때 구현 범위만 적지 않는다. 정상 경로, 가장 비용·정확성·보안 영향이 큰 실패 경로, fallback/재시도 상한, cache·상태 전이, 외부 의존 실패, 공개 계약과 변경 금지 경계를 **같은 작업 ID의 완료 기준**에 함께 쓴다.
- 행동을 보장해야 하는 작업은 source 문자열 검사만 완료 근거로 삼지 않는다. 고정 fixture에서 실제 공개 entry를 실행하고 입력·반환값·부수효과 횟수(요청, cache write, lease, 저장 등)를 검증하도록 지시한다. 불가피하게 source 계약만 가능한 부분은 지시 단계에서 명시하고, 활성화 조건과 분리한다.
- 다음 작업에서야 발견될 수 있는 미정 사항은 “후속 보완”으로 막연히 남기지 않는다. 구현 전 확인 가능한 반례라면 현재 작업의 필수 fixture에 넣고, 계정 승인·배포·실기기처럼 지금 확인할 수 없는 항목만 별도 활성화 게이트로 남긴다.
- 작업자는 완료 기록에 변경 파일, 변경하지 않은 공개 경계, 실행한 검증과 결과, 남은 활성화 조건을 남긴다. 통합·결정은 이 네 항목과 최초 완료 기준을 대조한 뒤에만 수락한다.
- 상세 작업 문서는 `목적·사용자 관찰 → 확정 원인/미확정 가설 → 현행/철회 이력 → 호출 순서의 구현 명령 → 불변 경계 → 핵심 반례 fixture → 검증 명령·합격값 → 인수인계` 순서로 작성한다. 작업자가 제품 의도를 다시 추측해야 하거나 정상 경로만 구현한 뒤 다음 세션에서 실패 경로를 발견하게 만드는 지시는 완결된 명령으로 보지 않는다.
- 작업 범위가 넓더라도 구현 선택지를 여러 개 열어 두지 않는다. 통합·결정에서 확정된 방식 하나와 선택 이유를 명시한다. 사용자 결정이 필요한 선택이 남아 있으면 구현 명령으로 넘기기 전에 보드의 결정 대기로 분리한다.

## 보드 작성과 세션 시작

### 보드 작성자 경계

`docs/작업조정_보드.md`는 여러 역할의 상태를 한 표에 모으므로 **통합·결정 세션만 수정하는 단일 작성자 파일**이다. 데이터·추천 엔진·외부 API·UIUX·DB·QA 세션은 이 보드를 읽어 자신의 작업 ID와 상세 문서를 찾지만, 상태·링크·archive 요약을 직접 고치지 않는다.

각 작업 세션은 자기 역할의 현재 작업 묶음에만 변경 파일, 유지 경계, 테스트 결과, 다음 결정·위험·재현 조건을 남긴다. 완료 사실은 통합·결정에 인계하고, 통합·결정이 이를 검토한 뒤 보드 상태를 한 번 갱신한다. 수락된 완료 요약은 작업 소유자가 역할 archive에 append한다. 긴급 차단 사항도 보드를 직접 고치지 않고 현재 작업 묶음의 인계와 함께 알린다.

새 작업 세션은 아래 순서로 읽고, 보드만 읽은 뒤 구현을 시작하지 않는다.

1. 루트 `AGENTS.md`와 [문서 안내](README.md)를 읽는다.
2. 이 보드에서 자기 역할의 `진행 예정` 또는 `진행 중` 작업 ID를 찾는다.
3. 해당 행의 **상세 현재 작업 묶음 링크**와 역할 기준 문서를 읽는다.
4. 자기 소유 경로와 완료 기준이 맞을 때만 구현한다. 링크가 없거나 담당이 불명확하면 수정하지 않고 통합·결정에 인계한다.

통합·결정 세션이 다른 세션에 보내는 최소 지시는 다음 형식을 쓴다: `docs/작업조정_보드.md를 읽고, [작업 ID]의 상세 현재 작업 묶음과 역할 기준 문서를 확인한 뒤 자기 소유 경로와 현재 작업 묶음만 수정하라. 보드는 수정하지 말고 완료 인계를 현재 작업 묶음에 남겨라.`

## 현재 운영 원칙

- 새 세션은 위 표의 자기 역할 행과 해당 역할 `work/<role>/README.md`·현재 작업 묶음만 읽는다.
- 완료 행은 이 보드에 누적하지 않는다. 통합·결정 수락 뒤 역할 archive와 [보드 archive](work/integration-decision/archive/2026-08-board-history.md)에만 보관한다.
- `2-O`와 `DATA-DWELL-01`, `U-1-DWELL-01`, `QA-DWELL-01`이 모두 수락된 뒤에만 새 체류 정책을 포함한 `RD-B12`를 실행한다. B12 결과 전에는 A8 production 상한·tier 순서를 바꾸지 않는다.
- `API-4-F`는 수락됐다. 0개 코스 관찰은 receipt 전송 실패가 아니라 추천 엔진의 시간·경로 결과로 분리하며, 체류 정책 검증과 혼동하지 않는다.
- `DEC-RESULTS-02`의 1~3곳·첫 8→조건부 16회는 배포 후 다장소 이력이다. 출시 기본은 `DEC-ONE-STOP-MORE-01`의 실제 검증 one-stop이며, 첫 8회 뒤 자동 보충하지 않는다. 사용자가 누를 때만 다음 single을 최대 8회·새 3개씩 이어 검증한다. 조건부 시장·거리·골목은 10:00–18:00 정보 확인 영역으로만 분리한다.
- `DEC-CONTINUATION-01`의 보안 원칙은 one-stop에서도 유지한다. 이어보기는 continuation만으로 서버 상태를 만들거나 비직렬 runtime context를 보관하지 않는다. UI 메모리의 원래 `CourseV1LimitedInput`을 single 전용 continuation과 함께 새 release page entry에 전달하고, 엔진이 같은 provider의 공개 single 후보 ID를 재수화한다. 기존 multi-stop `continueLimitedRepresentativeCourseV1`를 release 화면에서 호출하지 않는다.
