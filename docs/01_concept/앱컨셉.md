> 맥락(공모전·마감·왜 이 방향인가)은 자매 문서 `프로젝트여정.md` 참조.

## 0. 이 문서의 성격 — 고정된 최종안이 아니다 (★먼저 읽기)

**이 문서에 적힌 컨셉·기능·결정은 "확정된 최종 목표"가 아니라 "현재 시점의 최선의 방향"이다.** 새로 합류하는 개발/에이전트는 이걸 *움직일 수 없는 스펙*으로 취급하지 말 것.

- **지속적 커뮤니케이션으로 계속 개선한다.** 사용자(기획자)와 대화하며 더 나은 방향이 나오면 _언제든 바꾼다._ 여기까지 오는 동안에도 방향은 여러 번 크게 바뀌었다(AR → AI 짬-플래너). 앞으로도 그럴 수 있다.
- **두 개의 북극성(North Star)을 향해 개선한다:**
  1. **사용자가 실제로 쓸 법한가** — 페인이 진짜인가, 다시 켤 이유(지속성·리텐션)가 있는가. 가정은 *검증*하고, 안 통하면 _바꾼다_.
  2. **공모전에서 수상할 법한가** — 심사기준(아래 §X 또는 `프로젝트여정.md`)에 정렬되는가. 기획력(독창성·트렌드)·완성도·데이터활용·발전성(지속성·확장성)·실용성에 점수가 붙는 방향으로 다듬는다.
- **그래서 에이전트가 할 일**: 결정을 *재검토 가능한 것*으로 다루고, 핵심 가정(페인·리텐션·차별점)을 의심·검증하며, 더 나은 개선안을 *먼저 제안*한다. "문서에 이렇게 쓰여 있으니 그대로 만든다"는 금물.
- **단, 개선이 곧 sprawl은 아니다.** 개선하되 _단일 정체성_(남는 시간 → 가능한 미니코스)은 지킨다. 기둥을 늘려 "종합앱=정체성 없음"으로 되돌아가지 말 것(이게 우리가 가장 크게 겪은 실패다 — `프로젝트여정.md` §2-5 참조).

> 한마디로: **이 문서는 "지금까지의 결론"일 뿐, "끝"이 아니다. 사용자와 계속 대화하며 *실사용성·수상가능성*이 높아지는 쪽으로 끊임없이 개선하라.**

## 1. 한 줄 정체성

> **"부산에서 붕 뜬 시간에, 이동·소요·혼잡·운영시간까지 따져 _진짜 가능한_ 미니 코스를 알아서 짜주는 짬-플래너."**

(가칭 — 이름 미정. 예: "부산 짬", "틈", "BusanGap" 등 추후 결정)

---

## 2. 해결하는 문제 / 상황

여행·출장 중 **약속이나 다음 일정 사이에 1~3시간이 애매하게 비는** 상황은 매우 흔하다. 사용자는:

- "여기서 다음 약속까지 2시간 남았는데 뭐하지?"
- 딱히 계획도 없고, 일일이 검색해 _시간 안에 되는지_ 따지기 귀찮다.

기존 지도/추천앱은 "근처 관광지 목록"은 주지만 **"내 남은 시간에 _실제로_ 가능한가"는 안 따져준다.** 그 빈틈이 이 앱의 자리다.

---

## 3. 타깃 / 메인 동사

- **타깃(상황 기반)**: 부산에서 *애매하게 남는 시간*을 가진 여행자·출장자·현지인. (데모그래픽이 아니라 **상황**으로 좁힌 타깃)
- **메인 동사**: **"남는 시간을 채운다"** (plan-ahead가 아니라 _지금 이 짬을 해결_).

---

## 4. 핵심 가치 = "시간-적합" 계산 (이 앱의 심장)

단순 근처 추천과의 차이는 **남은 시간 안에 실제로 들어가는지**를 계산하는 것이다. 이게 없으면 그냥 흔한 추천앱이다.

```
추천 후보가 가능한가? =
   이동시간(현재위치 ↔ 후보지, 필요시 → 다음 약속장소)
 + 체류(소요)시간(그 활동에 걸리는 시간)
 + 혼잡 보정(붐비면 대기·체류 ↑ 또는 회피)
 + 운영시간 체크(지금 열려 있고, 남은 시간 동안 영업)
 ≤ 사용자가 입력한 남은 시간
```

- AI(LLM)는 위 제약을 만족하는 **후보 선별 + 짧은 동선 구성 + "왜 이게 시간에 맞는지" 설명**을 담당한다.
- 예: "2시간, 서면" → ❌ 감천문화마을(왕복+관람 ~2.5h 초과) / ✅ 전포 카페거리 산책 50분 + 인근 전망카페 40분 (+이동 25분). "왜 가능한지"까지 설명.

## 5. 기능 상세

### 5.1 입력

- **남은 시간** (필수): 예 30분 / 1시간 / 2시간 …
- **현재 위치** (GPS 자동, 수동 보정 가능)
- **다음 약속** (선택): _시각 + 장소_. 입력 시 _"약속장소로 가는 길에 들를 곳"_ 경유 최적화. 미입력 시 남은시간 직접입력 + 현재 위치 왕복 기준.
- **필터**: 이동수단·예산은 입력에서, 활동·분위기는 결과 화면 칩으로 점진 적용. **입력 단계 취향 프리셋 없음** — 모든 사용자가 같은 시간-적합 추천을 받는다(개인화는 §5.4 완료 피드백에서만).

### 5.2 출력 — 시간 적응형 포맷 (특색 포인트)

앱이 **남은 시간에 따라 포맷을 알아서** 정한다:

- `~60분` → **단일 1곳** 추천
- `60~150분` → **미니 코스 2~3곳** (예: 카페 + 산책 + 전망)
- `>150분` → 코스 + 식사/여유 포함
- 각 추천에 **소요/이동 시간 분해 + "시간에 맞는 이유" AI 설명** 표시.

### 5.3 AI 역할

- 제약 만족(시간 예산 내) + 단거리 동선 추론 + 자연어 설명/추천 (**시간 계산은 결정적 엔진, 절대 미위임**).
- 호출 방식은 §8 참고(키 보안 위해 서버 프록시 권장).

### 5.4 실행 · 알림 (코스 수락 후)

- 사용자가 코스를 **수락**하면 실행 화면으로: _현재 → 장소1 → (장소2) → 약속장소_ 경로 + 구간별 소요.
- **로컬 알림**(출발예정시각 기반): "14:40 다음 장소로 이동", "15:10 약속장소로 출발". 서버 불필요(expo-notifications).
- 실시간 GPS 추적 기반 동적 재계산은 post-MVP.

### 5.5 피드백 · 개인화 (완료 후)

- 코스 종료 시 **완료 설문**(만족도·실제 체류·재방문 의향)을 받는다.
- **개인화는 오직 이 피드백에서만** 일어난다 — 입력·추천 단계엔 개인화가 없고, 누적된 피드백이 다음 추천을 점진적으로 맞춤화한다.
- 로그인은 알림·피드백·개인화를 위해 **수락 이후**에만 유도(추천의 전제조건 아님).

## 6. 데이터 소스 (TourAPI 중심 + 결합)

> 상세 오퍼레이션은 `TourAPI카탈로그.md` 참조. 한국어 앱이므로 **`KorService2`(국문 관광정보 서비스\_GW)** 사용.

| 용도                    | 데이터 / 오퍼레이션                                           | 비고                                                                    |
| ----------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 주변 후보 탐색          | TourAPI `locationBasedList2` (위치기반)                       | 현재 위치 반경                                                          |
| 운영시간·휴무·소요·주차 | TourAPI `detailIntro2` (`usetime/restdate/spendtime/parking`) | 시간-적합 핵심                                                          |

| 혼잡 보정(강화)         | KTO 집중률 `15128555` (KT+ML, 향후 30일)                      | **가능한 곳만**. 부산 POI 커버리지 미확인 → 없으면 시간대/요일 휴리스틱 |

- 가점: TMAP(타 기관 데이터) 결합 + 부산 지역특화.

## 7. 차별점 & 채점 매핑

### 수상작 대비 차별점

1. **시간-예산 기반 즉흥 추천** — "미리 짜는 플래너"(비트리뷰·담임)와 정반대 축.
2. **혼잡을 상품이 아닌 재료로** — 2025 수상작(혼잡도 표시)과 다르게, 시간 계산 정확도용 입력으로만 사용.
3. **시간 적응형 포맷** — 남은 시간에 따라 앱이 단일/코스를 알아서 결정.

### 심사 배점과의 연결

- **독창성·기획(30)**: 짬-시간 + 시간적합 계산이라는 새 프레임.
- **완성도(30/25)**: AR 없음 → 1인이 *실제 동작*까지 완성 가능(수상작 다수가 프로토타입이라 우위).
- **데이터 활용(20)**: TourAPI 위치·운영시간·연관·행사 + TMAP/혼잡 결합 → 깊고 창의적.
- **사업성(20→30, 최고배점)**: 짬 시간 = 즉흥 소비 유도 → **지역상권 제휴(이 시간에 이 카페/식당)**, 확장(부산100 → 전국 기초지자체) = TourAPI 기반이라 데이터만 갈면 복제.

## 9. 레이어드 빌드 + 14주 개략 계획 (1인 · ~6/15→9/21)

> 원칙: **확실히 끝나는 MVP 코어를 먼저** 완성하고, 데이터 리스크가 있는 것(혼잡·대중교통 소요)은 **강화 레이어**로 뒤에 붙인다.

- **MVP 코어 (필수 완성)**: 시간/약속 입력 + 위치 + TourAPI 후보 + 운영시간 + 이동시간(TMAP+휴리스틱) + 체류시간 → 단일/미니코스 자동 → **수락 → 경로+로컬알림 → 완료 피드백**.
- **강화 레이어 (시간 되는 만큼)**: ① 약속장소 경유 최적화 ② TMAP 대중교통 소요시간 ③ 혼잡 보정 ④ 피드백 기반 개인화 ⑤ 지역상권 제휴(사업성 데모).

| 주차  | 작업(개략)                                                            |
| ----- | --------------------------------------------------------------------- |
| 1–2   | 새 프로젝트 셋업, TourAPI 클라이언트 복사·정비, KorService2 연동·캐싱 |
| 3–5   | 시간-적합 계산 엔진(이동 추정 + 소요 기본값 + 운영시간), 후보 필터    |
| 6–8   | AI(LLM) 연동 — 제약 만족 추천 + 코스 구성 + 설명, 프록시 서버         |

## 10. 미해결 / 새 에이전트가 결정·검증할 것

1. **지도 SDK**: MapKit(가벼움) vs TMAP(한국 교통 소요시간). → 이동시간 정확도가 핵심이라 TMAP/ODsay 검토 가치. MVP는 휴리스틱으로 시작 가능.
2. **완료 피드백 설문 항목 구체안**: 만족도·실제체류·재방문 외 무엇을 받아 개인화에 쓸지 (개인화는 이 피드백에서만)
3. **이동수단 기본값**: 도보 / 대중교통 / 차 — 입력받을지, 기본(도보+대중교통)으로 둘지.
4. **LLM 호출 구조**: 온디바이스 불가 → 서버 프록시(키 보안) 설계. 비용·지연 관리.
5. **혼잡 데이터(15128555) 부산 POI 커버리지 검증** — 유효 serviceKey로 실제 부산 데이터 나오는지 확인. 없으면 시간대/요일 휴리스틱 fallback.
6. **소요시간 기본값 테이블** — 카테고리별(카페/전망/시장/산책/박물관 등) 합리적 기본 소요 정의.
7. **앱 이름·브랜딩**.

## 11. 오픈 리스크 (인지하고 관리)

- **"근처 추천"으로 전락 위험** → 시간-적합 계산을 반드시 메인 가치로 유지.
- **이동/소요/혼잡 데이터 정확도** → MVP는 휴리스틱, 정확도는 강화 레이어로 점진 개선. 과한 정밀 추구 금지(마감 우선).
- **사업성 서사 약화 위험** → 지역상권 제휴·확장성(전국 복제) 스토리를 PT용으로 미리 준비(결선 최고배점).

## 12. 한 줄 요약 (새 에이전트용)

**AR/길찾기 다 버리고, TourAPI를 깊게 쓰는 "부산 짬-시간 AI 플래너"를 1인이 9/21까지 새 프로젝트로 완성한다. 핵심은 '남은 시간 안에 실제로 가능한 미니 코스'를 시간-적합 계산(이동+소요+혼잡+운영) + AI로 짜주는 것.**
