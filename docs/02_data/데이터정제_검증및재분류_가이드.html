데이터 엔지니어링 가이드북

TimeFit 데이터 정제·검증 및 재분류 가이드

약속 전 자투리 시간을 활용하는 TimeFit의 핵심 경쟁력은 "실제로 열려있고, 시간 안에 안전하게 즐길 수 있는 장소 추천"입니다.
인기도나 AI 추정이 아닌 객관적 원천 근거(Evidence)를 바탕으로 장소를 4등급으로 재분류하는 규칙을 이해하기 쉽게 설명합니다.

✅ 수정 가능: data/, scripts/, src/data/, 데이터 계약 테스트
🚫 수정 금지: 추천 정책, React UI, 엔진 시간 계산식, API 어댑터, DB 스키마

1

왜 이 작업이 필요한가요? (핵심 철학)

🎯 자투리 시간 추천의 생명 = "신뢰성"

일반 여행 앱은 "사진이 예쁜 곳", "리뷰 많은 핫플"을 추천해도 사용자가 천천히 찾아가면 됩니다. 하지만 TimeFit은 다음 약속까지 30분~1시간 남은 사용자를 위한 앱입니다. 만약 추천받고 갔는데 문이 닫혀 있거나, 예상보다 체류 시간이 오래 걸려 약속에 늦는다면 서비스의 가치는 즉시 파괴됩니다.

❌ 과거 또는 흔한 실수 방식

  • 블로그나 리뷰 수, 카카오 별점이 높으면 자동 추천
  • "공원이니까 24시간 열려있겠지?"라고 임의 추정
  • 운영시간 모르는 장소도 '추천할 곳이 없으니 일단 노출'
  • 식당을 자투리 장소로 아무 근거 없이 섞어서 추천

✅ TimeFit의 현행 원칙

  • 시간 신뢰 절대 타협 불가: 공식 운영시간 확인된 곳만 대표 추천
  • 근거(Evidence) 보존: 언제, 어디서 가져온 정보인지 원문 함께 보관
  • 정직한 정보 표시: 추정값은 '추정'이라고 밝히고 더보기에만 노출
  • 결정론적 스크립트: 손으로 수동 편집하지 않고 코드로 재생성
💡 주니어 개발자를 위한 요약 "장소 개수를 억지로 늘리는 것이 목적이 아닙니다. '언제 가도 실패하지 않는 100% 검증된 장소'를 코어에 두고, 불확실한 장소는 보류하거나 조건을 명확히 걸어 분리하는 작업입니다."
2

한눈에 보는 4단계 장소 등급 (신호등 시스템)

기존의 단순 approved / review / hold 체계에서, 근거의 확실성에 따라 명확히 4가지로 세분화했습니다.

최우선 🟢
representative_core

대표 코스 최우선 후보군 (품질 보증 100%)

필수 조건:
  • 장소 일치: verified
  • 활동·체류: 장소/권역 자체 근거
  • 운영시간: 공식 확인 완료
✨ 메인 추천 코스 조립 시 1순위 사용
표준 🔵
representative_standard

대표 코스 가능 후보군 (표준 템플릿 검증)

필수 조건:
  • 장소 일치 & 운영시간 확인 완료
  • 활동/체류 중 하나가 검토된 activity_template
✨ Core와 시간 적합성 같으면 2순위
조건부 🟡
conditional_more

운영시간만 미확인된 장소 (더보기 전용)

필수 조건:
  • 장소 일치 + 활동/체류 근거 있음
  • 운영시간만 unknown
⚠️ [더보기]에서만 "운영시간 확인 필요" 배지로 노출
제외 🔴
hold

추천에서 제외 및 재검토 보류 목록

사유:
  • 장소 일치/활동/체류 근거 불명확
  • 내부 중복, 예약 필수/행사 종료
🚫 앱 노출 일체 차단 (사유 기록 보관)
⚠️ 주의: conditional_more의 엄격한 정의 "장소 동일성이나 활동 근거까지 애매한 장소를 conditional_more로 넣으면 안 됩니다. 모든 게 확실한데 오직 '운영시간' 하나만 공식 확인이 안 된 경우에만 conditional_more가 됩니다. 나머지는 전부 hold입니다!"
3

장소별 필수 근거 프로필 (데이터 모델)

단순히 값만 저장하지 않고, "이 정보를 어디서 언제 가져왔는지(evidence)"를 원문 링크와 함께 보관합니다. 

// 장소 데이터 필수 스키마 구조
{
  "placeId": "busan_poi_0123",
  "canonicalName": "부산근현대역사관",
  "coordinates": { "lat": 35.1023, "lng": 129.0315 },
  "placeKind": "point_facility",         // point_facility | area | outdoor_route | event
  "identity": "verified",                // verified | area_verified | unverified
  "activityType": "culture_exhibit",
  "activityEvidence": "place_specific",  // place_specific | area_specific | activity_template | unknown
  "stayEvidence": "place_observed",      // place_observed | area_observed | activity_template | unknown
  "availability": "fixed_hours",         // fixed_hours | area_hours | always_accessible_audited | event_window | unknown
  "accessFriction": "open",              // open | known_ticket_or_fee | reservation_required | program_dependent
  "evidence": [                          // 필수 근거 배열 (Audit Trail)
    {
      "field": "availability",
      "source": "official_website",
      "sourceIdOrUrl": "https://museum.busan.go.kr/modern/info",
      "sourceText": "화~일 09:00~18:00 (입장마감 17:00), 매주 월요일 휴무",
      "retrievedAt": "2026-08-24T00:00:00Z",
      "appliesTo": "all_year"
    }
  ],
  "classification": "representative_core",
  "classificationReason": "공식 홈페이지 운영시간 및 AI-Hub 실측 체류시간 확인 완료"
}
4

신뢰 가능한 원천 수집 규칙 & 우선순위

항목 1차 원천 (신뢰도 최고) 보조 원천 🚫 절대 금지 사항 (사용 제한)
장소 동일성 TourAPI · 부산시 공공데이터 (ID/좌표) 카카오 Place ID 일치 검증 이름이 비슷하다고 합치기 금지
시설 운영시간 시설/지자체 공식 홈페이지 · 공식 API TourAPI 상세 필드 카카오맵/블로그 후기 시간만으로 승격 금지
권역 이용시간 구청 · 상인회 · 공식 관광안내 TourAPI 권역 상세 내부 한 점포 시간을 권역 전체에 상속 금지
야외 접근성 공원/해변 관리주체 공식 안내 지자체 공식 관광 안내 자연관광지라고 '상시 개방' 멋대로 추정 금지
체류 시간 범위 정확 매칭 AI-Hub 관측 데이터 권역 관측 데이터, 활동 템플릿 리뷰 글자 수나 느낌으로 임의 추정 금지
예약/입장 부담 공식 예매 페이지 / 시설 안내 공식 행사 안내문 "줄 안 설 것이다 / 예약 필요없다" 추정 금지
💡 카카오맵(Kakao) 데이터는 왜 1차 근거가 아닌가요? 카카오맵 정보는 점주/사용자 수정 등으로 최신성이 다를 수 있으며 비정기 휴무가 누락되기도 합니다. 카카오맵은 "사용자가 최종 확인하기 위한 링크(URL)"로만 제공하고, 추천 판정의 근거는 반드시 공식 홈페이지/지자체 원천을 따릅니다.
5

데이터 정제 5단계 실행 파이프라인

A
기준선 고정 (Baseline Snapshot)
현재 카탈로그의 상태를 박제하고 출발점을 명확히 합니다.
  • 현재 활성 356개 POI 및 보류/제외 목록을 스냅샷으로 저장
  • 기존 생성 스크립트(scripts/build_*.mjs)의 입출력 관계 문서화
B
자동 원천 수집 및 정규화 (Batch Gathering)
공식 API와 원천에서 결정론적 스크립트로 데이터를 모으고 파싱합니다.
  • TourAPI 및 부산시 원천에서 소개, 운영시간 원문, 좌표 일괄 수집
  • 파싱 실패나 값 충돌 발생 시 임의로 덮어쓰지 않고 [감사 산출물]로 분리
C
사람 검토 큐 (Human-in-the-Loop)
모호하거나 충돌하는 케이스만 선별하여 사람이 직접 검토합니다.
  • 이름이 같거나 10m 이내로 붙어 있는 중복 경쟁 장소 판정
  • 원천 간 운영시간 불일치, 권역(시장/거리)과 내부 점포 간 관계 정리
  • 원문 링크와 명확한 판정 이유가 적혀야만 검토 완료 처리
D
생활권 공백 우선 보강 (Matrix Gap Filling)
인기순이 아닌, '생활권 × 활동 × 시간대' 매트릭스의 빈 칸을 채웁니다.
  • 예: [서면·전포 × 쇼핑·거리 × 오후], [해운대 × 야외산책 × 저녁]
  • Core/Standard가 없는 빈 칸을 채우되, 빈 칸을 채우려고 기준을 낮추는 것은 절대 금지
E
재생성 및 계약 검증 (Build & Test)
스크립트로 최종 JSON을 빌드하고 자동화 테스트를 통과시킵니다.
  • scripts/build_runtime_poi_catalog.mjs 실행으로 런타임 카탈로그 빌드
  • DATA-19~24 계약 테스트 및 npm test 통과 확인
6

절대 금지 사항 (Don'ts 인터랙티브 체크리스트)

정제 작업을 진행하면서 아래 6가지 금지 사항을 위반하지 않았는지 하나씩 체크해보세요.

  • 1. 일반 식당을 자투리 장소로 끼워넣지 않았는가?
    후보가 부족하다고 해서 식사/음식점을 대표 자투리 코스로 자동 추천하면 안 됩니다.
  • 2. 차량 기준 이동 시간이나 직선거리를 사용하지 않았는가?
    오직 '도보'와 '대중교통'의 실제 도보 네트워크 경로만 사용해야 합니다.
  • 3. 카카오맵 리뷰, 블로그, AI 추정만으로 장소를 승격하지 않았는가?
    AI는 태그 후보 제안만 가능하며, 공식 홈페이지나 지자체 근거 없이 승격할 수 없습니다.
  • 4. 시장/거리 등 권역의 운영시간을 내부 상점에 그대로 물려주지 않았는가?
    전포카페거리의 운영시간과 카페거리 안 특정 카페의 운영시간은 엄격히 분리되어야 합니다.
  • 5. 과거 상태값(approved/conditional)을 새 분류로 무지성 복사하지 않았는가?
    새로운 4단계 체계(Core/Standard/More/Hold)의 엄격한 근거 기준을 새로 대입해야 합니다.
  • 6. 런타임 JSON 파일을 직접 손(수동)으로 수정하지 않았는가?
    항상 원천 데이터와 build_*.mjs 스크립트를 통해 재현 가능하게 빌드해야 합니다.
7

최종 완료 기준 (Definition of Done)

제출해야 하는 7대 산출물 📦

  1. 변경한 파일 목록과 각 변경의 명확한 목적
  2. 재분류 전후 장소 개수 통계 (core / standard / more / hold)
  3. 생활권 × 활동 유형 × 시간대별 대표 후보 공백 매트릭스 표
  4. conditional_more 및 hold의 상위 사유 목록 & 재검토 큐
  5. 원천 충돌, 파싱 실패, 카카오 불일치 장소 ID 목록
  6. 실행한 생성·감사 스크립트 및 테스트 성공 결과
  7. 다음 작업 세션을 위한 정책 결정 필요사항 및 잠재 위험
🎯 최종 통과 게이트:
대표 추천 대상(Core/Standard)의 100%가 장소 동일성, 운영 가능성, 활동/체류 근거, 원천 URL, 확인일을 온전히 가지고 있어야 정제 완료로 판정합니다.
