# TimeFit 데이터 정제: 검증·재분류 실행 프롬프트

> 대상 역할: **데이터 정제 세션**
>
> 목적: 현재 활성 카탈로그가 실제로 근거를 갖춘 장소를 담고 있는지 재현 가능하게 검증하고, 다음 일정 전 부산의 계획 밖 장소를 안전하게 제안할 수 있는 `representative_core / representative_standard / conditional_more / hold` 카탈로그로 재분류한다.
>
> 상태: **현행 데이터 정제 실행 기준**. 제품 정책은 [추천로직](../03_product/추천로직.md), 검증 항목은 [테스트 현황](../테스트.md)의 `DATA-19~24`를 우선한다.

---

## 0. 역할·수정 경계

당신의 역할은 데이터 정제다.

- 수정 가능 범위: `data/`, `scripts/build_*.mjs`, `scripts/audit_*.mjs`, `src/data/`, 데이터 계약 테스트 및 이 문서가 가리키는 데이터 감사 문서.
- 수정하지 않는 범위: 추천 정책, React UI, 엔진 시간식, 외부 API 어댑터, DB 스키마.
- 정책·UI·엔진과 충돌하는 발견은 직접 정책을 바꾸지 말고, 장소 ID·원천·재현 조건·영향을 인수인계에 남긴다.
- 기존 장소 ID, 원천 응답, 제외·보류 기록은 삭제하지 않는다. 중복·근거 부족은 `hold`와 사유로 보존한다.
- 런타임 카탈로그를 수동으로 직접 고치지 않는다. 항상 검토 원천과 생성 스크립트에서 재생성한다.

### 1-1. 과거 문서 해석 규칙

`자투리장소_선별및체류범위_계획.md`에는 과거의 `출발 → 장소 1곳 → 도착/복귀`, `approved / review / hold / excluded` 표현이 남아 있다. 이 문서에서는 활동 유형, 체류, 제외 사유, 원천 조사 방법만 참고한다.

현행 실행 정책은 다음을 우선한다.

- 대표 결과는 엔진이 조립한 **1개, 1~3곳 코스**다.
- 차량은 추천 판정에 쓰지 않고, 도보·대중교통 실제 경로만 쓴다.
- 운영시간 미확인 장소는 대표 추천·자동 확정에 넣지 않는다.
- 새 분류는 `representative_core / representative_standard / conditional_more / hold`다.

`data/processed/archive/`, `src/data/busan_poi_catalog.legacy.json`은 현재 입력이 아니다. 현재 장소의 원천 추적이 꼭 필요할 때만 읽는다.

## 2. 재분류의 원칙

목표는 장소 수를 무조건 늘리거나 A등급 장소만 남기는 것이 아니다.

1. **시간 신뢰는 양보하지 않는다.** 실제 경로, 운영 가능 시간, 최소 체류, 도착 여유는 대표 추천의 하드 조건이다.
2. **활동·체류 근거는 계층적으로 허용한다.** 장소별 근거가 없더라도 검토된 권역 또는 활동 템플릿 근거가 있으면 자동 추천 풀을 넓힐 수 있다.
3. **근거의 약점을 숨기지 않는다.** 템플릿 체류를 장소별 관측 체류처럼 기록하거나 표시하지 않는다.
4. **운영시간의 불확실성만 조건부로 남긴다.** 장소 동일성·활동·체류 근거까지 부족한 장소는 `conditional_more`가 아니라 `hold`다.
5. **소비·인기도를 근거로 쓰지 않는다.** 리뷰 수, 블로그 문구, 일반적 인기, 예상 소비, GPS 방문 추정은 자동 추천의 근거가 아니다.

## 3. 장소별 필수 근거 프로필

모든 활성·재검토 장소에 아래 필드를 보존한다. 값만 저장하지 말고 `evidence`에 원천·원문·수집 시각·적용 범위를 연결한다.

```text
placeId
canonicalName
coordinates
placeKind
identity
activityType
activityEvidence
stayEvidence
availability
accessFriction
evidence[] = { field, source, sourceIdOrUrl, sourceText, retrievedAt, appliesTo }
verifiedAt
reviewDueAt
classification
classificationReason
```

| 필드               | 허용 값                                                                               | 판정 기준                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `identity`         | `verified`, `area_verified`, `unverified`                                             | 공식 원천 ID 또는 정규화 대표명·좌표가 일치하면 `verified`. 시장·거리 등 권역은 대표 권역명과 범위 설명이 일치할 때 `area_verified`. 유사 이름만으로 확정하지 않는다. |
| `placeKind`        | `point_facility`, `area`, `outdoor_route`, `event`                                    | 시설·권역·검토된 야외 접근형·기간 한정 행사를 구분한다. 권역은 내부 장소의 근거를 상속하지 않는다.                                                                    |
| `activityEvidence` | `place_specific`, `area_specific`, `activity_template`, `unknown`                     | 공식 소개 또는 검토된 활동 유형에서 도출한다. 관광 카테고리만으로 활동을 자동 부여하지 않는다.                                                                        |
| `stayEvidence`     | `place_observed`, `area_observed`, `activity_template`, `unknown`                     | 정확 매칭 AI-Hub 관측을 우선하고, 권역 관측, 활동 템플릿 순으로 사용한다.                                                                                             |
| `availability`     | `fixed_hours`, `area_hours`, `always_accessible_audited`, `event_window`, `unknown`   | 공식 정기 시간, 공식 권역 가능 시간, 검토된 야외 상시 접근, 공식 행사 기간·시간만 자동 추천 근거가 된다.                                                              |
| `accessFriction`   | `open`, `known_ticket_or_fee`, `reservation_required`, `program_dependent`, `unknown` | 유료 자체는 제외 사유가 아니다. 예약 필수·프로그램 의존은 해당 회차의 시간·정원 근거가 없으면 보류한다.                                                               |

## 4. 원천 수집 방법과 우선순위

### 4-1. 항목별 원천

| 항목           | 1차 원천                               | 보조 원천                        | 사용 제한                                     |
| -------------- | -------------------------------------- | -------------------------------- | --------------------------------------------- |
| 장소 동일성    | TourAPI·부산시 공식 데이터의 ID·좌표   | 카카오 Place ID·좌표의 일치 검증 | 유사 이름만으로 병합 금지                     |
| 시설 운영시간  | 시설·지자체의 공식 페이지/API          | TourAPI 상세                     | 카카오·블로그·후기 시간만으로 자동 승격 금지  |
| 권역 이용 시간 | 구청·상인회·공식 관광 안내             | TourAPI 권역 상세                | 내부 점포 시간을 권역 전체에 상속 금지        |
| 야외 접근      | 공원·해변·산책로 관리 주체의 공식 안내 | 지자체 공식 관광 안내            | 자연관광지 카테고리만으로 상시 접근 추정 금지 |
| 행사 일정      | 주최 기관 공식 일정                    | TourAPI 행사 상세                | 종료 행사·미래 일정 추정 금지                 |
| 활동 유형      | 공식 소개 문구, 검토된 권역 설명       | 활동 카탈로그 템플릿             | 관광 분류·리뷰 문구만으로 자동 확정 금지      |
| 체류 범위      | 정확 매칭 AI-Hub 관측                  | 권역 관측, 활동 템플릿           | 리뷰 수·임의 추정 금지                        |
| 예약·입장 부담 | 공식 시설 안내·예매 페이지             | 공식 행사 안내                   | 대기 없음·예약 불필요 추정 금지               |

### 4-2. 수집·보관 규칙

1. 모든 외부 응답은 원천 식별자, 원문, 수집 시각을 검토 산출물에 남긴다.
2. 파서가 구조화한 값과 원문을 함께 보관한다. 파싱 실패를 빈 값으로 덮어쓰지 않고 검토 큐로 보낸다.
3. 원천끼리 충돌하면 자동으로 최신값을 고르지 않는다. 장소 범위, 계절·요일, 입장 마감, 내부 시설 여부를 검토한 뒤 `classificationReason`에 기록한다.
4. 카카오는 장소 링크와 사용자의 최종 확인 경로로만 쓴다. 카카오 운영시간은 공식 운영시간 근거를 대체하지 않는다.
5. AI가 원문에서 활동 태그 후보를 제안할 수는 있지만, 원천을 만들거나 최종 분류를 확정할 수 없다.

## 5. 재분류 규칙

| 결과                      | 필수 조건                                                                                       | 런타임 처리                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `representative_core`     | `identity`가 `verified/area_verified`, 활동·체류가 장소 또는 권역 근거, `availability`가 확인됨 | 대표 코스 우선 후보. 실제 경로·운영시간·시간 예산 게이트를 추가 통과해야 한다.                       |
| `representative_standard` | 장소 동일성과 이용 가능성은 확인됨, 활동 또는 체류 중 하나가 검토된 `activity_template`         | 대표 코스 가능 후보. 시간 적합성이 같으면 `core`보다 뒤에 두되, 숨은 폴백으로 취급하지 않는다.       |
| `conditional_more`        | 장소 동일성·활동 적합성·체류 범위는 있으나 `availability = unknown`                             | 더보기에만 `운영시간 확인 필요`로 표시한다. 사용자 확인 뒤에도 대표 추천·검증됨으로 승격하지 않는다. |
| `hold`                    | 장소 동일성·활동·체류 중 하나가 미확인, 내부 중복, 예약 필수·프로그램 의존, 행사 만료           | 자동 추천·조건부 수동 포함에서 제외한다. 누락 근거와 재검토 행동을 남긴다.                           |

## 6. 실행 순서

### 단계 A — 기준선 고정

1. 현재 `busan_poi_catalog.json`과 검토 카탈로그의 장소 ID·분류·필드를 스냅샷으로 저장한다.
2. 활성 356개, 보류·제외 목록, 중복 목록의 수와 ID를 보고한다.
3. 현재 생성 스크립트의 입력·출력·상태 변환을 문서화한다.

### 단계 B — 자동 원천 수집과 정규화

1. TourAPI·부산시 공식 원천에서 장소 ID, 좌표, 공식 소개, 운영시간 원문, 행사 기간을 수집한다.
2. 장소명 정규화, 좌표 비교, 권역·내부 장소 관계를 결정론적 규칙으로 처리한다.
3. 원천 값, 파싱 값, 파싱 실패, 원천 충돌을 별도 감사 산출물로 보관한다.

### 단계 C — 사람 검토 큐

다음만 사람이 검토한다.

- 동일한 이름 또는 근접 좌표로 두 장소가 경쟁하는 경우
- 원천별 운영시간이 충돌하는 경우
- 시장·거리·골목의 권역 범위와 내부 장소 관계
- 야외 상시 접근 여부
- 예약 필수·프로그램 의존·행사 기간 장소
- `conditional_more` 승격 후보

사람 검토는 원문 링크·적용 범위·판정 이유 없이는 완료로 처리하지 않는다.

### 단계 D — 생활권 공백 우선 보강

인기도나 리뷰 수 대신 `생활권 × 활동 유형 × 시간대`의 공백을 계산한다.

```text
예: 서면·전포 × 쇼핑·거리 × 오후
    남포·광복 × 시장·거리 × 오전
    해운대 × 야외 산책 × 저녁
```

`core` 또는 `standard`가 없는 칸에서, 이미 공식 운영시간이 있는 장소부터 조사·승격한다. 빈 칸을 채우기 위해 운영시간·동일성 기준을 낮추지 않는다.

### 단계 E — 재생성과 계약 검증

1. 검토 원천에서 새 카탈로그를 스크립트로 생성한다.
2. `DATA-19~24`에 대응하는 데이터 계약 테스트를 추가·갱신한다.
3. 기존 추천·UI·엔진 테스트가 데이터 구조 변경으로 깨지지 않는지 확인한다.
4. 실제 API 재조회는 호출 수·대상·실행 시각을 기록한 소수의 수동 감사로 분리한다.

## 8. Goal 완료 기준과 산출물

이 Goal은 일부 장소를 조사하거나 보고서만 만든 것으로 완료되지 않는다. **현재 입력으로 사용 중인 모든 장소가 새 계약으로 재분류되고, 그 결과가 재생성·검증된 경우에만 완료**다.

### 8-1. 완료 판정 체크리스트

아래 항목을 전부 만족했을 때만 Goal 상태를 `complete`로 바꾼다.

1. 기준선 스냅샷의 모든 활성·보류·제외 장소 ID가 결과에 정확히 하나씩 대응한다. ID를 조용히 삭제하거나 새 ID로 바꾸지 않는다.
2. 모든 장소가 `representative_core`, `representative_standard`, `conditional_more`, `hold` 중 정확히 하나를 가진다.
3. 모든 장소에 `classificationReason`, `verifiedAt`, `reviewDueAt` 또는 명시적 `not_applicable` 사유가 있다.
4. `representative_core`와 `representative_standard`의 100%가 장소 동일성, 활동, 체류, 운영 가능성의 각 필드에 원천·원문·수집 시각·적용 범위를 가진다.
5. `conditional_more`의 100%가 장소 동일성·활동·체류 근거를 가지며, 유일한 자동 추천 불가 사유가 운영 가능성 미확인이다.
6. `hold`의 100%가 누락 또는 제외 사유와 다음 재검토 행동을 가진다. `hold`를 단순 쓰레기통으로 쓰지 않는다.
7. 권역 대표와 내부 장소의 관계, 동일 장소 중복, 행사 종료, 예약 필수·프로그램 의존, 운영시간 충돌이 분류·추천 입력에서 의도대로 차단된다.
8. 검토 원천에서 런타임 `src/data/busan_poi_catalog.json`을 생성 스크립트로 재생성했고, 수동 JSON 편집 없이 동일한 결과를 다시 만들 수 있다.
9. `DATA-19~24`에 대응하는 계약 테스트와 기존 데이터·추천 테스트를 실행해 통과시킨다. 실제 외부 API 감사는 대상 수·호출 시각·성공/실패를 별도 기록한다.
10. 현재 정책과 충돌하던 데이터 문서의 단일 장소·`approved/conditional` 현행 표현을 새 분류·1~3곳 코스 정책으로 갱신하거나, 명확한 **철회 이력**으로 격리한다.

외부 원천 장애, 공식 근거 부재, 파싱 실패는 완료를 막는 이유가 아니다. 그런 장소를 근거 없이 승격하지 않고 `conditional_more` 또는 `hold`로 분류해 사유·재검토 행동을 남겼다면 완료 조건을 충족할 수 있다.

### 8-2. 완료 보고에 반드시 포함할 산출물

1. 변경 파일과 각 변경 목적
2. 기준선과 결과의 장소 ID 대조표 및 누락·신규·병합 목록
3. 재분류 전후 수: `representative_core / representative_standard / conditional_more / hold`
4. 생활권·활동 유형·시간대별 대표 후보 공백 표
5. `conditional_more`와 `hold`의 상위 사유, 재검토 기한, 재검토 큐
6. 원천 충돌·파싱 실패·카카오 불일치의 장소 ID별 목록과 처리 결과
7. 실행한 생성·감사·계약 테스트, fixture, 명령, 성공/실패 결과
8. 변경하지 않은 정책·엔진·UI 계약과 다음 세션의 결정 필요 사항

### 8-3. 완료로 처리하면 안 되는 상태

- 몇 개 생활권·표본만 조사했고 전체 활성 카탈로그의 분류가 끝나지 않은 경우
- 원천 URL 없이 `approved`, `가능`, `영업 중`처럼 결론만 적은 경우
- 운영시간 미확인 장소를 단순히 삭제하거나 대표 추천으로 승격한 경우
- 검토 JSON만 고치고 런타임 카탈로그 재생성·계약 테스트를 하지 않은 경우
- 과거 `approved/conditional` 값만 새 이름으로 치환하고 근거 프로필을 채우지 않은 경우
- 테스트 실패, 원천 충돌, ID 누락을 기록하지 않은 채 보고서에 성공으로 적은 경우

## 9. 후속 단계: 추천 공급량 회복과 고정 시나리오 측정

이 단계의 목적은 전체 후보 수를 부풀리는 것이 아니라, 안전한 자동 추천 후보와 새 추천 가능한 코스 수가 실제 생활권·시간대에서 충분한지 확인하는 것이다. 현재 운영시간 원천 충돌 44개 중 자동 대표 후보인 **39개(`core` 13개, `standard` 26개)**를 우선 처리한다.

### 9-1. 운영시간 충돌 39개 해소

1. `사용중_장소_운영시간_원천감사.json`에서 원천 시간값이 둘 이상인 장소를 전수 추출한다.
2. 각 충돌을 아래 넷 중 하나로 판정하고, 원문·원천 ID·적용 범위·판정자를 기록한다.

| 충돌 유형      | 예시                                             | 처리                                                                                                         |
| -------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| 표기 차이      | 공백, 요일 표기만 다른 같은 시간                 | 정규화한 단일 시간식과 두 원문을 보존한 뒤 대표 후보 유지 가능                                               |
| 범위 불일치    | 권역은 상시 접근, 내부 시설은 10:00~22:00        | 장소 범위를 바로잡는다. 내부 시설 시간을 권역에 상속하지 않으며, 해소 전 자동 대표 추천에서 제외한다.        |
| 시간 조건 차이 | 계절·요일·입장 마감·단체/개인 관람 조건          | 파서가 조건을 구조화할 수 있을 때만 대표 후보 유지 가능하다. 그렇지 않으면 `conditional_more` 또는 `hold`다. |
| 실질 충돌      | 같은 장소에 서로 다른 운영시간, 원천 최신성 불명 | 최신값을 임의 선택하지 않는다. 공식 원천 재조사 전에는 `conditional_more` 또는 `hold`다.                     |

3. 자동 대표 후보에 남는 충돌은 `표기 차이` 또는 구조화 가능한 `시간 조건 차이`여야 한다. 미해결 충돌은 `core/standard`에 남겨서는 안 된다.
4. 처리 결과를 `장소 ID / 기존 분류 / 충돌 유형 / 채택 또는 보류 근거 / 새 분류 / 다음 재검토일` 표로 감사 문서에 추가한다.
5. 원천 충돌 fixture를 추가해, 미해결 충돌이 대표 추천으로 재유입하지 않는지 검증한다.

### 9-2. 생활권 공백의 안전한 `standard` 보강

`representative_standard`는 후보 부족을 위한 예외가 아니다. 장소 동일성과 운영 가능성이 확인되고, 활동 또는 체류에 검토된 템플릿 근거가 있는 독립 분류다.

1. `생활권 × 활동 유형 × 시간대` 표에서 `core/standard`가 없는 칸을 뽑는다.
2. 해당 칸의 `conditional_more`와 `hold` 중 **공식 운영시간 원문이 이미 있으나 카탈로그 연결·파싱·권역 범위 정리가 안 된 장소**를 우선 조사한다.
3. 다음을 모두 채운 경우에만 `standard`로 승격한다.

```text
identity = verified 또는 area_verified
availability = fixed_hours / area_hours / always_accessible_audited / event_window
activityEvidence 또는 stayEvidence 중 하나 = 검토된 activity_template 이상
운영시간 원천·원문·수집일·적용 범위 보존
예약 필수·프로그램 의존·미해결 시간 충돌 아님
```

4. 공식 운영시간이 없는 장소를 카카오·리뷰·추정으로 승격하지 않는다. 해당 장소는 계속 `conditional_more` 또는 `hold`다.
5. 승격은 생활권 공백을 줄인 정도와 함께 보고한다. 단순히 `standard` 수만 늘린 보고는 완료 근거가 아니다.

### 9-3. 1~3곳 코스 공급량 측정 계약

### 9-3-1. 공급량 fixture의 유효성 규칙

아래 조건을 만족하지 않는 fixture는 형식 검사용일 뿐, 생활권별 추천량·데이터 보강 우선순위의 근거로 사용하면 안 된다.

1. **실제 좌표 필수**: 모든 출발지·별도 도착지는 고정된 유효 위도·경도를 가져야 한다. `null` 좌표, 구 이름만 있는 가상 원점은 불가하다.
2. **실제 장소쌍 경로 fixture 필수**: `출발 → 첫 장소`, `장소 A → 장소 B`, `마지막 장소 → 도착/복귀`마다 실제 경로 조회 스냅샷을 저장한다. fixture에는 `fromId`, `toId`, 좌표, 수단(도보/대중교통 또는 실제 조합), 총 이동시간, 도보·대기·탑승·환승의 제공 가능 세부값, 조회 공급자, 조회 시각, 응답 식별자 또는 원문 요약을 둔다. 모든 장소에 같은 2분·7분·2분을 적용하거나 직선거리·속도식으로 이 값을 생성해서는 안 된다.
3. **복귀와 별도 도착지 분리**: 별도 도착지는 복귀와 **다른 ID 및 좌표**·구간 이동시간·가능 코스를 가져야 한다. 두 형태가 같은 후보 집합과 시간식을 공유하면 도착지 제약을 검증한 것이 아니다. 출발·도착 fixture에는 선택 이유(예: 역, 약속 거점, 관광 거점)를 기록한다.
4. **1~3곳 비강제 조립**: 시간 예산이 180분이어도 1·2·3곳 후보를 모두 비교한다. 3곳 순열만 만들거나 예산에 따라 코스 크기를 고정하지 않는다. 대표 코스 수는 엔진이 시간 적합성·이동 부담·활동 중복을 비교해 결정한다.
5. **후보 범위의 투명성**: 임의의 가까운 N개 절단은 실제 공급량 측정에 쓰지 않는다. 성능 진단을 위해 `localTopN`을 쓸 때는 전체 적격 후보 수·절단 전후 유효 코스 수·제외 장소 ID를 별도 보고하고, 결과 등급을 `heuristic_diagnostic`으로 표시한다. `route_verified_measurement`는 정책상 정의된 공간 범위의 모든 적격 후보를 평가한다.
6. **장소 관계 게이트**: 같은 `siteGroupId`, 권역과 내부 장소, 동일 장소 반복은 하드 제외한다. 활동 유형이 같은 것만으로 자동 제외하지 않는다. 실제 경험 중복을 하드 제외하려면 장소쌍별 중복 근거와 정책 인계가 필요하다. 근거가 없으면 활동 반복은 순위 하향 후보로만 기록한다.
7. **대안 중복 제거**: 같은 장소 집합·같은 순서·같은 구간 시간식은 한 코스다. 순서가 다르더라도 실제 구간·도착 여유가 같거나 더 나쁘면 새 추천으로 세지 않는다. 경로 fixture가 근사치인 경우에는 우열을 주장하지 않고 순서가 다른 코스를 별도 보존한다.
8. **구조화 운영시간의 전체 일정 검증**: 원문을 시나리오 빌드 시점에 정규식으로 다시 해석하지 않는다. 요일·기간·복수 시간대·휴무일·입장 마감·상시 접근을 포함한 구조화 availability를 입력으로 사용한다. 각 장소의 도착부터 최소 또는 권장 체류 종료까지 전체 일정이 가능한지 판정한다. 구조화할 수 없는 조건은 대표 측정에서 제외하고 사유를 남긴다.

공급량 보고서에는 아래 수치를 분리해 적는다.

```text
rawCoursePermutationCount       # 조합 생성 직후 수, 참고용
deduplicatedFeasibleCourseCount # 중복·관계·시간 게이트 통과 뒤 실제 대안 수
representativeCourseCount       # 엔진이 대표로 비교 가능한 코스 수
newRecommendationCount          # 아직 보지 않은, 더 나쁘지 않은 대체 코스 수
zeroResultRate                  # 고정 시나리오 중 대표 코스 0개 비율
zeroReasonBreakdown             # 공간/운영시간/체류/경로/중복별 원인
```

`rawCoursePermutationCount`를 추천량이나 새 추천 가능 수로 보고하는 것은 금지한다.

보고서는 전체 합계만으로 끝내지 않고, 아래를 모두 제공한다.

1. `생활권 × 시간대 × 시간 예산 × 도착 형태`별 결과: 후보 수, 원시 순열, 관계 필터 후 수, 운영시간·경로 통과 수, 중복 제거 유효 코스 수, 대표 상태, 새 추천 수, 결과 등급.
2. 1·2·3곳 코스의 시나리오별 및 전체 분포. 180분 시나리오마다 세 규모를 실제 비교했는지 표시한다.
3. 후보 0개와 대안 0개의 사유를 장소 ID·탈락 단계와 함께 제시한다.
4. 사용한 장소쌍 경로 fixture 목록, 조회 일시·공급자·수단·누락 구간, 그리고 구조화 운영시간의 원천/버전을 제시한다.
5. `route_verified_measurement`와 `heuristic_diagnostic`의 합계·0개율·결론을 분리한다. 후자의 수치로 데이터 보강 우선순위를 결정하지 않는다.

최소 측정 매트릭스는 아래와 같다.

| 축        | 고정 값                                            |
| --------- | -------------------------------------------------- |
| 생활권    | 현재 런타임 카탈로그가 있는 각 구·군과 공백 생활권 |
| 시간대    | 평일 오전·오후·저녁, 주말 오후                     |
| 시간 예산 | 45분, 60분, 90분, 180분                            |
| 도착 형태 | 출발지 복귀, 별도 도착지                           |
| 코스 규모 | 1곳 가능, 2곳 가능, 3곳 가능, 후보 0개             |

- 3곳 코스는 **충분한 시간과 낮은 장소 간 이동 부담이 있는 fixture**에서만 기대 결과로 둔다. 모든 시나리오에서 3곳을 만들도록 데이터를 왜곡하지 않는다.
- 1곳 코스는 실패·축소 결과가 아니라, 주어진 시간에 가장 안전하고 완결된 경험일 때의 정상 결과다.
- 측정은 전체 부산 후보 수가 아니라 시나리오별 `유효 코스 수`, `서로 다른 새 추천 수`, `후보 0개율`, `탈락 원인`으로 보고한다.

### 9-4. 새 추천 가능 수와 UI 인계 계약

데이터 세션은 시나리오마다 순서·장소 구성·실제 경로가 다른 유효 코스를 식별한다. 같은 장소·같은 순서·같은 시간식의 재표시는 다른 추천으로 세지 않는다.

| 유효 코스 수 | 데이터/엔진 계약                       | UIUX 인계                                                                       |
| -----------: | -------------------------------------- | ------------------------------------------------------------------------------- |
|            0 | 빈 결과 원인과 대안 탐색 범위를 반환   | 후보 없음 행동을 표시                                                           |
|            1 | 대표 코스와 `새 추천 없음` 상태를 반환 | 새 추천을 반복 실행하지 않고 **`이 조건에서 다른 검증 코스가 없습니다`**를 표시 |
|       2 이상 | 대표 외 대체 코스 ID 목록을 반환       | 새 추천은 아직 보지 않은 유효 코스로만 전환                                     |

이 표는 UI 구현 지시가 아니라, 데이터·엔진이 반환해야 할 상태 계약이다. UI 세션은 이 계약을 받아 문구·버튼 상태를 구현한다.

### 9-5. 이 후속 단계의 완료 기준

데이터 세션은 다음을 충족했을 때 이 단계만 완료로 인계할 수 있다.

1. 자동 대표 후보였던 운영시간 충돌 39개 각각이 충돌 유형·처리 원천·새 분류를 가진다.
2. 미해결 충돌 장소는 `core/standard`에 남아 있지 않다.
3. 생활권 공백별로 공식 운영시간이 있는 승격 후보와 승격 불가 사유를 조사했다.
4. 최소 측정 매트릭스를 만족하는 **의미 있는 출발/도착 좌표와 실제 장소쌍 경로 스냅샷** fixture를 만들었다. 복귀와 별도 도착지는 ID·좌표·시간식이 서로 다르다. 실제 경로가 없는 시나리오는 `heuristic_diagnostic`으로 분리했으며, 완료 근거의 공급량 결론에 포함하지 않았다.
5. 각 시나리오에 1·2·3곳을 모두 비교한 뒤의 중복 제거 유효 코스 수, 대표 비교 가능 수, 새 추천 가능 수, 0개일 때 장소 ID별 탈락 원인이 기록돼 있다. 임의 후보 상한을 사용했다면 절단 전후 수와 제외 ID도 기록돼 있다.
6. 원천 충돌, 1곳 정상 코스, 3곳 비강제, 출발·도착 좌표 분리, 실제 장소쌍 fixture, 장소 관계 하드 중복 차단, 활동 반복의 비자동 배제, 복수 시간대·휴무일을 포함한 운영시간 전체 일정 검증, 유효 코스 1개일 때 새 추천 없음 상태를 계약 테스트로 검증했다.
7. 생활권·시간대·예산·도착 형태별 표와 측정 등급별 결론을 보고서에 포함했다. 전체 합계만 있거나 근사 진단을 실제 공급량처럼 보고하면 완료가 아니다.
8. 추천 엔진 세션과 UIUX 세션에 각각 필요한 fixture·입출력 계약·미구현 항목을 분리해 인계했다.

## 10. 금지 사항

- 일반 식당을 후보 부족 해소용으로 자동 추천하지 않는다.
- 차량 기준 후보, 직선거리만으로 가능한 후보, 운영시간 미확인 장소를 대표 추천으로 넣지 않는다.
- 카카오 운영시간, 블로그, 후기, 리뷰 수, AI 추정만으로 장소를 자동 승격하지 않는다.
- 권역 근거를 내부 점포·시설에 상속하지 않는다.
- 과거 `approved / conditional` 상태를 새 분류에 기계적으로 복사하지 않는다.
- 확인되지 않은 값을 `열려 있음`, `시간 안에 가능`, `처음 가보는`, `인기 장소`로 표현하지 않는다.
