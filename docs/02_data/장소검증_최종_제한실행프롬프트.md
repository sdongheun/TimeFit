# TimeFit 장소 검증: 배포 후보 직전 제한 실행 프롬프트

> 대상 역할: **데이터 정제 세션**
>
> 실행 시점: 추천 엔진의 1~3곳 코스와 대표/조건부 UI 흐름이 고정된 뒤, TestFlight 또는 출시 후보를 만들기 직전.
>
> 목적: 새 장소를 많이 모으는 것이 아니라, 현재 대표 추천에 쓰는 장소가 출시 시점에도 안전한지 확인한다.
>
> 상태: **보류된 최종 게이트**. 현재는 실행하지 않는다.

## 0. 왜 지금 실행하지 않는가

| 이전 방식 | 문제 | 현행 방식 | 이유 | 상태 |
| --- | --- | --- | --- | --- |
| 부산 전체 후보·장소쌍을 반복 수집해 공급량을 먼저 확정 | 엔진·후보 범위가 구현 전환 중이면 같은 장소도 다시 측정해야 하며, 호출량과 토큰만 늘어난다. 500m·근사 진단값은 제품 공급량 결론이 아니다. | 현재 근거 프로필·구조화 운영시간·실경로 fixture를 보존하고, 출시 후보 직전에 제한된 이상 징후만 재확인한다. | 제품 흐름이 확정된 뒤에만 외부 조회가 재현 가능한 출시 게이트가 된다. | 현행 |

이 작업은 장소 수 확대, 부산 전수 실경로 측정, 생활권별 공급량 확정 작업이 아니다. 그런 작업은 별도 승인·호출 예산·API 어댑터 계약 없이는 시작하지 않는다.

## 1. 시작 전 확인

다음을 읽는다.

1. 루트 `AGENTS.md`, `docs/README.md`
2. `docs/03_product/추천로직.md`의 1.0.3, 1.1, 1.5
3. `docs/테스트.md`의 `REC-17`, `REC-21`, `REC-23`, `DATA-19~24`
4. `data/processed/review/부산_장소_근거프로필_재분류.json`
5. `data/processed/review/운영시간_충돌_처리결과.json`
6. `data/processed/review/부산_장소_구조화_운영시간.json`, `src/data/busan_poi_catalog.json`
7. `docs/02_data/작업중단_인수인계.md`

아래 중 하나라도 미완료면 외부 조회를 시작하지 않고, 중단 사유만 인수인계한다.

- 1~3곳 대표 코스가 고정 fixture로 엔진 검증되지 않았다.
- 조건부 후보가 대표 추천에서 제외되는 UI·저장 흐름이 검증되지 않았다.
- 실제 경로 후보 범위·호출 상한·캐시 정책이 추천 엔진 및 API 어댑터 역할에서 확정되지 않았다.

## 2. 엄격한 범위와 호출 상한

### 2-1. 우선하는 무호출 검증

외부 호출 없이 아래를 먼저 수행한다.

1. 런타임에 `hold`가 없는지, 대표 후보가 `representative_core` 또는 `representative_standard`뿐인지 검사한다.
2. 대표 후보 166개와 조건부 176개의 분류·근거 프로필·`reviewDueAt`·운영시간 구조화 연결을 전수 계약 검사한다.
3. 39개 운영시간 충돌의 `25 유지 / 14 hold` 결과가 런타임에 그대로 반영됐는지 검사한다.
4. 출시 기준일을 고정해 90일 시설/상권, 365일 야외, 행사 종료 경계로 만료 후보가 대표 풀에 남지 않는지 검사한다.
5. 이전 수치(356개, `approved/conditional`)가 현행 실행 기준 문서·카탈로그에 남아 혼동을 일으키는지 보고한다. 정책 문서는 직접 수정하지 않는다.

### 2-2. 허용되는 제한 수동 재확인

무호출 검증에서 이상이 발견된 장소만 대상으로 한다. 자동 루프·전수 API 수집·장소쌍 경로 수집은 금지한다.

- 공식 운영시간 또는 행사 기간 재확인: **최대 12개 장소**
- 대상 우선순위: 만료 임박/경과 대표 후보 → 기존 충돌 유지 25개 중 영향이 큰 장소 → 출시 데모 코스에 쓰는 장소
- 실제 경로 재확인: **최대 6개 장소쌍**, 대표 코스·대안·도착지 형태를 각각 포함한다. 수단별 실제 경로 값은 API 어댑터의 캐시·호출량 기록을 통해서만 얻는다.
- 원천 실패·모호함은 재시도 확대가 아니라 `hold` 또는 `conditional_more` 후보로 인계한다. 사용자 영향이 있는 분류 변경은 통합·결정 세션에 장소 ID와 근거를 전달하고, 독자적으로 정책을 바꾸지 않는다.

## 3. 검증 기준

### 대표 후보

- `core/standard`는 장소 동일성, 활동·체류 근거, 운영 가능성, 근거 원문·수집 시각·적용 범위를 모두 보유한다.
- 운영시간이 요일·계절·휴무·입장마감·복수 구간으로 해석되지 않으면 대표 후보로 유지하지 않는다.
- 권역과 내부 시설, 같은 `siteGroupId`, 행사 종료, 예약·프로그램 의존 장소가 자동 대표 코스에 재유입하지 않는다.

### 조건부 후보

- `conditional_more`의 자동 추천 불가 이유는 운영 가능성 미확인 하나뿐이다.
- 카카오 정보는 사용자의 최종 확인 링크일 뿐, 대표 후보 승격 근거가 아니다.
- 조건부 후보의 수가 줄어도 근거 없이 `core/standard`로 올리지 않는다.

### 실제 경로 표본

- 대표 결과·새 추천·상세·코스 확인은 같은 고정 실제 경로 구간 시간을 사용한다.
- 도보·대중교통 조합 정책을 검증하며, 차량 기준 통과나 직선거리 근사값을 사용자 표시 근거로 쓰지 않는다.
- 1곳 정상 코스, 2~3곳 코스, 대안 없음, 별도 도착지의 네 상태가 적어도 하나씩 포함돼야 한다.

## 4. 산출물과 완료 기준

새 원천·스크립트·런타임 카탈로그를 필요 없이 대량 변경하지 않는다. 아래의 짧은 출시 게이트 보고서와 필요한 fixture만 남긴다.

보고서에는 반드시 다음을 포함한다.

1. 기준일, 런타임 장소 수와 `core / standard / conditional / hold` 수
2. 무호출 계약 검사의 명령·통과/실패·이상 장소 ID
3. 실제 외부 조회 수(운영시간 장소 수, 경로 장소쌍 수), 대상 선정 이유, 호출 시각과 결과
4. 상태 변경이 필요했던 장소와 사용자 영향. 변경이 없으면 `변경 없음`을 명시한다.
5. 대표/조건부/보류 경계, 추천 정책, UI 문구를 변경하지 않았다는 확인
6. 다음 재검토일과 남은 위험

아래를 모두 만족할 때만 이 제한 게이트를 완료로 보고한다.

1. 무호출 계약 테스트가 통과한다.
2. 호출 상한(운영시간 12곳, 장소쌍 6개)을 넘기지 않았거나, 넘겨야 할 근거와 사용자 승인이 기록돼 있다.
3. 만료·충돌·구조화 불가 장소가 대표 후보로 남아 있지 않다.
4. 실제 경로 표본은 제품 전체 공급량 결론으로 과장하지 않고 fixture 범위만 보고한다.
5. `git diff --check`와 변경 영역의 데이터 계약 테스트가 통과한다.

## 5. 명시적 금지 사항

- 부산 전체 512 시나리오의 실제 경로 수집·재측정을 이 작업에 끼워 넣지 않는다.
- 후보 부족을 이유로 일반 식당, `hold`, 운영시간 미확인 장소를 대표 추천으로 승격하지 않는다.
- 실제 API 결과가 부족하다는 이유로 직선거리 추정치를 `route_verified_measurement`로 표시하지 않는다.
- 정책·엔진·UI 문서를 직접 변경하지 않는다. 충돌은 인수인계한다.
