## 0. 한 줄 요약

**TourAPI는 "후보 + (텍스트)운영시간"까지만 준다. 시간-적합의 3대 입력(체류·이동·혼잡)은 TourAPI가 안정적으로 주는 게 0개다.** → 자체 알고리즘/외부데이터로 메워야 하며, 그 타당성을 먼저 검증한다.

## 1. 엔진 입력 × TourAPI 제공 매핑 (카탈로그 분석 결과)

| 엔진 입력 | TourAPI | 상태 | 메우는 방법(가설) |

## 6. 라이브 검증 결과 (2026-06-15 · `scripts/verify_tourapi.mjs` · 전국 표본 5개 시도)

| contentType | 운영시간 필드/채움률 | 휴무/기타 | 체류시간 |
|---|---|---|---|
| 관광지(12) | `usetime` **90%** | `restdate` 93% | ❌ 필드 없음 |
| 문화시설(14) | `usetimeculture` **100%** | `restdateculture` 100% | `spendtime` **10%**(사실상 무용) |
| 음식점(39) | `opentimefood` **100%** | `restdatefood` 97% | ❌ 필드 없음 |
| 쇼핑(38) | `opentime` **97%** | `restdateshopping` 97% | ❌ 필드 없음 |
| 여행코스(25) | `taketime` 90% · `schedule` 100% | `distance` 97% | (코스 전체 소요값) |
| 레포츠(28) | `usetimeleports` 90% | `openperiod` 0% | ❌ 필드 없음 |

**집중률(15128555) 프로빙**: `TatsCnctrRateService/tatsCnctrRatedList` → 403(활용신청 미승인 추정), `…Service1` → 500, `DataLabService/tarRlteTarService` → 404. → 정확 경로는 R2로 확정 후 활용신청.

### V2-심화: per-POI 체류시간 전체 필드 덤프 (`scripts/probe_dwell_fields.mjs`)
**확정: TourAPI에 관광지별(per-POI) 체류시간 데이터는 없다.** 6개 타입 전체 필드 덤프 + 여행코스 구성지점(`detailInfo2`)까지 확인한 결과, 체류시간으로 잡힌 값은 모두 **운영시간(`usetime`류)** 또는 false positive였다.
- 관광지(12)/음식점(39)/쇼핑(38)/레포츠(28): per-POI 체류 필드 **없음**.
- 문화시설(14) `spendtime`: 명목상 존재하나 샘플 0% (전체 10%) → 무용.
- 여행코스(25) `taketime`: 존재하나 **코스 전체 소요**(예 7시간)이지 per-POI 아님. `detailInfo2`로 쪼개도 구성지점별 소요 없음(이름·개요·이미지뿐).
- → 결론: 필드스키마·채움률·전체덤프 3중 확인 일치. **체류시간은 자체 추정 필수.**

### per-POI 체류시간 추정 아키텍처 (TourAPI 직접값 부재 → POI별 추정)
1. **`cat1/cat2/cat3` 신분류코드 기반 세분류 체류 테이블** — contentTypeId(8종)보다 촘촘. "per-POI"에 가장 근접. (1차 진실원)
2. **실제값 override**: 문화시설 `spendtime`(10%), 여행코스 `taketime` 정규식 분 추출 성공 시.
3. **`overview` LLM 추출**(보조·불확실): "관람 약 1시간" 류 언급 채택.
4. **상위 후보 한정 BestTime.app 라이브 보정**(R1) — 전국 전수 불가.

**결론**:
- **운영시간 = 데이터 탄탄(신뢰 가능)** → 시간-적합의 "지금 열려있나" 축은 TourAPI로 해결.
- **체류시간 = TourAPI 불가 → 자체 테이블 필수**(R1 산출물).
- **이동시간 = TourAPI 없음 → TMAP/휴리스틱**(R3 산출물).
- **혼잡 = 옵션(재료). MVP는 시간대·요일 휴리스틱**(R2 산출물), 라이브는 활용신청 후.
