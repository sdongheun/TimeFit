# QA-MULTISTOP-RECEIPT-01 — 다장소 unavailable 원인 실기기 판정

## 상태

실행 전. `2-T` → `API-MULTISTOP-RECEIPT-02` → `U-DIAG-SHAPE-02` 수락 뒤의 [통합 관찰 계약](../integration-decision/multistop-receipt-observability-contract.md) 마지막 단계다.

## 목적

production A8에서 다장소 receipt가 `unavailable`일 때, 이미 안전하게 보존된 reason을 두 고정 입력으로 읽어 **다음 수정 소유 경계 하나**를 정한다. 추천 수·호출 한도·데이터를 바꾸는 검증이 아니다.

## 시작 전 확인

1. 다음 값이 bundle 시점에 정확히 적용된 새 iOS internal build여야 한다.

```text
EXPO_PUBLIC_RECOMMENDATION_DIAGNOSTICS=true
EXPO_PUBLIC_RECOMMENDATION_INTERNAL_B12=false
```

2. 결과 화면에 `개발용 추천 진단`, `내부 정책: A8`, `1곳 코스`·`2곳 코스`·`3곳 코스`가 보인다.
3. 2곳 `경로 확인 불가`가 1 이상이면 바로 아래에 `확인 불가 사유`가 보일 수 있다.

1~2가 불일치하면 실행하지 않고 `빌드/환경 불일치`로 중단한다. `내부 정책: B12` 또는 N1/N2/W/T만 보이면 이 QA에 세지 않는다.

### 빌드 방법

환경값 자체는 이미 정해져 있으므로 새 값을 추가하거나 앱을 삭제할 필요는 없다. U-DIAG-SHAPE-02의 UI code를 기기에 반영하기 위해 Metro를 종료했다가 clear로 재시작하고, Xcode에서 새 internal build를 해당 실기기에 설치한다. 설치 후 기존 결과 화면을 재사용하지 말고 앱을 처음부터 열어 아래 입력을 설정한다.

## 실행 — 총 두 번만

각 흐름은 정확히 한 번만 실행한다. 새 추천, 같은 입력 재시도, cache 삭제, 앱 재설치 반복, B12 전환, 시간/장소 변경은 금지한다.

| ID | 입력 | 목적 |
| --- | --- | --- |
| RCV-01 | 서면역 복귀 · 개발 시작 15:00 · 약 120분 · 여유 10분 | 밀집 생활권 다장소 receipt 사유 |
| RCV-02 | 사상역 → 서면역 · 개발 시작 15:00 · 약 120분 · 여유 10분 | 도착지 흐름의 같은 사유 |

각 결과에서 장소 상세나 카카오맵을 열지 말고, 화면에 나온 아래 **숫자·안전 label만** 기록한다.

- 내부 정책 A8 여부
- 1·2·3곳의 `큐 후보 / 시도 / 검증 / 경로 확인 불가`
- 2·3곳 `확인 불가 사유` label별 건수 (없는 경우 `없음`)
- 총 `새 경로 확인 / adapter 호출 / 재사용`
- 결과 코스 수만 기록한다. 장소명·ID·좌표·주소·URL·provider 원문·cache key·JWT/token·사용자 ID·키는 기록 금지다.

앱 멈춤, 시간표 모순, 중복 장소, 조건부 자동 승격, route proxy/CAPTCHA 오류가 나타나면 즉시 중단하고 오류의 safe UI label만 적는다.

## 판정 — 다음 작업은 한 경계만 지정

| 관찰된 2곳 reason | 판정과 다음 소유 경계 |
| --- | --- |
| `제공사 한도` | API: budget/rate/cache 상태를 fixture로 재현. 호출 상한을 즉시 올리지 않는다. |
| `동일 경로 처리 중` | API: in-flight lease/reuse 이후 제한 재시도 정책만 검토. |
| `경로 저장소` | API·DB: Route Proxy RPC/store 가용성 경계를 분리. |
| `경로 제공사` 또는 `경로 통신` | API: Kakao 요청·응답 실패 fixture와 proxy timeout/변환 경계 조사. |
| `경로 응답 형식` | API: Kakao response normalizer 계약을 고정 fixture로 조사. |
| `경로 요청 거절` | API: public snapshot/catalog version·Auth request 경계를 조사. |
| `안전상 원인 미확인` 또는 사유 없음 | API: mobile adapter의 receipt 누락/로컬 budget 경계를 먼저 조사. 원인을 API 제공사로 단정하지 않는다. |
| 두 실행의 reason이 다름 | reason별로 분리 기록하되, 가장 자주 나온 reason을 임의 우선하지 않는다. 통합·결정이 두 원인을 함께 판정한다. |

`경로 확인 불가`가 0이면 이 문서의 원인 판정 대상이 아니다. 검증 수와 결과 코스 수가 어긋나는 엔진/UI 문제인지 통합·결정에 인계한다.

## 완료 기준

- 두 번 또는 유효한 중단 한 번의 입력·안전 숫자·판정만 이 문서에 기록한다.
- 실제 API 호출은 위 두 검증 요청 외 추가하지 않는다.
- 이 문서에서 코드·환경값·호출 상한·카탈로그·추천 정책·UI를 수정하거나 배포하지 않는다.

### 1. 변경 파일과 목적

- 이 문서: RCV-01의 화면 안전 집계와 중간 판정을 기록했다.

### 2. 유지한 공개 계약·정책 경계

- 추천 엔진·UIUX·API·cache·DB·환경값·호출 상한·카탈로그·제품 정책과 작업 조정 보드는 수정하지 않았다.
- build 전에 public flag를 비밀값 없이 확인했고, `diagnostics=true` 및 `internal B12=false` 조합이 유효했다. RCV-01은 A8 새 internal build에서 정확히 1회만 실행했으며 재시도·cache 삭제·B12 전환·더 보기·장소 상세·카카오맵 이동을 하지 않았다.

### 3. 테스트와 실기기 결과

- 실행 전 receipt/shape/UI 안전 계약 38/38 및 `npm run test:typecheck`를 통과했다. Metro cache-clear 상태의 새 A8 internal build를 설치·실행했다.
- **RCV-01 입력:** 서면역 복귀, 개발 시작 15:00, 약 120분, 여유 10분.
- 내부 정책은 `A8`, 결과 코스 수는 1개였다. 총 `새 경로 확인 3`, `adapter 호출 4`, `재사용 0`이 표시됐다.
- 1곳: 큐 후보 18 / 시도 1 / 검증 1 / 경로 확인 불가 0.
- 2곳: 큐 후보 153 / 시도 1 / 검증 0 / 경로 확인 불가 1. `확인 불가 사유`는 `경로 저장소 1`이었다. 시간 예산 초과·경로 미검증은 각각 0이었다.
- 3곳: 큐 후보 816 / 시도 0 / 검증 0 / 경로 확인 불가 0.
- 결과 탈락에는 `경로 확인 불가 1`이 표시됐다. 장소명·ID·좌표·주소·URL·provider 원문·cache key·JWT/token·사용자 ID·키는 기록하지 않았다.

### 4. 다음 실행·위험

- 2곳 후보/queue 부족이나 시간 초과가 아니라, 첫 다장소 receipt의 `경로 저장소` safe reason이 관찰됐다. 표의 단일 실행 기준으로는 API·DB 저장소 가용성 경계가 후보이나, 최종 소유 경계는 RCV-02의 사유와 함께 정한다.
- **RCV-02**(사상역→서면역, 개발 시작 15:00, 약 120분, 여유 10분)를 정확히 1회 실행한다. reason이 다르면 빈도 우선으로 단정하지 않고 통합·결정 인계로 남긴다. 오류/중복/시간표 모순이 나오면 즉시 중단한다.

### 1. 변경 파일과 목적

### 2. 유지한 공개 계약·정책 경계

### 3. 테스트와 실기기 결과

- 실행 전 receipt/shape/UI 안전 계약 38/38 및 `npm run test:typecheck`를 통과했고, cache-clear Metro 상태의 새 A8 internal build에서 실행했다.
- **RCV-01:** 서면역 복귀, 개발 시작 15:00, 약 120분, 여유 10분. A8, 결과 코스 1개. 1곳 18/1/1/0, 2곳 153/1/0/1, 3곳 816/0/0/0 (각각 큐 후보/시도/검증/경로 확인 불가). 2곳 사유 `경로 저장소 1`; 새 경로 확인 3, adapter 호출 4, 재사용 0.
- **RCV-02:** 사상역→서면역, 개발 시작 15:00, 약 120분, 여유 10분. A8, 결과 코스 1개. 1곳 18/1/1/0, 2곳 153/1/0/1, 3곳 816/0/0/0 (각각 큐 후보/시도/검증/경로 확인 불가). 2곳 사유 `경로 저장소 1`; 새 경로 확인 6, adapter 호출 4, 재사용 0.

- 장소명·ID·좌표·주소·URL·provider 원문·cache key·JWT/token·사용자 ID·키는 기록하지 않았다.

### 4. 다음 세션의 결정 필요 사항·위험·재현 조건

- **다음 수정 소유 경계: API·DB Route Proxy/RPC 저장소 가용성.** 두 독립 입력에서 2곳 후보가 153개로 존재하고 1회 시도됐으나, 동일한 non-zero safe reason `경로 저장소`으로 검증 전에 unavailable이 됐다. 따라서 후보 공급·queue 순서·시간 예산을 바꾸지 말고 API·DB가 Route Proxy receipt 저장/조회 RPC·store 가용성 경계를 fixture로 분리해야 한다.
- 이 결과는 provider, transport, response format, Auth rejection 또는 호출 한도의 원인이라고 말하지 않는다. `경로 저장소` safe label이 보존한 범위를 넘어 원인을 추정하지 않는다.
- 호출 상한 상향, 카탈로그 승격, 다장소 강제, production 배포는 이 QA의 범위 밖이다. API·DB 계약 보완 뒤 새 build가 제공될 때만 같은 두 고정 입력을 새 1회로 재개할 수 있다.
