# 2곳 코스 구현 기준 토의

## 문서 목적과 경계

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 근거 감사: [2-X 출시 2곳 코스 재도입 준비 감사](release-two-stop-readiness-audit.md)
- 목적: production one-stop을 유지한 상태에서 2곳 코스 구현 전에 필요한 제품·엔진·API·UI 계약을 사용자와 질의응답으로 결정한다.
- 현재 단계: 토의 전용. 이 문서의 답변만으로 production entry나 feature flag를 활성화하지 않는다.
- 수정 금지: 제품 코드, 테스트, `docs/03_product/추천로직.md`, `docs/테스트.md`, `docs/작업조정_보드.md`.
- 기록 원칙: 각 질문은 부모 결정, 질문 이유, 선택지별 영향, 사용자 답변, 상태를 남긴다. 답변하지 않은 사항은 `미답변`이며 하위 결론을 임의 확정하지 않는다.

## 2-X에서 확인된 출발점

- pair 생성, 세 exact leg 검증, 두 장소의 도착별 운영시간·체류·총시간 계산은 보존 엔진에서 재사용할 수 있다.
- 기존 다장소 entry는 1·2·3곳, 자동 8→16회, mixed continuation을 함께 포함하므로 production에 그대로 다시 연결할 수 없다.
- 2곳 한 코스는 `origin → A → B → destination/return`의 3개 leg이며, cache 재사용이 없으면 신규 provider attempt 최소 3·최대 6이다.
- 대표 장소 사이 `A→B`는 public store 경계를 통과하며, 과거 `store unavailable`의 구체적인 실패 RPC와 현재 복구 여부는 미확인이다.
- 2곳의 세 transit leg 양끝을 모두 보충하려면 상세 connector가 이론상 최대 6개여서 one-stop의 최대 4개 계약을 그대로 적용할 수 없다.
- 2-X 권장은 공모전 이후 재개였으며, 실제 구현 전 사용자 결정과 public store 재현이 선행돼야 한다.

## 질문 진행 순서

1. 2곳 코스의 제품상 위치와 대표 우선순위
2. single과 pair의 중복 의미
3. 최초 검증 예산과 요청형 이어보기
4. 2곳 전용 continuation과 부분 leg 재개
5. 한 leg 실패 시 처리
6. 45·78·120분 노출 범위와 결과 부족 표현
7. 세 geometry와 endpoint connector 상한
8. public `A→B` store 선행 게이트와 활성화 조건

하위 질문은 앞선 답변에 따라 선택지와 필요성이 달라질 수 있다.

## Q-2STOP-01 — 2곳 코스의 제품상 위치와 대표 우선순위

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 질문이 필요한 이유: 현행 결과는 실제 검증 single 대표 1개와 single 대안·더보기로 구성된다. 기존 mixed selector는 1곳과 2곳을 같은 대표 풀에서 비교하지만, 이를 다시 사용하면 사용자가 요청하지 않아도 대표가 2곳으로 바뀔 수 있다. 반대로 2곳을 항상 별도 영역에 두면 one-stop 안정성은 유지되지만 2곳이 더 적합해도 상단 대표가 되지 않는다. 이 선택이 후속 중복·pagination·호출 예산·UI 계약의 부모가 된다.

### 선택지와 영향

| 선택지 | 의미 | 사용자 경험 | 엔진·호출 영향 | 후속 질문 영향 |
| --- | --- | --- | --- | --- |
| A. single 대표 유지 + 2곳 별도 영역 | 현행 대표·대안은 그대로 두고, 검증된 pair를 별도 `2곳 코스` 영역에 추가 | 기존 결과가 흔들리지 않고 2곳을 추가 선택지로 이해하기 쉽다 | one-stop 계산 뒤 별도 요청 또는 분리된 pair budget이 필요하다 | mixed 중복과 pair 전용 continuation을 별도로 결정해야 한다 |
| B. single·pair 통합 순위 | 검증된 1·2곳을 같은 목록에서 비교해 가장 적합한 코스를 대표로 선택 | 시간에 따라 2곳이 바로 대표가 될 수 있지만 결과 형태가 입력마다 크게 달라진다 | 공통 budget·대표 comparator·nested 중복 정책을 다시 결정해야 한다 | 기존 single 대표 순서 보존 계약을 교체해야 한다 |
| C. 사용자가 `한 곳/두 곳` 모드를 먼저 선택 | 추천 시작 전에 사용자가 원하는 코스 형태를 고른다 | 의도는 명확하지만 첫 화면 선택이 늘고, 2곳 결과가 없을 때 실망·재시도 비용이 생긴다 | pair-only entry와 독립 budget을 설계하기 쉽다 | 모드 기본값과 실패 시 one-stop 전환 여부를 추가 결정해야 한다 |

- 현재 권고안: **A**. public `A→B` store와 3-leg 비용이 아직 불확실하므로 현행 one-stop 대표를 보존하면서 2곳을 독립적으로 검증하는 방식이 가장 되돌리기 쉽다. 이 권고는 사용자 답변 전 확정이 아니다.
- 사용자 답변: **B — single·pair 통합 순위**. 현재와 같은 API 호출량만으로는 2곳 코스가 나오지 않을 수 있으므로 호출량을 늘리는 것을 전제로 한다. 한 번의 기본 추천에서 1곳·2곳 코스를 합쳐 최소 3개 이상을 보여 주고, 추가 추천은 더보기 버튼으로 요청한다.
- 상태: **조건부 확정**. 통합 순위 방향은 확정했지만, `기본 3개 이상`이 목표인지 하드 보장인지, 세 결과에 1곳과 2곳을 각각 반드시 포함할지, 호출 상한과 검증 결과가 부족할 때의 종료 방식을 아직 결정하지 않았다.
- 부모 결정에 미치는 영향: A는 `DEC-RELEASE-MULTISTOP-01`의 one-stop 출시 경계를 유지한 점진 확장이고, B/C는 사용자 결과 구조 또는 입력 흐름을 바꾸므로 통합·결정 문서의 후속 확정이 필요하다.

### Q-2STOP-01 답변에 따른 영향

- 현행 single 대표 순서 보존 계약은 2곳 활성화 시 교체 대상이다. 검증된 single과 pair를 같은 comparator와 같은 기본 결과 목록에서 평가해야 한다.
- production one-stop entry를 그대로 확장하지 않는다. 2-X 결론대로 pair-only 내부 검증 경계를 먼저 만들고, 통합 결과 선택기는 별도 결정 뒤 설계해야 한다.
- 호출량 증가는 아직 숫자가 정해지지 않았다. 첫 public `A→B` store가 fail-closed이면 상한을 늘려도 pair 결과가 생기지 않는 반례가 유지되므로 API 선행 게이트를 제거하지 않는다.
- 더보기는 최초 결과를 재정렬하지 않고 다음 미검증 single/pair를 추가하는 방향 후보지만, continuation 통합 방식은 후속 질문 전 미확정이다.

## Q-2STOP-02 — 기본 3개의 구성과 부족할 때의 처리

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-01`의 B — single·pair 통합 순위
- 질문이 필요한 이유: API 호출량을 늘려도 실제 route, 두 장소의 운영시간, 최소 체류, public store 중 하나가 실패하면 검증 코스 3개를 항상 만들 수 없다. `3개 이상`을 하드 보장으로 해석하면 근사 경로, 미검증 장소, 자동 체류 축소 또는 호출 무제한 같은 현행 금지 방식을 요구하게 된다. 또한 세 결과가 모두 single이어도 되는지, pair를 반드시 포함해야 하는지에 따라 queue와 예산 배분이 달라진다.

### 선택지와 영향

| 선택지 | 기본 결과 계약 | 검증 결과가 3개 미만일 때 | 엔진·호출 영향 |
| --- | --- | --- | --- |
| A. 총 3개 목표, 형태 강제 없음 | 검증된 single/pair를 통합 순위로 최대한 모아 기본 3개 이상을 목표로 한다 | 상한 안에서 통과한 결과만 0~2개 표시하고 부족 이유를 안내한다 | 가장 안전하지만 세 결과가 모두 single이거나 모두 pair일 수 있다 |
| B. 총 3개 목표 + single/pair 각각 최소 1개 목표 | 가능하면 기본 세 결과에 single과 pair를 각각 하나 이상 포함한다 | 한 형태가 없으면 다른 형태로 억지로 채우지 않고 검증된 결과만 표시한다 | queue를 형태별로 배분해야 하며 pair의 public store 실패가 전체 초기 지연을 늘릴 수 있다 |
| C. 검증 결과 3개 하드 보장 | 기본 화면에 반드시 3개를 표시한다 | 정확 검증 3개가 없으면 추천 자체를 실패 처리하거나 별도 fallback을 새로 승인해야 한다 | 현재 fail-closed·유한 호출 계약과 충돌한다. 근사/미검증 fallback 없이는 가용성을 보장할 수 없다 |

- 현재 권고안: **B를 목표 계약으로 사용하되 부족하면 적은 결과를 정직하게 표시**. 사용자가 2곳 방향을 선택한 의미를 살리면서도 검증되지 않은 코스를 만들지 않는다. 다만 이 권고는 사용자 답변 전 확정이 아니다.
- 사용자 답변: **B — 총 3개 이상을 목표로 하고, 가능하면 single과 pair를 각각 최소 1개 포함한다.** 사용자는 가능한 한 많은 검증 추천이 제공되는 것이 UX에 좋다고 판단했다. 상한 안에서 한 형태가 부족하면 미검증·근사 결과로 채우지 않고 실제로 통과한 결과만 표시한다.
- 상태: **확정**. `기본 3개`는 정확 검증된 결과의 목표이며 하드 보장이 아니다. 실제 통과 결과가 3개 미만이어도 추천 전체를 실패시키거나 조건을 낮추지 않고 적은 결과를 정직하게 표시한다.
- Q-2STOP-01에 미치는 영향: A/B를 고르면 Q-2STOP-01의 통합 순위가 안전한 목표 계약으로 확정될 수 있다. C를 고르면 현행 fail-closed 정책과 충돌하므로 fallback 종류에 대한 상위 결정을 먼저 열어야 한다.

### Q-2STOP-02 확정에 따른 구현 기준

- 기본 결과 선택기는 검증된 single/pair 전체를 같은 순위 기준으로 비교하되, 결과가 3개 이상 가능한 경우 single과 pair가 각각 최소 1개 포함되도록 검증 기회를 배분한다.
- 이는 낮은 순위의 형태를 무조건 결과에 끼워 넣는 하드 quota가 아니다. 각 형태가 실제 route·운영시간·최소 체류·도착 여유를 통과했을 때만 구성 목표를 적용한다.
- 기본 결과가 목표를 충족하면 남은 후보는 자동 검증하지 않고 더보기용으로 보존하는 방향이다. 정확한 중단 시점과 attempt 상한은 Q-2STOP-03에서 결정한다.

## Q-2STOP-03 — 최초 추천의 provider attempt 상한과 조기 중단

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-01` B, `Q-2STOP-02` B
- 질문이 필요한 이유: one-stop은 첫 요청 최대 8 attempt지만, 비재사용 최악 기준 single 한 개는 최대 4, pair 한 개는 최대 6 attempt다. single/pair를 각각 포함한 세 코스를 얻을 가능성을 열려면 8회는 부족할 수 있다. 반면 상한을 무조건 소비하면 첫 화면 지연·Kakao 비용이 늘고 더보기의 의미가 약해진다. 첫 public `A→B` store가 실패하면 상한 증가도 pair를 만들지 못한다.

### 선택지와 영향

| 선택지 | 최초 검증 방식 | 장점 | 위험·비용 |
| --- | --- | --- | --- |
| A. 최대 12회 적응형 | single/pair를 교차 검증하고 총 3개+두 형태 충족 시 즉시 중단, 아니면 12회까지 사용 | 현행 8회보다 기회를 늘리면서 지연 증가를 제한 | worst-case 2-attempt leg에서는 single 1+pair 1 뒤 세 번째 코스를 완결하지 못할 수 있다 |
| B. 최대 16회 적응형 | 총 3개 이상과 single/pair 각 1개를 충족하면 즉시 중단하고, 부족할 때만 최대 16회까지 진행 | 1 single+2 pairs의 worst-case `4+6+6=16` 또는 2 singles+1 pair `4+4+6=14`까지 수용 가능 | 첫 결과가 부족한 입력에서는 현행보다 최대 2배 호출·지연. store 실패를 해결하지는 못함 |
| C. 16회 고정 소비 | 결과가 3개 생겨도 16회까지 계속 검증해 첫 화면에 가능한 결과를 더 많이 제공 | 첫 화면 결과 수가 가장 많을 가능성 | 불필요한 호출·지연이 크고 추가 결과는 더보기로 제공한다는 앞선 방향과 충돌 |

- 현재 권고안: **B — 최대 16회 적응형**. 기본 목표를 달성하면 즉시 멈추고 남은 후보를 더보기에 보존한다. 16은 목표 달성 가능성을 여는 상한이지 결과 3개 보장이나 store 실패 재시도 횟수가 아니다.
- 사용자 답변: **B — 최대 16회 적응형**.
- 상태: **확정**. 최초 추천은 신규 provider attempt 최대 16회이며, 정확 검증 결과가 총 3개 이상이고 single/pair가 각각 최소 1개 포함되는 즉시 중단한다. 목표를 충족하지 못할 때만 16회까지 진행하며, 16회는 결과 수 보장이나 store 실패 반복 재시도를 의미하지 않는다.
- 부모 결정에 미치는 영향: A/B는 유한 호출과 더보기 원칙을 유지한다. C는 기본 결과를 최대한 많이 보여 주려는 UX와 비용·응답시간 중 무엇을 우선할지 다시 상위 결정해야 한다.

### Q-2STOP-03 확정에 따른 구현 기준

- 현행 one-stop의 최대 8회 계약을 2곳 활성화 경로에 그대로 적용하지 않는다. 다만 one-stop-only fallback이나 기존 production entry의 상한을 이 토의만으로 변경하지 않는다.
- 16회에 도달하기 전에 `검증 코스 ≥3`, `검증 single ≥1`, `검증 pair ≥1`을 모두 충족하면 남은 후보·예산을 소비하지 않고 continuation에 보존한다.
- 목표 미충족 상태라도 candidate queue 소진, typed provider/store unavailable 같은 terminal 상태면 16회를 채우기 위해 계속 호출하지 않는다.
- cache/session/in-flight reuse의 `newProviderAttemptCount=0`은 16회에 포함하지 않되 adapter-call 상한은 별도 유지·결정해야 한다.

## Q-2STOP-04 — 최초 16회 예산의 single/pair 검증 순서

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-02` B, `Q-2STOP-03` B
- 질문이 필요한 이유: 통합 순위는 실제 경로 검증이 끝난 뒤에만 계산할 수 있다. 검증 전 queue를 공간 순서만으로 구성하면 single이 먼저 3개 성공해 pair가 16회 안에 시도되지 않거나, 반대로 비용이 큰 pair가 연속 실패해 기본 single 결과까지 늦어질 수 있다. 기본 세 결과에 두 형태를 포함하려는 목표를 위해 검증 기회 배분을 먼저 정해야 한다.

### 선택지와 영향

| 선택지 | queue 순서 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. single/pair 교차 | `S1 → P1 → S2 → P2 ...`; 한 형태가 소진되면 다른 형태 계속 | 두 형태에 조기에 검증 기회를 주고 single 기본 결과도 먼저 확보한다 | P1의 public store terminal 실패가 전체 queue를 중단할지 별도 결정 필요 |
| B. pair 하나 우선 확보 | `P1`을 먼저 검증하고 성공할 때까지 pair를 우선한 뒤 single과 교차 | 사용자가 원하는 2곳 코스가 첫 결과에 들어갈 가능성이 가장 높다 | public store·3-leg 실패가 초기 응답과 single 결과를 지연시킬 수 있다 |
| C. 형태 무시 공간 순서 | single/pair를 구분하지 않고 공간 부담이 낮은 코스부터 검증 | 가장 단순하고 순수 공간 관련성을 유지한다 | 한 형태가 예산을 선점해 Q-2STOP-02의 두 형태 목표를 반복해서 놓칠 수 있다 |

- 현재 권고안: **A — single/pair 교차**. 현행 one-stop 가용성을 먼저 한 번 확보하면서 pair에도 두 번째 검증 기회를 보장한다. 다만 pair의 typed store unavailable이 single 검증까지 끝낼지 여부는 별도 실패 처리 질문에서 확정해야 한다.
- 사용자 답변: **A — single/pair 교차**. 다만 `single: A,B,C`, `pair: A→B,A→C`처럼 같은 장소가 여러 카드에서 반복되는 결과는 UX에 좋지 않으므로 중복 방지 방법을 먼저 깊게 결정해야 한다.
- 상태: **조건부 확정**. `S1→P1→S2→P2` 형태의 검증 기회 교차는 선택됐지만, pair 후보가 이미 추천된 single 또는 다른 pair의 장소를 공유하지 않도록 하는 범위·시점을 Q-2STOP-05에서 확정해야 한다.
- 부모 결정에 미치는 영향: A/B는 형태별 queue와 diagnostics가 필요하다. C는 Q-2STOP-02의 “가능하면 각 형태 최소 1개”를 약화하므로 선택 시 해당 결정을 조건부로 되돌려야 한다.

### 현재 중복 제거 코드의 한계

- `preselectLimitedCourseV1`는 `A→B`와 `B→A`를 같은 place set으로 합쳐 한 순서만 continuation queue에 둔다.
- `selectNonNestedCourseV1`는 single `A`와 pair `A→B`처럼 한쪽이 다른 쪽의 부분집합인 결과를 함께 반환하지 않는다.
- 그러나 pair `A→B`와 pair `A→C`는 어느 쪽도 다른 쪽의 부분집합이 아니어서 함께 반환될 수 있다. `A`가 반복된다는 사용자 관점의 중복을 막지 못한다.
- 결과 선택 뒤에만 중복을 제거하면 이미 겹치는 pair의 세 leg API 비용을 소비할 수 있다. 반대로 검증 전부터 모든 겹침을 차단하면 아직 route 실패 여부를 모르는 장소를 너무 일찍 예약해 결과 수를 줄일 수 있다.

## Q-2STOP-05 — 장소 중복 금지 범위

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-01` B, `Q-2STOP-02` B, `Q-2STOP-04` A
- 질문이 필요한 이유: “같은 장소가 계속 추천되지 않아야 한다”를 구현하려면 중복 단위를 코스가 아니라 place ID로 정해야 한다. 또한 금지 범위를 기본 세 결과까지만 적용할지, 사용자가 더보기를 누른 뒤의 전체 세션까지 적용할지에 따라 continuation 상태와 확보 가능한 결과 수가 달라진다.

### 선택지와 영향

| 선택지 | 중복 규칙 | 장점 | 비용·제약 |
| --- | --- | --- | --- |
| A. 추천 세션 전체에서 place ID 1회만 노출 | 기본 결과와 모든 더보기 결과를 합쳐 한 장소는 한 카드에만 등장한다. `A`, `A→B`, `A→C`, `B→C` 중 선택된 카드와 장소가 겹치는 나머지는 표시하지 않는다 | 사용자가 매번 새로운 장소를 보며 중복 체감이 가장 적다 | 1 single+2 pairs로 기본 3개를 만들려면 최소 5개, 2 singles+1 pair면 최소 4개의 서로 다른 검증 장소가 필요하다. continuation에 사용 완료 place ID가 필요하다 |
| B. 기본 결과에서만 place ID 중복 금지 | 첫 화면의 세 코스는 서로 장소가 겹치지 않지만 더보기에서는 기존 장소를 포함한 새로운 조합을 허용한다 | 첫인상은 다양하고 후속 조합 수는 많이 확보한다 | 더보기를 누르면 사용자가 지적한 `A` 반복이 다시 나타날 수 있다 |
| C. 중복 금지가 아니라 강한 감점 | 겹치지 않는 코스를 우선하되 세 결과가 부족하면 겹치는 pair도 표시한다 | 기본 3개 목표를 달성하기 가장 쉽다 | “중복이 일어나선 안 된다”는 요구와 충돌한다 |

- 현재 권고안: **A — 추천 세션 전체에서 place ID 1회만 노출**. 사용자가 명시한 UX 문제를 가장 직접적으로 해결한다. 결과가 부족할 때도 중복 코스로 숫자를 채우지 않고, Q-2STOP-02에 따라 적은 결과를 표시한다.
- 사용자 답변: 사용자는 장소 중복의 명확한 기준을 세우기 어렵다고 판단했고, 대안으로 과거의 장바구니 시스템이 더 나은지 검토를 요청했다.
- 상태: **보류·상위 대안 검토 중**. 세션 전체/기본 결과 중복 범위는 확정하지 않는다. 추천 단위를 완성 코스로 유지할지 사용자 조립으로 바꿀지 Q-2STOP-06에서 먼저 결정한다.
- 부모 결정에 미치는 영향: A를 선택하면 결과 선택은 단순 정렬이 아니라 서로 겹치지 않는 코스 집합을 고르는 과정이 된다. one-stop/pair continuation은 `usedPlaceIds` 또는 동등한 opaque set을 공유해야 하며, 더보기에서도 이미 노출한 장소가 든 코스는 route 호출 전에 건너뛰어야 한다. B/C는 Q-2STOP-02의 결과 수를 더 쉽게 확보하지만 사용자가 제기한 반복 UX를 완전히 제거하지 못한다.

### Q-2STOP-05 이후에도 남는 구현 질문

- strict 중복 금지 시 어떤 코스 조합을 선택해야 전체 공간 관련성·시간 적합성이 가장 좋은지 결정해야 한다. 예를 들어 최고 점수 single `A`를 먼저 고르면 좋은 pair `A→B`를 잃을 수 있으므로, 카드 하나씩 greedy 선택할지 기본 결과 세트를 함께 비교할지 별도 결정이 필요하다.
- 검증 전 후보를 겹침 때문에 제거할지, 실제 검증은 허용하고 표시 세트에서만 제거할지, 두 단계 혼합으로 할지는 호출 비용 질문과 함께 결정해야 한다.
- route 실패로 표시되지 않은 장소는 `used`로 보지 않는다. 실패한 `A→B` 때문에 A와 B의 다른 유효 코스를 모두 막는 규칙은 아직 승인하지 않는다.

## Q-2STOP-06 — 추천 단위: 완성 코스와 장바구니 중 무엇을 사용할지

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-05`의 중복 문제
- 질문이 필요한 이유: place ID 중복은 엔진이 여러 완성 코스를 미리 조립하면서 생긴다. 장바구니는 사용자가 서로 다른 장소를 직접 고르므로 표시 중복 문제를 줄이고 public `A→B` 호출을 명시 선택 뒤로 미룰 수 있다. 그러나 사용자가 조립 책임을 지고, 개별로 가능한 두 장소도 조합하면 시간·운영시간·경로에서 실패할 수 있다. 이는 세부 중복 규칙이 아니라 제품의 추천 단위를 바꾸는 결정이다.

### 선택지와 영향

| 선택지 | 기본 흐름 | 장점 | 주요 문제·비용 | 앞선 결정 영향 |
| --- | --- | --- | --- | --- |
| A. 엔진이 완성된 single/pair 코스를 추천 | 기본 화면에 통합 순위 코스 3개 이상을 목표로 표시 | 사용자가 조립하지 않아도 바로 고를 수 있고 코스마다 세 leg가 이미 검증됨 | 중복 없는 코스 집합 선택, 최대 16회, public store와 mixed continuation이 모두 필요 | Q-2STOP-01~04 유지, Q-2STOP-05 중복 규칙 확정 필요 |
| B. 과거형 자유 장바구니 | 장소 후보를 보여 주고 사용자가 원하는 장소를 담아 순서·코스를 만든다 | 장소 반복은 선택 UI에서 쉽게 막고 사용자 통제권이 큼 | 후보를 코스 가능으로 오해할 수 있고 조립 후 실패가 잦을 수 있다. 순서 변경·삭제·재검증·저장 상태가 다시 필요 | 기본 mixed 코스 3개와 교차 queue 결정은 철회 또는 대체 필요 |
| C. 검증 장소 추천 + 최대 2곳 제한 조립 | 엔진이 서로 다른 single 후보를 제시하고 사용자가 두 번째 장소를 선택한 순간에만 `origin→A→B→target`을 검증 | 기본 추천은 단순하고 `A→B` 비용·store 위험을 사용자 행동 뒤로 미룬다. 선택 장소 중복은 구조적으로 차단 가능 | 선택 전에는 2곳 조합의 성공을 보장하지 못하며, A/B 순서를 누가 정할지와 조합 실패 후 복귀 UX가 필요 | Q-2STOP-01의 기본 통합 pair와 Q-2STOP-03의 최초 16회는 철회 후보. 더보기는 고유 장소 탐색으로 재정의 필요 |

- 현재 권고안: **C — 최대 2곳 제한 조립**. 완전 자유 장바구니보다 상태와 실패 범위를 제한하면서, 가장 비싼 public `A→B` 검증을 사용자가 2곳을 실제로 원할 때만 수행한다. 다만 사용자가 원한 “기본 화면에 2곳 코스 포함” 방향과 충돌하므로 편의성과 기본 pair 노출 중 무엇을 우선할지 답변이 필요하다.
- 사용자 답변: **C — 과거 장바구니의 필요한 요소만 가져온 최대 2곳 제한 조립**. 구체 조건은 (1) 최대 2곳만 선택, (2) 사용자는 순서를 바꾸지 않고 엔진이 최적 경로 순서를 결정, (3) 첫 장소 선택 시 전체 시간을 다시 계산해 실제로 하나 더 담을 수 있는 장소만 다음 선택지로 표시하는 것이다.
- 상태: **조건부 확정**. 제한형 조립이라는 제품 방향과 최대 2곳·순서 편집 없음·첫 선택 후 재선별은 확정했다. 다만 `최적 경로`를 두 방문 순서의 실제 route 비교로 정의할지, 두 번째 후보를 표시 전에 어디까지 exact 검증할지는 아직 미확정이다.
- 부모 결정에 미치는 영향: A를 고르면 기존 Q-2STOP-01~04를 유지하고 Q-2STOP-05로 돌아간다. B/C를 고르면 Q-2STOP-01의 B와 최초 16회 결정을 조건부 또는 철회로 바꾸고 장바구니/조립 흐름의 별도 질문 트리를 열어야 한다. 어느 경우에도 과거 장바구니 코드를 곧바로 현행으로 간주하거나 구현하지 않는다.

### Q-2STOP-06 답변에 따른 앞선 결정 상태

- `Q-2STOP-01`의 single/pair 완성 코스 통합 순위: **조건부안에서 교체 대기**. 기본 화면이 완성 pair를 자동 생성하는 구조가 아니라 고유 장소 선택 흐름으로 바뀐다.
- `Q-2STOP-02`의 기본 완성 코스 3개와 형태별 최소 1개: **재해석 필요**. 기본 3개가 최초 고유 장소 후보 수를 뜻하는지 아직 답변하지 않았으므로 임의 확정하지 않는다.
- `Q-2STOP-03`의 최초 최대 16 attempt: **재결정 필요**. pair API 비용이 첫 화면이 아니라 첫 장소 선택 뒤의 두 번째 후보 검증 단계로 이동한다.
- `Q-2STOP-04`의 single/pair 교차 queue: **교체**. 자동 pair queue를 만들지 않으므로 더 이상 적용하지 않는다.
- `Q-2STOP-05`의 카드 간 place ID 중복: **구조적으로 단순화**. 최초 고유 장소 목록은 place ID 중복을 제거하고, 두 번째 목록에서는 첫 선택 장소를 제외한다. 다만 서로 다른 두 번째 후보가 화면에 나란히 보이는 것은 각각 대안 장소이므로 중복 코스 문제가 아니다.

### 재계산 원칙

- 첫 장소 A의 기존 one-stop `origin→A→target` 시간에서 단순히 남는 시간을 차감해 B의 가능 여부를 판단하지 않는다.
- B를 추가하면 `A→target`이 `A→B→target` 또는 `origin→B→A→target`으로 교체되므로 전체 세 leg, A/B 도착별 운영시간, 각 선택 체류, 도착 여유를 새 snapshot으로 검증해야 한다.
- 두 번째 후보 목록에서 “담을 수 있음”이라고 표시하려면 근사 공간 점수만으로는 부족하다. exact 검증 전 후보는 `가능`으로 단정하지 않는 원칙을 유지한다.

### 합의된 사용자 선택 흐름

1. 엔진이 현재 위치·목적지·남은 시간 조건에서 방문 후보 장소들을 제시하고, 사용자가 첫 장소 A를 선택한다. 이는 사용자가 전체 카탈로그에서 임의 장소를 만드는 자유 장바구니가 아니다.
2. 엔진은 A를 들르는 경우를 기준으로 각 두 번째 후보 B의 두 순서 `origin→A→B→target`, `origin→B→A→target`을 다시 계산한다.
3. 재계산에는 세 leg의 실제 이동시간, A와 B 각각의 체류시간, 장소별 도착 시각과 운영 가능 여부, 최종 목적지 도착 여유를 모두 포함한다.
4. 두 순서 중 하나 이상이 모든 조건을 통과한 B만 사용자에게 두 번째 장소 후보로 보여 준다. 두 순서가 모두 가능하면 총 이동시간이 더 짧은 순서를 엔진이 채택한다.
5. 사용자는 이렇게 검증된 후보 중 두 번째 장소 하나를 선택할 수 있고, 총 선택 수는 최대 2곳이다. 방문 순서를 사용자가 직접 편집하지 않는다.

아직 정하지 않은 것은 두 번째 후보를 한 번에 몇 개까지 선검증·노출할지, 그 묶음의 provider attempt 상한, 더보기 단위다. 따라서 위 흐름은 합의됐지만 Q-2STOP-08의 호출·페이지 계약까지 확정된 것은 아니다.

## Q-2STOP-07 — 엔진이 정하는 `최적 경로 순서`의 정확도와 호출 비용

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-06` C
- 질문이 필요한 이유: 첫 선택 A와 두 번째 후보 B가 있을 때 실제 최적 순서를 알려면 `A→B`와 `B→A` 두 여정을 비교해야 한다. 첫 A의 one-stop 두 leg가 session cache에 있다고 가정해도, 두 순서를 모두 계산하면 후보 B마다 새 고유 leg가 최대 4개이며 신규 provider attempt가 이론상 최대 8회다. 여러 B를 표시 전에 모두 exact 비교하면 호출량이 급증한다.

### 선택지와 영향

| 선택지 | 순서 결정 방식 | 두 번째 후보 표시 의미 | 호출·정확성 영향 |
| --- | --- | --- | --- |
| A. 두 순서를 실제 경로로 모두 검증 | `origin→A→B→target`과 `origin→B→A→target`을 모두 계산해 totalMin이 작은 유효 순서를 선택 | 표시된 후보는 적어도 한 순서가 exact로 가능하고 선택 순서도 실제 비교상 최적 | A의 기존 leg 재사용 시에도 B당 새 leg 최대 4개·신규 attempt 최대 8회. 후보 여러 개 사전 검증 비용이 큼 |
| B. 공간 점수로 한 순서를 정한 뒤 그 순서만 exact 검증 | 직선 기반 우회 부담이 작은 순서를 먼저 정하고 세 leg 한 세트만 검증 | 표시된 후보는 선택된 순서에서 exact 가능하지만 반대 순서보다 실제로 빠르다는 보장은 없음 | A의 기존 leg 재사용 시 B당 새 leg 최대 2개·신규 attempt 최대 4회. 비용은 낮지만 `최적` 표현을 쓸 수 없음 |
| C. 1차 순서 exact, 실패할 때만 반대 순서 검증 | 공간 우선 순서를 검증하고 실패한 후보만 역순을 시도 | 표시된 후보는 exact 가능하지만 두 순서가 모두 성공할 때 더 빠른 쪽을 비교하지 않음 | 성공이 많으면 B와 비슷하고 실패 시 A 수준까지 증가. `가능한 순서 자동 선택`이라고 표현해야 함 |

- 현재 권고안: **C**. 호출량을 제한하면서 첫 순서가 시간·운영시간·route에서 실패해도 역순으로 살릴 수 있다. 다만 이는 엄밀한 최단 경로가 아니므로 사용자가 말한 `최적경로순`이 반드시 두 순서의 실제 시간 비교를 뜻한다면 A를 선택해야 한다.
- 사용자 답변: **A — 두 방문 순서를 실제 경로로 모두 검증하고, 유효한 순서 중 총 이동시간이 가장 짧은 순서를 엔진이 선택한다.**
- 상태: **확정**. 여기서 `최적`은 직선거리나 공간 점수의 추정값이 아니라 두 순서의 exact leg 결과를 비교한 최단 이동시간을 뜻한다. 한 순서만 유효하면 그 순서를 사용하고, 두 순서가 모두 무효이면 해당 두 번째 후보를 `담을 수 있음`으로 노출하지 않는다.
- 부모 결정에 미치는 영향: A는 두 번째 후보 사전 검증 수와 별도 attempt budget을 강하게 제한해야 한다. B/C는 UI와 문서에서 `최적` 대신 `추천 순서` 또는 `가능한 순서`로 표현해야 한다.

### Q-2STOP-07 확정에 따른 구현 기준

- 첫 선택 A와 두 번째 후보 B의 완성 코스는 `origin→A→B→target`과 `origin→B→A→target`을 각각 exact 검증한다.
- 두 순서가 모두 유효하면 장소 체류시간이 아니라 **세 leg의 총 이동시간 합계**가 짧은 순서를 선택한다. 이동시간이 같을 때의 tie-break는 아직 결정하지 않는다.
- 한 순서만 route·운영시간·최소 체류·도착 여유를 통과하면 그 순서를 선택한다. 두 순서가 모두 실패하면 B를 추가 가능 후보에서 제외한다.
- A의 one-stop 검증 결과와 session cache는 재사용할 수 있지만, 재사용 가능성을 호출 예산 보장으로 오해하지 않는다. 후보 B 하나에 신규 provider attempt가 최악 8회까지 필요할 수 있다.
- 이 결정은 실제 이동시간 최적화만 확정한다. 몇 개의 B를 표시 전에 검증할지, 한 화면의 추가 후보 수와 더보기별 attempt 상한은 Q-2STOP-08에서 결정한다.

## Q-2STOP-08 — 두 번째 장소의 사전 검증 범위와 더보기

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-06` C, `Q-2STOP-07` A
- 질문이 필요한 이유: 사용자는 첫 장소 선택 뒤 실제로 담을 수 있는 장소만 보기를 원한다. 따라서 화면에 표시하기 전에 후보마다 두 방문 순서를 exact 검증해야 한다. 후보 하나가 최악 8 attempt를 쓸 수 있어 모든 카탈로그 후보를 한꺼번에 확인하면 호출량과 대기시간이 사실상 무제한이 된다. 반대로 탭한 뒤에만 검증하면 실패할 후보도 화면에 보여 사용자 요구와 충돌한다.

### 선택지와 영향

| 선택지 | 두 번째 장소 목록 생성 방식 | 사용자 경험 | 호출·계약 영향 |
| --- | --- | --- | --- |
| A. 모든 후보를 exact 선검증 | 첫 장소와 조합 가능한 전체 후보를 모두 검증한 뒤 한 번에 표시 | 처음부터 가능한 후보를 가장 많이 볼 수 있음 | 카탈로그 크기에 따라 호출·대기 상한이 없어 운영하기 어렵고, 첫 성공 결과도 늦어진다 |
| B. 유한 묶음 exact 선검증 + 더보기 | 공간·운영시간 로컬 필터를 통과한 후보를 순서대로 exact 검증하고, 정해진 표시 목표 또는 attempt 상한에 도달하면 가능한 후보만 표시한다. 더보기는 다음 미검증 묶음을 이어서 검사한다 | 보이는 후보는 모두 실제로 추가 가능하며, 첫 화면 지연과 호출량을 제한할 수 있음 | 묶음별 표시 목표·attempt 상한과 continuation 상태를 후속 숫자 결정으로 정해야 한다. 실패가 많으면 목표 수보다 적게 표시될 수 있음 |
| C. 근사 후보 표시 후 탭 시 exact 검증 | 로컬 추정상 가능한 후보를 먼저 보여 주고 사용자가 고른 하나만 검증 | 최초 호출량과 대기시간이 가장 낮음 | 화면에 보인 장소가 선택 후 실패할 수 있어 “담을 수 있는 장소만 표시” 계약과 충돌한다 |

- 현재 권고안: **B — 유한 묶음 exact 선검증 + 더보기**. 화면에 보이는 후보의 정확성을 유지하면서 호출량을 유한하게 만들 수 있다. 각 묶음은 목표 수를 하드 보장하지 않고, 상한 안에서 exact 성공한 장소만 보여야 한다.
- 사용자 답변: **B — 유한 묶음 exact 선검증 + 더보기**. 첫 장소 선택 뒤 두 번째 장소 후보는 최소 3개 정도가 좋고, 최대 5~6개를 보여 줄 수 있는 수준의 API 호출량을 허용한다. `출발지→장소1→장소2→목적지`가 전체 시간 안에 가능한 후보만 표시하며, 주변 후보 부재 또는 시간 부족으로 결과가 없으면 그 이유를 안내한다. 한 번 불러온 장소는 최소 수 시간에서 최대 하루까지 캐시하기를 원한다. 이 흐름을 고려해 현재 최대 2시간 입력을 3~4시간으로 늘릴 가능성도 제안했다.
- 상태: **조건부 확정**. 유한 묶음 exact 선검증, 기본 후보 3개 지향, 최대 5~6개 노출, 부족 이유 안내는 방향으로 채택한다. 그러나 `최소 3개`가 결과 목표인지 하드 보장인지, 최대 노출을 5와 6 중 어느 값으로 고정할지, 실제 provider attempt hard cap, 캐시 대상별 TTL, 최대 입력시간 변경은 아직 미확정이다.
- 부모 결정에 미치는 영향: A는 비용·지연 상한을 정의하기 어렵다. B는 정확성, 유한 호출, 더보기 방향을 함께 유지한다. C는 Q-2STOP-06의 “실제로 하나 더 담을 수 있는 장소만 표시”를 조건부로 되돌려야 한다.

### `유한 묶음 exact 선검증`의 정확한 의미

- 사용자가 첫 장소 A를 선택했다고 해서 카탈로그의 모든 나머지 장소와 A의 조합을 즉시 API로 검증하지 않는다.
- 먼저 API 호출이 필요 없는 고정 조건으로 같은 place ID, 명백한 운영시간 불일치, 두 장소의 최소 체류시간만으로도 남은 시간을 초과하는 후보, 공간상 우회 하한이 큰 후보를 제거하거나 뒤로 보낸다. 이 단계의 통과는 `추가 가능` 판정이 아니라 exact 검증 순서를 정하는 prefilter다.
- prefilter 뒤의 후보를 정해진 순서로 꺼내 Q-2STOP-07에 따라 두 방문 순서를 실제 경로로 검증한다.
- 두 순서 중 하나 이상이 세 leg·운영시간·체류시간·최종 도착 여유를 모두 통과한 장소만 사용자 화면에 표시한다.
- 표시 목표 수 또는 provider attempt 상한 중 하나에 먼저 도달하면 현재 묶음을 끝낸다. 목표보다 성공 장소가 적어도 미검증 후보로 채우지 않는다.
- 더보기는 이전에 검증하거나 탈락시킨 후보를 반복하지 않고 다음 cursor부터 같은 절차를 계속한다. session cache의 성공 leg는 재사용한다.

### Q-2STOP-08에서 확정해야 할 기준

1. **prefilter와 검증 우선순위**: 어떤 로컬 조건을 hard exclusion으로 쓰고, 남은 후보를 공간 우회 하한·운영 여유·관련성 중 어떤 순서로 exact 검증할지 정해야 한다.
2. **한 묶음의 표시 목표 수**: 첫 선택 뒤 기본 화면에서 exact 성공 후보를 몇 개까지 모을지 정해야 한다. 앞서 말한 `기본 3개`는 완성 코스 기준이었으므로 제한형 조립의 두 번째 후보 수로 자동 승계하지 않는다.
3. **한 묶음의 provider attempt 상한**: 후보 하나가 두 순서 검증에 최악 8 attempt를 사용할 수 있으므로, 목표 수와 별개로 호출·대기시간의 hard cap이 필요하다.
4. **중단·부족 처리**: 목표 수 달성, attempt 소진, 후보 소진, typed provider/store unavailable 중 어떤 조건에서 멈추며 부족 결과를 어떻게 알릴지 정해야 한다.
5. **더보기 continuation**: 다음 후보 cursor, 이미 검증한 place ID, 실패 이유, 재사용 가능한 leg를 유지해 같은 호출과 장소 노출을 반복하지 않아야 한다.

현재 권고하는 결정 순서는 먼저 `한 번에 보여 줄 두 번째 후보의 목표 수`를 정하고, 그 수와 후보당 최악 8 attempt를 근거로 묶음별 hard cap을 별도 확정하는 것이다. 호출 상한을 먼저 임의로 정하면 사용자가 실제로 받는 선택지 수가 불명확해지고, 표시 수를 하드 보장하면 실패 후보가 많은 입력에서 무제한 호출이 필요해진다.

### 사용자 답변에서 분리해야 하는 계약

- **결과 수와 호출량**: exact 성공 장소 5~6개를 화면에 보여 주는 것과 provider 호출을 5~6회 하는 것은 다르다. Q-2STOP-07의 양방향 검증은 후보 하나당 최악 8 attempt가 필요하다. 따라서 `기본 성공 목표 3개`, `누적 노출 상한 5 또는 6개`, `요청당 provider attempt hard cap`을 서로 다른 숫자로 정해야 한다.
- **3개 부족 가능성**: 주변에 후보가 없거나 route·운영시간·체류·도착 여유에서 연속 탈락하면 유한 호출 안에서 3개를 만들 수 없다. 이때 사용자가 제안한 부족 이유 안내와 정합하려면 3개는 하드 보장이 아니라 목표여야 한다. 하드 보장을 원한다면 호출 무제한 또는 미검증 fallback이 필요해 현행 방향과 충돌한다.
- **가능 판정의 시간 범위**: `출발지→장소1→장소2→목적지`의 세 leg뿐 아니라 두 장소의 체류시간, 도착별 운영시간, 최종 도착 여유를 포함한 전체 소요가 입력 시간 이하여야 한다. 이는 Q-2STOP-06~07과 일치한다.
- **빈 결과 안내**: 단순히 `추천 없음`으로 합치지 않고 최소한 `주변에 다음 후보가 없음`과 `남은 시간 안에 검증된 조합이 없음`을 구분하는 방향이다. provider/store 장애를 시간 부족으로 잘못 안내하지 않으며, 장애 문구는 후속 실패 계약에서 별도로 정한다.
- **캐시 수명 분리**: 장소 이름·좌표·분류·정적 운영정보 같은 place metadata는 최대 하루 캐시 후보가 될 수 있다. 반면 실제 route 시간은 교통·출발 시각에 따라 변하고, `A와 함께 추가 가능` 판정은 현재 위치·목적지·남은 시간·체류 선택에 종속되므로 수 시간~하루 동안 그대로 재사용하면 잘못된 가능 판정이 된다. route leg와 완성 가능 판정의 TTL·cache key는 place metadata와 별도로 결정해야 한다.
- **최대 입력시간 3~4시간 제안**: 이는 2곳 조합의 성공 가능성을 높이지만 기존 최대 2시간 제품 정책, 시간 입력 UI, 후보 거리 범위, 체류시간, 테스트 시나리오를 함께 바꾸는 상위 요구사항이다. 이 토의에서 자동 확정하지 않고 `DEC-RELEASE-MULTISTOP-01` 아래 별도 조건부 결정으로 남긴다.

## Q-2STOP-09 — `기본 3개`의 보장 수준

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-08` B
- 질문이 필요한 이유: 사용자가 말한 `최소 3개 정도`는 UX 목표로 이해할 수도 있고 절대 보장으로 이해할 수도 있다. 그러나 근처 후보 부재·시간 부족 안내를 함께 선택했으므로 실제 성공 후보가 0~2개일 수 있다. 보장 수준을 먼저 확정해야 attempt cap과 더보기 수를 계산할 수 있다.

### 선택지와 영향

| 선택지 | 계약 | 영향 |
| --- | --- | --- |
| A. 3개는 기본 목표, 부족 허용 | hard cap 안에서 exact 성공 3개를 우선 모으되 부족하면 0~2개와 이유를 표시 | 유한 호출·정확 검증·부족 안내가 서로 정합한다 |
| B. 3개를 하드 보장 | 항상 exact 성공 후보 3개를 표시 | 후보 자체가 부족한 입력에서는 달성 불가능하다. 무제한 호출이나 정책 완화 없이는 보장할 수 없다 |

- 현재 권고안: **A — 기본 목표 3개, 부족 허용**. 사용자가 함께 제안한 `근처에 없거나 시간이 부족함` 안내와 유한 호출 원칙을 유지하는 유일한 정합안이다.
- 사용자 답변: **A — 3개는 기본 목표이며 하드 보장하지 않는다.** provider attempt 상한 안에서 exact 검증된 후보가 0~2개이면 그 결과만 보여 주고, 부족 이유를 함께 안내한다.
- 상태: **확정**
- 부모 결정에 미치는 영향: A가 확정돼야 요청당 hard cap을 소진한 뒤에도 3개 미만 결과를 정직하게 종료할 수 있다. B라면 Q-2STOP-08의 유한 묶음과 fail-closed 원칙을 다시 열어야 한다.

### Q-2STOP-09 확정에 따른 구현 기준

- 첫 장소 선택 뒤 두 번째 장소 후보는 exact 성공 3개를 기본 목표로 수집한다.
- 목표 달성 전이라도 provider attempt hard cap, candidate 소진 또는 terminal failure에 도달하면 검증을 종료한다.
- 0~2개만 성공해도 미검증·근사 후보로 채우거나 체류·운영·도착 여유 조건을 낮추지 않는다.
- 성공 후보가 일부 있으면 그 후보와 부족 안내를 함께 표시한다. 0개이면 `주변 후보 없음`, `시간 조건 불충족`, `경로 검증 불가`를 확인 가능한 범위에서 구분해야 하며 구체 reason mapping은 후속 질문에서 정한다.
- 누적 최대 노출 수와 provider attempt hard cap은 아직 확정되지 않았다.

## Q-2STOP-10 — 두 번째 장소 후보의 누적 노출 상한

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-08` B, `Q-2STOP-09` A
- 질문이 필요한 이유: 사용자가 최대 5~6개를 제안했으나 구현 계약에는 하나의 상한이 필요하다. 이 값은 더보기 종료 조건, continuation 완료 상태, 최악 호출 예산을 직접 결정한다.

### 선택지와 영향

| 선택지 | 기본·더보기 구조 | 영향 |
| --- | --- | --- |
| A. 누적 최대 5개 | 기본 3개 목표 후 더보기로 최대 2개 추가 | 선택 피로와 추가 검증량이 조금 작지만, 3개 이후 더보기의 증가 폭이 작다 |
| B. 누적 최대 6개 | 기본 3개 목표 후 더보기로 최대 3개 추가 | 기본 묶음과 추가 묶음을 각각 최대 3개로 이해하기 쉽지만, exact 성공 하나를 더 확보할 호출·대기 비용이 생긴다 |

- 현재 권고안: **B — 누적 최대 6개**. `기본 3개 + 더보기 3개`라는 단순한 UX·continuation 계약을 만들 수 있다. 단, 6개도 성공 보장이 아니며 두 번째 묶음의 hard cap 안에서 검증된 수만 추가한다.
- 사용자 답변: **B — 누적 최대 6개**. 기본 두 번째 후보 3개를 목표로 하고, 더보기를 통해 추가 검증 후보를 합쳐 최대 6개까지 노출한다.
- 상태: **확정**. 6개는 누적 노출 상한이지 성공 수 보장이 아니며, 각 묶음의 provider attempt hard cap 안에서 exact 검증된 수만 표시한다.
- 부모 결정에 미치는 영향: 상한을 확정한 뒤에도 `후보 6개 × 최악 8 attempt = 48`을 자동 호출 예산으로 채택하지 않는다. 실패 후보까지 고려하면 더 커질 수 있으므로 각 요청 묶음의 독립 hard cap을 다음 질문에서 정해야 한다.

### Q-2STOP-10 확정에 따른 구현 기준

- 첫 장소 선택 뒤 기본 두 번째 후보는 exact 성공 3개를 목표로 한다.
- 더보기는 남은 cursor에서 추가 후보를 검증하며, 이전 결과와 합쳐 최대 6개까지만 노출한다.
- 기본 또는 더보기에서 attempt 상한·후보 소진·terminal failure가 먼저 발생하면 목표 수보다 적게 종료할 수 있다.
- 이미 노출·검증 실패한 place ID를 다음 묶음에서 다시 검사하지 않고, 재사용 가능한 exact leg만 session cache에서 사용한다.

## Q-2STOP-11 — 첫 장소 선택 직후 두 번째 후보를 갱신하는 사용자 시나리오

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-06` C, `Q-2STOP-07` A, `Q-2STOP-09` A, `Q-2STOP-10` B
- 질문이 필요한 이유: 첫 추천 장소 3개 중 A를 고른 직후 기존 B·C 카드를 그대로 둘지, 검증 완료까지 기다렸다 한 번에 교체할지, exact 성공 순서대로 점진 표시할지 정해야 한다. 이 선택은 체감 대기시간, 목록 안정성, 취소·재선택 상태에 영향을 준다.

### 제안 사용자 시나리오

1. 최초 화면은 one-stop 조건을 통과한 서로 다른 첫 장소 후보 3개를 기본 목표로 보여 준다.
2. 사용자가 A를 선택하면 A를 `선택한 장소`로 고정하고, 기존의 다른 첫 장소 카드는 두 번째 장소 후보로 그대로 간주하지 않는다.
3. 화면은 즉시 `A와 함께 갈 수 있는 장소 확인 중` 상태로 전환한다. 사용자는 검증 중에도 A 선택을 취소하거나 다른 첫 장소로 바꿀 수 있어야 하며, 이전 요청 결과가 새 선택 화면에 섞이지 않도록 snapshot/request ID를 구분한다.
4. 엔진은 A를 제외한 후보에 로컬 prefilter를 적용한 뒤, 후보마다 `origin→A→B→target`과 `origin→B→A→target`을 exact 검증한다.
5. 여기서 A의 이동·체류시간을 한 번 빼서 모든 B에 공통인 `남은 시간`을 만드는 방식은 사용하지 않는다. B에 따라 중간 leg와 방문 순서가 바뀌므로 각 B의 세 leg, 두 체류, 도착별 운영시간, 최종 도착 여유를 전체 재계산한다.
6. exact 성공한 B만 두 번째 장소 후보로 표시하고, 카드에는 엔진이 고른 방문 순서와 전체 이동·체류·도착 여유 결과를 반영한다.
7. 기본 묶음은 성공 3개 목표 또는 요청 hard cap/후보 소진/terminal failure에서 끝난다. 부족하면 성공한 수와 이유를 표시한다.
8. 사용자가 더보기를 누르면 다음 후보부터 검증해 누적 최대 6개까지 추가한다.

### 표시 시점 선택지와 영향

| 선택지 | 동작 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. 묶음 완료 후 한 번에 교체 | 성공 3개 또는 종료 조건까지 기다린 후 목록을 표시 | 결과 목록이 움직이지 않고 최종 정렬을 한 번 적용하기 쉽다 | exact 양방향 호출 동안 빈 로딩 화면이 길어질 수 있다 |
| B. exact 성공 후보를 즉시 점진 표시 | 검증을 통과한 후보부터 하나씩 보여 주고 나머지는 확인 중으로 표시 | 첫 유효 결과를 가장 빨리 볼 수 있고 `바로 새로고침` 체감에 가깝다 | 뒤늦은 후보 때문에 순위를 다시 바꾸면 카드가 움직일 수 있다. 표시 후 순서를 고정하거나 정렬 정책이 필요하다 |
| C. 사용자가 갱신 버튼을 눌러 시작 | A 선택 후 설명을 보여 주고 별도 버튼을 눌러야 두 번째 후보를 검증 | API 소비 의도가 가장 명확하다 | 사용자가 이미 A를 골랐는데 추가 행동이 필요해 제한형 조립 흐름이 끊긴다 |

- 현재 권고안: **B — 선택 직후 자동 검증하고 exact 성공 후보를 점진 표시**. 성공한 카드의 표시 순서는 고정해 화면 점프를 막고, 남은 검증 진행 상태를 별도로 보여 준다. 전체 완료 뒤 순위를 재정렬하지 않는 대신 exact 전 prefilter 우선순위가 품질에 중요해진다.
- 사용자 답변: **미답변**
- 상태: **미확정**
- 부모 결정에 미치는 영향: A/B는 사용자 추가 버튼 없이 A 선택이 API 검증을 시작한다. B를 택하면 결과 안정성을 위해 이미 표시된 카드의 순서를 고정하는 계약이 필요하다. C는 호출량은 줄지만 사용자가 요청한 즉각적인 후보 갱신과 거리가 있다.

## Q-2STOP-12 — 양방향 exact 비교의 단계별 provider attempt 상한

- 부모 결정: `DEC-RELEASE-MULTISTOP-01`
- 직접 부모 질문: `Q-2STOP-07` A, `Q-2STOP-09` A, `Q-2STOP-10` B, `Q-2STOP-11`
- 질문이 필요한 이유: 사용자는 비교 때문에 API 호출이 적당히 늘어나는 것은 허용하지만 약 50회 수준이면 로직을 다시 검토해야 한다고 밝혔다. 누적 6개를 캐시 없이 모두 양방향 exact 검증하는 단순 구현은 실제로 이 경계에 근접하거나 초과한다.

### 현재 계약에 따른 비용 계산

- route receipt 한 directed leg는 신규 provider attempt 최소 1·최대 2다.
- 첫 장소 A의 두 순서를 후보 B와 비교할 때 필요한 고유 directed leg는 `origin→A`, `A→B`, `B→target`, `origin→B`, `B→A`, `A→target`의 최대 6개다.
- A의 one-stop 검증에서 `origin→A`, `A→target`을 같은 recommendation session에서 재사용하면 B당 새 leg는 최대 4개, 신규 provider attempt는 최대 8회다.
- B도 최초 one-stop 후보로 exact 검증돼 `origin→B`, `B→target`을 재사용할 수 있으면 새 leg는 `A→B`, `B→A` 두 개뿐이므로 B당 최대 4 attempt다.
- cache를 낙관적으로 가정하지 않고 누적 성공 후보 6개를 각 최대 8 attempt로 계산하면 두 번째 장소 단계만 최대 48회다. 최초 one-stop 요청 최대 8회까지 합치면 56회여서 사용자가 제시한 재검토 기준을 넘는다. 실패 후보까지 무제한 검사하면 더 커진다.
- `adapter call`과 실제 `new provider attempt`는 구분한다. session/cache hit는 adapter를 거쳐도 신규 외부 provider attempt 0회다. 비용 hard cap은 신규 provider attempt로 적용하고 adapter-call 상한도 안전장치로 별도 둬야 한다.

### 선택지와 영향

| 선택지 | 최초 one-stop | A 선택 후 기본 묶음 | 더보기 묶음 | 한 사용자 흐름의 신규 attempt 상한 | 영향 |
| --- | ---: | ---: | ---: | ---: | --- |
| A. 보수 상한 | 8 | 8 | 8 | 24 | 증가가 가장 작지만 양방향 worst-case에서는 기본 후보 1개만 완결할 수도 있어 3개 목표 달성률이 낮다 |
| B. 균형 상한 | 8 | 16 | 12 | 36 | 더보기 전 자동 구간은 최대 24회이고, 사용자가 더보기를 눌러야 누적 36회다. A와 후보 B의 endpoint leg가 충분히 재사용될 때 기본·추가 각 3개를 시도할 여지가 있다 |
| C. 대칭 상한 | 8 | 16 | 16 | 40 | 두 묶음의 구현은 단순하지만 사용자 행동 전체에서 B보다 4회 더 허용하며 실패 후보가 많을 때 비용이 커진다 |

- 현재 권고안: **B — 8 + 16 + 12, 누적 신규 provider attempt 최대 36회**. 50회 경계를 넘지 않고, 첫 장소 선택만으로는 최초 추천을 포함해 최대 24회이며 마지막 12회는 사용자가 더보기를 명시적으로 눌렀을 때만 연다. 모든 상한은 결과 수 보장이 아니므로 부족 안내 계약을 유지한다.

### B와 C의 차이 보충

사용자는 B와 C가 비슷하다고 질문했다. 둘 다 장소 선택 UI를 사용하지만 책임 경계가 다르다.
