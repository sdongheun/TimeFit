# DEC-RELEASE-MULTISTOP-01 — 공모전 출시 다장소 시간 상한

## 결정

공모전 출시에서 2곳은 **한 번의 저장소 준비 감사와 한 번의 최소 복구 시도**까지만 목표로 둔다. 그 범위를 넘어서는 작업이 필요하면 자동 추천의 출시 범위를 실제 경로 검증 **1곳**으로 고정하고, 2·3곳의 안정적 공급은 배포 후 개선으로 이동한다.

3곳은 현행 엔진이 실제 검증 시 반환할 수 있으나, 이번 출시의 기능 완료·생활권 공급량 목표로 삼지 않는다.

## 이유

엔진 fixture는 1~3곳 조립을 검증했지만, `QA-MULTISTOP-RECEIPT-01`에서 두 A8 입력 모두 첫 다장소 public segment가 `경로 저장소`로 unavailable이 됐다. 이 상태에서 A8 8회 상한을 12/16으로 올려도 첫 실패 뒤 fail-closed 중단하므로 다장소 결과는 늘지 않는다.

출시일이 가까운 상황에서 cache/lease/budget/RPC를 재설계하거나 새로운 제공사·fallback·대규모 DB 변경을 시작하는 것은 1곳 핵심 경험까지 위험하게 만든다.

## 허용 범위와 중단 조건

1. 현재 `API-PUBLIC-STORE-01`의 읽기 전용 remote 준비 상태 감사를 수행한다.
2. 감사가 기존 migration 미적용, 기존 RPC execute 권한 누락, Function secret 이름 누락처럼 **기존 설계의 국소 설정 결함 하나**를 확인하면, 사용자 승인 뒤 그 결함 한 건만 최소 복구하고 fixed contract test와 A8 두 입력을 새로 한 번씩 검증한다.
3. 아래 중 하나면 다장소 복구를 중단하고 1곳 출시 경계로 전환한다.
   - 새 DB schema/lease/cache 설계가 필요함
   - migration/권한/secret 복구 뒤에도 같은 A8 다장소 store 실패가 재현됨
   - 두 번째 원인 조사 또는 두 번째 복구 cycle이 필요함
   - Kakao 제공사 변경, fallback 추가, 호출 한도 상향, 엔진 queue 정책 변경이 선행돼야 함

## 1곳 출시 경계

전환 시 “다장소가 실패해도 1곳만 우연히 남는” 현 상태를 출시로 쓰지 않는다. 추천 엔진·UIUX는 다음을 별도 최소 작업으로 고정한다.

- 자동 대표·대안 계산에서 2·3곳 public segment 검증을 시작하지 않는다.
- `출발 → 1곳 → 도착/복귀`의 실제 route·운영시간·최소 체류·도착 여유를 통과한 결과만 표시한다.
- 조건부 시장/거리 영역은 자동 검증 코스와 계속 분리한다.
- 일반 사용자에게 “2~3곳 코스” 또는 대안 수를 약속하지 않는다. 남는 시간과 검증된 한 곳을 정직하게 표시한다.
- internal diagnostics·B12·다장소 실험 코드는 출시 build에서 숨긴다.

이 전환은 근사 이동시간, 임의 체류 연장, 저장소 오류 무시, 일반 카페/조건부 장소의 자동 승격을 허용하지 않는다.

## 이후 평가

저장소가 정상화된 뒤에만 동일 queue A에서 `A8 / A12 / A16`을 각각 비교한다. `B12`는 attempt 상한과 queue order가 함께 달라 호출량 효과의 근거로 사용하지 않는다.

## 2026-09-02 전환 기록

`API-PUBLIC-STORE-01`은 remote migration 3개, Function 존재와 필요한 secret **이름**, public store RPC 5개의 현 handler signature 및 `service_role` execute를 읽기 전용으로 확인했다. 모두 준비돼 있었고, QA 실행과 상관 가능한 안전 Edge 로그는 없었다. 따라서 허용 범위의 국소 설정 결함은 발견되지 않았다.

이 상태에서 stage 관찰을 새로 만들거나 cache/lease/RPC를 다시 추적하는 것은 이 결정의 “두 번째 원인 조사”에 해당한다. 사용자와 합의한 중단 조건을 적용하여 2·3곳 복구를 종료하고 `2-U — 출시용 1곳 실제 검증 전환`으로 이동한다. 이는 다장소 구현을 삭제하거나 원인을 해결했다고 주장하는 변경이 아니다. 다장소 entry·진단은 배포 후 제한된 재개를 위해 보존하되 출시 UI에서 사용하지 않는다.

## 2026-09-03 제한적 재개 — 구현 전 준비 감사만 허용

- **이전 방식:** 공모전 출시 안정성을 위해 2·3곳 원인 추적과 복구를 종료하고 one-stop만 production에 연결했다.
- **새 관찰:** one-stop 출시 흐름과 코스 상세 UX가 정리되는 동안, 사용자는 2곳을 즉시 활성화하는 것이 아니라 추후 변경 비용과 선행 차단점을 미리 알고 싶어 한다.
- **교체 방식:** `2-X`에서 현재 코드·기존 고정 fixture·완료 문서만 읽어 2곳 엔진 재사용성, public A→B store, 호출 비용, 3-leg UI/지도 영향을 감사한다. 제품 코드·테스트·API·DB·UI와 production flag는 변경하지 않는다.
- **교체 이유:** 구현을 다시 시작하기 전에 과거 실패가 단순 엔진 문제인지 외부 저장소·호출 예산·상세 지도 계약까지 포함한 문제인지 구분해, 불필요한 두 번째 복구 순환을 피하기 위해서다.
- **상태:** **조사 완료·수락, 구현 미개시.** 2-X는 엔진 primitive 재사용은 가능하지만 pair-only entry 분리, public A→B store 원인 규명, 코스당 최대 6 attempt, 3-leg UI/상세 connector 계약이 필요하다고 판정했다. one-stop 출시 결정은 유지되며, 2곳 구현·노출은 사용자 재결정 전까지 금지한다. 3곳은 계속 조사 대상 밖이다.

## 2026-09-03 사용자 재결정 — pair-only 제한 조립으로 부분 교체

- **이전 방식:** mixed 2·3곳 자동 복구는 중단하고 one-stop만 출시 대상으로 유지했다.
- **새 관찰:** one-stop 경로는 안정됐지만 사용자가 시간이 충분할 때 검증 장소 두 곳을 직접 선택할 통제와 선택 폭이 부족하다. 과거 mixed queue를 그대로 켜는 대신 첫 검증 장소를 사용자가 고른 뒤에만 두 번째 장소 비용을 쓰는 경계가 필요하다.
- **교체 방식:** [DEC-TWO-STOP-SELECTION-01](two-stop-limited-assembly.md)의 pair-only 제한 조립을 새 구현 목표로 연다. 2-Y·API-TWO-STOP-01·U-TWO-STOP-01·QA-TWO-STOP-01은 역할 경계에서 병렬 수행하고, 자동 통합 게이트 전까지 production one-stop을 fallback으로 유지한다.
- **교체 이유:** 자유 장바구니·3곳·mixed queue를 재도입하지 않으면서 사용자 의도가 있을 때만 A/B 양방향 exact 검증 비용을 사용하기 위해서다.
- **상태:** **2곳 구현 재개, 3곳·자유 장바구니 보류 유지.** 이 절은 최초 중단 결정이 당시 잘못됐다는 뜻이 아니라, 사용자가 비용 증가를 수용하고 더 작은 pair-only 계약을 새로 확정해 적용 범위를 바꾼 이력이다.
