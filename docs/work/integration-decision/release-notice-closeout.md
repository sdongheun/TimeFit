# RELEASE-NOTICE-CLOSEOUT-01 — 답변 대기 중 게시 준비 마감

2026-09-09. 사용자 결정: 새벽에는 위치 문의 답변을 기다리며 멈추지 않고 가능한 준비를 끝낸 뒤 답변의 실제 영향만 반영한다. DOCS-05-R1 및 ICON-01 로컬 완료를 재사용한다.

## 순서와 경계

- 아래 DB/API/출시 문서의 A 준비는 병렬 가능. 문서 B 통합은 DB/API 인계 후 진행한다. 별도 UIUX 재작업은 지금 없다.
- 위치 답변은 도착 즉시 통합·출시 문서 세션에 전달한다. **최종 문안 확정·공개 게시 전** 반영한다. 답변 전에도 계약 사실·기술 흐름·스토어 자료·로컬 페이지 검증을 마칠 수 있다.
- 답변이 앱 동의/권한/전송 변경을 요구하면 통합에서 영향과 작업을 분리하며 문서 담당이 제품을 임의 수정하지 않는다. 기존 자동 출시 결정은 유지하되 공개 차단 미해소를 자동 공개 승인으로 해석하지 않는다.
- 외부 게시·프로젝트 생성·registry 변경·가입/탈퇴·함수 배포·스토어 설정/업로드/제출·commit/push는 이번 범위 아님. 계약 동의·유료 변경·고객센터 문의 발송도 임의 실행하지 않는다.
- 기존 인계/공식 공개 자료/접근 가능한 설정 메타데이터만 재사용한다. 실제 사용자 행·토큰·키·메일/계약 원본 개인정보는 출력/저장하지 않는다. MCP 운영 데이터 테스트 금지. 접근 불가하면 필요한 화면과 필드만 한 묶음으로 남기고 독립 작업은 계속한다.
- 법적 분류는 기술 전송만으로 단정하지 않는다. 공식 약관의 일반 설명과 해당 계정에 적용되는 증거를 구분하고 URL·조항·확인일을 남긴다. 불명은 정확한 미확인 필드로 남기되 임의 숫자/법적 면책을 작성하지 않는다.

## DB-RELEASE-NOTICE-01 — DB 세션

읽기: AGENTS.md, docs/README.md, DB release-facts-final.md 최신 완료/공급자 관련 절, docs/05_release/publish/data-facts.md의 R1 표. 수정 소유는 `docs/work/db-personalization/release-notice-facts.md`만.

1. 이미 확인한 서울 region·데이터 종류·삭제 함수 배포/C 결과는 재사용하고 재실행하지 않는다.
2. 사용 중인 Supabase 계정에 적용되는 서비스 계약/DPA의 계약 법인·처리자명을 확인한다. 현행 공식 서비스 약관/DPA/하위처리자 자료와 실제 계약 적용 근거를 대조한다. 서명이 없는 표준 DPA나 공개 회사명만으로 개별 계약 체결을 주장하지 않는다.
3. 기존 설정 근거에서 DB/Auth 메일/Edge/로그/backup의 처리 범위·지역·보유를 분리한다. 이미 확인된 값은 재수집하지 않으며 공개 약관과 현재 plan 설정의 차이를 표시한다. 서울 DB를 모든 처리 국내로 확장하지 않는다.
4. 문서 담당에게 제공할 표는 처리 업무/받는 주체/전송 항목/확인 지역·보유·삭제/근거/미확인 필드다. 국외 이전 없음도 증거 없이 확정하지 않는다.
5. 공개자료로 해결 가능한 필드는 이번에 닫는다. 접근·계약 확인이 필요한 항목은 화면명·필드명·확인 이유만 한 번에 인계한다. 새로운 backup·로그 인프라·migration·탈퇴 테스트를 추가하지 않는다.

완료: 네 항목 인계(변경 파일·유지 계약·확인 방법/결과·남은 위험). DB/API 호출로 실제 기록 검증0, 운영 쓰기0. 문서만이면 앱 전체 테스트0.

## API-RELEASE-NOTICE-01 — API 세션

읽기: AGENTS.md, docs/README.md, API release-facts-final.md 최신 OPS 근거, R1 공급자 표 및 관련 production 빌드 인계. 수정 소유는 `docs/work/external-api/release-notice-facts.md`만.

1. Kakao Local/Maps/경로를 실제 사용하는 상품·요청 경계별로 분리하고 현행 공식 약관·개인정보 안내·개발자 정책의 적용 조항을 확보한다. 일반 소비자 카카오맵 약관을 모든 API 계약으로 대체하지 않는다.
2. 운영자/공급자의 처리 목적·역할에 대한 명시 근거가 있는지 확인한다. 계약 주체, 항목, 공개된 보유/지역을 근거와 함께 정리한다. 위탁/제3자 제공 판정이 조항만으로 안 되면 정확한 쟁점과 필요한 확인 질문 하나로 좁힌다. 문의 발송은 하지 않는다.
3. 기존 public export·release wrapper·설정 근거를 이용해 Turnstile/Worker의 production 사용 여부를 확인한다. 실제 사용자 인증·CAPTCHA 반복 호출 없이 endpoint 소비 경로와 활성 플래그를 대조한다. Cloudflare Pages와 앱 보안 흐름을 별도 취급한다. 비밀 값은 출력하지 않는다.
4. TMAP/ODsay는 파일 존재나 문자열 포함만으로 도달 가능을 판단하지 않는다. public entry→화면/이벤트→service까지 읽기 전용으로 추적하고 flag·인증·저장 코스 조건을 명시한다. 도달 불가 증명 없으면 없다고 하지 않는다. 실제 provider 호출·legacy 코드 제거·App.tsx 수정·새 Archive는 하지 않는다. 최종 산출물 재확인이 필요하면 기존 증거와 그 한계를 인계한다.
5. 공급자별 확정 사실/공식 근거/계정 화면 확인 필요 필드/법적 해석 잔여를 분리해 문서 담당에게 전달한다. 이미 완료된 cache·route·키 감사를 반복하지 않는다.

완료: 네 항목 인계. 제한적인 기존 fixture 확인이 필요하면 네트워크 없는 테스트만 사용하고 호출0을 기록한다.

## RELEASE-DOCS-06 — 출시 문서 세션

읽기: AGENTS.md, docs/README.md, DOCS-05-R1 인계, release-user-decisions.md 현행 결정, publish/와 public-site/ 관련 파일. 수정 소유는 docs/05_release/만.

### A. 지금 병렬 준비

1. 기존 공개 페이지·확정 운영자/메일/연령/180분·2곳/개인화/탈퇴 함수 배포 사실은 유지한다. 위치 답변에 의해 바뀔 문단과 공급자 인계로 채울 필드만 내부 표로 표시한다. 미확정 정책을 공개 본문에 새로 만들지 않는다.
2. Cloudflare Pages 예정 호스팅에 적용되는 공식 계약·기본 데이터 처리 사실을 공개자료와 기존 계정 근거로 확인한다. 프로젝트 생성 후에만 알 수 있는 설정은 배포 시 확인 항목으로 분리해 생성 전 문안 준비가 불가능한 순환을 만들지 않는다. 아직 호스팅 중이라고 쓰지 않는다.
3. 기존 App Store 설명·부제·키워드·지원/개인정보 URL 슬롯·App Privacy 사실표·부산 외 지역 심사 절차·연령/수출규정 응답의 근거를 로컬 제출용으로 정리한다. 확정된 사용자 선택은 재질문하지 않는다. 모르는 응답을 대신 확정하지 않으며 전화번호/심사 계정 비밀번호를 문서에 받지 않는다.
4. 스크린샷 요구 규격/필요 화면과 최종 빌드에서 확인할 항목을 기존 자료로 한 목록에 정리한다. 오래된 화면을 최신 스크린샷으로 취급하거나 촬영을 이번 문서 완료의 선행 조건으로 추가하지 않는다.

### B. DB/API 완료 뒤, 위치 답변 전에도 진행

5. 두 release-notice-facts.md를 대조해 확인된 내용만 privacy/terms/support·HTML·App Privacy·gate에 반영한다. 기존 표의 ‘차단’도 실제 근거로 재평가하고 필수/조건부/미판정 사유를 남긴다. 단순 미확인 로그 기간을 일괄 차단하거나 자동 해제하지 않는다.
6. 모든 독립 작업을 끝낸 뒤 남는 항목을 ‘위치 답변만 필요한 것 / 계정 화면의 특정 사실 / 전문 해석 필요 / 게시 승인’으로 분리한다. 사용자에게 요청할 화면·필드는 한 묶음으로 최소화한다. 조사 완료를 법적 적합성 보장으로 쓰지 않는다.
