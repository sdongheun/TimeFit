# DEC-LIVE-DWELL-01 — Live Activity 기반 사용자 확인 체류 측정·개인화

> 결정일: 2026-09-04
> 상태: **제품 정책 확정·구현 전**
> 부모 목적: 코스를 실제로 이용하는 흐름을 방해하지 않으면서, 일반 로그인 사용자가 명시적으로 확인한 대략적인 체류시간으로 이후 추천을 개인화한다.

## 1. 목적과 사용자 관찰

- 사용자는 TimeFit에서 코스를 고른 뒤 카카오맵으로 이동하므로, 장소에 도착한 순간 앱을 다시 열지 않을 가능성이 높다.
- 완전한 GPS 궤적보다 `도착했어요`와 다음 길찾기/완료 행동 사이의 대략적인 체류시간이면 개인별 체류 성향을 보정하는 데 충분하다.
- 예상 이동시간이 끝나는 즉시 도착 여부를 묻으면 느린 보행·환승·신호 대기 때문에 아직 이동 중인 사용자가 기능을 끄거나 알림을 무시할 수 있다.
- Live Activity는 자동 센서가 아니라 진행 상태와 확인 행동의 표면이다. 정확한 주의 환기는 예약 로컬 알림이 담당한다.

## 3. 확정 상태 전이와 시각 계산

### 3.1 상태

`idle → traveling → arrival_pending → dwelling → departure_due → traveling/completed`

종료 상태는 `completed`, `cancelled`, `expired`, `incomplete`로 구분한다. 동일 course/stop/event의 중복 탭은 한 번만 반영한다.

### 3.2 길찾기와 도착 확인

1. 기존 Kakao app → HTTPS → browser handoff 중 하나가 실제 성공한 때만 `routeOpenedAt`을 기록한다.
2. 엔진의 검증 snapshot `moveMin`만 예상 이동시간으로 사용한다. 카카오맵으로 넘긴 뒤의 실제 교통·보행시간을 TimeFit이 안다고 표현하지 않는다.
3. `arrivalGraceMin = clamp(round(moveMin × 0.20), 3, 10)`이다.
4. `arrivalPromptAt = routeOpenedAt + moveMin + arrivalGraceMin`이다.
5. Live Activity는 handoff 성공 직후 시작해 목적 장소와 예상 도착 시각을 표시한다. 사용자는 알림 전에도 `도착했어요`를 실행할 수 있다.
6. `arrivalPromptAt`에는 로컬 알림을 한 번 예약한다. 행동은 `도착했어요`, `5분 뒤 다시 알림`이며 거절·종료 버튼을 도착 질문에 두지 않는다.
7. 다시 알림은 한 번만 예약한다. 두 번째 알림을 무시해도 Live Activity는 유지한다.
8. `도착했어요`가 처음 성공한 시각을 `arrivedAt`으로 확정하고 `dwelling`으로 전이한다.

### 3.3 출발 알림과 체류 종료

- `latestSafeDepartureAt = 최종 도착/복귀 시각 - 사용자 설정 도착 여유 - 남은 검증 snapshot 이동 합 - 이후 선택 장소의 snapshot 체류 합`이다. 여기서 이동 합은 GPS로 잰 실시간 이동이 아니라 추천 때 실제 경로로 검증해 저장한 분 수다.
- `departureReminderAt = latestSafeDepartureAt - 5분`이다. 사용자가 처음 입력한 전체 자투리 시간을 `남은 일정`으로 다시 빼지 않는다.
- 도착 확인이 늦어도 최종 약속 시각을 뒤로 미루지 않는다. `departureReminderAt`이 이미 지났으면 한 번만 즉시 `곧 이동해야 해요` 상태를 보여 준다.
- `다음 장소 길찾기`, `목적지 길찾기`, `복귀 길찾기`는 기존 handoff가 성공했을 때만 직전 stop의 `departedAt`을 기록한다. handoff 실패는 체류 종료가 아니다.
- 앱 안의 명시적 `둘러보기 완료`도 같은 idempotent departure event를 사용한다.
- `actualDwellMin = floor((departedAt - arrivedAt) / 60초)`이며, 도착·출발 중 하나라도 없으면 개인화 표본이 아니다.

## 4. 기기 표면과 권한

- Dynamic Island 지원 기기: Lock Screen Live Activity + Dynamic Island + 예약 로컬 알림.
- 미지원 기기: Lock Screen Live Activity + 시스템이 허용하는 배너 + 예약 로컬 알림/알림센터.
- Live Activity·알림 노출은 시스템 설정과 집중 모드에 따라 달라질 수 있으며 항상 보인다고 약속하지 않는다.
- iOS 17 이상 App Intent로 `도착했어요`, `5분 뒤 다시 알림`, `이제 출발해요`를 처리한다.
- 알림 권한은 첫 실행·로그인 직후 묻지 않는다. 처음 `카카오맵에서 길찾기`를 실행해 도착·출발 알림이 실제로 필요한 순간, 외부 handoff 전에 한 번 목적을 설명하고 요청한다. 허용·거절과 관계없이 길찾기는 계속 진행하며, 이후 변경은 내 정보의 시스템 상태 행에서 설정 앱으로 안내한다.
- 원격 ActivityKit push와 APNs 서버 갱신은 이번 범위에 포함하지 않는다. 예약 시각 주의 환기는 `expo-notifications` 로컬 알림으로 처리한다.
- 내 정보의 `맞춤 추천을 위한 체류 기록`만 앱이 직접 바꾸는 토글이다. 알림·위치·Live Activity는 현재 시스템 상태와 `설정에서 변경` 행동으로 표시하며 가짜 시스템 토글을 만들지 않는다.
- GPS 자동 도착/이탈, 연속 좌표, 이동 polyline 저장, `Always` 위치 권한과 background location mode는 이번 배포에서 금지한다.

## 5. 로그인·동의·최소 수집

- 일반 로그인과 `맞춤 추천을 위한 체류 기록` 동의가 모두 있을 때만 완료된 체류 표본을 서버에 저장한다.
- Route Proxy용 Supabase anonymous Auth는 제품 로그인이나 개인화 동의로 간주하지 않는다.
- 비로그인·미동의 사용자는 Live Activity와 로컬 진행을 이용할 수 있지만 서버 체류 표본·개인화 프로필을 만들지 않는다.
- 최초 거절 뒤에도 내 정보에서 언제든 켤 수 있다. 활성화 이전 기록은 소급 수집하지 않는다.
- 사용자가 끄면 새 수집·새 프로필 적용을 즉시 멈춘다. `개인화 데이터 초기화`와 계정 삭제는 저장 표본과 파생 프로필을 함께 삭제해야 한다.
- exact `arrivedAt`/`departedAt`은 활성 코스 복구에 필요한 동안 App Group 로컬 상태에서만 유지한다. 서버 영속 표본은 DB 작업에서 목적에 필요한 최소 필드와 보유 기간을 migration/RLS로 확정하며, 좌표·전체 GPS 이력을 추가하지 않는다.

## 6. 개인화 계산 계약

- 개인화 그룹 키는 **정제 카탈로그의 `(category, subCategory)` 복합 키**다. `거리·골목`처럼 같은 subCategory 문자열이 서로 다른 상위 category에 존재하므로 subCategory 문자열 하나만 전역 키로 쓰지 않는다. `subCategory`가 없는 기록은 원시 완료 표본으로 보존할 수 있지만 체류 프로필 계산에는 쓰지 않는다. UI가 category/subCategory를 합성하거나 장소명으로 추정하지 않는다.
- 유효 표본은 일반 로그인·동의·동일 사용자·동일 category+subCategory·명시 도착/출발 완료·양의 체류시간을 모두 만족해야 한다.
- 표본 1~2개는 수집만 하고 기본 체류 정책을 유지한다.
- 3개부터 새 유효 표본마다 최근 최대 5개의 중앙값을 계산한다. 짝수 개면 가운데 두 값의 산술평균을 쓰고, `Math.round(median / 5) × 5` 방식으로 가장 가까운 5분에 반올림한다.
- 개인화 조정은 카탈로그 기본 권장값 대비 한 번에 최대 `±10분`, 장소의 `minStayMin...maxStayMin` 안으로 제한한다.
- 개인화 값은 기존 체류 배정기의 **soft recommended override**로만 전달한다. 엔진은 먼저 기존 최소 체류·실제 경로·운영시간·도착 여유로 후보 가능성을 확정하고, 개인화 목표가 같은 시간표 안에 맞을 때만 선택 체류에 반영한다. 1곳 또는 2곳에서 개인화 목표 때문에 운영시간·총예산을 넘으면 해당 목표를 줄이거나 기존 비개인화 선택 체류로 되돌리며 후보를 탈락시키거나 새 route를 호출하지 않는다.
- 개인화는 위 선택 체류와 하드 조건이 같은 후보의 동률 보조 순위에만 적용한다. 실제 경로·운영시간·최소 체류·도착 여유 하드 조건을 완화하지 않으며, 개인화 시간이 맞지 않는다는 이유만으로 기본적으로 가능한 장소를 없애지 않는다.
- 최빈값·평균·ML은 이번 버전에서 사용하지 않는다. 충분한 표본 뒤 별도 결정으로만 교체한다.

## 7. 실패·미확인 규칙

- 도착 미확인: 체류 시작 없음, 개인화 표본 없음.
- 도착 확인 후 출발 미확인: `incomplete`, 개인화 표본 없음. 예상 출발시각으로 `departedAt`을 합성하지 않는다.
- 알림 권한 거절: Live Activity와 앱 안 CTA는 유지하고, 내 정보에서 시스템 설정으로 안내한다.
- Live Activity 비활성/시작 실패: 기존 앱 진행 화면과 로컬 알림 가능한 범위는 유지한다. 추천·길찾기를 차단하지 않는다.
- 앱 강제 종료·기기 재부팅: App Group에 보존한 최소 활성 상태로 한 코스만 복구한다. 서로 다른 코스가 동시에 활성 상태가 되지 않는다.
- 코스 취소·완료·만료는 예약된 도착/출발 알림과 Live Activity를 함께 정리한다.

## 8. 역할 경계와 구현 순서

현재 코드 감사 결과 `app.json`과 `ios/Podfile.properties.json`은 iOS 16.4, `ios/mobile/Info.plist`에는 generic Always location 설명이 있으며 Widget Extension·App Group·`NSSupportsLiveActivities`는 없다. `VerifiedCourseProgressScreen`도 화면 메모리 전용이라고 명시한다. 이는 문서 충돌이 아니라 아래 작업으로 닫아야 하는 **확인된 구현 격차**이며, 지금 기능이 이미 구현됐다고 해석하면 안 된다.

1. **현재 UI 안정화 완료:** `U-INTERACTION-01`의 공용 눌림·시간 제어 햅틱·전환과 실기기 촉각을 수락했다. 이후에도 같은 `App.tsx`/UI 파일을 동시에 편집하지 않는다.
2. **Wave 1 병렬:**
   - DB·개인화 `DB-DWELL-01`: 동의, 완료 표본, 파생 프로필, RLS·삭제 계약.
   - 추천 엔진 `2-AB`: 순수 개인화 계산과 기존 추천 정책에 대한 bounded 적용.
3. **Wave 2 UI/네이티브:** `U-LIVE-ACTIVITY-01`이 iOS 17 target, Widget Extension/App Group, ActivityKit/App Intent, 로컬 알림, 진행 화면·내 정보 연결을 한 작업에서 구현한다.
4. **Wave 3 QA:** `QA-LIVE-ACTIVITY-01`이 고정 clock/notification/activity/DB fixture 후 실제 iOS 기기 1·2곳 코스를 제한 확인한다.

외부 API 세션 작업은 없다. 예상 이동시간은 기존 검증 snapshot을 소비하고, Live Activity 때문에 Kakao/Route Proxy를 다시 호출하지 않는다.

## 9. 아직 구현 전 반드시 닫을 항목

- 서버 완료 표본의 정확한 보유 기간은 DB 작업에서 개인정보 처리방침과 함께 제안하고 통합·결정 승인을 받아야 한다. 임의 영구 보관은 금지한다.
- `subCategory`가 없는 문화시설·카페 등의 세분화는 데이터 정제 후속이며, 이번 기능을 위해 UI/엔진이 추정 분류를 만들지 않는다.
- 실제 알림 문구·Live Activity 레이아웃은 UIUX 작업에서 정하되, 시각 계산·확인 행동·저장 조건은 이 결정을 바꿀 수 없다.
