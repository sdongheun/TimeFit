## 1. 변경 배경과 목표

### 1.1 이전 방식

TourAPI와 부산 공공데이터에서 장소·운영시간·주소·좌표·설명·사진 등의 원천 정보를 개발 중 수집하고 정제했다. 그 결과를 `src/data/busan_poi_catalog.json` 등 앱 번들 JSON에 포함해 추천·상세·주변 둘러보기에서 사용했다.

### 1.2 발생한 문제

1. 원천 API의 등록·수정·삭제·운영시간 변경이 앱 업데이트 전까지 반영되지 않는다.
2. 한국관광공사는 콘텐츠를 매일 정기 동기화하거나 긴급 변경할 수 있다고 안내했다.
3. 공모전은 실제 서비스에서 TourAPI를 활용하는지 운영계정 호출 이력과 화면 기능으로 검증할 수 있다.
4. 운영팀은 승인 없는 대량 수집이 서비스키 차단 대상이 될 수 있다고 안내했다.
5. 앱 번들 JSON도 원천 API 응답을 미리 저장해 사용자에게 제공한다는 점에서 로컬 저장 방식 관련 위험을 보수적으로 검토해야 한다.
6. 반대로 원본 API만 즉시 추천에 투입하면 현재의 추천 가능 등급·체류시간·중복·운영시간 구조화·사진 근거·개인화 분류가 사라진다.

### 1.3 교체할 방식

원천 제공자가 관리하는 최신 사실은 실제 사용자 추천 흐름에서 API로 조회한다. 짜투리가 자체 생성한 추천 정책·분석 결과는 로컬 정책 데이터로 유지한다. 실시간 응답을 검증·정규화한 뒤 로컬 정책과 결합한 **세션 한정 후보 snapshot**을 기존 추천 엔진에 전달한다.

임시 검증용 `EXPO_PUBLIC_LIVE_PUBLIC_DATA_ENABLED` 기본 OFF 방식은 2026-09-29 철회했다. 일반 빌드가 번들 원천을 계속 읽어 실제 전환이 아니며 사용자가 ON/OFF 이중 운영을 원하지 않았기 때문이다. 현재 공개 추천·주변 둘러보기 entry는 별도 환경변수 없이 live를 기본 사용하고, 실패를 번들 장소 성공으로 바꾸지 않는다. 기존 정적 엔진은 순수 계산 회귀용 명시 테스트 seam에만 남긴다. 번들 카탈로그 자체는 과거 기록 위치 해석·사진·표시 호환 계약이 남아 있어 아직 삭제하지 않는다. 로컬 코드 전환과 새 TestFlight/배포 artifact의 수락은 구분한다.

2026-09-30 사진 충돌 해결: live 어댑터의 `verified` exact 사진 101개만 화면에 전달하던 방식은 기존 203개 표시 결정 중 `operator_approved` 102개를 누락시켰다. 장소 사실을 번들 JSON으로 되돌리는 대신, live candidate의 exact 내부 장소 ID에 한해 기존 검토 사진 표현 자산을 별도 결합한다. 새·변경 API 사진은 자동 승인하지 않으며 이미지 실패는 기존 기본 이미지로 닫는다. 선택 코스 복원에는 1~2곳의 승인 사진 표현 정보만 보존하고 전체 live 응답·장소 설명·운영시간·공급자 입력은 보존하지 않는다. 상태: **로컬 구현·집중 자동 검증 완료, 실기기 재확인 전**.

### 1.4 목표

- [x] TourAPI 호출 결과가 실제 추천 후보의 포함·제외와 표시 정보에 영향을 주게 한다.
- [x] 기존 짜투리 추천 기준과 체류 개인화 계약을 유지한다.
- [x] API 호출 이력만 만들기 위한 형식적·무의미한 호출을 금지한다.
- [x] TourAPI 원본 응답을 파일·AsyncStorage·Supabase에 영구 저장하지 않는 방향을 기본으로 한다.
- [x] TourAPI 전환을 먼저 완결하고 부산 공공데이터는 같은 계약으로 후속 전환한다.
- [ ] 전환 완료 후 앱 업데이트 없이 원천의 수정·삭제·운영시간 변경이 추천에 반영되는 것을 검증한다.
- [ ] 외부 장애에도 앱이 멈추거나 잘못된 추천을 성공으로 표시하지 않게 한다.

### 1.5 비목표

- 실시간 API 응답만으로 신규 장소를 자동 추천 등급으로 승격하지 않는다.
- AI-Hub 체류 분석과 회원 개인화 표본을 TourAPI 값으로 대체하지 않는다.
- GPS 또는 자동 현재 위치를 다시 도입하지 않는다.
- 전체 원천을 매 실행마다 대량 다운로드하지 않는다.
- 호출 이력을 만들 목적으로 화면과 무관한 백그라운드 요청을 발생시키지 않는다.
- 부산 공공데이터 전환 전 TourAPI 작업을 기다리게 만들지 않는다.

### 3.2 2026-09-21 구현 승인

- 호출 주체는 **Supabase Edge Function의 인증형 원본 비저장 pass-through**로 확정한다.
- 목록은 부산 전체를 콘텐츠 유형별 `areaBasedList2`로 조회하고 앱/서버 메모리에서 승인된 내부 장소와 결합한다. 조회 유형은 `12 관광지`, `14 문화시설`, `28 레포츠`, `38 쇼핑`, `39 음식점`으로 제한한다. `39`는 일반 음식점을 새로 편입하기 위한 것이 아니라 기존 exact mapping 중 카페 15곳의 최신 사실을 확인하기 위한 조회이며, 승인 ID/type 교집합 밖의 음식점은 사용하지 않는다. `15 축제`, `25 여행코스`, `32 숙박`은 호출하지 않는다.
- `locationBasedList2`를 사용하지 않으며 사용자가 수동 선택한 좌표도 TourAPI에 전송하지 않는다.
- 원본 응답·서비스키·전체 URL query·좌표·사용자 ID는 DB, 파일, 캐시, 로그, trace에 저장하지 않는다.
- 전체 목록을 신뢰할 수 없으면 오래된 번들을 최신 성공으로 표시하지 않고 `unavailable`과 명시 재시도를 제공한다.
- 목록과 상세 조회를 분리한다. 먼저 부산 전체 목록의 최신 공통 사실을 받아 기기 메모리에서 사용자 수동 출발지·도착지와의 공간 적합성을 계산하고, 그 결과에만 운영시간 상세를 점진 조회한다.
- 운영시간 상세는 **초기 12곳 → 부족하면 6곳씩 보충 → 한 추천 세션 최대 30곳**으로 확정한다. 상세 동시성은 3을 유지한다.
- 상세 검증을 통과한 장소 중 실제 경로 검증 후보는 최대 18곳으로 제한한다. 운영시간 탈락 때문에 18곳을 채우지 못했다는 이유로 오래된 로컬 운영시간을 사용하거나 신규 source ID를 승격하지 않는다.
- 목록은 콘텐츠 유형별 최대 2페이지(유형 5개이므로 최악 10회), 동시성 3으로 제한한다. `detailCommon2`는 표시 결과 최대 4회, `detailImage2`는 사용자가 연 상세 최대 1회를 시작값으로 유지한다. 목록 4초·상세 3초, 자동 재시도 0회·사용자 명시 재시도 1회를 적용하되, 전체 시간 제한은 점진 조회의 조기 종료와 함께 실측 후 확정한다.
- 서버 전환이 검증되면 `EXPO_PUBLIC_TOURAPI_KEY`의 release 입력과 앱 직접 호출 경로를 제거한다.
- TourAPI 운영 수락 뒤 부산 공공데이터를 같은 비저장 snapshot 계약으로 전환한다.
- 현재 공공데이터포털 계정은 **개발계정**이다. 운영계정 한도처럼 가장하지 않으며 fixture-first 구현 후 개발계정에서 실제 공급자 호출을 최소 1회 검증한다.
- 2026-09-23 사용자가 실제 개발계정에서 확인한 일일 한도는 TourAPI 1,000회, 부산 전시·맛집·쇼핑 API 각각 10,000회다. 최초 운영은 공급자 한도를 그대로 소진하지 않고 TourAPI 800회/rolling 24h, 부산 세 API 공통 8,000회/rolling 24h로 제한한다. 현재 부산 Edge가 세 API를 하나의 `busan_public_data` credential scope로 예약하므로 공통 8,000회는 각 API의 개별 10,000회 한도를 넘지 않는 보수적 상한이다. 호출 추이와 실제 공급자 reset 정책을 검증하기 전에는 scope를 세 개로 분리하거나 상한을 높이지 않는다. 이 값은 **확정된 로컬 운영 설정 기준**이며 원격 DB 적용·Edge 배포 완료를 뜻하지 않는다.
- 현재 코드의 TourAPI 추천 세션 최악 요청량은 유형별 목록 10회+상세 30회=40회다. 각 유형이 1페이지에서 끝나면 통상 목록은 5회다. 따라서 다른 호출·실패 시도를 제외하면 공급자 한도 1,000회는 최악 약 25세션, 초기 서버 상한 800회는 최악 약 20세션/rolling 24h에 해당한다. 이는 실제 평균이 아니라 용량 위험을 드러내는 최악 상한 계산이다. 실제 호출 수를 계측하고 목록·상세 요청 절감 효과를 확인하기 전에는 공개 기본 ON을 완료로 간주하지 않는다.
- 2026-09-23 사용자 결정: 개발계정 호출량을 줄이기 위해 초기 상세 배치를 임의로 축소하면 추천 공급량과 UX가 달라질 수 있으므로 `초기 12곳 → 부족하면 6곳씩 → 최대 30곳`을 유지한다. 개발계정에서는 800회 서버 상한 안에서 제한 검증하고, 운영계정의 100,000회 한도를 실제 승인받은 뒤 승인 화면·reset 정책·실제 호출량을 다시 대조해 운영 상한을 별도 변경한다. 승인 전에는 100,000회를 현재 한도로 간주하거나 상한을 미리 높이지 않는다. 상태: **현행 유지 확정**.
- [ ] 원천 응답 누락이 앱 파생 정책의 기본값으로 조용히 합성되지 않는다.
- [ ] 로컬 파생 데이터가 원천 사실인 것처럼 사용자에게 표시되지 않는다.

### 3.3 2026-09-21 장소 기준·전환 시점 승인

- 짜투리의 기준 장소는 이미 검토된 내부 장소 369개다. 실시간 API 응답으로 내부 장소를 새로 만들거나 추천 등급을 자동 승격하지 않는다.
- AI-Hub 장소와 TourAPI·부산 장소를 런타임에서 새로 매칭하지 않는다. AI-Hub는 활동 카테고리 체류시간 근거로만 사용한다.
- 현행 체류 정책 `최소 20분·권장 30분·일반 최대 60분·문화시설 최대 120분`을 유지한다. 과거 AI-Hub 정확 매칭 46건의 장소별 분포는 감사 근거일 뿐 추천 체류시간으로 적용하지 않는다.
- 실시간 결합은 기존에 검토·확정된 source ID exact mapping만 사용한다. 신규 source ID는 이름·좌표로 자동 연결하지 않는다.
- 동일 `TourAPI contentId + contentTypeId`의 일반적인 제목·주소·좌표 수정은 최신 원천 사실로 반영한다. 거리 단독·명칭 단독 변화는 ID 재사용으로 간주하지 않는다.
- `contentTypeId`가 바뀌거나, 제목이 기존 제목·검토 별칭과 모두 다르면서 좌표도 1km 이상 이동한 복합 이상만 `review_required`로 제외한다. AI-Hub 값은 이 판정에 사용하지 않는다.
- 대표 추천 191개는 TourAPI 전용 82개, 부산 공식 전용 93개, 양쪽 연결 16개다. 구현은 TourAPI부터 진행하되 앱 운영 전환은 TourAPI와 부산 실시간 원천을 함께 검증한 뒤 수행한다.
- 전통시장 원천 전용 118개는 TourAPI·부산 장소로 자동 연결하지 않는다. 2026-09-23 사용자 결정에 따라 `traditional_market_standard`의 별도 정적 원천임을 구분하고 주변 둘러보기의 정보·독립 길찾기 용도로 유지한다. 현재 118곳 모두 운영시간 원문이 비어 있고 `conditional_more`이므로 대표 추천·코스·체류·기록으로 자동 승격하지 않는다. 공식 시간 근거가 새로 확인되더라도 기존 대표 적격성·구조화 시간·실경로 검증을 모두 통과한 뒤 별도 데이터 감사로만 승격한다.
- 새 실시간 구현이 완료되기 전 App Store 현재 버전과 현재 운영 추천 경로는 변경하지 않는다.

### 3.4 2026-09-22 부산 3원천 호출 계약 승인

- 호출 주체는 TourAPI와 분리한 **인증형 Supabase Edge 원본 비저장 pass-through**로 확정한다.
- 부산 명소·맛집·쇼핑을 각각 `numOfRows=500`, 원천당 최대 2페이지로 완결 조회한다.
- 정상 예상은 추천 세션당 3회, hard cap은 3원천 합계 6회다. HTTP page 요청 1건을 호출량 1회로 계산한다.
- 사용자 수동 출발지·도착지·GPS 좌표를 부산 API에 보내지 않는다.
- 완결 목록과 기존 exact `source key + UC_SEQ`만 결합한다. 신규 ID 자동 매칭·승격은 금지한다.
- 한 원천 실패는 다른 원천 성공을 삭제하지 않는다. 실패 원천은 stale 로컬 snapshot으로 보충하지 않는다.
- `numOfRows=500` 거부, 원천 1,000행 초과, 페이지 불완전 시 호출 cap을 자동 확대하지 않고 해당 원천을 `unavailable` 처리한다.
- 사진은 기존 exact 승인 evidence가 같은 URL에 있을 때만 전달하며 변경·미확인 URL은 기본 이미지로 처리한다.
- 현재 개발계정의 보수적 한도는 1,000회로 본다. 실제 운영 전 세 서비스의 운영 승인·일/초 한도·500행 허용을 계정 화면과 제한 호출로 확인한다.
- **상태:** 사용자 승인 / fixture-first 구현·원격 검증 전.

### 3.5 2026-09-22 TourAPI·부산 중복 장소 필드 소유 승인

- TourAPI와 부산 공식 원천에 모두 연결된 장소는 공급자 전체 우선순위를 두지 않고 **필드별 소유 규칙**을 적용한다.
- 양쪽 원천이 정상일 때 장소명·주소·좌표·운영시간은 TourAPI live를 사용한다.
- 설명과 부산 전용 정보는 부산 live를 사용한다.
- TourAPI가 unavailable/inactive이고 부산 exact identity가 active이면 부산 live 공통 사실을 사용한다. 반대의 경우 TourAPI live를 사용한다.
- 모든 mapped provider가 complete inactive일 때만 장소 전체를 inactive 처리한다.
- exact source ID/type, 검토 별칭, 복합 identity gate 자체가 충돌할 때만 `review_required`로 제외한다. 공급자 간 5~178m 좌표 차이만으로 제외하지 않는다.
- 두 공급자의 운영시간 문자열을 합치지 않는다. 양쪽 정상 시 TourAPI live 운영시간만 검증하고, TourAPI를 사용할 수 없을 때만 부산 live 운영시간을 검증한다.
- 사진은 기존 exact 승인 evidence와 현재 URL이 일치할 때만 사용한다.
- **상태:** 사용자 승인 / projection 보완·추천 연결 전.

#### 3.3.1 2026-09-21 점진 상세 조회 결정

- **이전 제안:** 로컬 번들 좌표로 최대 18곳을 먼저 고른 뒤 `detailIntro2`를 최대 18회 호출한다.
- **발생한 문제:** 번들 좌표가 원천에서 수정되면 실제로 가까워진 장소를 사전선정에서 놓칠 수 있고, 선택한 18곳이 휴무·운영시간 불명·행사기간 밖이면 유효 후보가 지나치게 적어질 수 있다.
- **교체한 방식:** 최신 부산 전체 목록의 좌표로 공간 후보 순서를 만든 뒤 상세를 12곳부터 확인하고, 충분한 코스가 없을 때만 6곳씩 추가하여 최대 30곳까지 확인한다. 경로 검증 후보 상한 18곳과 기존 route attempt 예산은 유지한다.
- **교체 이유:** 최신성, 공급자 호출량, 응답 지연을 함께 통제하고 휴무 후보 때문에 추천 성공률이 우연히 낮아지는 문제를 줄이기 위해서다.
- **상태:** 정책 승인 / API 2단계 계약·orchestrator 구현 전.

점진 조회 종료 조건:

- 결과 화면에 필요한 유효 코스와 대체 후보가 확보되면 30곳을 다 확인하지 않고 즉시 종료한다.
- 상세 실패·휴무·운영시간 불명 후보는 기존 fail-closed 규칙에 따라 제외하고 다음 배치를 확인한다.
- 30곳을 모두 확인해도 부족하면 `적합한 장소 없음` 또는 입력 수정 상태로 종료한다. 로컬 원천 사실 fallback은 사용하지 않는다.
- 한 세션의 목록 snapshot과 상세 배치 결과는 같은 `liveSourceSnapshotId`에 누적하며 새 추천 세션에서만 다시 조회한다.

### 3.4 추천 세션의 일관성

한 추천 세션은 시작 시 확정한 실시간 응답 snapshot을 끝까지 사용한다. 같은 세션 도중 원천 값이 바뀌어 후보·코스 확인·진행 화면이 서로 달라지지 않게 한다.

- [ ] 추천 시작 시 `liveSourceSnapshotId`와 조회 시각을 생성한다.
- [ ] 후보 목록·장소 상세·코스 확인은 같은 snapshot을 사용한다.
- [ ] 선택 완료 뒤 백그라운드 응답으로 장소가 몰래 교체되지 않는다.
- [ ] 새 추천 세션에서만 최신 원천을 다시 조회한다.
- [ ] snapshot ID에는 키·좌표·개인정보를 포함하지 않는다.

### 3.5 영속 저장과 세션 재사용

- TourAPI 원본 응답은 앱 파일, AsyncStorage, SQLite, Supabase DB에 영구 저장하지 않는다.
- 같은 추천 세션 안의 동일 요청은 메모리에서만 중복 제거할 수 있다.
- 앱 프로세스 종료 또는 세션 종료 시 원천 응답 메모리를 폐기한다.
- 영구 보존이 꼭 필요해지면 구현 전에 한국관광공사 로컬 저장 방식 승인 범위와 동기화 책임을 다시 결정한다.

체크:

- [ ] 원본 응답 영속 write 경로가 0개임을 코드 검색과 테스트로 확인했다.
- [ ] 메모리 재사용의 key·범위·종료 조건을 계약 테스트로 고정했다.
- [ ] 오류 응답과 부분 응답은 재사용하지 않는다.
- [ ] 디버그 로그에 원본 전체 응답·서비스키·사용자 선택 좌표를 남기지 않는다.

### 3.6 신규·수정·삭제 콘텐츠

- 기존 승인 content ID: 실시간 사실을 검증한 뒤 추천 가능.
- 수정 콘텐츠: 최신 사실을 사용하되 앱 파생 정책은 자동 변경하지 않음.
- 삭제·비공개 콘텐츠: 해당 세션 후보에서 즉시 제외.
- 신규 content ID: 발견은 가능하지만 추천 후보로 자동 승격하지 않음.
- ID 재사용 의심: 확정 source ID/type을 우선하되 `contentTypeId` 변경 또는 미등록 제목과 1km 이상 좌표 이동이 함께 발생한 복합 이상만 충돌 대기열로 분리.

체크:

- [ ] 삭제 콘텐츠가 로컬 fallback으로 되살아나지 않는다.
- [ ] 신규 콘텐츠가 체류시간 기본값을 합성해 자동 추천되지 않는다.
- [x] 좌표·명칭 급변은 단독 차단하지 않고 복합 이상 기준으로 확정했다.
- [ ] 충돌 데이터는 사용자 화면이 아니라 검토 가능한 안전 상태로 남는다.

### 3.7 출처와 콘텐츠 이용

- TourAPI 표시 콘텐츠에는 운영팀이 안내한 `출처 : ⓒ한국관광콘텐츠랩` 또는 `출처 : ⓒ한국관광공사` 형식을 적용한다.
- 원문을 의미가 달라지도록 훼손하지 않는다.
- 사진은 실시간 URL이라고 해서 자동 사용 허용으로 간주하지 않는다.
- 기존 사진별 표시·변형 제한과 운영자 승인 이력을 유지한다.

체크:

- [x] 추천 카드·상세·사진 표시에서 필요한 출처가 누락되지 않는다.
- [x] 1유형·3유형 또는 별도 제한을 사진별로 구분한다.
- [x] 권리 상태가 불명확한 신규 사진은 기본 이미지로 대체한다.
- [x] 이미지 실패가 장소 추천 전체 실패로 확대되지 않는다.

## 4. 목표 런타임 구조

```text
사용자 수동 출발지·도착지·시간 입력
                ↓
실시간 원천 준비 계층
  ├─ TourAPI adapter
  └─ 후속 부산 공공데이터 adapter
                ↓
응답 스키마 검증·정규화
                ↓
로컬 앱 파생 정책과 content ID 기준 결합
                ↓
세션 한정 LiveCandidateSnapshot 확정
                ↓
기존 CourseV1 추천 엔진
                ↓
결과·상세·코스 확인
```

구조 원칙:

- API 어댑터는 추천 순위나 체류시간을 결정하지 않는다.
- 추천 엔진은 HTTP·키·재시도·응답 원문을 알지 않는다.
- UI는 raw API 응답을 직접 읽지 않는다.
- 로딩·실패·재시도 상태는 typed result로 전달한다.
- 기존 동기식 엔진을 무리하게 네트워크 엔진으로 바꾸지 않는다.
- 비동기 원천 준비가 끝난 뒤 순수 snapshot을 엔진에 주입한다.

예상 공개 계약:

```ts
type LivePlaceSourceResult =
  | { status: 'ready'; snapshot: LiveCandidateSnapshot }
  | { status: 'partial'; snapshot: LiveCandidateSnapshot; failures: readonly SafeFailure[] }
  | { status: 'unavailable'; reason: SafeUnavailableReason };
```

정확한 타입 이름과 필드는 API·엔진 역할이 함께 검토하되, `ready/partial/unavailable`의 의미를 화면별 문자열로 분산시키지 않는다.

## 12. 완료 정의

다음 항목을 모두 충족해야 TourAPI 실시간 전환 완료로 판정한다.

- [ ] 실제 추천 흐름에서 운영계정 TourAPI 호출이 발생한다.
- [ ] 응답의 최신 상태·운영정보가 추천 결과에 실제 반영된다.
- [ ] 원본 TourAPI 응답을 영구 저장하지 않는다.
- [ ] 기존 추천·체류·개인화·최대 2곳 정책이 유지된다.
- [ ] 신규·삭제·오류·부분 실패 fixture가 통과한다.
- [ ] 호출 예산과 timeout이 자동 테스트로 고정됐다.
- [ ] TestFlight 실기기 E2E를 통과했다.
- [ ] 출처가 올바르게 표시된다.
- [ ] 개인정보처리방침·App Privacy·README·추천 문서가 실제 동작과 일치한다.
