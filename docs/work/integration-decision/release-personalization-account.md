## DEC-RELEASE-DB-READINESS-01 — 사용자 권장안 확정 (2026-09-07)

부모: 출시 개인화·보존 서버 적용 결정. 관계: 기존 적용 준비의 **보완**, 기능/학습 정책 변경 없음. 이전에는 실제 백업/가입 영향이 미확정 → R1에서 백업 목록 비어 있음·신규 가입 차단·MAINTAIN/timeout 잔여 확인 → 사용자 “권장대로 진행”으로 다음을 확정 → 데이터 보존과 안전한 서버 적용 준비를 위한 결정. 상태: **승인·준비 작업 전, 서버 적용 승인 전**.

1. Auth/public/migration 이력 포함 새 보호 백업 생성과 격리 복원 검증을 승인한다. repo 밖 암호화 위치/복원 방법을 먼저 제시하며 보관 책임자는 사용자다. 비밀은 채팅/문서/로그에 남기지 않는다. 실제 위치/키 준비는 실행 단계에서 확인하고 미확인을 합성하지 않는다. 유료 서비스 구매·운영 복원은 별도 승인이다.
2. 실제 약관 준비 전 신규 일반 가입 일시 차단을 수락한다. 출시 전 실제 문서 등록과 가입 검증은 필요하며 가짜 문서·동의 우회는 금지한다.
3. exact MAINTAIN 권한 회수와 transaction-local timeout은 DB 기술 보완으로 로컬 구현/검증한다. 새 hash·백업·대상·영향을 제시한 뒤 실제015/016 적용은 사용자 최종 승인받는다. 기존 나이 삭제 선택도 원격 적용 승인과 구분한다.

실행 문서: `../db-personalization/release-backup-apply-readiness.md`. 백업 보유기간을 영구로 확정하지 않으며 적용/QA 종료 시 폐기 여부 재확인. 방문/표본 기존 보유·개인화·UI 동작 정책은 변경하지 않는다.

## DEC-LIVE-LEARNING-EVIDENCE-01 — 사용자 최종 확정 (2026-09-07)

부모: DEC-RELEASE-PERSONALIZATION-01 / DEC-GUEST-MEMBER-BENEFIT-01 / DEC-RELEASE-DATA-LIFECYCLE-01. 관계: REC-34·DB-08/09/11·COURSE-13 **보완**. 질문 이유는 native 도착의 당시 동의 증거 누락이며 부모의 회원 전용 학습·소급 학습 금지·보유기간은 유지한다. 상태: **정책 확정·구현/검증 전**.

1. 일반 로그인+별도 동의로 시작한 새 적격 코스에 한해 앱/Live Activity 버튼 모두 같은 학습 경계를 사용한다. 비로그인 반복 이용·나중 로그인·guest/legacy 가져오기는 방문 이력만 유지하며 과거 체류 학습0.
2. 권장 로컬 증거 참조 방식을 채택한다. 시작 당시 확정 owner/동의, 확인 순간의 exact run/stop/event 증거, 제출 전 현재 owner/epoch/generation 검증을 함께 사용한다. 로컬 참조는 서버 인증서나 GPS 방문 증명이 아니다. 당시 증거 없음/손상/불일치/무효화는 학습 제외; 정상 증거의 일시적 서버 오류는 기존 허용 기간 내 재시도다. 불명확성 때문에 진행을 막거나 도착 재탭을 요구하지 않는다.
3. 활성 증거는 완료·취소·만료·교체 시 정리하며 별도 장기 보유기간을 추가하지 않는다. 정상 완료는 필요한 증거를 검증하여 최소 적격 표본/기존 전송 대기에 안전하게 반영한 뒤 활성 증거를 정리한다. 증거 처리가 확정되지 못해도 필수 완료를 지연하지 않으며 해당 학습만 제외한다. late callback 재생성0. 생성된 최소 표본은 기존 outbox32건/최초 기준7일·서버180일을 그대로 따른다.
4. 일반 알림 액션은 클릭 당시 증거 확보 전까지 학습 제외한다. Live Activity 버튼과 구분한다. 진행 동작은 유지하며 알림 수신/예상시각/JS 복귀시각을 확인 당시 증거로 합성하지 않는다.
5. 중복 확인은 1회, 로그아웃/계정 변경·off/reset/delete 이후 stale 증거의 신규 학습 재생0. 다른 기기 철회는 제출 전 서버 게이트로 거절하며 offline 즉시 인지를 보장한다고 표현하지 않는다. 새 권한/GPS/원격 push/서버 영구 receipt는 이번 결정에 포함하지 않는다.

이력: app_action만 학습·native 제외 → Live Activity 중심 사용의 학습 누락 → 당시 로컬 증거가 있는 app/native를 같은 경계로 소비, 불명확·구형·일반 알림은 제외 → 소급 동의 없이 회원 학습 목표 달성. app_action 전용은 **교체 예정**, 안전 제외는 새 계약 구현·회귀 전까지 유지. 조사 문서 DTO/함수명은 제안이므로 DB 공개 계약 인계 후 구현한다.

검증: 신규 native 독립 코스3건→완료→방문 ack→표본→다음 추천 실제 보정, 1/2건 기본, app/native 중복0, guest/import0, 계정/철회/삭제/구형0, 증거 장애 중 필수 완료·길찾기 유지, terminal 정리와7일/32건/180일 회귀. 실기기는 자동 검증 뒤 별도다.

결정일: 2026-09-07. 상태: **사용자 확정·구현/검증 전**. 이번 변경은 문서 결정이며 기능 완료·원격 데이터 삭제·배포 승인이 아니다.

## 확정 규칙

### DEC-GUEST-MEMBER-BENEFIT-01 — 이용 혜택 구분 (2026-09-07)

사용자 확정·구현/검증 전. 이전: guest의 Live Activity 체류 확인도 로그인 혜택처럼 보임 → 관찰: 가입 이유가 불명확함 → 교체: guest는 이번 코스 안내와 기기 방문 기록, account+별도 동의는 새 유효 체류 표본의 계정 축적과 다음 추천 개인화 → 이유: 체험 흐름을 막지 않고 장기 이용 가치를 구분.

- guest/anonymous/로그인 미동의도 Live Activity 및 앱의 도착·출발·길찾기를 동일하게 이용한다. 기본 체류 기준 추천은 유지한다.
- 로그인만으로 개인화 동의가 되지 않는다. 로그인+동의여도 해당 복합 카테고리의 유효 표본이 3개 미만이면 기본 체류를 사용한다.
- guest 완료 뒤 로그인 안내는 비차단으로 제공하고 매 완료마다 강제 로그인 모달을 띄우지 않는다. 문구 예: “내가 머무는 시간에 맞춰 추천받고 싶다면 로그인하세요.”
- account+동의는 실제 유효 표본 수에 근거한 카테고리별 준비 상태를 표시한다. missing subCategory는 1/3처럼 카운트하지 않고 기본 기준임을 표시한다.
- “내 체류 성향을 반영한 추천”은 서버 저장/로그인 여부가 아니라 해당 결과의 엔진 적용 근거가 있을 때만 표시한다. 기본값과 최종 선택 체류가 동일하거나 개인화 목표가 시간 조건으로 되돌아간 결과를 변화된 추천처럼 광고하지 않는다.
- 가져온 guest 방문 이력은 계정 기록에 표시할 수 있지만 과거 guest 체류는 학습하지 않는다. 계정별 기록의 저장/삭제, 학습 동의는 별도 경계다.

실행 명령과 역할별 선행 관계: [출시 개인화 작업 Wave](release-personalization-wave.md).

1. 일반 로그인 중 생성한 기록은 해당 계정 소유다. 로그아웃하면 그 계정 기록의 표시와 추천 반영을 중단한다. 로그아웃을 서버 기록 삭제로 해석하지 않는다. 다른 계정에도 노출/적용하지 않는다.
2. 로그인 직후 가져올 비로그인 방문 기록이 있을 때 한 번 가져오기 의사를 묻는다. 승인하면 중복 없이 해당 계정에 귀속하고 성공한 항목만 비로그인 목록에서 제거한다. 거절하면 비로그인 기록으로만 유지한다. 로그인 실패/요청 실패/재시도에서 기록을 유실하거나 두 계정에 귀속시키지 않는다.
3. 방문 기록 가져오기와 맞춤 체류 기록 동의는 별개다. 가져온 과거 비로그인 체류시간은 서버 학습 표본/개인화 계산에서 제외한다. 방문 이력을 옮겼다는 이유로 원시 도착·출발 시각까지 업로드하지 않는다.
4. 일반 로그인+별도 개인화 동의+본인 명시 도착/출발+완료를 만족하는 새 유효 표본만 개인화한다. anonymous Auth는 일반 로그인이 아니다. 소급 학습·계정 변경 도중 표본 소유권 재지정은 금지한다.
5. 기존 DEC-LIVE-DWELL-01의 같은 category+subCategory, 유효 3개부터 최근 최대 5개 중앙값 및 제한 범위를 유지한다. 시간/운영시간/최소 체류 안전 검증을 우회하지 않는다. GPS 자동 도착·원격 ActivityKit push는 추가하지 않는다.
6. 나이 입력과 신규 출생연도/연령대 수집은 제거한다. 기존 저장값 정리는 별도 migration과 삭제 범위 확인 뒤 실행한다.
7. 이용허락을 확인하지 못한 사진만 기본 이미지로 대체한다. 사진 부재를 장소 추천 제외 이유로 사용하지 않는다.

## 구현 전 남은 계약

### DEC-RELEASE-DATA-LIFECYCLE-01 — 1~6 승인 (2026-09-07)

상태: **사용자 확정·구현/검증 전**. 부모 DEC-RELEASE-PERSONALIZATION-01. 이전: 보유/이관/삭제/분류 범위 미확정 → 관찰: DB B와 출시 혜택 연결을 시작할 수 없음 → 교체: 아래 최소 보관·사용자 삭제·분류 보완 정책 → 이유: 개인화 효용·삭제 통제·구현 범위의 균형. Apple이 180일/32건/7일을 요구한다는 뜻은 아니며 승인 보장이나 법률 검토 완료가 아니다.

1. 체류 학습 표본은 완료 기준 최근 180일 rolling. 적격 표본 최신 최대 5개로 계산하고 3개 미만이면 기본 기준, 마지막 표본 소멸 시 파생 프로필도 삭제한다. 조회에도 만료 제외를 적용하고 물리 삭제 job을 검증한다. 서버 수신 시각으로 offline 완료 순서를 대체하지 않도록 완료 시각의 최소 정밀도·검증·동률 정렬은 DB 계약에서 보완한다.
2. 체류 전송 대기 표본은 기기에 최대 32건·7일. 기한 초과는 학습 대기 표본만 제거하고 방문 기록은 유지한다. 로그아웃·동의 철회 시 전송 중단, 타 계정으로 재귀속 금지. 다시 로그인해도 본인·동의 epoch·유효기간을 통과해야 한다. 도착/출발 raw 시각·좌표/경로를 outbox에 추가하지 않는다. import pending의 별도 100건/30일 제안까지 승인한 것은 아니다.
3. 구형 완료 저장은 하나의 기기 key와 owner/auth 없는 schema라 당시 로그인 소유권을 복원할 수 없다. 이를 legacy_unassigned로 분리하고 명시적으로 가져온 방문 이력만 계정에 연결한다. 자동 account/guest 추정 및 과거 체류 학습은 0이다. 현재 로그인 session이나 코스 ID를 과거 작성자의 증거로 사용하지 않는다.
4. 회원 방문 기록은 개별/전체 삭제 또는 탈퇴까지 유지하고 기록 탭에 삭제 수단을 제공한다. 탈퇴는 해당 회원 서버/기기 기록·개인화·연결 pending/진행/알림을 정리한다. 별도 guest/legacy 기록은 “이 기기의 기록도 모두 삭제” 선택 때만 제거한다. 처리 단계의 실제 성공과 실패/재시도를 표시하며 서버·기기·백업 전체 즉시 원자 삭제를 약속하지 않는다.
5. 개인화 초기화는 표본/파생을 모두 삭제하고 수집도 off로 전환한다. 이후 명시 enable부터 새 기록을 받는다. 일반 off는 수집/적용만 중단하고 기존 표본은 180일 정책 안에서 유지한다. reset/철회 이전 pending으로 삭제 자료가 재생성되지 않도록 epoch를 검증한다.
6. 출시 전 카페·문화시설 우선 근거 기반 subCategory 보완. 기존 분류와 중복 체계를 만들지 않고 승인된 분류 어휘/원천 증거를 사용한다. 불확실한 장소는 missing 유지·기본 추천, 장소명만 보고 추정하지 않는다. 새로운 그룹 때문에 과거 표본을 무단 재분류하지 않는다. 광범위한 장소 증설/운영시간 변경은 포함하지 않는다.

코드 근거: src/services/courseCompletionRepository.ts의 COURSE_COMPLETION_STORAGE_KEY와 CourseCompletionRecordV1에는 userId/owner/authKind가 없다. 코스 완료 기기 기록을 먼저 제공한 당시 구조이며, 계정 이력을 구분할 수 있도록 확장하는 작업이 누락되어 있었다.

후속 사용자 승인(2026-09-07): 닉네임은 선택 입력·중복 허용·1~20자·앞뒤 공백 제거·줄바꿈/제어문자 금지다. 탈퇴는 최근 10분 안의 비밀번호 재인증을 요구한다. 이전 추가 제안 미확정 → 사용자 명시 동의 → 구현 기준으로 확정 → 계정 구현 진행 → **현행·구현 전**. 일반 로그인/로그아웃에 재인증을 강제하지 않는다. 재인증은 서버가 검증 가능한 증거여야 하며 client boolean/JWT 갱신시각만 믿지 않는다.

공개 운영자/문서 URL·version은 공개 활성화 전에 필요하다. import pending와 DB 완료 시각·소유권 증명은 기술 계약 보완 후 통합 검토한다. 이 미확정을 독립적인 계정/RLS 구현 전체의 대기로 확대하지 않는다. 원격 삭제/배포는 실행하지 않는다.

- 기존 계정 구분 없는 기록의 소유자를 추정하지 않는다. 레거시 분류/이관, 가져오기 실패·중복·재질문 기준은 DB/UI 상세 작업에서 고정한다.
